## 文件目的

說明本專案的資料庫採用方案、`BackendDBContext` 結構、各 Entity 與彼此關聯，以及 Migration 與啟動 Seed 的行為。

## 1. 資料庫採用方案

- **唯一支援**：SQLite，連線字串由 `MagicObjectHelper.GetSQLiteConnectionString(databasePath)` 動態組成；`databasePath` 來自 `appsettings.json` 之 `SystemSettings.ExternalFileSystem.DatabasePath`（預設 `C:\temp\CustomerHelpAgent\DB`）。註冊處為 `ServiceCollectionExtensions.AddConfiguredDatabase`，固定呼叫 `UseSqlite`。
- 0.4.24 起**移除 SQL Server 支援**：`CustomerHelpAgent.AccessDatas.SqlServerMigrations` 專案、`SystemSettings.DatabaseProvider` 設定與 `ConnectionStrings.DefaultConnection` 皆已刪除（工作目錄裡同名資料夾若還在，只剩未追蹤的 `bin/`、`obj/`，見[速查表 §10](開發慣例與限制速查.md)）。
- **Collation**：`Chinese_Taiwan_Stroke_CI_AS`（於 `BackendDBContext.OnModelCreating` 統一指定）。此為 SQL Server 概念，SQLite 會忽略（只出現在模型快照，migration 的 `Up()` 不產生任何 COLLATE）；保留以避免產生不必要的模型差異。列為已知殘留，見[速查表 §10](開發慣例與限制速查.md)。

### 2.2 全域刪除政策

`OnModelCreating` 預設將所有外鍵的 `DeleteBehavior` 設為 `Restrict`：父資料表若仍有子資料時不可被強制刪除。

### 2.3 Cascade 例外

下列「主表 → 附件表」改為 `DeleteBehavior.Cascade`，主表刪除時連動清除附件紀錄：

```csharp
Project    → Project.Files     → ProjectFile.ProjectId
MyUser     → （導覽屬性 MyUser）  → PasswordResetToken.MyUserId   // 0.9.60 起
RoleView / Permission → RolePermissionMap   // RBAC 關聯表，見 3.1
MyUser / RoleView     → UserRole
MyUser / Team         → UserTeam
MyUser     → （導覽屬性 RecipientUser）→ Notification.RecipientUserId   // 0.9.100 起
Announcement / MyUser → AnnouncementDismissal                  // 0.9.100 起
MyUser     → （導覽屬性 MyUser）  → PasswordHistory.MyUserId        // 0.9.101 起
MyUser     → （導覽屬性 MyUser）  → TwoFactorBackupCode.MyUserId    // 0.9.104 起
```

> ⚠️ `PasswordResetToken` 的 Cascade 必須寫在 Restrict 迴圈**之後**：`MyUserService.DeleteAsync` 不會先刪相依資料，
> 設成 Restrict 會讓「有未用 token 的使用者」刪除失敗。由 `PasswordResetServiceTests.DeletingUserWithPendingToken_ShouldCascade` 守門。
> 0.9.100 的 `Notification`、`AnnouncementDismissal` 同理（永久刪除使用者時連帶刪除），由 `NotificationTests` 守門；0.9.101 的 `PasswordHistory`、0.9.104 的 `TwoFactorBackupCode` 也是。

> 注意：附件「資料表紀錄」會被 EF Core Cascade 處理；但**實體檔案**仍須由 Service 層在刪除前後手動移除。詳見 [檔案上傳機制](../features/檔案上傳機制.md)。

#### `TokenUsageLog` 的費用欄位（0.9.17 起）

費用在**記錄當下**算好並存進資料列，連同當時生效的單價與匯率一起存 —— 是**快照**，
日後調整 `AiPricingSettings` 不會改變已經記錄的帳。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `CostUsd` / `CostTwd` | `double?`（SQLite `REAL`） | **`null` 就是「未定價」**：找不到該模型的費率設定，或匯率未設定。有費率但用量為 0 時存 `0`，兩者意義不同 |
| `CostExchangeRate` | `double?` | 計算當下的匯率快照 |
| `CostPriceKey` | `string?` | 實際套用的費率設定鍵。與 `Model` 不同時代表來自前綴比對 |
| `CostLongContext` | `bool` | 是否套用長脈絡費率 |
| `CostRateSnapshot` | `string?` | 生效費率組的精簡 JSON（只含非零項） |

**為什麼用 `double` 而不是 `decimal`**：本功能的核心是「篩選範圍的總花費」，必須在 SQL 端
`SUM`，而 SQLite 把 `decimal` 存成 `TEXT`，無法可靠彙總（原本預留的 `EstimatedCost` 正是
`decimal?`，已於 0.9.17 移除）。單筆金額量級在 1e-6，`double` 有 15–16 位有效數字，
百萬列相對誤差仍在 1e-10 以下。**帳目可重現性不靠儲存的金額，而靠單價快照加 token 數** ——
兩者都存了，任何時候都能重算驗證。

**`CostTwd` 逐列儲存、不由美金總額換算**：匯率會被調整，篩選區間橫跨調整時只有逐列相加
才是正確的台幣帳。因此 `SUM(CostTwd) ≠ SUM(CostUsd) × 任何單一匯率`，這是正確行為。

⚠️ `CostRateSnapshot` 是本表「只留可聚合的數值欄位」原則的**刻意例外**。它是設定衍生資料、
不含任何使用者輸入或模型輸出，不踩安全紅線；也不能改寫進 `RawUsageFile` 那個檔，
因為那個檔可能是 `null`、而且會被「清除此日之前」獨立刪掉，帳就沒了。

### 3.1 RBAC 關聯資料模型（權限重構階段二）

資料驅動 RBAC 以四張關聯表取代原本寫在 `RoleView.TabViewJson` / `MyUser.RoleViewId` / `RoleView.DefaultTeamsJson` 的邏輯：

- `Permission`：權限鍵目錄（`Key` 唯一；階段四導入 `resource:action` 動作粒度）。
- `RolePermissionMap`：角色↔權限（取代 `TabViewJson`）。命名加 `Map` 以避開 UI 綁定模型 `CustomerHelpAgent.Models.Admins.RolePermission`。
- `UserRole`：使用者↔角色（取代單一 `RoleViewId`，支援多角色）。
- `UserTeam`：使用者↔團隊（團隊改直接綁使用者，取代綁在角色）。

**回填**：啟動時由 `IRbacBackfillService`（`RbacBackfillService`）冪等地將既有資料填入上述表；失敗僅記錄、不中止啟動。

**雙寫**：角色編輯（`RoleViewService`）與使用者指派（`MyUserService`）時，另由 `IRbacWriteService`（`RbacWriteService`）協調式同步 `RolePermissionMap` / `UserRole`，使新表隨編輯即時保持一致（不必等下次啟動回填）。0.9.136 起兩個服務的新增與修改都把主表與對應表包在同一個交易（`RbacWriteService` 帶 context 的多載），寫入失敗時整筆回復。

> **現況（階段三／四已落地）**：執行期授權**已以 RBAC 關聯表為權威來源**——API 以 `HasPermission` + `IPermissionChecker` 強制動作級授權（無權限回 403），UI 亦於登入時經 `IPermissionChecker.GetEffectivePermissionKeysAsync` 載入有效權限鍵（多角色聯集）；`TabViewJson` 退為角色編輯回填用的相容欄位。（上句原為階段二當時狀態，現已切換。）

### 4.2 啟動時自動處理

`Program.cs` 在 `app.Build()` 後呼叫 `IDatabaseInitializer.InitializeAsync`（0.9.91 起，`CustomerHelpAgent.Business/Startup/DatabaseInitializer.cs`）：

1. **跨行程鎖**：對資料庫檔旁的 `BackendDB.db.migration.lock` 取得獨佔控制代碼，最多等 60 秒（IIS in-process 的啟動時限預設 120 秒）。
   EF Core 9 起 `Migrate()` 本身有鎖，這把鎖保護的是之後的 seed —— `RoleView.Name`、`MyUser.Account` 沒有唯一索引，兩個行程同時 seed 會建出重複列。
   鎖檔不會自動刪除，停站時可以安全刪除。
2. **套用 migration**：`Database.MigrateAsync()`。`EnsureCreated()` 已移除（它建出的資料庫沒有 `__EFMigrationsHistory`，之後永遠無法 migrate；守門測試禁止產品程式呼叫它）。
3. **WAL**：`PRAGMA journal_mode=WAL`，設定存在資料庫檔內，之後每條連線自動生效；失敗只記警告。資料庫目錄因此會多出 `-wal`、`-shm` 兩個檔，備份時三個檔要一起複製。
4. **Seed 預設角色**（`DefaultRoleViewSeeder`，Order 10）：不存在 → 以全部頁面建立；已存在 → **只加入新頁面**（程式碼有、但 `Permission` 目錄裡從未出現過的頁面鍵），並在同一次 SaveChanges 補上這些 `Permission` 列。管理員移除過的頁面仍在目錄裡，所以不會被加回。
5. **Seed 預設帳號**（`SupportUserSeeder`，Order 20）：`MyUser.Account == BootstrapSettings.SupportAccount`（不存在則新增），密碼以 `SecurePasswordHasher.HashPassword`（**PBKDF2**）雜湊、`IsAdmin=true`、角色指向預設角色；既有帳號若設定檔密碼驗證不成功（設定檔改了密碼，或舊格式雜湊）就以設定檔密碼重新雜湊。
6. **RBAC 回填**（`RbacBackfillSeeder`，Order 30）：`IRbacBackfillService.RunAsync()`（見 3.1），失敗僅記錄、不中止啟動。
7. **匯入舊的 AI 提示詞設定**（`LegacySystemPromptSeeder`，Order 40，0.9.108 起）：`AiSettings:SystemPrompt` 有值、且日誌分析還沒有任何版本時建立第 1 版；之後只記警告提醒移除該鍵。

之後 `Program.cs` 才**補登崩潰紀錄**（0.9.77 起）：把上次啟動失敗或程序層級例外留下的補登檔（`{ExceptionPath}/pending/`）寫進 `ExceptionLog` 後刪檔。

> 啟動 Seed 為冪等行為。0.9.90 之前每次啟動都會把預設角色的 `TabViewJson` 蓋回全部頁面，RBAC 回填再依它把 `RolePermissionMap` 補回 ——
> 管理員對預設角色的限制重啟就失效；0.9.91 起改為只加入新頁面。預設帳號仍會每次強制 `IsAdmin = true`、角色指回預設角色，密碼與設定檔不符時重設（已刪除的會先還原），確保永遠可登入。
>
> 衍生專案要加自己的種子資料，實作 `IDatabaseSeeder`（冪等、Order 不重複）並在 `AddApplicationServices` 註冊成 Scoped，**不要寫回 Program.cs**（`DatabaseInitializerConventionTests` 會擋）。
>
> 限制：IIS 重疊回收時，舊的工作者行程不會重跑初始化，會以舊程式碼存取已升級的資料庫 —— migration 在重疊期間必須向下相容（新增欄位要可為 null 或有預設值，不要在同一版刪欄位）。
> 若行程在 migration 中途被強制結束（例如被 IIS 砍掉），EF 用來互斥的 `__EFMigrationsLock` 表**可能**留下一列（未實測）；若下次啟動一直卡在套用 migration，停站後檢查該表並刪除殘留的列。
