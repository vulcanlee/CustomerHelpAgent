## 1. 分層與依賴方向 ⚠️

依賴方向一律向上，**不得反向相依**：

```
CustomerHelpAgent.Web ──► CustomerHelpAgent.Business ──► CustomerHelpAgent.AccessDatas
       │                  │
       └──► CustomerHelpAgent.Dtos / CustomerHelpAgent.Models / CustomerHelpAgent.Share
```

- `CustomerHelpAgent.Share`：不得相依其他專案；`CustomerHelpAgent.Models`、`CustomerHelpAgent.Dtos`：只能相依 `CustomerHelpAgent.Share`。
- UI（Razor）**不得直接 `using` `BackendDBContext`**，只能呼叫 Service / Repository。
- 細節見 [架構總覽](架構總覽.md)。

## 2. 模型變更要產生 Migration ⚠️

本專案**只支援 SQLite**（0.4.24 起移除 SQL Server 支援），migration 一律放在單一組件：

- SQLite：`src/CustomerHelpAgent/CustomerHelpAgent.AccessDatas/Migrations/`

**任何 Entity／欄位變更都要產一次 migration**，否則程式碼與資料庫 schema 會不一致。指令見 [EFCore 指令備忘](../guides/EFCore.md)。

> 資料庫連線一律由 `ServiceCollectionExtensions.AddConfiguredDatabase` 以 `UseSqlite` 註冊，連線字串由 `MagicObjectHelper.GetSQLiteConnectionString` 結合 `SystemSettings.ExternalFileSystem.DatabasePath` 產生；`appsettings.json` 已無 `DatabaseProvider` 設定。

- ⚠️ **寫死腳手架 migration 名稱的測試要獨立成檔，並登記到 `scripts/New-StarterProject.ps1` 的 `$starterMigrationTests`**：衍生專案複刻時會清空 migration、重建單一 `Init`，這類測試在新專案必定失敗。現有 `CategoryTeamUniqueIndexMigrationTests.cs`、`TeamTreeMigrationTests.cs`（0.9.116 前後者混在 `TeamTreeTests.cs` 裡，衍生專案一複刻就有 1 個測試失敗）。

## 3. EF 追蹤與編輯隔離 ⚠️

- 表格列被編輯前要先 `Clone()` 隔離，避免雙向綁定污染來源資料。
- **Blazor 路徑的資料服務一律注入 `IDbContextFactory<BackendDBContext>`**（`Services/DataAccess/*`），
  每個方法開頭 `await using var context = await contextFactory.CreateDbContextAsync();`，用完即棄。
  私有輔助方法若參與同一個工作單元，請把 `context` 當參數傳進去，**不要自行 CreateDbContext**。
- ⚠️ **不要改回注入 scoped `BackendDBContext`**：在 Blazor Server，DI scope ＝ SignalR circuit，
  存活時間等同使用者整個連線（數分鐘到數小時），不是一次 HTTP 請求。scoped 會造成追蹤實體只增不減
  （記憶體成長、讀到過期資料），兩個元件事件重疊時還會拋
  「A second operation was started on this context」。由 `DataAccessServiceLifetimeTests` 守門。
- 沿革：0.4.36 之前用 scoped context，因而長出 `CleanTrackingHelper` 這條慣例（全專案 47 處呼叫，
  每個新模組都得記得照抄）。改用工廠後該慣例整條退場，`CleanTrackingHelper` 已移除。
  API 路徑的 Repository 仍用 scoped context —— 那裡 scope ＝ 單次 HTTP 請求，本來就正確。
- 附件「資料表紀錄」由 EF Core Cascade 處理，但**實體檔案**仍須由 Service 層手動移除。見 [檔案上傳機制](../features/檔案上傳機制.md)。
  ⚠️ 0.9.97 起刪除附件實體檔一律經 `ProjectFileStore.Delete`（會擋下跑出 `ProjectFilePath` 根目錄的路徑），而且在資料庫**存檔成功後**才刪檔；下載也用它的 `TryResolveFullPath`。

## 3.1 分頁查詢一律先排序 ⚠️（0.4.46 起）

**`Skip`／`Take` 之前必定要有 `OrderBy`。** 沒有 `ORDER BY` 時 SQLite 不保證回傳順序，
分頁會出現「同一筆在第 1、2 頁都看到」或「某筆翻遍所有頁都看不到」；EF Core 會記下
`RowLimitingOperationWithoutOrderByWarning` 警告。

- **Blazor 路徑**（`Services/DataAccess/*Service.GetAsync(DataRequest)`）：排序結果收在
  `IOrderedQueryable<T>? sorted`，分支未命中就留 `null`，最後在 `Skip` 之前收斂：

  ```csharp
  dataSource = sorted ?? dataSource.OrderByDescending(x => x.UpdatedAt).ThenByDescending(x => x.Id);
  ```

  這樣「欄位空白」「欄位不認得」「`SortDescending` 為 null」三種落空輸入都會退回預設排序。
  **不要**寫成 `: dataSource`（原樣回傳）—— 那正是 0.4.46 之前警告的來源。
- **API 路徑**（`Repositories/*Repository.GetPagedAsync`）：`switch` 運算式一定要留 `_ =>` 預設分支。
- 排序鍵要能唯一決定順序，因此一律 `ThenBy(x => x.Id)` 收尾，否則同值列在頁與頁之間仍會漂移。
- 守門：`CustomerHelpAgent.Tests/TestDbContextFactory.cs` 以
  `ConfigureWarnings(w => w.Throw(CoreEventId.RowLimitingOperationWithoutOrderByWarning))`
  把這個警告在測試中升級為例外，任何漏排序的分頁查詢只要被測試碰到就會失敗。
- 新模組請直接用 `scripts/New-CrudModule.ps1`，樣板已是正確寫法。

## 4. Web API 回應一律包信封 ⚠️

- 任何 Controller 一律回傳 `ApiResult<T>`；分頁則包 `PagedResult<T>`（定義於 `CustomerHelpAgent.Dtos`）。
- UI 用 Cookie 認證（`MagicObjectHelper.CookieScheme`）、API 用 JWT Bearer，兩套 scheme 互不干擾。
- ⚠️ 登入 Cookie 名稱明寫為 `.CustomerHelpAgent.Auth`（`Program.cs`），**必須帶專案名**：Cookie 不分連接埠，同一主機名稱部署多個衍生系統時，同名會互相覆蓋、互相登出。`New-StarterProject.ps1` 會隨專案名一起換掉；由 `ApiIntegrationTests.AuthCookieName_ShouldBeProjectSpecific` 守門。改這個值會讓既有登入全部失效一次（0.9.64）。
- CRUD API 預設需要 Bearer token；login / refresh 允許匿名。未授權／禁止存取的回應也包成 `ApiResult`。
- 除驗證身分外，受保護 CRUD **每個動作**另以 `[HasPermission("resource:action")]`（`HasPermissionAttribute` + `IPermissionChecker`）做**動作級授權**，無權限回 **403**（維持 `ApiResult`）；管理員短路。
- ⚠️ **claim 對應在 Cookie 與 JWT 兩套機制中是相反的**：Cookie 是 `Sid`=UserId、`NameIdentifier`=帳號、`Name`=**姓名（個資）**；JWT 是 `NameIdentifier`=UserId、`Name`=帳號。`HasPermissionAttribute.ResolveActor` 以「`NameIdentifier` 是不是數字」判斷來源，且只在 JWT 那一支取用 `ClaimTypes.Name`。新增從 claim 取身分的程式碼時照同樣方式處理，別假設只有一套對應。
- 平行路由：保留 `/api/...`，新用戶端優先用 `/api/v1/...`。
- 見 [Web API 設計慣例](Web%20API%20設計慣例.md)、[API Versioning 策略](API%20Versioning%20策略.md)、[認證授權與權限機制](../security/認證授權與權限機制.md)。

## 4.1 紀錄分類/團隊標籤與團隊權控 ⚠️

- Project 的 `Categories`/`Teams` 為**多值標籤**，以換行分隔字串儲存；務必透過 `TagStringHelper`（`ToStored`/`ToList`）轉換，AutoMapper 已以 `ForMember` 處理 List↔字串。
- **團隊行級權控**一律經 `RecordTeamScope`（0.9.105 起，`Business/Helpers/`）：Blazor 服務層（`ProjectService`／`CategoryService`）與 Web API 的 Repository（`ProjectRepository`／`CategoryRepository`）共用，清單、單筆、**修改**、刪除、檔案下載都套用。非管理員僅見「無團隊（公開）或與其有效團隊交集」的紀錄。透過 `IRecordAccessScopeProvider` 取得範圍。
  ⚠️ 新增讀寫紀錄的服務、Repository 或 Controller 時不要自己呼叫 `TagStringHelper.BuildTeamAccessPredicate`／`IsTeamAccessible`，走 `RecordTeamScope`（它也處理 `RecordAccessScope.Denied`）。
- ⚠️ **指派規則**（0.9.105 起）：非管理員新加的團隊必須在自己範圍內、原本有團隊的不可清成公開（`RecordTeamScope.CheckAssignment`）；寫入前呼叫，表單選項也只列範圍內的（加上這筆原本就有的）。
- 使用者**有效團隊**由 `IEffectiveTeamResolver` 計算＝直接綁使用者的 `UserTeam` ∪ 其角色 `RoleView.DefaultTeamsJson`（聯集去重），0.9.105 起再加上它們所有的下屬部門（§6.22）；登入時載入 `CurrentUser.TeamList`（見 `AuthenticationStateHelper.Check`），API/檔案下載走 `RecordAccessScopeProvider`。此設計讓「團隊綁使用者」與「團隊綁角色」並存，達成個別使用者差異化授權。
- ⚠️ **團隊欄位留空一律是合法值，不得改成 `[Required]` 硬擋**；要提醒就走軟性確認 `TeamBindingConfirm`（`Web/Components/Commons/`），目前涵蓋分類（`CategoryViewView`）、專案（`ProjectViewView`）與使用者（`MyUserView`，0.4.43 起）三處。呼叫端只負責提供「會有什麼影響」那句話，對話窗標題／按鈕文案一律由樣板決定，**不要各自寫 `ConfirmAsync`**。使用者維護那支另有兩項判斷：訊息依角色 `DefaultTeams` 有無而分兩種措辭，且勾選「管理員」時直接放行（管理員不受行級過濾，提醒只是雜訊）。
- **分類主檔本身也帶 `Teams` 標籤**（0.4.40 起）：`Category.Teams` 同樣是換行分隔字串，表示「哪些團隊可以使用這個分類」，未設定＝公用分類。過濾集中在 `CategoryService.ApplyTeamVisibility`，套用於清單 `GetAsync`、單筆 `GetAsync(id)` 與下拉用的 `GetAllEnabledNamesAsync`。
- ⚠️ **分類的空團隊規則與紀錄相反**：紀錄是「使用者沒有團隊 → 只看得到公開紀錄」；分類是「使用者沒有團隊 → 視為不受限，看得到全部分類」。分類可見性只是下拉清單的便利性過濾，安全邊界由 RBAC 負責，故採寬鬆規則。修改時勿「順手改成一致」，`CategoryServiceTeamVisibilityTests` 會擋。
- 分類的**名稱唯一性檢查不套團隊過濾**（全域比對），否則會出現「看不到卻建得出同名分類」。
- Web API（repository 路徑）0.9.105 起與畫面套用同一套過濾（之前完全不過濾）；範圍外一律 404，指定範圍外團隊回 400。⚠️ `CategoryController.Update` 是整筆覆寫，`CategoryCreateUpdateDto` 必須帶 `teams` 欄位，否則每次 API 更新都會把團隊綁定清空（非管理員會被「不能改成公開」擋下）。
- ⚠️ `RecordAccessScopeProvider` 以 `RequestActorResolver` 取使用者 Id（Cookie 在 Sid、JWT 在 NameIdentifier）；已登入卻取不到 → `RecordAccessScope.None`（什麼都看不到）。不要改回「退回只看公開」：分類的反向規則下會變成全部看得到。

### 4.2 分類／團隊的名稱唯一性 ⚠️（0.4.41 起）

- **寫入前一律正規化**：`Category.Name`、`Team.Name`、`Team.Code` 由 `NameNormalizer`（`Business/Helpers/`）處理，且**掛在 AutoMapper 的「→ Entity」映射上**，所以 Blazor 與 Web API 兩條路徑都涵蓋。新增這類欄位時請比照辦理。
  - ⚠️ 沿革：先前是「檢查時 Trim、寫入時不 Trim」，導致「技術文件 」原樣入庫後，「技術文件」再也比不到它（SQLite 的字串比較對尾隨空白敏感），兩筆看起來一模一樣的資料同時存在。**檢查與儲存必須比對同一個字串。**
  - `Team.Code` 用 `NormalizeOptional`，空白一律歸成 `null`。「未填」在資料庫中只能有一種表示法 —— SQLite 的唯一索引視 NULL 互不相等，但**空字串彼此相同**。
- **資料庫唯一索引**：`IX_Category_Name`、`IX_Team_Name`、`IX_Team_Code`（`BackendDBContext.OnModelCreating`），0.9.94 起為**部分索引**（`WHERE "IsDeleted" = 0`，只約束未刪除的資料；還原時由服務層重新檢查衝突）。前置檢查與寫入不在同一個交易裡（TOCTOU），索引是最後一道防線。索引採 SQLite 預設的 BINARY 定序（區分大小寫），服務層的不分大小寫判定更嚴格會先擋下；**刻意不改欄位 collation**，以免影響既有查詢。
- **UI 不得丟棄 `VerifyRecordResult`**：`AddAsync`／`UpdateAsync` 的回傳值必須檢查後才顯示成功。否則唯一索引擋下的寫入仍會顯示「新增成功」。
- **唯一索引違反須經 `UniqueConstraintHelper.TryGetFriendlyMessage` 轉譯**，否則會被服務層的泛用 `catch (Exception)` 變成看不懂的「新增失敗」。
- **UI 與 API 的判定語意必須一致**：`CategoryRepository.ExistsByNameAsync` 等 API 路徑的檢查也要走 `NameNormalizer` + 不分大小寫。曾經出現「UI 擋得下、API 塞得進去」。
- ⚠️ **加唯一索引的 migration 必須先清理既有資料**：每次啟動都會自動套用 migration（0.9.91 起由 `DatabaseInitializer` 執行），只要有一筆重複就會 migration 回滾、`__EFMigrationsHistory` 不寫入、**每次重啟都再失敗一次**。作法見 `20260826073047_AddCategoryTeamNameUniqueIndex`（去空白 → 空代號歸 NULL → 重複改名為「原名 (重複-Id)」→ 建索引），由 `CategoryTeamUniqueIndexMigrationTests` 以真正的 `MigrateAsync()` 守門（其餘測試 fixture 用 `EnsureCreatedAsync()`，測不到 migration）。衍生專案複刻後只剩 `Init`、這支測試也已刪除，要看範例請對照腳手架原始 repo。
- 已知限制（非本次回歸，中文名稱不受影響）：SQLite 的 `lower()` 只折疊 ASCII，`ÉCOLE`／`école`、全形英數不視為重複；亦未做 Unicode 正規化。現有大小寫測試用 ASCII 剛好綠燈，**不要據此以為非 ASCII 也有保護**。
- 待辦：`MyUser.Account` 與 `RoleView.Name` 的唯一性檢查更弱（未 Trim、區分大小寫、無索引），影響登入與權限，另案處理。

## 5. 權限與選單對應（已改為宣告式，非位置索引）

側邊選單以**選單 Id → 權限鍵**的宣告式對應決定顯示，**重排 Menu.json 不會錯位**（已移除舊的位置索引耦合）：

- `src/CustomerHelpAgent/CustomerHelpAgent.Web/Datas/Menu.json` — Sidebar 結構（含各項 `id`）。
- `SidebarMenuService.MenuPermissionMap`（`src/CustomerHelpAgent/CustomerHelpAgent.Web/Components/Layout/SidebarMenuService.cs`）— `Id → 權限鍵` 對應，權限鍵取自 `MagicObjectHelper` 常數。
- `MagicObjectHelper`（`src/CustomerHelpAgent/CustomerHelpAgent.Share/Helpers/MagicObjectHelper.cs`）— 權限鍵常數。

新增受權限控管的頁面時：於 `MagicObjectHelper` 新增權限鍵常數、於 `Menu.json` 新增項目（給定唯一 `id`）、於 `MenuPermissionMap` 加入 `id → 權限鍵`。三者以 **`id` 對應**，不再依賴排列順序。

頁面本身的「登入閘門」與「檢查完成前不渲染」另見 **§5.1**。

**⚠️ 選單支援三層（0.9.21 起實際使用）**：資料模型（`SidebarMenuItemModel.SubMenu` 自我參照）、
權限過濾（`ApplyPermissionStructure`／`FilterAuthorizedMenuItems`）與展開模式渲染（`SidebarMenuNode.razor` 自我遞迴）
都是深度無關的，但**收合模式的 flyout 不是**：
`NavMenu.razor` 的 `collapsed-menu-flyout` 區塊只輸出帶 `url` 的節點，
群組型節點（無 `url`）必須由該區塊明確渲染成「可懸停的群組列 + 屬於它自己的巢狀 flyout」
（`.collapsed-flyout-group` ＋ `.collapsed-flyout-submenu`）才看得到。
新增群組型節點時請實際收合側邊欄確認 flyout 不是空白，並確認滑鼠能從群組列平移到第二層不斷開
（靠第二層的透明 `::before` 橋接，其寬度必須大於兩者的水平間距）。

**側邊欄初始狀態（0.9.112 起）**：寬螢幕預設展開並記住上次選擇，窄螢幕（≤ 640px）一律從收合開始，
由 `wwwroot/js/nav-state.js` 決定（檔名刻意不含 `sidebar`，見檔頭註解）；斷點 `640.98px` 必須與 `MainLayout.razor.css`／`NavMenu.razor.css` 一致。
⚠️ 一開始就展開時，目前頁面所屬的群組要在 `NavMenu.OnAfterRender` 才套用 `OpenKeys`（0.9.113）：AntDesign `Menu` 只把 `OpenKeys` 套到已註冊的 `SubMenu`，
選單與 `SubMenu` 在同一次渲染建立時初始值會落空，群組不會自動打開。

**⚠️ flyout 顯示條件用 `:has(:focus-visible)`，不可改回 `:focus-within`。**
`:focus-within` 會讓滑鼠點完子項後焦點黏在該連結上、flyout 收不起來（曾因此被移除）；
但完全不含焦點條件，鍵盤使用者又永遠進不了 flyout。`:focus-visible` 本身會區分鍵盤與滑鼠，
是唯一同時滿足兩者的寫法。`NavMenu.razor.css` 該區塊的註解已寫明，改動前請先讀。

群組節點同樣需要自己的權限鍵與 `MenuPermissionMap` 條目（`MenuPermissionConsistencyTests` 要求 id 集合完全相等）；
若該群組屬管理員專屬，還要登錄到 `CustomerHelpAgent.Tests/AdminOnlyPermissionTests.cs` 的 `AdminOnlyPermissionKeys`。

**⚠️ 還有第四方：頁面自己的權限檢查（0.4.33 起納管）**

檢視在 `OnInitializedAsync` 內呼叫的 `CheckAccessPage(權限鍵)`，**必須與該路由在 `MenuPermissionMap` 中的鍵一致**。

三方 id 對得上、第四方卻用錯鍵，症狀是「使用者看得到選單、點進去被踢出」——
0.4.33 之前 `ProjectViewView` 就是用**群組鍵**（`角色_專案管理`）而非葉節點鍵（`角色_專案項目`），
只被授予「專案項目」的角色會被擋在門外。

新增檢視時請一併於 `CustomerHelpAgent.Tests/MenuPermissionConsistencyTests.cs` 的 `ViewToMenuId` 登錄
（管理員專屬檢視則登錄到 `AdminOnlyViews`），測試會驗證四方一致。

**⚠️ `CheckAccessPage` 接受「裸頁面鍵」與「`頁面鍵:view`」兩種（0.9.37 起）**

角色矩陣只勾「檢視」時產生的是 `專案項目:view`，**不含裸鍵**。若 `CheckAccessPage` 只認裸鍵，
唯讀角色會連頁面都打不開、選單也不顯示 ——「可看不可改」就只剩 API 端生效。
這是 `CheckAccessAction`「動作鍵不中則退回裸鍵」的鏡像，由 `AuthenticationStateHelperTests` 釘住
上下界（`:view` 通過、`:create` 不通過）。⚠️ 放寬僅限 `view`，不可改成「任何動作鍵都能進頁面」。

**⚠️ 動作只有四個**：`view`／`create`／`edit`／`delete`。`export` 於 0.9.37 自矩陣下架
（勾得到但全系統沒有檢查點，屬死權限），`AdminOnlyPermissionTests` 守門；
要重新上架必須**先**有會檢查它的程式。完整教學見
[腳手架開發指引 §7](../guides/腳手架開發指引.md)。

**權限鍵常數不得帶前後空白**：權限鍵會被寫進 RBAC 資料表並以 **Ordinal** 比對，
空白會讓授權靜默對不上。同一個測試檔會擋下。

**管理員專屬頁面（權限鍵刻意不上架角色矩陣）**：

- 「系統管理」群組底下**只放子群組、不放單一頁面**（0.9.113 起重整，`New-CrudModule.ps1` 會擋 `-MenuGroupId 3`）：
  - 帳號與權限（id 34）：`/myusers`、`/roleviews`（**0.4.33 起**）、`/audit-logs`
  - 監控與診斷（id 6，0.9.113 前名為「統計與分析」）：`/system-health`、`/logs`、`/log-level-setting`、`/system-exceptions`、`/database-usage`
  - AI 管理（id 7）：`/prompt-templates`、`/ai-call-logs`、`/token-usage`
  - 系統設定與維運（id 8）：`/system-parameters`、`/announcements`、`/scheduled-jobs`、`/backups`、`/data-retention`（0.9.133 起）、`/demo-console`（1.0.5 起，另需示範模式）

這些群組與頁面的權限鍵都**不列入** `RolePermissionService.GetRoleListPermissionAllName()`，
因此不種 `Permission` 資料列、角色矩陣不顯示、任何角色都無法被授予，
只有頁面的 `CheckIsAdmin()` 能通過。由 `AdminOnlyPermissionTests` 守門，**請勿補上**。

> 沿革：0.4.33 之前「系統管理」群組有上架矩陣，但兩個頁面實際以 `CheckIsAdmin()` 守門，
> 形成「勾得到卻永遠無效」的死權限。

補充現況（RBAC 已落地）：
- **權限粒度到動作級**：`view/create/edit/delete`（見 `PermissionKeys.cs`；`export` 已於 0.9.37 下架），可做「可看不可改」；裸頁面鍵＝該頁全動作（向後相容）。
- **一使用者多角色**：`UserRole` 多對多，權限取**聯集**；團隊直綁使用者（`UserTeam`）。
- **UI 與 API 共用單一權威來源** `IPermissionChecker`（RBAC 關聯表）：登入時 `AuthenticationStateHelper.Check` 以 `GetEffectivePermissionKeysAsync` 一次載入有效權限鍵（含多角色聯集）到 `CurrentUser.RoleList`，供選單/`CheckAccessPage`/`CheckAccessAction` 同步比對；`TabViewJson` 退為角色編輯回填用的相容欄位。

> 權限判定的權威來源為 RBAC 關聯表（見 [認證授權與權限機制](../security/認證授權與權限機制.md)）。

## 5.1 頁面授權：預設需登入、匿名需列白名單、檢查完成前不渲染 ⚠️（0.9.41 起）

0.9.41 之前頁面一律不標 `[Authorize]`，全靠 `OnInitializedAsync` 內的 `AuthenticationStateHelper.Check()`。
那個檢查要等元件**先渲染一次**才會導走，未登入者直接輸入 `/App` 等網址，會瞬間看到側邊欄、頁首與頁面內容；
已登入但沒權限的人，也會先看到工具列與表格框架才換成「你沒有權限存取此頁面」。現在分三層擋：

| 層 | 位置 | 擋什麼 |
|---|---|---|
| HTTP 閘門 | `Components/Pages/_Imports.razor` 的 `@attribute [Authorize]` | 未登入的整頁請求在授權中介軟體就被 302 到 `/Auths/Login?ReturnUrl=…`，**瀏覽器收不到任何頁面內容** |
| circuit 內 | `Routes.razor` 的 `AuthorizeRouteView`（`Authorizing` 與 `NotAuthorized` 皆不渲染，後者用 `RedirectToLogin` 導走） | circuit 內導覽不經過 HTTP，靠它讓 `[Authorize]` 同樣生效 |
| 檢查完成前不渲染 | `MainLayout` 的 `@if (isAuthenticated)`；各檢視的 `@if (!isAccessChecked) { }` | Cookie 還在但帳號停用／被刪／缺角色；已登入但沒有該頁權限 |

**新增頁面時：**

- 放在 `Components/Pages/`（含子資料夾）底下就**自動需要登入**，不必自己標。
- 需要匿名存取的頁面自己標 `@attribute [AllowAnonymous]`，**並**加進 `PageAuthorizationTests.AnonymousPages` 白名單 ——
  沒列入白名單的匿名頁面、或沒宣告 `[Authorize]`／`[AllowAnonymous]` 的可路由元件（例如放在 `Pages/` 以外），測試都會失敗。
  目前的白名單：`Home`（`/` 啟動頁）、`Error`、`NotFound`、`Login`、`Logout`、`Pending`、`ForgotPassword`、`ResetPassword`（後兩者 0.9.60 起）、`RefreshSession`（0.9.103 起）、`TwoFactor`（0.9.104 起）。
- 檢視若呼叫 `AuthenticationStateHelper.Check()`，照既有檢視的寫法：宣告 `isAccessChecked`，登入檢查通過後、
  權限判定之前設為 `true`，markup 最外層以 `@if (!isAccessChecked) { } else if (RoleMessage…)` 擋住。同一個測試檔會掃描原始碼守門。

**⚠️ `NotFound` 必須匿名，不可改成需要登入。** `UseStatusCodePagesWithReExecute` 會把「沒有 body 的錯誤狀態碼」
（API 的 404、`/UploadFiles` 的 401…）改寫成 `/not-found` 再跑一次管線；這頁若需要登入，那些回應會全被
Cookie challenge 換成 302，API 呼叫端拿不到真正的狀態碼（`ApiIntegrationTests` 會紅）。未登入者照樣看不到內容：
頁面是 `prerender: false`，HTTP 回應只有空殼，circuit 起來後 `MainLayout` 在檢查通過前不渲染並把人導去登入頁。

**⚠️ `ReturnUrl` 一律經 `ReturnUrlGuard.Sanitize`。** Cookie handler 對明寫的 `AuthenticationProperties.RedirectUri`
**不做站內檢查**，0.9.41 之前 `/Auths/Login?ReturnUrl=https://evil.com` 登入成功後會被導去外站（open redirect）。
現在只接受 `/` 開頭、且不是 `//`、`/\` 開頭、不含控制字元的站內路徑，其餘回 `/App`。

> 為什麼不用 `AuthorizationOptions.FallbackPolicy`：它會連 `/Auths/Login`、靜態資源重跑等端點一起鎖住，
> 例外得一個個補 `[AllowAnonymous]` 且不易察覺漏網；以資料夾層級的 `_Imports.razor` 預設需登入、
> 例外以白名單測試釘住，範圍明確。Controller 仍各自由 `MapControllers().RequireAuthorization()` 管。

## 6.1 按鈕與圖示慣例

- 圖示函式庫是 **BlazorMaterialIcons**（`readme.md` 技術堆疊表已宣告）。**不要使用 emoji，也不要使用 AntDesign 的 `<Icon>`** —— 後者全專案零使用。
- 載入的是 **classic Material Icons** 字型（`App.razor` 的 Google Fonts），**不是 Material Symbols**。使用 Symbols 專有名稱（例如 `database`）會渲染成破圖方塊。同理，下載圖示要用 `file_download` 而非較新的 `download`。
- **按鈕圖示一律透過共用元件**，不要自己寫 `<Button>` 塞圖示：

  | 情境 | 元件 | 樣式 |
  |---|---|---|
  | 工具列（新增／重新整理／搜尋／清空／匯出）| `<ToolbarIconButton Title Icon OnClick [Disabled] />` | 36×36，一般 Default 外觀 |
  | 表格操作欄（修改／刪除／移除）| `<CrudActionButton Title Icon OnClick [Danger] [Disabled] />` | 28×28，透明無框 |

  兩者都自帶 `<Tooltip>` 與視覺隱藏的無障礙標籤，**外層不需再包 `<Tooltip>`**，也不需自訂 `*-icon-button` CSS。

- 常用對應：新增 `add`、重新整理 `refresh`、搜尋 `search`、清空 `close`、匯出 `file_download`、修改 `edit`、刪除 `delete`、移除 `close`。
- **表格排序解析一律用 `TableSortHelper`**（`Components/Commons/`）：它以 reflection 讀 AntDesign
  內部屬性，對套件升版脆弱，因此全專案只留一份。不要複製回檢視。
- **通知訊息一律用 `ViewNotification`**（`Components/Commons/`）。
  注意「新增成功／修改成功／刪除成功」沿用 `NotificationType.Warning`（既有外觀，非筆誤），
  因此刻意不提供 `Success` 多載。
  錯誤（`Error`／`UnexpectedError`／`ValidationError`）與真正的警告（`Caution`，0.9.129 起）會附「複製」按鈕、
  **不自動關閉**，並在顯示當下寫一筆日誌（`UnexpectedError` 記 Error，其餘記 Warning；帶追蹤碼，/logs 查得到）。
  呼叫點原本的 log 照寫（那筆有例外與上下文）；通知內文會進日誌，所以**不可夾帶密碼／token／Email**。
  成功訊息繼續用 `Warning`，失敗、衝突、結果不完整用 `Caution`。**不要直接呼叫 `NotificationService.Open`**
  （`ViewNotificationTests` 會擋下）。
  **`UnexpectedError` 必須傳入例外**（0.9.130 起，`UnexpectedError(service, 訊息, ex)`）：管理員或 `ExceptionDetailPolicy` 允許時，
  「複製」會附上完整 `ex.ToString()`；畫面與通知日誌不含。`catch` 裡不要用 `Error`，一律 `UnexpectedError(…, ex)`。
  沒有例外但有技術細節的失敗（AI 上游 HTTP 錯誤）用 `Error(service, 訊息, detail)`，detail 不可含上游回應本文。
- **新模組請用 `scripts/New-CrudModule.ps1` 產生**，不要複製既有檢視 ——
  0.4.27 的 emoji 回歸正是複製貼上造成的。改了慣例請一併更新產生器樣板。
- 選單圖示另受 `CustomerHelpAgent.Tests/MenuIconTests.cs` 的白名單管控（`Menu.json` 新增 icon 須同步加入，例如 0.9.21 的 `manage_accounts`、0.9.22 的 `monitor_heart`）；按鈕圖示則由 `CustomerHelpAgent.Tests/ButtonIconConventionTests.cs` 擋下 emoji。
- ⚠️ **圖示大小只能從 `MaterialIcon` 的 `Size` 參數改，CSS 改不動。**
  該元件會輸出行內的 `style="font-size:…"`，`font-size` 規則一律被壓過。
  0.9.16 已把四個 CSS 檔裡 9 條無效的 `font-size` 清掉（`NavMenu`／`MainLayout`／
  `ToolbarIconButton`／`CrudActionButton`），**不要再往那裡加**。
  所有圖示目前的 computed font-size 都是 24px（側邊欄 `home` 27px）。
  ⚠️ 當年那些規則其實帶著「工具列 18px、漢堡鈕 17.6px、使用者選單 19.2px」的設計意圖，
  但從未生效。現在的 24px 就是定案；真要縮小請補 `Size` 參數
  （`ToolbarIconButton`／`CrudActionButton` 目前沒有這個參數），不是把 CSS 改回去。
- **光學尺寸補正**（0.9.15 起）：各字面的墨跡在同一個 em 方框裡佔的高度差很多，
  字級一樣不代表看起來一樣大（`home` 72 vs `work` 80 vs `admin_panel_settings` 84，
  以 100px 字級量測）。側邊欄的補正表在 `Components/Layout/MaterialIconOpticalSize.cs`。
  ⚠️ 要新增補正請**先量墨跡高度再決定**，不要憑感覺調，也不要把矮的字面一律放大 ——
  `storage` 更矮但視覺密度夠，補了反而突兀。

## 6.2 版面層級（z-index）約定 ⚠️（0.4.44 起）

⚠️ **帶 `z-index` 的定位元素會建立 stacking context —— 內層再高也翻不出去。** 這是本專案踩過的坑：
`.top-row` 是 `position: sticky` ＋ `z-index`，所以 `.user-menu-dropdown` 的 `z-index: 20`
**只在頂部列內部有效**；對整頁而言，整個頂部列是以 `.top-row` 自己的數值參與根層級堆疊。
要調整某個元素跟頁面內容的前後關係，**改的是它最外層那個 stacking context 的值，不是它自己的**。

現行根層級由低到高（`MainLayout.razor.css` 的 `@media (min-width: 641px)` 區塊）：

| 層 | 值 | 來源 |
|---|---|---|
| AntDesign 表格固定欄儲存格（`.ant-table-cell-fix-left/right`，另帶 `background: #fff`）| 2 | AntDesign 套件 |
| AntDesign 表格 sticky 標頭、選取欄 | 3 | AntDesign 套件 |
| AntDesign 表格容器邊框（`.ant-table-container::after`）| 4 | AntDesign 套件 |
| `.top-row`（頂部列，含使用者選單）| **20** | `MainLayout.razor.css` |
| `.page.sidebar-collapsed .sidebar`（含 `z-index: 40` 的飛出選單）| **30** | `MainLayout.razor.css` |
| AntDesign Modal／Notification／Tooltip | 1000+ | AntDesign 套件 |

- `.top-row` 必須 **> 4**，否則使用者選單的「關於」「登出」會被有固定「操作」欄的頁面蓋住
  （`MyUserView`、`RoleViewView`、`CategoryViewView`、`ProjectViewView`、`TeamViewView` 等十四個檢視用
  `<ActionColumn Fixed="ColumnFixPlacement.Right">`）。
- `.sidebar` 必須 **> `.top-row`**，否則收合側邊欄的飛出選單會被頂部列蓋掉。
- **不要用「移除 `z-index`」來解**：`.top-row` 沒有 `z-index` 就不建立 stacking context，選單確實會浮上來，
  但 sticky 標頭反而會被表格固定欄穿透 —— 換一個 bug 而已。
- `.ant-table-resizing` 是 99，但本專案沒有任何表格開 `Resizable`；日後若要啟用，這張表要重算。
- 沿革：`Fixed` 自建立 `MyUserView` 起就有，`.top-row` 的 `z-index: 1` 自 `Init` 起就有，屬長期潛伏。
  0.4.24 新增「關於」讓選單面板多一項、變高，把「登出」推進表格範圍才變得明顯。
  **症狀會隨捲動位置與視窗高度飄移**，容易誤判成「有時好有時壞」的偶發問題。

## 6.3 對話窗表單不得攔截鍵盤事件 ⚠️（0.9.3 起）

**`@onkeydown` 絕不可掛在 `<EditForm>`／`<form>` 上。** keydown 會從表單內**任何**子元素冒泡上來，
表單層一旦攔截，對話窗裡每一個能取得焦點的元件按 Enter 都會觸發存檔關窗 —— 而使用者的輸入
通常還沒完成。

- **AntDesign 的 overlay 攔截幫不上忙**：`ant-design-blazor.js` 的 `preventKeyOnCondition`
  只呼叫 `preventDefault()`，**沒有 `stopPropagation()`**，所以「`Select` 按 Enter 選取選項」
  之後事件照樣往上冒到 form。`DatePicker`、`InputNumber` 同理。
- **`Enter` 與 `Shift+Enter` 要分開想**：`KeyboardEventArgs.Key` 兩者都是 `"Enter"`，
  只比對 `Key` 會讓「TextArea 換行」這個標準手勢變成存檔關窗。
- **存檔的唯一入口是 `<Modal OnOk>`**（「確定」按鈕）。`@bind-Value` 在 change／blur 才回寫，
  點按鈕會先讓欄位 blur，值才會進模型；用鍵盤送出則會撞上這個延遲
  —— 0.9.3 之前靠 `await Task.Delay(200)` 硬等，在慢連線的 SignalR circuit 上並不可靠。
- **Escape 交給 `<Modal Keyboard="true">`**，不要自己處理。由 Modal 處理時，下拉／日期面板
  展開中的 Esc 會先被該元件消化（只收合面板）；自己在 form 層攔截則會連整個對話窗一起關掉、
  丟棄已輸入的內容。
- 真的需要鍵盤捷徑時，**綁在個別元件上**（例如 `<Input OnPressEnter="..." />`），
  不要綁在表單層。
- 守門：`CustomerHelpAgent.Tests/ModalKeyboardConventionTests.cs` 掃描 `Components/**/*.razor`，
  只要 `<EditForm>`／`<form>` 帶 `@onkeydown`／`@onkeyup`／`@onkeypress` 就失敗。

> 沿革：五個 CRUD 檢視（使用者、角色、分類、團隊、專案）自建立起就複製了同一段
> `OnModalKeyDownAsync`，受影響的不只多行文字與下拉 —— `DatePicker`、`InputNumber`、
> `Checkbox`／`Switch`、`InputFile`，甚至「移除待上傳檔案」按鈕按 Enter 都會順便存檔關窗。
> 0.9.3 整段移除並加上守門測試。

表單對話窗的完整版型與行為規範見 §6.8 與
[對話窗 UI 設計規範](對話窗%20UI%20設計規範.md)。

## 6.4 對話窗尺寸與「會計費的對話窗」

- **尺寸一律寫在 `Components/Commons/OverlayStyles.razor` 的全域 `<style>`**
  （該檔整個就是一個 style 區塊，非 scoped，所以能直接命中 `.ant-modal-*`），

## 6.5 AI 輸出一律經安全管線渲染 ⚠️（0.9.4 起）

日誌檢視頁的 AI 分析結果，以及 0.9.68 起系統例外紀錄的 AI 例外分析對話（`ExceptionAiAnalysisModal`），
是全專案**僅有的**把**不可信內容**丟進 `MarkupString` 的地方。它們都必須先經過
`CustomerHelpAgent.Web/Ai/AiMarkdownRenderer.ToSafeHtml`，不可把模型回應直接丟進 `MarkupString`。
（另一個 `MarkupString` 使用者是頁面操作說明，內容是隨原始碼進版控的可信檔案，走自己的管線，見 §6.14。
兩條管線**不可合併**：AI 這條不可擴充，說明那條需要表格。）

原因：日誌與例外訊息有一部分來自使用者輸入，所以模型的輸出是**攻擊者可部分控制的**不可信輸入。
使用者在 AI 例外分析打的追問只以純文字顯示，絕不經 `MarkupString`。

管線刻意最小化，三條紅線：

- Markdig 只開 `DisableHtml()`。**不可**加 `UseAdvancedExtensions()` 或
  `UseGenericAttributes()` —— 後者會讓 `## 標題 {onclick="..."}` 直接注入 HTML 屬性。
  也**不可**加 `UseAutoLinks()`，否則日誌裡的裸 URL 會變成可點連結。
- ⚠️ **`DisableHtml()` 本身不夠**：它完全不管連結的 URL scheme，`[點我](javascript:...)`
  會原封不動渲染成可點連結。因此解析後還要走訪語法樹，**移除所有圖片**、
  把 scheme 限制在 `http`／`https`／`mailto`，其餘清空 URL。
- 保留下來的連結必須帶 `rel="noopener noreferrer nofollow"` 與 `target="_blank"`。

另外三條與此功能相關的資料外洩紅線：

- 呼叫 AI 的錯誤訊息只能由固定中文字串加上上游 `error.code` 組成，**絕不回吐上游
  回應 body** —— body 可能夾帶整份提示詞，也就是日誌內容。
- 寫進 `AuditLog` 的 `Detail` 只能有數量、模型、用量與耗時，**不可寫入日誌內容、例外內容、
  使用者的追問或 AI 輸出**：稽核紀錄的可視範圍比日誌檢視頁更廣。
- ⚠️ **AI 例外分析不得把例外紀錄的 `Account`／`UserId` 送往外部 AI**，只送「有／無登入使用者」
  （`AiExceptionPromptBuilder.BuildDetailLines` 是唯一出口，`AiExceptionPromptBuilderTests` 以哨兵守門）。
- API 金鑰只掛在單次 `HttpRequestMessage` 上，不可設到 `HttpClient.DefaultRequestHeaders`。

守門：`CustomerHelpAgent.Tests/AiMarkdownRendererTests.cs`、`AiLogAnalysisServiceTests.cs`
（含「錯誤訊息絕不含金鑰或上游 body」的哨兵字串斷言）、`AiExceptionPromptBuilderTests.cs`。
完整說明見 [AI 日誌分析](../features/AI日誌分析.md) 與 [AI 例外分析](../features/AI例外分析.md)。

## 6.6 例外自動記錄管線與防遞迴紅線 ⚠️（0.9.11 起）

全專案任何 `logger.LogError(ex, …)` 都會被自訂的 `ILoggerProvider` 收進「系統例外紀錄」
（`/system-exceptions`，管理員專屬）。**0.9.11 當時既有的 75 個 `catch (Exception ex)` 一行都不用改**，
日後新寫的 catch 也自動涵蓋。管線：

```
ILogger → ExceptionLogProvider → ExceptionContextAccessor(AsyncLocal)
        → Channel(有界 1000，滿載丟棄並計數) → ExceptionLogWriter(IHostedService，關機時清空)
        → ExceptionLogService → SQLite ＋ ExceptionStackFileStore → 檔案系統
```

### 三條紅線

1. ⚠️ **管線內的四支類別絕不可注入 `ILogger`**：`ExceptionContextAccessor`、`ExceptionLogProvider`、
   `ExceptionLogWriter`、`ExceptionStackFileStore`。用 `ILogger` 記自己的失敗會形成
   「失敗 → 記錄 → 再失敗」的無限遞迴。需要留話時一律走 `NLog.Common.InternalLogger`。
   它們已列在 `LoggingConventionTests` 的豁免清單，**請勿「順手補上」logger**。

2. ⚠️ **「操作」必須取日誌訊息的「樣板」（`{OriginalFormat}`），不是算好的訊息。**
   合併鍵＝類型＋訊息＋頁面＋操作。取成 `Name=技術文件` 而非 `Name={CategoryName}`，
   會讓每個參數值都變成一個新簽章，列數立刻失控 —— 而這個症狀要等正式環境累積一陣子才看得出來。
   由 `ExceptionSignatureTests` 與 `ExceptionLogProviderTests` 守門。

3. ⚠️ **堆疊檔的生命週期只能經由 `ExceptionStackFileStore`。**
   刪單列、清空全部、清除舊紀錄三條路徑都要走它；資料列建立失敗時也必須把剛寫的檔刪掉。
   否則會重蹈專案附件「資料列刪了、實體檔還在」的覆轍。

### 其他要點

- 收錄門檻是 **Error 以上且帶例外物件**；`OperationCanceledException` 刻意不收（使用者取消、正常關機）。
- `ApplicationCircuitHandler.CreateInboundActivityHandler` 負責提供「誰、哪一頁」。
  ⚠️ 它是**全站每一次互動都會經過**的路徑，內部全程 `try/catch`，改動後務必做全站回歸。
- ⚠️ **在 `ExternalFileSystem` 新增任何路徑設定，都要同步加進 `ApiIntegrationTests.CreateSettings()`**。
  整合測試會啟動真實 host，管線是活的；漏改會讓測試把檔案寫進開發者的真實目錄。
  0.9.11 的 `ExceptionPath` 就踩過這個坑；0.9.14 的 `TokenUsagePath`、0.9.72 的 `AiCallLogPath`、0.9.131 的 `AuditContentPath` 依此在寫程式的同時就補上。
  後者更危險：AI 對話紀錄的自動過期是背景服務，host 一啟動就會去清月份目錄，漏改等於讓測試刪真實資料。
- ⚠️ **Channel 必須維持 `BoundedChannelFullMode.Wait`**（0.9.77）：`DropWrite` 下 `TryWrite` 永遠回 true，丟棄筆數永遠是 0。
- **同一個例外實例只收一次**（0.9.77，`ConditionalWeakTable`）：不要為了「去重」逐一排除框架 logger 類別。
- ⚠️ **`app.UseExceptionContextUser()` 必須排在 `UseAuthorization()` 之後**（0.9.77）：JWT 不是預設驗證機制，
  JWT 端點的 User 要到授權中介軟體才驗證出來；`UseHttpRequestLogging` 則**留在原位**（移到
  `UseStatusCodePagesWithReExecute` 之後會讓每個請求記兩次）。帳號一律經 `RequestActorResolver` 依 claim 解析，不依路徑。
- ⚠️ **`UseExceptionHandler("/Error", createScopeForErrors: true)` 的 `createScopeForErrors` 不可拿掉**（0.9.115）：
  少了它，重跑 `/Error` 沿用原請求的 DI scope，Blazor 的 NavigationManager 已初始化，錯誤頁本身拋 "already initialized"，
  Production 任何 SSR 階段例外都只回空白 500、看不到追蹤碼。由 `ErrorPageRenderTests` 守門。
- ⚠️ **`UseRejectInvalidHost()` 排在 `UseHttpRequestLogging` 之後、`UseStatusCodePagesWithReExecute` 之前**（0.9.115）：
  HTTP/1.0 可以不帶 Host，這種請求進到 Blazor 頁面會組出 `https:///` 而拋 UriFormatException，一次記 5 筆 ERROR。
  `AllowedHosts` 擋不到（HostFiltering 預設 `AllowEmptyHosts = true`）。排在請求日誌之後才會留一筆 Information 400；
  排在 StatusCodePages 之前，400 才不會被重跑成 `/not-found`。由 `InvalidHostRequestTests` 守門。
- **`CrashMarkerStore`（補登檔）同樣不得注入 `ILogger`**：它在程序即將結束或 host 尚未建立時被呼叫，記錄機制可能已失效。
  `Program.cs` 的頂層 catch 排除 `HostAbortedException`（`dotnet ef` 的正常中止，不是啟動失敗）。
- ⚠️ **`ProcessExceptionHooks` 訂閱的兩個事件是行程全域的**，必須在 `ApplicationStopped` 取消訂閱 ——
  整合測試會在同一個行程連續啟動多個 host。
- **錯誤追蹤碼**（0.9.78）：一律經 `TraceCode`（`Diagnostics/TraceCode.cs`）。HTTP 請求由 `UseHttpRequestLogging` 產生並取代
  `HttpContext.TraceIdentifier`（⚠️ 重新執行 `/Error`、`/not-found` 時沿用 `HttpContext.Items` 裡的同一個碼），
  Blazor 每次互動由 `ApplicationCircuitHandler` 產生；日誌檔第 2 欄是 `${scopeproperty:item=TraceCode:…}`，**欄位數維持 7**（`LogQueryService.FieldCount`）。
  畫面上「未預期例外」的錯誤通知用 `ViewNotification.UnexpectedError(…, ex)`（自動附碼，管理員複製時附完整例外）；「名稱重複」這類一般訊息仍用 `Error`。
- ⚠️ **`ExceptionAlertService`（告警）也不得注入 `ILogger`**：它在寫入器的抑制範圍內被呼叫，寄信失敗經 ILogger 會再被收成例外、再觸發告警。
  寄信背景作業自己的例外（頁面 `EmailDispatch`）不告警。
- **稽核動作代碼只能引用 `AuditActions` 常數**（`Business/Helpers/AuditActions.cs`，0.9.78），由 `AuditConventionTests` 守門。
  API 端寫稽核用 `this.WriteAuditAsync(...)`（`ControllerAuditExtensions`，操作者由 JWT／Cookie 解析）；
  Blazor 頁面權限拒絕用 `AuthenticationStateHelper.RecordPageAccessDeniedAsync`，**不可**寫進 `CheckIsAdmin`／`CheckAccessPage`（側邊欄也呼叫它們）。
- **稽核的來源 IP 不由呼叫端傳**（0.9.117）：`AuditLogService` 寫入時向 `IClientIpProvider` 取（實作 `Web/Auth/ClientIpProvider`，scoped）。
  SSR 與 API 讀 `HttpContext`；Blazor circuit 內沒有可靠的 HttpContext，由 `ApplicationCircuitHandler.OnConnectionUpAsync` 寫入；排程作業為 null。
  ⚠️ 自己用 `IServiceScopeFactory` 開新 scope 再寫稽核，會拿不到 circuit 的 IP。部署在反向代理後面要設 `ForwardedHeaders`，否則記到代理的 IP。
  讀取端：稽核紀錄頁的「來源 IP」篩選是**前綴比對**（`AuditLogQueryService`，沒有 IP 的舊紀錄不符合，匯出 CSV 同條件）；
  個人資料頁「最近 20 筆登入紀錄」與首頁「上一次登入」也從同一欄顯示 IP（`ProfileService.LoginRecord.ClientIp`，0.9.123 起）。
- **稽核的長內容寫成檔案**（0.9.131）：修改前後差異、完整查詢條件走 `WriteAsync(content: …)`，由 `AuditContentFileStore` 寫到 `AuditContentPath`，資料表只存 `ContentFile`；Detail 仍只放短摘要（**不放搜尋原文**）。差異一律用 `AuditDiff`（密碼類欄位放進 ignore 再 `Masked`），查詢用 `ViewAudit.WriteSearchAsync`（使用者自由輸入的條件用 `AuditSearchCondition.Text`）。清除稽核要連同內容檔（`AuditLogQueryService` 已處理）。
- **`AuditLogService` 每次寫入各用一個 DbContext**（0.9.131，`IDbContextFactory`）：換頁稽核在 `ApplicationCircuitHandler` 射後不理，共用 circuit 的 scoped context 會和頁面初始化撞在一起。它每寫一筆就記一行 Debug `Audit recorded.`（不含內容檔）。
- 例外紀錄、稽核紀錄與 Token 用量的保存期限讀 `LogRetentionSettings`（0.9.78；Token 用量 0.9.96 起），由排程作業清理；時間基準不同（例外與 Token 用量為本地、稽核為 UTC）。
  0.9.98 起保留天數可在「系統參數」頁覆寫（§6.15），作業一律在執行時讀 `IOptionsMonitor.CurrentValue`。
- ⚠️ **排程作業**（0.9.96 起，`Web/Scheduling`）：
  - 週期性的背景工作一律實作 `IScheduledJob`，在 `ServiceCollectionExtensions.AddScheduledJobs()` 以 `AddScheduledJob<T>(名稱, 顯示名稱, 說明, 預設 cron)` 註冊；
    **不要再新增 `BackgroundService` + `PeriodicTimer` 的計時器** —— 沒有執行紀錄、IIS 每次回收都重跑、重疊回收時兩個行程各跑一次。
  - 作業是 scoped、每次執行在新的 scope 解析；⚠️ 不可從根容器列舉 `IScheduledJob`（singleton 的排程器與驗證器只讀 `ScheduledJobDescriptor`）。
  - 作業回傳 `ScheduledJobResult`：服務層已自己記錄的失敗回 `Failure`（不要再丟例外，否則系統例外紀錄出現兩筆）；沒預料到的例外直接丟出，框架會記錄並附追蹤碼。
  - 跨行程只跑一次靠 `ScheduledJobState.LastScheduledForUtc` 的原子搶占（一條 `ExecuteUpdate`）；同一作業不重疊靠 `*.job-<名稱>.lock` 檔案鎖（`CrossProcessFileLock`）。
    補跑的錨點在 `ScheduledJobState`（不清除），不要改成依賴會被清除的 `JobRun`。
  - ⚠️ Cronos 只接受 UTC 的 `DateTime`；從資料庫讀回的時間一律先經 `ScheduleCalculator.AsUtc`。cron 依伺服器本地時區解讀。
  - 長時間的作業要分批並在批次之間檢查 `CancellationToken`；刪檔一律經對應的 file store（§6.6、§6.7）。
  - 手動「立即執行」只放進 `ScheduledJobTriggerQueue`，由排程器啟動；⚠️ 不可在 Blazor 事件裡 `Task.Run` 執行作業（會繼承畫面的 ExceptionContext 與追蹤碼）。
  - 排程器必須註冊在 `ExceptionLogWriter` 之後（`ScheduledJobWiringTests` 守門）。
  - 例外：`SystemParameterRefreshWorker`（0.9.98 起）是 `PeriodicTimer` 背景服務而不是排程作業 —— 每個行程都要刷新自己的設定，排程作業卻是跨行程只跑一次，也不該每分鐘寫執行紀錄。
- ⚠️ **`LoggingPipelineMonitor`（日誌管線監控，0.9.79）不得注入 `ILogger`**：它訂閱 NLog 的 `InternalLogger.InternalEventOccurred`，
  在那個事件裡呼叫任何 NLog logger 會死結或遞迴；事件是行程全域的，`ApplicationStopped` 時取消訂閱。
- **瀏覽器錯誤回報**（0.9.79）：`client-error-reporter.js` → `BrowserErrorReporter.Report`（`[JSInvokable]`，Scoped＝每個 circuit 一份）。
  只由 MainLayout 在登入後註冊；前端送來的內容一律在伺服器端再截長度、頁面只留路徑。
- **慢操作**（0.9.79）：門檻在 `SlowOperationSettings`。資料庫指令由 `SlowDbCommandInterceptor`（掛在 `AddDbContextFactory`）量，
  ⚠️ 只記指令類型，**絕不記 SQL 本文與參數**；HTTP 請求排除 `/_blazor`。刻意不量 Blazor 單次互動（AI 與確認窗會誤報）。
- 完整說明見 [系統例外紀錄 PRD](../prd/系統例外紀錄-prd.md) 與 [日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md)。

## 6.7 LLM 用量記錄的擴充點 ⚠️（0.9.14 起；0.9.17 起含費用）

**每一個發出 LLM API 呼叫的地方，都必須記一筆用量。**否則「Token 用量」頁會漏帳，
而漏掉的那一筆通常正是花掉最多錢的那一筆。

```
LLM 呼叫點 → ITokenUsageRecorder.RecordAsync(TokenUsageEntry)
           → TokenUsageLogService → IAiUsageCostCalculator（費用＋單價／匯率快照）
                                  → SQLite（可聚合的數值欄位）
                                  → TokenUsageRawStore → 檔案系統（原始 usage JSON）
           → IAiCallLogRecorder.RecordAsync(AiCallLogEntry)（0.9.72 起，同一個 CallId）
           → AiCallLogService → AiCallLogFileStore → 檔案系統（完整請求與回應，AiCallLogPath）
                              → SQLite（AiCallLog：可篩選的中繼資料）
```

目前的呼叫點有三個：
- `AiChatCompletionClient.CompleteAsync`（0.9.68 起的共用核心，使用者主動觸發）：
  AI 日誌分析（作業「AI 日誌分析」）與 AI 例外分析（作業「AI 例外分析」，初始分析與每一輪追問）都經由它。
  **新增「使用者按按鈕、送一段對話給 LLM」的功能時，直接用它**，只要給 `Operation` 與三段情境化提示文字，
  記帳、錯誤對應、取消與逾時的區分都不必再寫一次。
- `AiHealthProbe.ProbeAsync`（系統健康監控頁每次載入自動發出，作業名稱「系統健康檢測」；自帶短逾時，所以不走共用核心）。
- `AuditingChatClient`（1.0.2 起，Microsoft Agent Framework）：**Agent 呼叫一律經 `AgentChatClientFactory.Create`**，
  它回傳的 `IChatClient` 在函式呼叫迴圈內側逐次查額度、記 Token 用量與 AI 對話紀錄（同一個 `ConversationId`）；
  自行 `new OpenAIClient(...)` 會漏帳。見 [售後 Agent 示範系統](../features/售後Agent示範系統.md)。

⚠️ 健康檢查類的呼叫**必須自帶短逾時**：`AiSettings.TimeoutSeconds` 預設 **600 秒**，
那是給「使用者按下按鈕、願意等」的情境用的。自動載入的頁面沿用它，端點一失聯就會卡住十分鐘。
作法是 `CancellationTokenSource.CreateLinkedTokenSource(ct)` + `CancelAfter(...)`，
不要去動具名 client 的 `Timeout`（那是共用的）。

### 新增呼叫點要做的四件事

1. 注入 `ITokenUsageRecorder`（**不要**直接相依 `TokenUsageLogService`）。
2. 在 `TokenUsageOperations`／`TokenUsageCallKinds` 登記常數（作業名稱與呼叫型別）。
3. 拿到 API 回應後呼叫一次 `RecordAsync`。
4. （0.9.72 起）注入 `IAiCallLogRecorder`，記一筆 **AI 對話紀錄**：送出前建立 `AiCallCapture`、
   緊接在 `SendAsync` 之前 `MarkSent()`、各分支填入 `HttpStatus`／`ResponseBody`／`ResponseText`
   與結果（`SetOutcome`），並把 `capture.CallId` 放進 `TokenUsageEntry.CallId`，最後在**單一 `finally`** 裡呼叫
   `AiCallCapture.RecordSafelyAsync`。走 `AiChatCompletionClient` 的呼叫點這一步已經做好，只要在
   `AiChatCompletionRequest` 帶上 `RelatedInfo`（與需要時的 `ConversationId`）。

做完這幾件事，該次呼叫就會自動出現在 `/token-usage` 與五個統計頁籤上，**不需要改頁面**。
費用也會自動算好 —— 呼叫端完全不必知道 `IAiUsageCostCalculator` 的存在。

⚠️ 但**要記得在 `AiPricingSettings.Models` 補上該模型的費率**，否則那些呼叫會全部記成
「未定價」（有筆數、沒金額）。更新費率或增減模型的步驟見
[AI 模型計費更新指南](../operations/AI模型計費更新指南.md)。

### 四條紅線

1. ⚠️ **Token 用量只存 `usage` 子物件，絕不存提示詞與模型回應內文。**
   AI 日誌分析的提示詞就是整份日誌內容（AI 例外分析則是例外明細與堆疊），用量紀錄保存期以「年」計、
   又會被統計與匯出，內文放進來等於繞過日誌檢視頁的管理員限制。
   切取工作由 `AiChatResponseParser.ExtractUsageJson` 負責，**不可**改成回傳整個回應 body。
   完整內文（0.9.72 起）**只准**進「AI 對話紀錄」：`IAiCallLogRecorder` → `AiCallLogService` → `AiCallLogFileStore`
   （`AiCallLogPath`），頁面管理員專屬、依 `AiCallLogSettings:RetentionDays` 自動過期、`Enabled=false` 即不記。
   其他資料表、NLog 日誌與稽核紀錄**仍不得**寫入內文（稽核只記動作、Id 與筆數）。
2. ⚠️ **記錄點放在發出 HTTP 的那一層，不可放畫面層。**
   原始 usage、實際模型名稱與耗時，回到畫面之前就已經丟失了。
3. ⚠️ **失敗也要記。**特別是「回應成功但內容為空」——那是付了錢卻沒拿到東西，最值得被看見。
   只有「設定不完整」（沒發出請求）與「使用者取消」不記。AI 對話紀錄則**取消與非預期錯誤也記**，
   只有沒送出的不記 —— 所以兩頁的筆數可能不同，這是刻意的。
4. ⚠️ **原始 JSON 檔的生命週期只能經由 `TokenUsageRawStore`。**
   刪單筆、清除此日之前、清空全部三條路徑都要走它。AI 對話紀錄的內容檔同理，只能經由 `AiCallLogFileStore`
   （另多一條自動過期：排程作業「AI 對話紀錄清理」呼叫 `AiCallLogService.PurgeExpiredAsync`；Token 用量同理由「Token 用量紀錄清理」分批刪除並經 `TokenUsageRawStore` 刪檔，0.9.96 起）。

### AI 對話紀錄的四個踩雷點（0.9.72 起）

1. ⚠️ **記錄只能放在 `finally`，而且要經 `RecordSafelyAsync`。**`finally` 裡丟出的例外會蓋掉原本的回傳值，
   記錄失敗就會把一次成功的 AI 呼叫變成例外；recorder 已保證不丟，這裡仍再包一層
   （`AiChatCompletionClientTests` 以會丟例外的 recorder 守門）。
2. ⚠️ **`MarkSent()` 必須緊貼在 `SendAsync` 之前。**放早了，設定錯誤之類「根本沒送出」的失敗也會被記成一筆；
   放晚了，連線失敗那一支就記不到。
3. ⚠️ **原始請求是逐字保存的 JSON，中文是 `\uXXXX`。**這是 `Utf8JsonWriter` 的預設編碼，**不要**為了好讀去改
   `AiChatRequestFactory`（那會改變實際送出的內容）；畫面由 `AiCallLogMessages.Parse` 解析、原始 Request 檢視另行排版。
   內容檔本身則以 `UnsafeRelaxedJsonEscaping` 序列化，避免外層再跳脫一次。
4. ⚠️ **內容可能數 MB（AI 日誌分析沒有字元上限）。**明細窗只渲染目前的檢視、每段只顯示前 20 萬字元、
   Markdown 渲染結果超過 512 KB 就退回純文字；完整內容一律走「複製」或下載 JSON。
- `ConversationId` 由 `ExceptionAiAnalysisModal` 開窗時產生、經 `AiExceptionCallContext` 傳給服務 ——
  `AiExceptionAnalysisService` 無狀態，對話是窗內持有的。
- 自動過期原本是本專案**第一個定時型** `BackgroundService`（`AiCallLogRetentionWorker`）；0.9.96 起已改為排程作業「AI 對話紀錄清理」（`AiCallLogRetentionJob`，見 §6.6「排程作業」），
  不要再新增定時型 `BackgroundService`。

### 費用計算的三條紅線（0.9.17 起）

1. ⚠️ **子集晶格不可破**：`CachedInputCount` ⊂ `InputCount`、`ReasoningCount` ⊂ `OutputCount`、
   `ImageInputCount`／`ImageCachedInputCount` ⊂ `InputCount`、`ImageOutputCount` ⊂ `OutputCount`。
   供應商把圖片 token 算在 `prompt_tokens` 裡面，**若改成額外加項，每筆圖片呼叫都會重複計費**，
   而且費用已經是寫死的快照，回頭沒得修。推理 token 完全不參與費用計算。
2. ⚠️ **費用算不出來不得吃掉整列用量。**`RecordAsync` 內對計算器另有一層 `try/catch`：
   外層那個雖然也會吞例外，但它會在 `AddAsync` 之前就中止 —— 計算器有 bug 會讓每一列用量
   都靜默消失，那比丟掉費用嚴重得多。**用量比費用重要。**
3. ⚠️ **算不出來要回 `null`（未定價），不是回 0。**「找不到費率」與「有費率但用量是 0」
   在畫面上意義完全不同；記成 0 會讓漏帳看起來像免費。

### 新增一種計費單位要同時改四處

`AiModelRates` 的屬性數有測試釘住（`AiUsageCostCalculatorTests`），漏改會被擋下來：

1. `AiModelRates` 加費率屬性。
2. `AiUsageCostCalculator.Compute` 加算式、`HasAnyRate` 加判斷。
3. `AiUsageCostCalculator.BuildRateSnapshot` 加序列化項目。
4. `docs/operations/日誌與設定檔說明.md` §4.9.2 的費率表與該測試的守門數字。

若新單位需要新的用量數字（例如圖片 token 數），還要一併加 `TokenUsageLog`／`TokenUsageEntry`
／`TokenUsageLogAdapterModel` 三個欄位與一份 migration。

### 其他要點

- **記錄不需要 Channel ＋ `IHostedService`**（與 §6.5 的例外管線不同）：LLM 呼叫是使用者主動觸發、
  一次數秒到數分鐘，多一次幾毫秒的資料庫寫入可忽略。直接 `await` 並全程 `try/catch`，
  記錄失敗**絕不可**影響呼叫端的結果。
- ⚠️ **日誌訊息不得出現 `token` 字樣**（`LoggingConventionTests` 的禁用清單）。
  這也是欄位叫 `InputCount` 而非 `InputTokens` 的原因。
- 合計語意：**快取是輸入的折扣子集、推理計入輸出**，兩者只回報「其中多少」，不再加進合計。
- 費用欄位用 `double`（SQLite `REAL`）而非 `decimal`：`decimal` 在 SQLite 存成 `TEXT`，
  無法在 SQL 端可靠 `SUM`，而「篩選範圍的總花費」正是這個功能的核心。
- `CostTwd` **逐列儲存**，不由美金總額乘匯率換算 —— 區間橫跨匯率調整時只有逐列相加才正確。
- 完整說明見 [Token 用量 PRD](../prd/Token用量-prd.md)、[AI 對話紀錄 PRD](../prd/AI對話紀錄-prd.md) 與
  [日誌與設定檔說明 §4.9](../operations/日誌與設定檔說明.md)。

## 6.9 樣式歸屬與全站色票 ⚠️（0.9.30 起）

**樣式要寫哪裡，判準是 DOM 位置，不是元件名稱，也不是「是不是 `.ant-*`」。**

| 樣式種類 | 位置 |
|---|---|
| 色票 token、形狀、動態 easing | `wwwroot/theme.css` 的 `:root` |
| AntDesign 渲染在 **`AntContainer` 底下**（Modal／Confirm／Notification／Message）| `Components/Commons/OverlayStyles.razor` |
| AntDesign 渲染在 **頁面 DOM 內**（Table／Pagination／Input／Select／DatePicker／Tag）| `wwwroot/theme.css` |
| 元件或檢視自己寫的 markup | 各自的 `.razor.css`，顏色一律 `var(--app-*)` |

- ⚠️ **`theme.css` 的 `<link>` 必須排在 AntDesign 的 CSS 之後**（`App.razor`）。排在前面的話，
  同分特異性會輸給後載入的 AntDesign，**所有清單頁的表格／分頁／輸入框樣式會同時靜默失效**
  —— 建置、`dotnet format`、`TreatWarningsAsErrors` 三道關卡全都看不到。
  由 `ThemeConventionTests.ThemeCss_ShouldLoadAfterAntDesignStylesheet` 守門。
- ⚠️ **色票字面值只能住在 `theme.css`。** `--ov-*`（OverlayStyles）與 `--login-*`（Login）
  是別名層，一律指向 `var(--app-*)`。需要新的深淺請用 `rgba(var(--app-…-rgb), a)` 組出來。
  由 `ThemeConventionTests.PaletteHexes_ShouldOnlyLiveInThemeCss` 守門。
  沿革：0.9.30 之前同一組粉梅色分散在三個以上的地方，換品牌色要翻五個檔。
- ⚠️ `theme.css` 是真正的 `.css`，at 規則寫**一個** `@`。從 `OverlayStyles.razor`（`.razor` 檔，
  要寫 `@@media`）複製規則過來時忘了改回來，會讓**整個區塊**靜默失效，主控台不會有訊息。
- ⚠️ **表格列的底色一律寫在 `> td` 上，不可寫在 `tr` 上。** 固定欄
  （`.ant-table-cell-fix-left/right`）自帶不透明白底，寫在 `tr` 上打不到它 ——
  十四個有 `<ActionColumn Fixed>` 的頁面滑過整列時，「操作」欄會留下一塊白。
  同理，列底色不可用半透明（會透出捲到底下的內容）。
- ⚠️ **排序中的欄位要一起覆寫**（`td.ant-table-column-sort`）。每張表都有 `DefaultSortOrder`，
  所以永遠有一欄吃到 AntDesign 的灰底；漏掉就是「整列變暖、只有那一欄還是灰的」。
- ⚠️ **AntDesign 元件內部若多包一層 `<a>`，打在外層的 `color` 不會繼承進去**（0.9.40 起）。
  `MenuItem` 帶 `RouterLink` 時渲染成 `<li class="ant-menu-item"><a>…</a></li>`，
  而 AntDesign 自帶 `.ant-menu-item a { color: rgba(0,0,0,.85) }`、
  `.ant-menu-item-selected a { color: #1890ff }` —— 只打在 `<li>` 上的覆寫到不了文字，
  深梅側邊欄上會出現**黑字與藍字**（實測 1.78:1 與 2.09:1，遠低於 AA）。
  難察覺之處在於「看起來大部分都對」：群組標題是 `<div>`、「登出」走 `OnClick`，
  兩者沒有 `<a>` 所以一直正常；圖示用後代選擇器也穿得過去。
  由 `SidebarLinkColorConventionTests` 守門。**改 AntDesign 元件顏色前，先看它渲染出什麼 DOM。**
- 狀態徽章一律用 `Components/Commons/StatusPill.razor`，語氣對應寫在呼叫端。
  0.9.120 起給 `OnClick`（＋`Hint`）就渲染成可點的 button（清單上點「啟用／停用」直接切換），不給仍是 span；
  有權限才可點的用 `<RequirePermission>` 的 `Fallback` 放不可點的那一份。
- 完整規範見 [介面視覺設計規範](介面視覺設計規範.md)。

## 6.10 模型名稱一律不帶日期後綴 ⚠️（0.9.36 起）

**`AiSettings:Model` 只填不帶日期的名稱** —— Azure 填部署名稱、OpenAI 填模型別名。
0.9.36 以真實呼叫驗證過（Azure AI Foundry，`/openai/v1/chat/completions`）：

| 送出的 `model` | 結果 |
|---|---|
| `gpt-5.6-sol`（部署名稱）| ✔ 200，而回應的 `model` 是 `gpt-5.6-sol-2026-07-09` |
| `gpt-5.6-sol-2026-07-09`（帶日期）| ✘ 404 `DeploymentNotFound` |

### 三條紅線

1. ⚠️ **送出的 `model` 必須是設定的原字串，不可做任何字串加工。**
   `AiChatRequestFactory.CreateRequestJson` 就只有 `writer.WriteString("model", settings.Model)` 一行。
   想在這裡補日期、補後綴或查對照表的都是錯的 —— 對 Azure 而言那個欄位是**部署名稱**
   （使用者自取的任意字串），加工出來的名稱必然對不上任何部署，上表第二列就是後果。
2. ⚠️ **`/token-usage` 顯示的是「回應」的模型名稱，不是設定值 —— 兩者不一樣是正常的。**
   `AiChatResponseParser` 讀回應根物件的 `model`，記帳時優先採用它（§6.7：要記**實際**模型名稱）；
   只有 HTTP 非 2xx／逾時／傳輸失敗這三個沒有回應 body 的分支才退回設定值。
   所以「設定填 `gpt-5.6-sol`、頁面顯示 `gpt-5.6-sol-2026-07-09`」**不是 bug**，
   也不代表系統偷偷在你送出的名稱後面加了日期。
3. ⚠️ **費率表 `AiPricingSettings:Models` 的鍵同樣維持不帶日期。**
   帶日期的回應名稱靠受限前綴比對命中（見 §4.9.3）；另外多寫一個帶日期的鍵，
   只會在供應商換版後變成永遠命不中的死鍵。

### 取捨（知情選擇，不是純粹的好處）

不帶日期＝跟著供應商換版走：輸出品質、速度與費率都可能在你沒有改過任何設定的情況下變動。

本專案選擇前者，並以「回應的實際模型名稱會被記進 `TokenUsageLog`」作為事後可追溯的補償 ——
上游換版了，用量頁的模型名稱就會跟著變，翻得到。

## 6.11 進 PDF 的中文一律先過 `CjkLineBreak` ⚠️（0.9.52 起）

**MigraDoc 不會替中文換行，而且沒有任何設定可以打開。**

`PdfFlattenVisitor` 的斷行機會是一組寫死且封閉的字元 —— 空白、減號、軟連字號、
U+200B、U+200C。中文落在該 switch 的 `default` 分支被一路累積，所以「一整段沒有空格的
中文」會變成**單一個不可分割的字**；`ParagraphRenderer.HandleNonFittingLine()` 遇到比整行
還寬的「字」時，會把行寬設成整個字的寬度，也就是**刻意讓它溢出頁面**。溢出紙張的部分**直接消失**。

### 規則

⚠️ **任何要進 PDF 的中文，都必須經由 `CjkLineBreak.AddTo(paragraph.Elements, text)` 加入，
不可以直接 `AddText(中文)` 或 `AddParagraph(中文)`。** 新增 PDF 產生器時同樣適用。

`AddTo` 把文字依中文斷行規則切成多個 `Text` 元素 —— MigraDoc 把每個元素當成一個「字」，
相鄰兩個之間就能斷行。規則含行首禁則（不在 `。、，）」` 之前斷）與行尾禁則
（不在 `（「【` 之後斷），全形空格後面則要斷得開（它不是 ASCII 空白，MigraDoc 不認）。

### ⚠️ 不要改用插入零寬空格（U+200B）的寫法

看起來更簡單（U+200B 就在 MigraDoc 的斷行機會清單裡），但**內嵌的 Noto Sans TC
沒有這個字圖**：cmap 查到的是 glyph 0（.notdef），而該字圖有 5 條輪廓、寬度整整 1 個 em。
實測 10pt 下一個 U+200B 量到 **10pt**，13 字的句子從 130pt 膨脹到 250pt ——
等於每兩個中文字之間印一個看得見的方框。

**而且頁數測試抓不到**：方框一樣會撐寬、一樣造成換行，測試照樣變綠。
守門的是 `CjkLineBreakTests.Split_ShouldNotChangeTheText`（切出來的段落接回去必須與原文
一字不差），它是「不新增任何字元」的保證。

### 相關常數

`CjkLineBreak.NoBreakSpace`（U+00A0）用來把「標籤」與「數字」黏在一起
（見 `TokenUsageReportPdfBuilder` 的合計行）—— MigraDoc 只把 ASCII `' '` 當斷行機會。
這個字元**有字圖**（對到 glyph 1，與一般空格同一個），不會變成方框。

## 6.12 寄信管線 ⚠️（0.9.59 起）

寄信有兩個入口，**用錯會洩漏資訊**：

| 介面 | 行為 | 何時用 |
|---|---|---|
| `IEmailSender.SendAsync` | 同步寄出，失敗拋例外 | 使用者要當場知道結果（例如健康頁的測試寄信）|
| `IEmailQueue.TryEnqueue` | 入列即返回，背景 `EmailDispatchWorker` 寄出 | **匿名流程一律用它**：同步寄信時「帳號存在」會比「不存在」慢數秒，回應時間就洩漏了帳號是否存在 |

兩者都在 Business（`Services/Other/`），實作在 `Web/Email/`；Business 不引用 MailKit。
信件內容一律用 `Business/Helpers/EmailTemplates` 產生（HTML＋純文字、變數 HTML 編碼）。

### 四條紅線

1. **日誌只記 `Kind`（信件種類），不記收件者、主旨、內文。** 佔位名稱不可含 `mail`／`email`／`token`
   （`LoggingConventionTests` 會擋），要記就用 `{Kind}`、`{Provider}`、`{UserId}`。稽核 detail 同樣不放收件者。
2. **provider 在解析 `IEmailSender` 時才決定**（scoped factory 讀 `IOptionsMonitor`）。
   不要改成註冊時 switch —— `WebApplicationFactory` 子類的組態覆寫會失效，測試就切不了 provider。
3. **佇列的 `FullMode` 必須是 `Wait`**，並用 `TryWrite`。Drop 系列模式下 `TryWrite` 永遠回 true，信丟了也不知道。
4. **不要設 `ServerCertificateValidationCallback`**。憑證驗證失敗就該失敗，略過等於允許中間人攔截 SMTP 密碼與信件。

### 其他要點

- 佇列只在記憶體（容量 100），重啟遺失；寄送失敗**不重試**，記 Error 進系統例外紀錄（來源＝背景作業）。
- `Pickup` 只供開發：`.eml` 是明文，Production 由 `StartupSafetyValidator` 拒絕啟動。
- 信中連結以 `EmailSettings:PublicBaseUrl` 為準，**不要用請求的 Host header 組網址**（password reset poisoning）。
- 整合測試的 `ApiTestApplicationFactory` 固定 `EmailSettings:Provider=None`，不會真的寄信。

## 6.13 忘記密碼的紅線 ⚠️（0.9.60 起）

`PasswordResetService`（Business）＋ `/Auths/ForgotPassword`、`/Auths/ResetPassword`（Web，靜態 SSR）。
改這一塊之前先讀完這五條：

1. **不在 `MyUser` 加任何重設相關欄位。** token 放獨立表 `PasswordResetToken`：管理員編輯使用者時
   `MyUserService.UpdateAsync` 會把 AdapterModel 沒帶的 `MyUser` 欄位覆寫成預設值，放在 `MyUser` 上會被悄悄清掉。
2. **`PasswordResetToken` 的 FK 必須在 `OnModelCreating` 的 Restrict 迴圈之後明確設 Cascade。**
   `MyUserService.DeleteAsync` 不先刪相依資料，Restrict 會讓「有未用 token 的使用者」刪不掉。
3. **畫面不得透露帳號是否存在。** `RequestAsync` 只回兩種結果：輸入內建帳號名稱 `support` 回
   `SupportAccountNotAllowed`（名稱公開，明說不洩漏資訊），其餘一律 `Accepted`；信一律走 `IEmailQueue`（見 §6.12）；
   不寄信的原因只寫稽核 detail。不要為了「好心提示」加上「查無此帳號」或「Email 無效」——
   Email 無效改由 `MyUserService` 存檔時擋下（0.9.85 起）。
4. **單次使用靠搶占，不靠先查後刪。** 交易內 `ExecuteDelete(t => t.Id == id)` 回 1 才改密碼；
   密碼規則或歷史不過時**不可**消耗 token（0.9.101 起規則與歷史來自 `IPasswordPolicy`，§6.18）。資料庫只存 SHA-256，原始 token 只出現在信裡。
5. **日誌不記使用者輸入的帳號／Email、token 與連結**，只記 `UserId`；稽核在交易 commit 之後才寫
   （`AuditLogService` 自己 SaveChanges）。

### 其他要點

- 靜態 SSR 頁面的 `NavigationManager.NavigateTo` **不會丟例外中斷執行**（csproj 的 `BlazorDisableThrowNavigationException`），
  呼叫後一定要 `return`。只有登入頁的 `SignInAsync` 會自動導向，其他頁要自己導。
- 重設頁回應 `Referrer-Policy: no-referrer`、`Cache-Control: no-store`（token 在網址裡）。
- 信中連結的網址基準用 `PublicBaseUrlResolver`（`EmailSettings:PublicBaseUrl`），**不要自己拿 `Request.Host` 組**。
- 登入、忘記、重設、兩步驟驗證（`TwoFactor`，0.9.104 起）四頁共用 `AuthShell` 外框，並在 `CustomerHelpAgent.Web.csproj` 以 `CssScope="b-auth-shell"` 共用
  `Login.razor.css` 的 scope。新增同外觀的頁面：加進那個 ItemGroup，並附一個（可以只有註解的）`.razor.css`。
- 已知限制：沒有 IP 限流、驗證碼只是減速帶。（重設成功後其他裝置的工作階段會失效：0.9.103 起 `IPasswordPolicy.ApplyAsync` 一併換 `SecurityStamp`，§6.20。）見
  [登入與帳號流程 PRD §6.1](../prd/登入與帳號流程-prd.md)。

## 6.15 系統參數（資料庫覆寫層）⚠️（0.9.98 起）

管理員在 `/system-parameters`（管理員專屬）修改的值存在 `SystemParameter` 表，由 `SystemParameterConfigurationProvider`
疊在 appsettings、環境變數、命令列**之上**（`Web/Configuration/Parameters/`）。存檔後立即生效、每分鐘跨行程同步。

### appsettings 與系統參數各管什麼

| 放系統參數（可在畫面改） | 只放 appsettings／環境變數 |
|---|---|
| 非機密、執行期讀得到新值、單一純量（int／bool／string）、屬於啟動時驗證的設定類別、預設值仍寫在 appsettings | 密碼、金鑰、連線字串、路徑、版本號；Cookie／JWT／CORS／快取這類**啟動時就被讀走**的值；陣列與字典（告警收件人、各作業 cron） |

同一個值**不會兩邊各存一份**：appsettings 是預設值，系統參數只是覆寫；頁面同時顯示「目前值」與「設定檔的值」。
啟動與升級都**不會**把 appsettings 寫進資料表（不要加種子資料）。⚠️ 新增 appsettings 區段或鍵而不放進目錄時，同步
[日誌與設定檔說明 §4.15](../operations/日誌與設定檔說明.md)「只在設定檔的區段」表與 `Datas/Help/system-parameters.md`「哪些設定只能改伺服器設定檔」表（兩份內容相同，沒有測試守門）。

### 紅線

1. ⚠️ **可覆寫的鍵只在 `SystemParameterCatalog.All` 定義。** 不在目錄的鍵就算在資料表裡也不套用（安全邊界）。
   `SystemParameterTests` 守門：每個鍵綁得到設定類別、範圍與真的驗證器一致、不含機密類名稱、版本號不在目錄、每個鍵寫進
   [日誌與設定檔說明 §4.15](../operations/日誌與設定檔說明.md)。
2. ⚠️ **目錄內的設定類別一律以 `IOptionsMonitor<T>.CurrentValue` 讀，不可用 `IOptions<T>`**（啟動時的快照，改了要重啟）；
   也不要在建構子把值複製到欄位。系統名稱與簡介**只准經 `ISystemIdentity`** 讀（它在設定被改壞時回傳上一次的正確值，而且不注入 `ILogger`）。同一個測試檔掃描原始碼守門。
3. ⚠️ **存檔前一定先驗證**（`SystemParameterValidator`：設定檔的值＋候選覆寫 → 真的 options 管線與所有 `IValidateOptions<T>`）。
   `IOptionsMonitor.CurrentValue` 遇到不合法的設定會丟例外，全站讀它的地方都會壞。不可用既有 provider 建新的 `ConfigurationRoot`（會觸發全域 reload）。
4. ⚠️ **只有內容變了才 `Apply`**：每次 reload 會讓所有 options 重新綁定。
5. 已存的覆寫在載入時不合法（升級後範圍變窄）→ 略過、記錯誤、頁面標「未套用」，**不讓啟動失敗**；設定檔本身有誤的區段拒絕存檔並明講。
6. 覆寫也蓋過環境變數；`WebApplicationFactory` 之後加入的測試設定會蓋過覆寫層 —— 整合測試要用不在測試設定裡的鍵。
7. 依上限值快取的元件要把值放進快取鍵（例：限流的分割鍵含配額，`BuildRateLimitPartitionKey`），否則改了不生效。

### 新增一個可覆寫的鍵

確認讀取端是 `IOptionsMonitor<T>.CurrentValue` → 在 `SystemParameterCatalog.All` 加一行 `Define<T, TValue>(...)`（範圍讀 `[Range]`，
驗證器裡的範圍要明列 min／max）→ 寫進日誌與設定檔說明 §4.15 的表 → 跑測試。設定類別要是 `AddConfiguredOptions`／`AddConfiguredEmail` 註冊、有啟動驗證的。

## 6.16 系統備份 ⚠️（0.9.99 起）

排程作業 `SystemBackup`（`Web/Backup/SystemBackupService`）把資料庫快照＋附件、例外堆疊檔、Token 原始檔、金鑰環打包到 `ExternalFileSystem:BackupPath`。

1. ⚠️ **資料庫一律用 `VACUUM INTO` 取快照，絕不直接複製 `BackendDB.db`**（WAL 模式下最近的寫入還在 `-wal`）。用不經連線池、
   `CommandTimeout = 0` 的獨立 `SqliteConnection`，不走 EF（慢查詢攔截器與 30 秒逾時）；快照後跑 `PRAGMA quick_check`。
2. **先資料庫、後檔案**；來源檔打不開只計數。新增一種「要備份的資料夾」時，在 `SystemBackupService.SelectFolders` 加一行、`manifest` 記設定鍵名，

   （腳手架不寫入永久檔案），衍生專案若改在這兩處存檔，必須照上面的步驟把它加進備份。
3. 一律先寫 `.work/` 與 `*.partial`，完成才改名；`finally` 與下一次執行都清。**成功後才**依份數刪舊備份。
4. 備份清單只在檔案系統（不建資料表：還原會把清單倒回去）；下載與刪除先經 `BackupStore.TryResolveFullPath`（檔名規則＋根目錄）。
5. ⚠️ 備份不加密且含金鑰環：`BackupPath` 啟動驗證不可與其他資料目錄重疊、不可在網站目錄底下；下載端點每次從資料庫確認是管理員。
6. 還原只走停站＋腳本；腳本不可寫死專案名稱（`New-StarterProject.ps1` 會文字替換），要用 Windows PowerShell 5.1 語法、UTF-8 含 BOM。

## 6.17 站內通知與公告 ⚠️（0.9.100 起）

系統或業務模組要「通知某人某件事」時，注入 `INotificationSender`（⚠️ 不是 AntDesign 的 `INotificationService` —— 那是右下角的暫時提示），呼叫
`SendAsync(new NotificationRequest(類別, 標題, 內文, 站內連結, NotificationTarget.Users(id) / Role(角色 Id) / Team(團隊 Id) / AllAdmins() / Union(...), AlsoEmail, SourceKey))`。

1. ⚠️ **`SendAsync` 絕不丟例外**（失敗記錯誤、回 `Failed`），呼叫端不必包 try/catch，也**不可**依結果改變自己的流程（通知是附帶的）。
   ⚠️ **例外記錄管線內（`ExceptionLogProvider`、`ExceptionLogWriter`、`ExceptionLogService`、`ExceptionAlertService` 等）不可發通知**：發送失敗會記錯誤，形成遞迴（§6.6）。
2. 收件人只算**啟用、未刪除**的帳號；角色＝`UserRole` ∪ 主要角色並經 `RoleView` 排除已刪除角色；團隊一律經 `IEffectiveTeamResolver.GetUserIdsInTeamAsync`（與列級權控同一定義，有對照測試）。
3. 同一事件可能重複觸發時給 `SourceKey`（例：`AccountPending:{userId}`），已收過同鍵的人不會再收到。0.9.136 起看 `NotificationDispatch`（通知被刪除也不重發，跟著通知的建立保留天數清除），所以鍵要能區分「該再發一次」的情況（例如含期間或日期）。類別常數放 `NotificationCategories`。
4. 內容一律**純文字**（畫面不經 Markdown／HTML），連結只放站內相對路徑（鈴鐺經 `ReturnUrlGuard` 檢查才導向）；`AlsoEmail` 的信件連結以 `EmailSettings:PublicBaseUrl` 組成。
5. 即時更新靠 singleton `INotificationSignal`（只送「有變動」，畫面自己重查）；訂閱回傳 `IDisposable`，元件 `Dispose` 一定要釋放。
   多行程（IIS 重疊回收、多台主機）收不到訊號，由鈴鐺、橫幅與首頁「我的通知」（0.9.122 起）各自 **60 秒輪詢**補足 —— 不要把輪詢拿掉。
   0.9.122 起 `NotificationQueryService` 標為已讀（0.9.125 起含刪除單則、清除已讀）真的改到資料時也 `Publish([userId])`，同一個人開著的鈴鐺、小工具、其他分頁一起更新；會訂閱訊號的新元件照樣要能接受「已讀」引起的重查。
6. 背景作業裡發送要用**自己的 scope**（比照 `ScheduledJobRunner.NotifyFailureAsync`），不可沿用已結束的 scope。
   保存期限由排程作業「站內通知清理」（`NotificationRetentionJob`）執行：建立超過 `NotificationSettings:RetentionDays`（預設 90）天的不論已讀未讀都刪，
   0.9.125 起已讀的另依 `ReadRetentionDays`（預設 7，從 `ReadAtUtc` 起算）提早刪；兩者各自 0＝不清除。使用者的單則刪除與「清除已讀」只能刪自己的（`NotificationQueryService.DeleteAsync`／`DeleteReadAsync` 都以收件人篩選）。
   系統健康監控頁的「發送測試通知」走 `NotificationTestService`（0.9.122 起）：發給全體管理員、不寄信、不設 `SourceKey`（可重複測），稽核 `Notification.Test`。
7. 公告：`AnnouncementCache`（singleton）共用「還沒結束的公告」；新增修改公告的程式路徑都要 `Invalidate()` 並 `PublishAnnouncementsChanged()`（`AnnouncementView` 已示範）。
   ⚠️ `Announcement` 以條件式 `ExecuteUpdate` 比對 `ConcurrencyStamp`，刻意**不**實作 `IConcurrencyStamped`（那會要求 `ProtectFlags`／`ISoftDeletable`）。

## 6.18 密碼原則與登入鎖定 ⚠️（0.9.101 起）

設定在 `PasswordPolicySettings`、`LockoutSettings`（系統參數「密碼與登入」）；規則與狀態集中在 singleton `IPasswordPolicy`（`Business/Services/Other/PasswordPolicy.cs`）。

1. ⚠️ **新增任何「設定密碼」的路徑都要依序：`Check`（規則）→ `IsReusedAsync`（歷史，含目前密碼）→ `ApplyAsync`（寫入）。**
   `ApplyAsync` 是唯一呼叫 `SecurePasswordHasher.HashPassword` 的地方（另外只有 support 種子與登入時的舊雜湊升級），
   它同時寫入密碼設定時間、「下次登入須變更密碼」旗標、解除鎖定、寫歷史並裁到 N 筆；不呼叫 SaveChanges（交易由呼叫端決定）。
   `PasswordPolicyTests.HashPassword_ShouldOnlyBeCalledFrom…` 守門。
2. 忘記密碼重設：規則與歷史都要在**搶占 token 之前**檢查（不合格不消耗連結，§6.13）。
3. 「必須變更密碼」＝`MustChangePassword` 旗標或已到期（`RequiresChange`）。⚠️ support 帳號與沒有本機密碼的帳號豁免，否則會永遠卡在 `/ChangePassword`。
   `AuthenticationStateHelper.Check` 每次換頁只看這兩個欄位，**不再以 PBKDF2 比對 123456**（舊做法每次換頁都要算一次雜湊）。
4. 舊的 123456 哨兵只剩一個用途：登入成功時明文是 123456 就補上旗標（既有資料無法以 SQL 轉換）。新程式**不可**再用密碼內容表達狀態。
5. ⚠️ 鎖定到期要**先把失敗次數歸零再驗證密碼**；稽核 `Login.LockedOut` 只記造成鎖定的那一次，鎖定中的嘗試記 `Login.Failed`（`reason=Locked`）。
6. ⚠️ 登入失敗（帳號不存在、密碼錯、鎖定中）一律回 `MyUserServiceLogin.InvalidCredentialsMessage`；登入頁固定顯示鎖定規則。不要為了好心提示改回分開的訊息。
7. 解鎖（`MyUserService.UnlockAsync`）只以 `ExecuteUpdate` 改兩個欄位、**不換版本號**，別人開著編輯窗也不會衝突；稽核 `User.Unlock`。
8. Google 登入的處理順序集中在 `ExternalLoginResult.Evaluate`（已刪除 → 待開通 → 鎖定 → 登入），新增條件時加在那裡並補測試。

## 6.20 工作階段失效 ⚠️（0.9.103 起）

`MyUser.SecurityStamp`（工作階段版本）＋ claim `MagicObjectHelper.SecurityStampClaimType`。完整規則見 [認證授權與權限機制](../security/認證授權與權限機制.md)「工作階段失效」。

1. ⚠️ **新增「改變一個人能做什麼或能不能登入」的操作時，要換版本**：在實體上設 `SecurityStamps.New()` 一起存檔，或呼叫 `MyUserService.ForceLogoutAsync`／`ISecurityStampService.RotateAsync`（後者會清同一行程的快取）。
   設新密碼一律經 `IPasswordPolicy.ApplyAsync`，它已經會換。只改姓名、Email 這類資料**不要**換（會把人無故踢出去）。換版本**不動** `ConcurrencyStamp`。
2. 登入 Cookie 的 claims 一律經 `CookieClaims.Create`（帶版本）；JWT 由 `JwtTokenService` 帶版本。⚠️ 不要在別處自己組 claims —— 少了版本的 Cookie 會在第一個請求就被登出。測試手工產生 Cookie 也用它。
3. 已開著的頁面靠 `AuthenticationStateHelper.Check` 在換頁時比對（SignalR 不經過 Cookie 中介軟體）；HTTP 請求靠 `SecurityStampCookieEvents`（快取 `CookieSettings:ValidationIntervalMinutes`）。
   兩者都經 `ISecurityStampService.IsValidAsync`：⚠️ 快取裡的版本不符時會再查一次資料庫才判定失效 —— 直接用快取判定，剛換過版本後重新登入的人會被踢回登入頁數分鐘。
   ⚠️ 不要把「上次檢查時間」寫進票證再 `ShouldRenew`：每次續發都會讓 Cookie 滑動，「不滑動」與記住我的期限都會失效。
4. 互動頁做了會換掉**自己**版本的事（改自己的密碼、改自己的角色）之後，呼叫 `SessionRefreshNavigator.KeepSignedInAsync(returnUrl)`，否則下一次換頁就把自己登出。
   `/Auths/RefreshSession` 必須同時比對原本 Cookie 的使用者與舊版本、ticket 的新版本與資料庫 —— 不可只憑 ticket 登入。
5. 空字串版本代表「尚未設定」（重疊回收時舊版程式新增的列），`SecurityStamps.Matches` 一律判定不符；登入時補上。版本不可寫進日誌（`LoggingConventionTests` 禁記）。
6. Bearer 只接受 `token_type = access`（`Program.cs` 的 `OnTokenValidated`）；0.9.136 起 access token 在效期內也比對工作階段版本與啟用狀態（同一套快取，`CookieSettings:ValidationIntervalMinutes`），refresh 換發時則直接回查資料庫。之前 access token 不回查版本，要等效期（預設 60 分鐘）到才失效。

## 6.21 兩步驟驗證 ⚠️（0.9.104 起）

服務 `ITwoFactorService`（`Business/Services/Other/TwoFactorService.cs`）；登入用 Cookie `TwoFactorLoginCookies`（`Web/Auth/`）。完整規則見 [認證授權與權限機制](../security/認證授權與權限機制.md)「兩步驟驗證」、需求見 [PRD](../prd/兩步驟驗證-prd.md)。

1. ⚠️ **新增任何登入入口（發 Cookie 或 token 的地方）都要處理 `LoginAttemptResult.RequiresTwoFactor`**：為 true 時 `User` 有值但**還不能發證**，要經 `MyUserServiceLogin.CompleteSecondFactorAsync`。
   `var (message, user) = attempt` 的解構在需要第二步時刻意給 `user = null`，舊寫法不會誤發證；直接讀 `attempt.User` 的程式要自己判斷。Google 回呼（`ExternalAuthController`）不經 `LoginAsync`，另外判斷 `TwoFactorEnabled`。
2. ⚠️ 密碼對了但還沒過第二步：**不**歸零失敗次數、**不**寫 `Login.Success`；第二步錯誤累加同一個次數。改登入流程時別把歸零提前 —— 會讓人靠重輸密碼無限猜驗證碼（`TwoFactorTests` 守門）。
3. ⚠️ 驗證碼的接受一律經 `VerifyAsync` 的條件式 `ExecuteUpdate`（`TwoFactorLastStep < step`、備用碼 `UsedAtUtc IS NULL`）；不要改成「先查再寫」，並行請求會讓同一組碼用兩次。
4. 密鑰只經 `ITwoFactorSecretProtector`（Data Protection）存取；解不開時回 null（等同驗證失敗）並記警告，需要管理員重設。密鑰、備用碼明文都不可寫進日誌或稽核。
5. 強制判斷（`IsRequiredAsync`）放在 `AuthenticationStateHelper.Check` 的「必須變更密碼」之後，`/ChangePassword` 與 `/TwoFactorSetup` 互不導向；support（`BootstrapSettings:SupportAccount`）與沒有本機密碼的帳號豁免 —— 漏掉會把救援帳號或 Google 使用者永遠卡在設定頁。
6. 啟用、停用、重設都換工作階段版本（§6.20）；本人操作後經 `SessionRefreshNavigator.KeepSignedInAsync` 保持這台登入。「記住這台裝置」的 Cookie 綁定版本，版本一換就失效。
7. `/Auths/TwoFactor` 是靜態 SSR 匿名頁：誰在登入只存在 5 分鐘的加密 Cookie，不在網址或表單；送出時重查版本與帳號狀態。

## 6.28 列表頁多筆刪除 ⚠️（0.9.132 起）

有單筆「刪除」的列表頁都要能勾選多筆後「刪除選取」：`<Table @bind-SelectedRows="selectedRows">`＋第一欄 `<Selection />`＋工具列 `<BatchDeleteButton>`，流程走 `Components/Commons/BatchDelete.cs`（`AskAsync` → `RunAsync` → `Notify`）。由 `BatchDeleteConventionTests` 守門（有 `CrudActionButton Title="刪除"` 就要有兩者），`TableSelectionContractTests` 鎖住依賴的 AntDesign 行為。

1. ⚠️ **批次一律逐筆呼叫該頁既有的單筆刪除**，不要另寫批次服務方法或一次 `ExecuteDelete` —— 每頁的規則（團隊範圍、自己與 support、預設角色、還有下屬部門）與每筆一列的 `*.Delete` 稽核都在單筆刪除裡，另寫一條路就會漏。單筆刪除若在頁面上另外寫稽核，先抽成 `DeleteOneAsync`（回傳 `VerifyRecordResult`）讓兩邊共用。
2. ⚠️ **勾選只在目前這一頁**：`ReloadAsync` 第一行 `selectedRows = [];`（AntDesign 在 `DataSource` 換掉時重套綁定的選取，一處涵蓋換頁、排序、搜尋、切換與刪除後）。畫面上分頁的表格（公告）換頁不經 `ReloadAsync`，要在 `OnPageIndexChange` 呼叫 `table.SetSelection(Array.Empty<T>())`。「顯示已刪除」時不放勾選欄。
3. 已知不能刪的列用 `<Selection Disabled="…">` 反灰（表頭全選會略過）；要查資料庫才知道的（例如角色仍是某人的主要角色）不要在畫面上預查，交給刪除時的規則擋下並列在結果通知。
4. 樹狀表格用 `CheckStrictly="true"`（勾上層不連帶勾下屬，收合看不到的不會被刪到），並以 `BatchDelete.DeepestFirst` 由深到淺刪，同時勾了上層與它全部下屬時上層才刪得掉。
5. 確認與結果的名稱清單會進日誌（`ViewNotification` 記通知內文），**不可放姓名或 Email**：使用者頁只列帳號；`RunAsync` 的 `keyOf` 給 Id 或檔名。
6. 點列有動作的表格（例外紀錄點列複製）要用 `Selection` 的 `CellRender` 包一層 `@onclick:stopPropagation` 的勾選格，否則勾一下就觸發列點擊。勾選欄不要設 `Fixed`（相鄰固定欄缺寬度時 AntDesign 會丟例外，見 TokenUsageView 註解）。

## 7. 啟動時的 Seed 行為

`Program.cs` 於 `app.Build()` 後呼叫 `IDatabaseInitializer`（0.9.91 起，`CustomerHelpAgent.Business/Startup/`）：跨行程鎖 → migration → WAL →
依 `Order` 執行 `IDatabaseSeeder`：預設角色（不存在才以全部頁面建立，**之後只自動加入新頁面，不會覆寫管理員的修改**）、
預設帳號（`BootstrapSettings.SupportAccount`，密碼以 `SecurePasswordHasher.HashPassword`（**PBKDF2**）雜湊、`IsAdmin=true`；既有帳號密碼驗證失敗時重設）、RBAC 回填、匯入舊的 AI 提示詞設定（0.9.108 起，只匯入一次）、售後展示示範帳號（Order 50）與示範商品／訂單／規則（Order 60；兩者都只在 `DemoSettings:Enabled` 時執行、只建不存在的，定義集中在 `DemoSeedData`）。此為冪等行為。

- ⚠️ **新增種子資料一律實作 `IDatabaseSeeder`**（冪等、Order 不可重複、在 `AddApplicationServices` 註冊成 Scoped），不要寫回 Program.cs ——
  那裡沒有測試也沒有跨行程鎖。`DatabaseInitializerConventionTests` 會擋 Program.cs 裡的 `Migrate()`／`EnsureCreated()`，以及沒註冊的 seeder。
- ⚠️ **產品程式不得呼叫 `EnsureCreated()`**（建出的資料庫無法 migrate）；測試的 in-memory fixture 可以。
- ⚠️ **軟刪除**（0.9.94 起：Project、Category、Team；0.9.95 起：MyUser、RoleView 實作 `ISoftDeletable`）：
  - 具名全域過濾器 `ISoftDeletable.FilterName`（`"SoftDelete"`）讓所有查詢自動排除已刪除資料；「顯示已刪除」、還原、永久刪除才用 `IgnoreQueryFilters([ISoftDeletable.FilterName])`。
  - ⚠️ **關聯表（UserTeam、UserRole、RolePermissionMap、PasswordResetToken、ProjectFile…）一律用明確 Join 查主體，不可 Include 或經導覽屬性存取有過濾器的主體**：從相依端經必要導覽查詢時，相依資料列會隨主體被過濾而靜默消失（EF 警告 10622 已在 `BackendDBContext` 忽略，前提就是遵守這條規則）。
  - ⚠️ **整筆覆蓋的存檔必須呼叫 `SoftDeleteHelper.ProtectFlags(entry)`**（每個 `ConcurrencyStampHelper.Apply` 旁邊都要有），否則畫面模型的 `IsDeleted = false` 會把已刪除的資料救活；AutoMapper 的「→ 實體」對應一律 `IgnoreSoftDeleteFields()`。
  - 刪除、還原一律經 `SoftDeleteHelper.MarkDeleted`／`Restore`（會換新版本號）；刪除、還原、永久刪除都要在伺服器端檢查團隊範圍。
    唯一的例外是排程作業「已刪除資料清理」的 `SoftDeletePurgeService`（0.9.97 起）：系統層級清除、沒有登入者，刻意不套團隊範圍，也不重用各服務的 `PurgeAsync`。
  - 查不到父資料不可當成「公開」：例如附件下載要先確認父專案存在（`TagStringHelper.IsTeamAccessible(null)` 回 true）。
  - 指向已刪除主體的關聯要保留（例如 `RbacWriteService.SyncUserTeamsAsync` 只在有效團隊間計算差異），否則還原後關聯回不來。不要在關聯表上加過濾器。
  - 稽核代碼 `X.Delete` 代表軟刪除；`X.Restore`、`X.Purge` 是還原與永久刪除。
  - ⚠️ **權限判斷必須經 `context.RoleView` 過濾**（0.9.95 起）：`UserRole` 與 legacy `MyUser.RoleViewId` 都不看角色是否已刪除，`PermissionChecker.GetKeysForRolesAsync` 在 Join `RolePermissionMap` 時一併 Join `RoleView`，一處涵蓋兩個來源。新增任何「由角色推出權限或團隊」的查詢都要比照。
  - ⚠️ **角色仍是未刪除使用者的主要角色時不可刪除**（否則那些人每次換頁都被 `AuthenticationStateHelper` 登出）；使用者存檔時也驗證角色未刪除。兩邊各在不同 DbContext，`RoleViewService.DeleteAsync` 存檔後會再複查一次。
  - ⚠️ **種子資料以名稱／帳號查找時要 `IgnoreQueryFilters` 並優先取未刪除的列**（`OrderBy(IsDeleted).ThenBy(Id)`），找到已刪除的才還原；只看有過濾的集合會建出重複的 support／預設角色。
  - 永久刪除一律 `IgnoreQueryFilters` 追蹤載入後 `Remove`；`ExecuteDelete`／`ExecuteUpdate` 也會套用具名過濾器，對已刪除的列會影響 0 筆。
  - support 帳號（比對設定檔 `BootstrapSettings.SupportAccount`，不分大小寫）、自己、「預設角色」不可刪除；「預設角色」0.9.136 起也不可改名（`RoleViewService` 以名稱找它，改名後啟動時會重建一個帶全部權限的新「預設角色」）。
  - ⚠️ **自動永久刪除**（0.9.97 起，`SoftDeletePurgeService`，`SoftDeleteSettings:PurgeAfterDays` 預設 90 天）：
    - 順序固定為專案 → 分類 → 團隊 → **使用者 → 角色**（使用者先刪，同一輪中它們引用的角色才刪得掉；`MyUser.RoleViewId` 是 Restrict）。
    - **每一筆用新的 DbContext** 載入並重新確認條件：共用 context 時一筆存檔失敗的實體會留在追蹤裡，之後每一筆都跟著失敗。
    - 追蹤中 `Remove` 讓 DELETE 帶著版本號，候選之後被還原 → 並行衝突 → 略過。⚠️ **不可改用 `ExecuteDelete`**（不比對版本號，會刪掉剛還原的資料）。
    - support 帳號與「預設角色」永遠不刪；仍被任何使用者（含已刪除未到期的）當主要角色的角色留到下次，刪除當下被指派的外鍵錯誤也算「留到下次」而不是失敗。仍是訂單（`SalesOrder`）或售後申請（`AfterSalesRequest`）顧客的使用者同樣算使用中（`CustomerUserId` 是 Restrict，業務紀錄不連帶刪除）；新增任何指向 `MyUser` 的 Restrict 外鍵都要補進 `SoftDeletePurgeService` 的使用中檢查，否則整批使用者清除會中止。
    - 取消時不丟例外，回傳部分結果，作業先寫稽核（`X.AutoPurge`）再把取消交回框架。
- ⚠️ **`/Auths/*` 頁面一律指定不跑身分檢查的版面**（`NoFooterLayout` 或 `EmptyLayout`），不可落到預設的 `MainLayout`：`MainLayout` 會呼叫 `AuthenticationStateHelper.Check`，失效的使用者被導向 `/Auths/Logout`，若登出頁本身也套 `MainLayout` 就形成重新導向迴圈（0.9.95 修正）。
- ⚠️ **樂觀並行**（0.9.93 起）：Project、Category、Team、MyUser、RoleView 實作 `IConcurrencyStamped`，`ConcurrencyStamp` 是 concurrency token。
  - **使用者編輯存檔**的路徑（Blazor 服務 `UpdateAsync`、API 的 PUT）必須呼叫 `ConcurrencyStampHelper.Apply(entry, 開窗時的版本號)`；
    「先載入再複製欄位」的寫法（tracked 載入、`SetValues`）若不設比對基準，**永遠偵測不到衝突**（`OptimisticConcurrencyTests` 會抓到）。
  - **新增**路徑一律 `ConcurrencyStampHelper.New()`，不信任客戶端傳來的值。
  - 登入失敗計數、改密碼、種子資料、RBAC 回填等**其他更新路徑不換版本號**，改為「只更新自己負責的欄位」，避免誤報衝突。
  - 衝突時 Blazor 回 `VerifyRecordResult` 失敗（`ConcurrencyStampHelper.ConflictMessage`，表單維持開啟）；API 回 409。
  - 新增需要編輯畫面的實體時，讓它實作 `IConcurrencyStamped`，`BackendDBContext` 會自動設為 token。
- ⚠️ **新增設定類別一律在啟動時驗證**（0.9.92 起）：`services.AddValidatedOptions<T, TValidator>(configuration, section)`
  或至少 `AddOptions<T>().Bind(...).ValidateOnStart()`；不要用單純的 `services.Configure<T>(GetSection(...))`（`OptionsValidationTests` 會擋）。
  政策是「設定矛盾一律拒絕啟動」：開了功能卻沒填齊、拼錯、格式錯誤都要在啟動時失敗，不要讓功能靜默失效。
- 連線字串由 `AddConfiguredDatabase` 以 `SqliteConnectionStringBuilder` 組成，明確開啟 `Foreign Keys`；**刻意不加 `busy_timeout`**：
  Microsoft.Data.Sqlite 遇到 SQLITE_BUSY 會自己重試到命令逾時（預設 30 秒）。兩者由 `SqliteBehaviorTests` 釘住。見 [資料模型與資料庫](資料模型與資料庫.md)、[密碼種類與儲存機制](../security/密碼種類與儲存機制.md)。

## 7.1 建置設定一律走共用檔 ⚠️（0.4.32 起）

## 8. 版本與文件 ⚠️

- **單一版本來源**：`appsettings.json` 的 `SystemSettings.SystemInformation.SystemVersion`，每次完成異動一律將**最後一碼（Patch）+1**（例：`0.4.0 → 0.4.1`，不進位、不分異動性質；顯示格式 `Major.Minor.Patch (YYYY/MM/DD)`），並於 commit message 說明。
- **文件編碼**：`docs/` 下與根目錄的所有 `.md` 一律 **UTF-8 含 BOM**，提交前在本機以 [`scripts/Test-DocsEncoding.ps1`](../../scripts/Test-DocsEncoding.ps1) 遞迴檢查（專案沒有 CI，見 §7.1）；繁體中文不得有亂碼。
- ⚠️ **匯出檔的位元組一律走 `TextDownloadPayload.Utf8WithBom`**（`Components/Commons/`）。
  `new UTF8Encoding(encoderShouldEmitUTF8Identifier: true).GetBytes(text)` **不會**輸出前導碼 ——
  那個旗標只影響 `GetPreamble()` 與 `StreamWriter`。少了 BOM，Excel 開啟匯出的 CSV 會整片變亂碼，
  而且編譯、測試、程式碼審閱都看不出來（0.9.16 之前三個匯出點有兩個是壞的）。
  由 `ExportEncodingConventionTests` 守門：該旗標只能出現在 `TextDownloadPayload.cs`。
  驗收時直接看頭三個位元組是不是 `EF BB BF`。
- 異動若影響既有功能／API／資料表／設定／UI，須同步更新對應文件並更新索引。對照表見 [維護規範](../operations/維護規範.md)。
- 引用程式碼請用「相對路徑」（必要時加行號），勿臆測。
- **環境上手與腳手架更名**：VS Code 啟動與偵錯、User Secrets 機密設定、複製本腳手架後的完整更名步驟與高風險字串清單，見 [VS Code 開發環境與新專案上手指南](../guides/VS%20Code%20開發環境與新專案上手指南.md)。
