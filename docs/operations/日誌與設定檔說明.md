## 1. 日誌方案：NLog

採 `NLog.Web.AspNetCore 6.1.2`，於 [`src/CustomerHelpAgent/CustomerHelpAgent.Web/Program.cs:59-91`](../../src/CustomerHelpAgent/CustomerHelpAgent.Web/Program.cs) 完成設定：

1. 從 `appsettings.json` 讀取 `NLog.BasePath`（預設 `C:\temp\Logs`）。
2. 在 `BasePath/CustomerHelpAgent.Web/` 下建立日誌目錄。
3. 設定 NLog Internal Logger 寫入 `CustomerHelpAgent.Web-nlog-internal.log`。
4. 將 `BasePath` 與 `LogFilenamePrefix` 變數寫入 NLog 設定，供 `nlog.config` 內 `${var:BasePath}` 引用。
5. `builder.Logging.ClearProviders()` 清除預設 Provider，由 `builder.Host.UseNLog()` 接管。

`nlog.config` 位於 `CustomerHelpAgent.Web/` 根目錄，定義具體 Target / Rule。

**TraceId 欄位＝錯誤追蹤碼**（0.9.78 起，[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) LOG-10）：
版面的第 2 欄是 `${scopeproperty:item=TraceCode:whenEmpty=${aspnet-TraceIdentifier}}`，
一律是 8 碼短碼（例如 `K7Q2M9XA`）。HTTP 請求由 `UseHttpRequestLogging` 產生並**取代 `HttpContext.TraceIdentifier`**
（API 回應的 `TraceId`、`/Error` 頁顯示的碼都是它）；Blazor 每次互動由 `ApplicationCircuitHandler` 產生一個
（0.9.78 之前 circuit 內這一欄是空的）。欄位數維持 7 個，舊日誌檔照樣解析。
使用者回報的錯誤追蹤碼可在 `/logs` 的「錯誤追蹤碼」欄位篩出該次操作的所有日誌行。

**稽核紀錄同步寫 Debug**（0.9.131 起）：`AuditLogService` 每寫一筆稽核就以記錄器 `CustomerHelpAgent.Business.Services.Other.AuditLogService` 記一行 Debug
`Audit recorded. Action=…, Success=…, ActorUserId=…, ActorAccount=…, TargetType=…, TargetId=…, Detail=…, ContentFile=…`。
只有資料庫裡的短摘要與內容檔名，**不含內容檔本身**（修改差異、搜尋原文）。Debug 預設不寫進檔案：要看時到「日誌等級設定」調到 Debug（重啟後恢復）。

**右下角通知也會寫日誌**（0.9.129 起）：錯誤與警告通知（`ViewNotification` 的 `Error`／`UnexpectedError`／`ValidationError`／`Caution`）
在顯示當下以記錄器 `CustomerHelpAgent.Web.Components.Commons.ViewNotification` 寫一筆 `Notification shown to user. Title=…, Kind=…, Text=…`，
`UnexpectedError` 記 Error、其餘記 Warning，不帶例外物件（所以不進系統例外紀錄）。使用者按通知上的「複製」貼來的內容含追蹤碼，
貼到「錯誤追蹤碼」欄位、最低等級選「不限」，就能看到通知那一筆與同一次操作的其他日誌。成功訊息與 `Info` 不寫。

系統內有兩處會讀取日誌檔，皆僅限管理員使用；但日誌本身仍不應寫入密碼、token 或完整連線字串。

- `/system-health` 人工巡檢頁：依 `NLog.BasePath` 與專案命名空間定位日誌檔，在頁尾以表格列出**最近 24 小時、WARN 以上**的原始日誌（可分頁、可展開原文，最多最新 10,000 筆）。
- `/logs` 日誌檢視頁：可依時間區段（上限 3 天）、筆數、最低等級與關鍵字篩選，跨日時會合併多個日誌檔，並可將查詢結果以原始 nlog 文字格式匯出下載。詳見 [日誌檢視 PRD](../prd/日誌檢視-prd.md)。

## 執行期調整日誌等級

`/log-level-setting`（系統管理 › 監控與診斷 › 日誌等級設定，僅管理員）可在**不重新啟動、不異動任何設定檔**的情況下調整最低輸出等級，排查問題時調到 DEBUG／TRACE，查完再還原。詳見 [日誌等級設定 PRD](../prd/日誌等級設定-prd.md)。

幾個需要知道的行為：

- 設定**只在執行期有效**，重新啟動就回到 `nlog.config` 的值。
- **只影響應用程式日誌**。`Microsoft.*`／`System.*` 有專屬的 `final` 規則，調低不會引來框架日誌洪水；但反過來調高也**無法靜音**那些框架警告。
- 套用後即使 `nlog.config` 被 autoReload 重新載入，設定仍會保留 —— 因此**改檔案的 minlevel 不會立即生效**，要回到檔案的值請按「還原為系統預設等級」。
- 每次變更都會寫入稽核軌跡。

> **0.4.29 修掉的既有缺陷**：`autoReload` 重載時 NLog 會整個換掉設定物件，連帶清空 `Program.cs` 注入的 `BasePath`／`LogFilenamePrefix` 變數，導致日誌改寫到磁碟根目錄。現在重載後會自動補回這兩個變數。

> `appsettings.json` 的 `Logging:LogLevel` 區段是**死設定** —— `UseNLog()` 預設會移除 Microsoft 的過濾器，全部由 `nlog.config` 決定。改它不會有任何效果。

## 2. 日誌撰寫規範

日誌是本系統可觀測性的唯一來源。目標是：**只看 Information 就能重建「使用者當時做了什麼」，需要細節時再降到 Debug。**

> **等級規則以 [日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) §三 為準**（0.9.76 起）。本節 §2.1–2.3 是同一套規則的寫法說明與範例；
> PRD 另外補上外部呼叫、背景作業、慢操作、設定缺漏、迴圈內的等級，以及例外分類表（§四）與未捕捉例外涵蓋矩陣（§五）。
> 兩邊若不一致，以 PRD 為準並回頭修正本節。

### 2.1 選等級的三個問題

依序問，第一個答「是」的就是答案：

1. 這個結果是**使用者輸入的正常後果**，行為端正的使用者日常操作就會遇到嗎？
   → **Information**（若屬純查詢／換頁／排序則為 **Debug**）
2. 這是**非預期但已處理**的狀況 —— 可能的誤用、設定錯誤、安全相關的拒絕、資料完整性異常？
   → **Warning**
3. 使用者要求的操作**失敗了**，需要程式或維運介入（例外、外部資源失敗）？
   → **Error**

兩條可直接套用的細則：

- **讀取查無資料 = Information；寫入查無資料 = Warning。** GET 一筆已刪除的資料是常態；UPDATE／DELETE 一筆不存在的資料代表畫面過期或有人在探測。
- **欄位／重複名稱驗證失敗一律 Information；權限與身分驗證失敗一律 Warning。**

> **0.4.30 的修正**：本節先前把「業務驗證未通過」列在 Warning，導致 Warning 數量與 Information 相當（各 139 筆），真正的異常被淹沒。已重新分類 50 處。**Warning 是給「維運人員應該看一眼」的事；使用者打錯字不是。**

### 2.2 等級對照

| 等級 | 使用時機 | 範例 |
|------|----------|------|
| `Trace` | 迴圈內／逐筆的追蹤。**目前專案未使用**；有需要時才寫，不為了填滿等級而寫。 | 逐行解析、逐表統計的每一次迭代。 |
| `Debug` | 流程細節、查詢條件、分頁排序、快取命中、權限判定過程。**排查時才會看。** | `logger.LogDebug("Paged category query executed. PageIndex={PageIndex}, TotalCount={TotalCount}", ...)` |
| `Information` | **使用者做了什麼**（畫面切換、新增／修改／刪除／匯出／登入登出）、商業流程完成、啟動與關閉。 | `logger.LogInformation("User navigated. Path={Path}, Account={Account}, ...")` |
| `Warning` | 授權被拒、身分驗證失敗、寫入時查無資料、設定或資料完整性異常、連線中斷。 | `logger.LogWarning("API request denied by permission check. UserId={UserId}, PermissionKey={PermissionKey}", ...)` |
| `Error` | 例外、外部資源失敗、重要流程中斷。 | `logger.LogError(ex, "Failed to search categories.")` |
| `Critical` | 應用程式無法繼續運作而終止。**全專案只有一處**（`Program.cs` 頂層 catch）。 | `logger.LogCritical(ex, "Application is stopping because of an unhandled exception.")` |

### 2.3 使用者操作追蹤

| 操作 | 等級 | 記在哪裡 |
|------|------|----------|
| 畫面切換 | **Information** | `ApplicationCircuitHandler`（集中一處，涵蓋所有版面，**頁面不需要自己寫**） |
| 改變狀態的按鈕（新增／修改／刪除／匯出／套用／登入登出） | **Information** | 各自的事件處理方法 |
| 純查詢的按鈕（搜尋／重新整理／分頁／排序） | **Debug** | 各自的事件處理方法 |
| circuit 開啟／關閉／斷線 | Information／Warning | `ApplicationCircuitHandler` |

寫入性操作請記兩筆：**意圖**（使用者按下了什麼）與**結果**（成功或失敗）。中間的失敗分支依 §2.1 判斷等級。

### 2.4 不可寫入日誌的資料

日誌是純文字、保留 30 天，且**管理員可從 `/logs` 匯出原始檔案**。以下絕對不可進入日誌：

- 密碼（明文或雜湊）、`Salt`
- JWT／Refresh token、`SigningKey`、OAuth `ClientSecret`、API 金鑰
- 忘記密碼的重設 token 與重設連結，以及使用者在忘記密碼頁輸入的帳號／Email（0.9.60 起；只記 `UserId`）
- TOTP secret，**以及 `GenerateProvisioningUri` 的回傳值**（secret 內嵌在該 URI 裡）
- 圖形驗證碼（正確答案與使用者輸入皆是）
- 連線字串、SMTP 密碼（`EmailSettings:Password`）
- **Email、姓名、電話等個資** —— 包含寄信時的收件者；寄信相關日誌只記信件種類 `Kind`（例如 `Test`）
- 使用者輸入的搜尋關鍵字內容（可記「有沒有關鍵字」，不記關鍵字是什麼 —— 搜尋「王小明」等於記錄了一個人名）

**可以記錄的身分資訊只有 `Account` 與 `UserId`。**

> **已知且已接受的取捨**：Google SSO 使用者的 `MyUser.Account` 本身就是 Email（`ExternalLoginService` 建立帳號時如此設定）。因此對 SSO 使用者而言記 Account 等於記 Email。這是刻意接受的，因為 Account 是追蹤「是誰做的」最直接的依據，也與稽核表的 `ActorAccount` 一致。

**claim 對應在兩套驗證機制中是相反的，取用時務必確認：**

| Claim | Cookie（Blazor 頁面） | JWT（API） |
|---|---|---|
| `ClaimTypes.Name` | **使用者姓名（個資，絕不記錄）** | Account |
| `ClaimTypes.NameIdentifier` | Account | UserId |
| `ClaimTypes.Sid` | UserId | 未使用 |

在 Blazor 端誤用 `ClaimTypes.Name` 會把使用者姓名寫進日誌。

`HasPermissionAttribute` 同時掛在兩種端點上，因此以「`NameIdentifier` 是不是數字」判斷來源，並且只在 JWT 那一支取用 `ClaimTypes.Name`（見 `HasPermissionAttribute.ResolveActor`）。新增從 claim 取用身分的程式碼時，請照同樣的方式處理，不要假設只有一套對應。

### 2.5 撰寫格式

- 訊息一律**英文**句子；中文保留給 `ApiResult.Message` 與畫面通知，不要混進日誌。
- 結構化參數用 **PascalCase** 佔位：`Account={Account}`、`UserId={UserId}`。
- **不得使用 `{@Model}` 解構整包物件** —— 那是一次外洩全部欄位最快的方式。逐一列出需要的欄位。
- 例外一律放第一個參數：`logger.LogError(ex, "...")`。
- 不要記錄 QueryString、HTTP header、cookie。

### 2.6 守門測試

`CustomerHelpAgent.Tests/LoggingConventionTests.cs` 會擋下：

| 規則 | 說明 |
|---|---|
| 訊息含中文 | 一律英文 |
| 佔位名稱非 PascalCase | 便於檢索 |
| 佔位名稱含敏感字詞 | `password`／`token`／`secret`／`email`／`captcha` 等 |
| 引數取用敏感屬性 | 樣板寫 `{Value}` 但引數是 `user.Password` 一樣會被擋 |
| 使用 `{@}` 解構 | 禁止整包記錄 |
| 行為類別缺少 `ILogger` | Services／Repositories／Controllers／Diagnostics |

0.9.77 起另有兩條（PRD LOG-08）：

| 規則 | 說明 |
|---|---|
| 佔位名稱含 `search`／`keyword` | 查詢關鍵字只記 `HasSearch`／`SearchLength`（Web API 為 `HasKeyword`／`KeywordLength`） |
| catch 本體為空或只有註解 | 至少記一筆 Debug／Warning 並說明為何可忽略；取消／斷線類例外與例外紀錄管線類別列白名單，須註明理由 |

**測試擋不了的**：訊息內容是否有意義、等級選得對不對、有沒有記到該記的東西。這些仍需人工審查 —— 文件是判斷依據，測試只是最低防線。

若某個佔位名稱含敏感字詞但其實無害（例如布林旗標 `NeedChangePassword`），請加入測試中的 `SafePlaceholderNames` 並註明理由，不要放寬規則本身。

## 3. 全域請求日誌

`CustomerHelpAgent.Web/Extensions/ApplicationBuilderExtensions.cs` 的 `UseHttpRequestLogging` 註冊一個自訂 middleware：

- 對每筆 HTTP 請求記錄 `Method`、`Path`、`StatusCode`、`ElapsedMilliseconds`。
- 例外發生時改寫為 `Error`，並重新拋出讓上層 ExceptionHandler 處理。
- 同時設定系統例外紀錄的情境（來源、路徑）。這時還在驗證之前，**帳號由排在 `UseAuthorization` 之後的
  `UseExceptionContextUser` 補上**；本中介軟體的 catch 在記錄前也會再取一次帳號（0.9.77 之前例外紀錄的帳號欄恆為空）。

由此可在不額外加程式的情況下取得每個 endpoint 的響應耗時。

**Host 空白或組不成網址的請求回 400**（0.9.115，`UseRejectInvalidHost`，排在本中介軟體之後）：
HTTP/1.0 可以不帶 Host（掃描器、直接打 IP 的機器人常見）。這種請求以前會一路進到 Blazor 頁面，組網址時拋
`UriFormatException: Invalid URI: The hostname could not be parsed`，接著重跑的 `/Error` 再拋
`'RemoteNavigationManager' already initialized`，**一個請求留下 5 筆 ERROR**（本中介軟體兩筆、框架 ExceptionHandlerMiddleware 兩筆、
IIS 一筆）。現在只會記一筆 Information：`HTTP GET / responded 400`。

**低價值路徑記在 Debug**（0.4.30 起）：靜態資產（`/css`、`/js`、`/lib`、`/_framework`、`/_content`）、框架端點（`/_blazor`）、健康探針（`/health`）與 `/swagger`、`/favicon`、`/UploadFiles`。

原因很實際：`/health/live` 若每 10 秒被輪詢一次，一天就是 **8,640 筆** Information —— 比一位使用者一整天的操作紀錄還多，會把「使用者做了什麼」整個淹沒。

**但狀態碼 400 以上一律維持 Information 以上**，即使路徑屬於低價值清單。靜態資產的 404 往往正是「連結壞掉」最早的線索。

**慢請求另記一筆 Warning**（0.9.79 起）：耗時超過 `SlowOperationSettings:HttpRequestMs`（預設 3 秒）時記
`Slow HTTP request. Method=…, Path=…, StatusCode=…, ElapsedMilliseconds=…, ThresholdMilliseconds=…`。
`/_blazor` 不算：它是 Blazor 的 WebSocket 長連線，會持續整個 circuit。門檻與其他慢操作見 §4.13。

### 4.3.2.1 `CookieSettings`（0.9.39 起）

Blazor UI 登入 Cookie 的效期。與 `JwtSettings` 平行 —— 那一份管 API 的 session 長度，
這一份管畫面的；同樣以 `ValidateDataAnnotations` ＋ `ValidateOnStart` 驗證，**寫壞就啟動失敗**。

| 鍵 | 型別 | 預設 | 範圍 | 說明 |
|----|------|------|------|------|
| `CookieSettings:ExpireMinutes` | int | `480`（8 小時）| 1–43200 | **沒勾**「記住我」時的票證效期。此時 Cookie 同時是 session cookie，關瀏覽器就沒了 —— 兩個條件取先到者。 |
| `CookieSettings:RememberMeDays` | int | `30` | 1–365 | **勾了**「記住我」時的票證效期。 |
| `CookieSettings:SlidingExpiration` | bool | `true` | — | 滑動續期。 |
| `CookieSettings:ValidationIntervalMinutes` | int | `5` | 1–60 | 工作階段版本在 HTTP 請求上的檢查間隔（0.9.103 起）：改密碼、停用、強制登出後，其他瀏覽器的下一個請求最晚在這段時間內被登出；已開著的頁面在換頁時檢查。調小會增加查資料庫的次數。 |

⚠️ **0.9.39 之前這三項完全沒有設定**，吃框架隱藏預設（14 天 ＋ 滑動續期）。

⚠️ **滑動續期不是「每次使用都續」**：已用掉**超過一半**效期時的那一次請求才續，
並從那一刻起重新算滿。設 `false` 則到期就是到期。

⚠️ **Blazor Server 特有**：續期只發生在真正的 HTTP 請求上；circuit 內的 SignalR 換頁
不經過 Cookie 中介軟體，所以「開著分頁操作一整天」不保證會續到 Cookie。

⚠️ 兩種效期無法只靠設定達成：`ExpireTimeSpan` 是整個 scheme 共用的，
`RememberMeDays` 是在登入時以 `AuthenticationProperties.ExpiresUtc` 明寫覆蓋的。

### 4.3.2.2 `EmailSettings`（0.9.59 起）

寄信服務。`Provider` 三選一，出貨為 `None`（不寄任何信）。程式由 `IEmailSender`（同步寄出）與
`IEmailQueue`（背景佇列）兩個介面使用它，切換 provider 不需改呼叫端。
以 `ValidateDataAnnotations` ＋ `ValidateOnStart` 驗證，**寫壞就啟動失敗**（所有環境）。

| 鍵 | 型別 | 預設 | 說明 |
|----|------|------|------|
| `Provider` | string | `None` | `None`：停用，信件直接丟棄（只留一筆日誌）。`Pickup`：把信存成 `.eml` 到 `PickupDirectory`，**開發用**。`Smtp`：以 MailKit 寄出。空字串視為 `None`，未知值啟動失敗。 |
| `Host` | string | `""` | SMTP 主機。`Smtp` 時必填。 |
| `Port` | int | `587` | 1–65535。 |
| `Security` | string | `StartTls` | `Auto`、`None`、`StartTls`（587）或 `SslOnConnect`（465）。 |
| `UserName` | string | `""` | SMTP 登入帳號；留空代表不登入（內網中繼）。 |
| `Password` | string | `""` | 🔴 **機密**。出貨一律空字串；開發機用 User Secrets，正式環境用環境變數 `EmailSettings__Password`。 |
| `FromAddress` | string | `""` | 寄件者位址。`Smtp` 時必填且須為有效 Email；`Pickup` 留空時以 `no-reply@localhost` 代替。 |
| `FromName` | string | `""` | 寄件者顯示名稱；留空用 `SystemSettings:SystemInformation:SystemName`。 |
| `PickupDirectory` | string | `C:\temp\CustomerHelpAgent\Mails` | `Pickup` 存放 `.eml` 的資料夾，第一次寫信時才建立。 |
| `PublicBaseUrl` | string | `""` | 對外公開網址（例如 `https://erp.example.com`），信中連結以它為準。**不從請求的 Host header 組網址**，避免被偽造 Host 的請求把連結導到別處。 |
| `TimeoutSeconds` | int | `30` | 1–300。單一網路操作的逾時；背景寄送每封信的總上限是它的兩倍。 |

Production 另由 `StartupSafetyValidator` 檢查：

- `Provider=Pickup` → **拒絕啟動**。`.eml` 是明文、含完整內文，讀得到資料夾就讀得到所有信。
- `Provider=Smtp` → `Host`、`FromAddress` 不可留空，`PublicBaseUrl` 必須是完整的 `http(s)` 網址。

⚠️ **開發環境同樣是 `None`**（0.9.62 起，`appsettings.Development.json` 不再覆寫），見 §5；本機要測寄信，用 User Secrets 設 `Provider=Pickup`。

⚠️ **背景佇列只在記憶體**（容量 100）：程式重啟時尚未寄出的信會遺失；寄送失敗**不重試**，
錯誤記成 Error，會出現在「系統例外紀錄」（來源＝背景作業）。

檢查方式：系統健康監控頁的「寄信服務」項（`Smtp` 會實際連線＋登入，不寄信）與「寄信測試」區塊。
完整說明見 [寄信服務 PRD](../prd/寄信服務-prd.md)。
以 Gmail 帳號寄信的逐步設定（應用程式密碼、各值從哪裡取得）見 [Gmail 寄信設定指南](Gmail寄信設定指南.md)（0.9.84 起）。

|------|------|------|------|

註冊，**寫壞就啟動失敗**。0.9.92 起**所有**從設定檔綁定的類別都在啟動時驗證（設定矛盾、拼錯、格式錯誤一律拒絕啟動，

換掉 `SigningKey` 會讓所有既有 token 立刻失效 —— 那也是目前唯一的批次撤銷手段
（refresh token 無法個別撤銷）。

### 4.3.4 `BootstrapSettings` 🔴 最需要小心的一段

| 鍵 | 型別 | JSON 值 |
|------|------|------|
| `SupportAccount` | string | `support` |
| `SupportName` | string | `support` |
| `SupportEmail` | string | `support` |
| `SupportPassword` | string | **`support`** |

0.9.91 起註冊成 `IOptions<BootstrapSettings>`（現行為 `ServiceCollectionExtensions.AddConfiguredOptions` 的 `AddValidatedOptions<BootstrapSettings, BootstrapSettingsValidator>`），
由啟動時的 `SupportUserSeeder`（`CustomerHelpAgent.Business/Startup/SupportUserSeeder.cs`）讀取。行為是冪等 seed：帳號不存在就建立；
帳號存在但密碼對不上，就**用這裡的值覆寫回資料庫**。

🔴 **三個必須知道的事實**

1. 範本出貨的是 `appsettings.json` 的 `support`，**帳號與密碼相同、人人猜得到**，
   只適合本機開發。
2. `appsettings.Production.json:15` 出貨的是**空字串**。
   而 seed 的 `HashPassword(...)` 沒有防呆 ——
   **support 管理員帳號會變成空密碼**，且因為每次啟動都比對，**每次重啟都重新套用**。
   （現行 `BootstrapSettingsValidator` 在**所有環境**都拒絕空白的 `SupportAccount`／`SupportPassword`，留空會直接啟動失敗。）
3. 因為是每次啟動覆寫，**在畫面上改 support 的密碼是沒用的**，重啟就被打回去。

**0.9.48 起由啟動檢查強制**：Production 若留空、或沿用範本出貨的 `support`，
啟動會直接失敗。請用環境變數 `BootstrapSettings__SupportPassword` 提供真正的密碼。

⚠️ **不要**把它放進 User Secrets —— 它會反向覆寫資料庫，行為與一般機密不同。

### 4.8 `AiSettings`（0.9.4 起）

日誌檢視頁「AI 分析」功能的設定。完整機制說明見 [AI 日誌分析](../features/AI日誌分析.md)。

```json
"AiSettings": {
  "Provider": "AzureOpenAI",
  "Endpoint": "",
  "ApiKey": "",
  "Model": "",
  "TimeoutSeconds": 600
}
```

**沒有 `Enabled` 這種功能開關** —— 有沒有填 `ApiKey` 就是開關。出貨時是空字串，
所以功能預設關閉；設定不齊時按鈕停用並以 Tooltip 說明缺哪一項。

#### 4.8.1 程式預設值總表 ⚠️

**0.9.7 起 `appsettings.json` 只列出上面五個鍵**，其餘刻意不寫進範本、走程式預設
（與 `SystemSettings.Upload` 同一作法）。**這張表因此是那些鍵唯一查得到預設值的地方**，
要覆寫請自行在 `appsettings.json` 或 User Secrets 加上該鍵。

| 鍵 | 程式預設值 | 在 appsettings | 實際效果 |
|---|---|---|---|
| `Provider` | `"AzureOpenAI"` | ✅ | 走 Azure v1 路徑；填 `"OpenAI"` 改走官方 OpenAI |
| `Endpoint` | `""` | ✅ | Azure 必填；OpenAI 留空即用 `https://api.openai.com` |
| `ApiKey` | `""` | ✅ | **必填，也是功能的開關** —— 沒填就停用 |
| `Model` | `""` | ✅ | **必填**。Azure 填部署名稱，OpenAI 填模型 id |
| `TimeoutSeconds` | `600` | ✅ | HTTP 逾時 10 分鐘。推論模型對上百筆日誌可能想很久 |
| `MaxEntries` | `100` | ❌ | 送出最新的 100 筆；**這是唯一的送出量防線** |
| `MaxFollowUpRounds` | `10` | ❌ | AI 例外分析最多追問 10 輪（0.9.68 起）|
| `MaxOutputTokens` | `null` | ❌ | 不送 `max_completion_tokens`，由模型決定 |
| `Temperature` | `null` | ❌ | 不送 `temperature`，由模型決定 |

這張表由 `AiSettingsTests.Defaults_ShouldMatchDocumentedValues` 逐一斷言。
改動任何一個 C# 預設值而沒同步這裡時，測試會先紅。

#### 4.8.2 各鍵細節

| 鍵 | 說明 |
|----|------|
| `Provider` | `AzureOpenAI` 或 `OpenAI`（不分大小寫）。值打錯時按鈕停用並顯示「不支援的 AI provider」，不會讓頁面壞掉。 |
| `Endpoint` | Azure：入口網站「**Azure OpenAI 端點**」的值，形如 `https://xxx.openai.azure.com/openai/v1`（必填）。⚠️ 不要填成含 `/api/projects/` 的「專案端點」。OpenAI：留空即用 `https://api.openai.com`。 |
| `ApiKey` | API 金鑰，**必填**（也是功能的開關）。⚠️ 見下方 4.8.3。 |
| `Model` | 要呼叫的模型，**必填**且刻意沒有預設值。**Azure 請填部署名稱**（入口網站 Deployments 那一頁的名稱），OpenAI 填模型 id。兩者都送進請求 body 的 `model` 欄位。⚠️ **一律不帶日期後綴**（不要填 `xxx-2026-07-09` 這種在用量頁看到的名稱，Azure 會回 404 `DeploymentNotFound`）；送出的值就是這裡的原字串，系統不會加工。見[速查表 §6.10](../architecture/開發慣例與限制速查.md)。 |
| ~~`SystemPrompt`~~ | **0.9.108 起移除**，提示詞改在「AI 提示詞」頁管理（[PRD](../prd/AI提示詞管理-prd.md)）。升級後第一次啟動時，若這個鍵有值、且日誌分析還沒有任何版本，會匯入成第 1 版並記警告；之後這個鍵不再有作用，請移除。留著不會讓啟動失敗。 |
| `MaxEntries` | 送出的日誌筆數上限。超過時取**最新**的 N 筆。**0.9.7 起這是唯一的送出量防線** —— 字元層級的上限全部移除了，所以撞到模型內容視窗時，調低這一項是最直接的辦法。 |
| `MaxFollowUpRounds` | **AI 例外分析**（系統例外紀錄的明細窗，0.9.68 起）單次對話的追問輪數上限，不含第一次的分析報告；0 或負數代表不開放追問。每一輪都帶整段前文送出，輸入量與費用隨輪數累加，這個上限就是單次對話的費用天花板。畫面與服務層兩處都會擋，超過時**不發請求、不計費**。見 [AI 例外分析](../features/AI例外分析.md)。 |
| `TimeoutSeconds` | HTTP 逾時秒數，預設 **600（10 分鐘）**，遠高於一般 API：推論模型對上百筆日誌可能想很久。⚠️ 等待期間按鈕停用且沒有取消機制，上游若卡住，使用者最久會被困滿這個秒數。 |
| `MaxOutputTokens` | 回應長度上限（送出的 `max_completion_tokens`），**預設 `null`（不送）**。⚠️ 這個額度同時涵蓋推論模型的思考 token，設太小會在產出任何可見文字之前耗盡 —— 空回應，費用照付。微軟建議至少保留 25000。非正數視同不送。 |
| `Temperature` | 取樣溫度，**預設 `null`（不送這個參數）**。推論模型（o 系列、gpt-5 家族）只接受預設值，送任何數字都會被回 400 `unsupported_value`；不送就能相容所有模型，要調的人再自己填。⚠️ 要停用請設 `null`，**不要**設空字串 —— 空字串會讓組態繫結在使用者按下按鈕時才丟例外，而不是啟動時。 |

兩家供應商的實際差異：

| | Azure OpenAI（v1）| OpenAI |
|---|---|---|
| 路徑 | `{Endpoint}/chat/completions` | `{Endpoint}/v1/chat/completions` |
| 查詢參數 | 無（v1 採隱含版本，不需要 `api-version`）| 無 |
| 認證標頭 | `api-key: {ApiKey}` | `Authorization: Bearer {ApiKey}` |
| 模型指定 | 請求 body 的 `model`（填部署名稱）| 請求 body 的 `model`（填模型 id）|

⚠️ 本系統只支援 Azure 的 **v1 API**，不支援傳統的
`/openai/deployments/{部署名}/chat/completions?api-version=…` 路徑。
理由與遷移方式見 [AI 日誌分析 §2.5](../features/AI日誌分析.md)。

兩家的 `Endpoint` 都會**自動補上缺少的版本路徑後綴**（Azure 補 `/openai/v1`、
OpenAI 補 `/v1`），所以下列寫法都能用，不會組出重複的路徑：

| Provider | 可接受的 `Endpoint` 寫法 |
|---|---|
| Azure | `https://xxx.openai.azure.com/openai/v1`（入口網站原樣）、`https://xxx.openai.azure.com` |
| OpenAI | 留空、`https://api.openai.com`、`https://api.openai.com/v1`（官方文件的 base_url 寫法）|

#### 4.8.3 金鑰保管 ⚠️

`appsettings.json` 的 `ApiKey` **一律留空字串**當範本（與 `GoogleOAuthSettings` 一致），
實際值走 User Secrets、環境變數或 `appsettings.Development.json`：

```powershell
dotnet user-secrets --project src/CustomerHelpAgent/CustomerHelpAgent.Web set "AiSettings:ApiKey" "<金鑰>"
```

環境變數等價鍵為 `AiSettings__ApiKey`。

Production 環境下**沒填金鑰不會擋**（等於功能關閉，腳手架不帶金鑰也要能部署）；
但若**填了**金鑰卻缺 `Model`（Azure 再加 `Endpoint`），`StartupSafetyValidator`
會在啟動時擋下 —— 操作者顯然打算啟用，這種缺漏等到使用者按下按鈕才發現太晚。

### 4.9 `AiPricingSettings`（0.9.17 起）

LLM 呼叫的計價設定。費用在**記錄當下**算好並存進 `TokenUsageLog`，連同當時生效的單價與
匯率一起存 —— 是**快照**，調整本區段**不會改變已經記錄的帳**，只影響之後的呼叫。

```jsonc
"AiPricingSettings": {
  "UsdToTwd": 31.5,
  "Models": {
    "gpt-6-astra": {
      "LongContextThresholdTokens": 272000,
      "Rates":            { "TextInputPerMillion": 10.0, "TextCachedInputPerMillion": 1.0, "TextOutputPerMillion": 50.0 },
      "LongContextRates": { "TextInputPerMillion": 20.0, "TextCachedInputPerMillion": 2.0, "TextOutputPerMillion": 75.0 }
    },
    "gpt-6-sol": {
      "LongContextThresholdTokens": 272000,
      "Rates":            { "TextInputPerMillion": 2.0, "TextCachedInputPerMillion": 0.2, "TextOutputPerMillion": 10.0 },
      "LongContextRates": { "TextInputPerMillion": 4.0, "TextCachedInputPerMillion": 0.4, "TextOutputPerMillion": 15.0 }
    },
    "gpt-6-luna": {
      "LongContextThresholdTokens": 272000,
      "Rates":            { "TextInputPerMillion": 0.1, "TextCachedInputPerMillion": 0.01, "TextOutputPerMillion": 0.5 },
      "LongContextRates": { "TextInputPerMillion": 0.2, "TextCachedInputPerMillion": 0.02, "TextOutputPerMillion": 0.75 }
    },
    "gpt-transcribe": { "Rates": { "AudioPerMinute": 0.0045 } }
  }
}
```

#### 4.9.1 鍵一覽

| 鍵 | 型別 | 說明 |
|---|---|---|
| `UsdToTwd` | `double` | 1 美金折合多少台幣。**小於等於 0 視為未設定**，此時所有呼叫一律記為「未定價」（沒有另外的啟用旗標，比照 `AiSettings.ApiKey` 留空即停用） |
| `Models` | 字典 | 鍵是模型名稱，比對**不分大小寫** |
| `Models.<model>.Rates` | 物件 | 標準費率組，見 4.9.2 |
| `Models.<model>.LongContextRates` | 物件 | 長脈絡費率組。**省略代表此模型沒有分級**，永遠套用 `Rates` |
| `Models.<model>.LongContextThresholdTokens` | `int` | 本次**輸入 token 數嚴格大於**此值就改用長脈絡費率。只在 `LongContextRates` 存在時有意義 |

#### 4.9.2 費率組（`Rates` / `LongContextRates`）

八種計費單位，除 `AudioPerMinute` 外都是「每 1,000,000 單位」的美金價格：

| 鍵 | 計費單位 |
|---|---|
| `TextInputPerMillion` | 文字輸入 token |
| `TextCachedInputPerMillion` | 文字輸入中的快取命中 |
| `TextOutputPerMillion` | 文字輸出 token |
| `ImageInputPerMillion` | 圖片輸入 token |
| `ImageCachedInputPerMillion` | 圖片輸入中的快取命中 |
| `ImageOutputPerMillion` | 圖片輸出 token |
| `AudioPerMinute` | 音訊**每分鐘**（不是每 1M） |
| `SpeechPerMillionCharacters` | 語音合成每 1,000,000 **字元** |

**省略某個鍵的語意分成兩種，刻意不一致**：

- 兩個 cached 費率省略時，**快取部分退回以對應的 input 費率計算（不打折）**，不是免費。
  寧可高估也不要靜默少算。
- 其餘費率省略時，該計費單位不計費。
- 整組費率全部省略或全為 0 時視為未設定，該次呼叫記為「未定價」。這是設定檔被寫壞、
  或熱更新讀到半寫入 JSON 時的防線 —— 寧可顯示「未定價」，也不要把一整批呼叫以 0 元
  寫成永久快照。

⚠️ 計算時的**子集語意**：快取是輸入的折扣子集、推理已含在輸出內、圖片是同模態的子集。
每一項只會被算一次。推理 token 數完全不參與費用計算。

#### 4.9.3 模型比對規則

1. **完全比對**（不分大小寫，前後空白會被 trim）。
2. 否則**受限前綴比對**：前綴命中後，剩餘後綴必須符合 `^-\d[\d-]*$`
   （連字號接數字，其後只有數字與連字號），取符合條件的最長鍵。
3. 都沒中 → 費用留空，頁面顯示「未定價」，合計橫幅提示未計入筆數。

| 模型名稱 | 結果 |
|---|---|
| `gpt-4o-2024-08-06` | ✔ 套用 `gpt-4o` |
| `gpt-3.5-turbo-0125` | ✔ 套用 `gpt-3.5-turbo` |
| `gpt-4o-mini` | ✘ 未定價 |
| `gpt-4.1` | ✘ 未定價（不會套用 `gpt-4`） |

⚠️ **後綴限制是刻意的，不要放寬成「任何後綴」**。純前綴比對會讓 `gpt-4o-mini` 命中
`gpt-4o`（價差約 30 倍）、`gpt-4.1` 命中 `gpt-4`（價差約 15 倍），而且**完全靜默**，
錯誤金額還會被寫成永久快照。寧可顯示「未定價」讓人看得到沒算到。

#### 4.9.4 Azure OpenAI 的部署名稱 ⚠️

`AiSettings.Model` 對 Azure 而言填的是**部署名稱**（任意字串），而 `TokenUsageLog.Model`
是「優先取回應的 `model`，空的才退回設定值」。成功的呼叫通常拿得到真實模型 id（前綴比對
可用），但 **HTTP 非 2xx／逾時／傳輸失敗這三種分支根本沒有回應 body，必然退回部署名稱**，
一律變成「未定價」。

這不是 bug，但頁面上的未定價筆數會比預期高。要讓這些列也能計價，**直接把部署名稱當成
`Models` 的鍵再加一筆即可**，不需要改程式。

⚠️ 由此可知，**`/token-usage` 的「模型」欄顯示的是回應的模型名稱，通常帶日期後綴
（例如設定填 `gpt-5.6-sol`、頁面卻顯示 `gpt-5.6-sol-2026-07-09`），與 `AiSettings.Model`
不一樣是正常的**。不要反過來把頁面上看到的帶日期名稱填回設定，那會讓呼叫全部失敗。

- **長脈絡門檻 `272000`**：官方規則是輸入 token **嚴格超過**此值時，整筆請求套用

該測試另有一支**遞迴**的未知鍵守門：本區段有三層結構，打錯一個費率鍵名會讓該計費單位
靜默變成 0、帳直接少算而且沒有任何跡象。

### 4.10 `AiCallLogSettings`（0.9.72 起）

> 0.9.98 起 `RetentionDays` 與 `Enabled` 可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

「AI 對話紀錄」頁（`/ai-call-logs`）的記錄開關與保留期。內容檔放在 §4.6 的 `AiCallLogPath`。

```json
"AiCallLogSettings": {
  "Enabled": true,
  "RetentionDays": 90
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `Enabled` | `true` | 是否記錄每次 AI 呼叫的完整請求與回應。`false` 時新的呼叫一律不記（也不佔記憶體），頁面上方會提示「已停用記錄」；**已存在的紀錄仍依保留天數自動清除**。支援設定重載，改了不必重啟。 |
| `RetentionDays` | `90` | 保留天數，範圍 **1～3650**。排程作業「AI 對話紀錄清理」（0.9.96 起預設每天 03:00，見 §4.11 的 `ScheduledJobSettings`；之前是啟動時與每天一次）刪除送出時間早於「今天減保留天數」的紀錄與內容檔，並清掉更早月份的整個目錄（孤兒檔）。超出範圍時 `ValidateOnStart` 讓**啟動直接失敗**，不讓自動過期用錯的門檻刪資料。 |

- 記錄的是**確實送出**的呼叫：成功、上游錯誤、逾時、連線失敗、使用者取消、非預期錯誤都記；設定不完整、根本沒送出的不記。
  Token 用量不記取消與非預期錯誤，所以兩頁筆數可能不同。
- 與 Token 用量以 `CallId` 關聯；兩邊的清除各自獨立（Token 用量 0.9.96 起依 `LogRetentionSettings:TokenUsageLogDays` 自動過期，預設 365 天）。
- ⚠️ 關閉記錄**不會**刪除既有內容；要立即清掉請到頁面按「清空全部紀錄」。

### 4.11 `LogRetentionSettings`（0.9.78 起）

> 0.9.98 起三個天數可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

系統例外紀錄、稽核紀錄與 Token 用量紀錄的自動保存期限（[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) LOG-13；Token 用量 0.9.96 起）。

```json
"LogRetentionSettings": {
  "ExceptionLogDays": 90,
  "AuditLogDays": 365,
  "TokenUsageLogDays": 365
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `ExceptionLogDays` | `90` | 例外紀錄「最後發生」早於今天減 N 天的列，連同堆疊檔刪除。範圍 **0～36500**，`0`＝不自動清理。 |
| `AuditLogDays` | `365` | 稽核紀錄早於 N 天前的列刪除（以 UTC 計算）。`0`＝不自動清理。稽核是責任證據，有法規或內控保存要求時請調大或設 `0`。 |
| `TokenUsageLogDays` | `365` | Token 用量紀錄早於「今天減 N 天」的列，連同原始 JSON 檔刪除（0.9.96 起；之前完全不會自動清除）。`0`＝不自動清理。分批刪除，不會長時間佔住資料庫寫入。 |

- 0.9.96 起由**排程作業**執行（「稽核紀錄清理」「系統例外紀錄清理」「Token 用量紀錄清理」，各自獨立，預設每天 03:00；之前是 `LogRetentionWorker` 啟動時與每天一次）。
  執行時間與總開關見下方 `ScheduledJobSettings`，執行結果在「排程作業」頁。
- 真的刪到資料時各寫一筆稽核：`ExceptionLog.AutoPurge`／`Audit.AutoPurge`／`TokenUsage.AutoPurge`（AI 對話紀錄為 `AiCallLog.AutoPurge`，0.9.96 起），
  操作者顯示「（系統／匿名）」，Detail 為筆數、天數與觸發方式；空跑不寫。
- 「系統例外紀錄」與「稽核紀錄」頁的「清除 N 天前」按鈕讀同一組天數；設為 `0` 時按鈕退回預設 90／365 天。
- AI 對話紀錄有自己的 §4.10；日誌檔由 `nlog.config` 的 `maxArchiveDays`（30 天）管。
- 超出範圍時 `ValidateOnStart` 讓**啟動直接失敗**。

密碼原則（[登入與帳號流程 PRD](../prd/登入與帳號流程-prd.md)、[速查表 §6.18](../architecture/開發慣例與限制速查.md)）。管理員新增與修改使用者、「變更密碼」頁、忘記密碼重設**全部**套用；只影響之後設定的密碼。

```json
"PasswordPolicySettings": {
  "MinimumLength": 8,

  "RequireDigit": true,
  "RequireUppercase": false,
  "RequireSymbol": false,
  "HistoryCount": 3,
  "ExpiryDays": 0

```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `MinimumLength` | `8` | 最少字元數，範圍 **6～64**。 |
| `RequireLetter` | `true` | 必須包含英文字母（A–Z、a–z；中文字不算）。 |
| `RequireDigit` | `true` | 必須包含數字。 |
| `RequireUppercase` | `false` | 必須包含大寫英文字母。 |
| `RequireSymbol` | `false` | 必須包含符號（標點或符號字元）。 |

| `ExpiryDays` | `0` | 密碼幾天後到期，範圍 **0～3650**；`0`＝不過期。到期後登入會被導去「變更密碼」頁；排程作業「密碼到期提醒」（`PasswordExpiryReminder`，預設 `0 8 * * *`）在到期前 7 天內每天通知本人一次（同一個到期日只一次）。 |

- support 帳號（`BootstrapSettings:SupportAccount`）與只用 Google 登入、沒有本機密碼的帳號**不受**「必須變更」與到期影響。

#### `TwoFactorSettings`（0.9.104 起）

> 兩個欄位都可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

```json
"TwoFactorSettings": {
  "RequireForAdmins": false,
  "RememberDeviceDays": 30
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `RequireForAdmins` | `false` | `true` 時所有管理員必須使用兩步驟驗證；還沒設定的人登入後每次換頁都被帶到「兩步驟驗證」頁。support 帳號（`BootstrapSettings:SupportAccount`）與只用 Google 登入、沒有本機密碼的帳號豁免。角色層級的強制在「角色管理」勾「需要兩步驟驗證」。 |

#### `ScheduledJobSettings`（0.9.96 起）

> 0.9.98 起 `JobRunRetentionDays`（`Enabled` 與各作業的 cron 仍只在設定檔），可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

排程作業的執行時間與總開關（[排程作業 PRD](../prd/排程作業-prd.md)）。各作業的啟用／停用在「排程作業」頁切換（存在資料庫），不在這裡。

```json
"ScheduledJobSettings": {
  "Enabled": true,
  "JobRunRetentionDays": 90,
  "Jobs": {
    "AuditLogRetention": { "Cron": "0 3 * * *" },
    "ExceptionLogRetention": { "Cron": "0 3 * * *" },
    "AiCallLogRetention": { "Cron": "0 3 * * *" },
    "TokenUsageLogRetention": { "Cron": "0 3 * * *" },
    "SoftDeletePurge": { "Cron": "0 3 * * *" },
    "SystemBackup": { "Cron": "0 2 * * *" },
    "NotificationRetention": { "Cron": "0 3 * * *" },
    "PasswordExpiryReminder": { "Cron": "0 8 * * *" }
  }
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `Enabled` | `true` | 總開關。`false` 時不依排程執行、也不補跑，但頁面仍可「立即執行」。用途：維護期間暫停所有排程。 |
| `JobRunRetentionDays` | `90` | 執行紀錄保留天數，範圍 **0～36500**，`0`＝不清除。 |
| `Jobs:<名稱>:Cron` | 每天 03:00 | 5 欄位 cron（分 時 日 月 星期），依**伺服器本地時區**。名稱不分大小寫；沒列出的作業用程式內建的預設時間。 |

- 啟動時驗證：名稱必須是已註冊的作業、cron 必須是 5 欄位而且真的會觸發（例如 `0 0 30 2 *` 永遠不會到，會被擋下），任何一項不合法**啟動直接失敗**。
- 執行中修改會在一分鐘內生效；改壞的話排程沿用上一份合法設定並記錯誤，「排程作業」頁與「系統健康監控」會顯示警示。
- 網站在該執行的時間沒開著（例如 IIS 閒置停止）時，下次啟動補跑一次；全新安裝、新加入或重新啟用的作業不會補跑。
- 同一時段跨行程只跑一次（資料庫搶占）；同一個作業不重疊執行（資料庫檔旁的 `*.job-<名稱>.lock` 檔案鎖，停站時可以刪除）。

### 4.12 `ExceptionAlertSettings`（0.9.78 起）

> 0.9.98 起四個數值門檻（收件人 `Recipients` 仍只在設定檔），可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

系統例外的 Email 告警（[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) LOG-12）。**出貨預設停用**（收件人空清單）。

```json
"ExceptionAlertSettings": {
  "Recipients": ["ops@example.com"],
  "BurstThreshold": 20,
  "BurstWindowMinutes": 10,
  "PerSignatureCooldownMinutes": 60,
  "MaxEmailsPerHour": 20
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `Recipients` | `[]` | 收件人清單；**空清單＝停用**。與系統帳號無關，可填維運群組信箱。 |
| `BurstThreshold` ／ `BurstWindowMinutes` | `20` ／ `10` | 同一種例外在 N 分鐘內發生達 M 次即告警（暴增）。 |
| `PerSignatureCooldownMinutes` | `60` | 同一種例外在冷卻時間內只寄一次。 |
| `MaxEmailsPerHour` | `20` | 全系統每小時上限；超過的不寄，筆數併入下一封信告知。 |

- **觸發**：新種類的例外第一次發生、Critical（啟動失敗、程序層級例外，經補登檔補進時）、暴增。
- **前提**：`EmailSettings:Provider` 不是 `None`；信中的連結取自 `EmailSettings:PublicBaseUrl`，未設定時只寫頁面路徑。
- **信件只含摘要**：觸發原因、例外類型、來源、頁面、次數、首次／最後時間、錯誤追蹤碼與連結；**不含**例外訊息全文、堆疊、帳號。
- 寄信背景作業本身的錯誤（頁面 `EmailDispatch`）不觸發告警，避免 SMTP 故障時自己告自己。
- 節流狀態只在記憶體，重啟歸零（單機設計）。

慢操作記錄（[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) LOG-21）：超過門檻就記一筆 **Warning**（含操作名稱、耗時與門檻）。

|------|------|--------|----------|
| `HttpRequestMs` | `3000` | 每個 HTTP 請求（排除 `/_blazor` 長連線）。Google SSO 的 `/signin-google` 與回呼也算在這裡 | `Slow HTTP request.` |
| `DbCommandMs` | `1000` | 單一資料庫指令（EF Core 攔截器 `SlowDbCommandInterceptor`）。**只記指令類型**（SELECT／INSERT…），不記 SQL 與參數 | `Slow database command.` |
| `ExternalCallMs` | `10000` | 背景寄信作業寄出一封信（只記信件種類 `Kind`） | `Slow email dispatch.` |
| `AiCallMs` | `60000` | 一次 AI 呼叫，以及健康監控的 AI 探測 | `Slow AI chat completion.`／`Slow AI health probe.` |

- 任一項設 `0` 即停用該項；範圍 0～3,600,000。
- **刻意不量「Blazor 單次互動」**：AI 分析在按鈕事件裡等待、確認窗等使用者按鈕都會算進去，每次都誤報。
  畫面變慢的原因幾乎都落在上面四類，用錯誤追蹤碼到 `/logs` 就能看到同一次操作裡是哪一步慢。
- 資料庫指令的耗時不含之後逐列讀取資料的時間。

### 4.14 `ClientErrorReporting`（0.9.79 起）

> 0.9.98 起兩個欄位可在「系統參數」頁覆寫，不需重啟（見 §4.15）。

瀏覽器端 JavaScript 錯誤回報（[日誌與例外處理 PRD](../prd/日誌與例外處理-prd.md) LOG-20）。

```json
"ClientErrorReporting": {
  "Enabled": true,
  "MaxPerCircuitPerMinute": 10
}
```

| 欄位 | 預設 | 用途 |
|------|------|------|
| `Enabled` | `true` | 是否回報。關閉後瀏覽器端仍會捕捉，但不再送給伺服器。 |
| `MaxPerCircuitPerMinute` | `10` | 每個 Blazor 連線（circuit）每分鐘最多記幾筆，超過的丟棄並計數（顯示在系統健康監控「日誌管線」）。範圍 1～1000。 |

- 由 `wwwroot/js/client-error-reporter.js` 掛上 `error` 與 `unhandledrejection`，**只有登入後的頁面**（MainLayout）會註冊回報；
  登入頁等靜態頁面沒有 circuit，錯誤只暫存在瀏覽器記憶體、不會送出，匿名者無法灌資料。
- 記成 Error（帶 `BrowserScriptException`），進系統例外紀錄，來源「瀏覽器」；同一個錯誤在同一頁重複發生會合併計次。
- 訊息最多 1000 字、堆疊 4000 字；頁面只記路徑（去掉查詢字串與 `#` 之後的內容）。
- 瀏覽器外掛（`chrome-extension://` 等）的錯誤，以及 `ResizeObserver loop`、`Script error.` 這類已知雜訊不回報。

### 4.15 系統參數（資料庫覆寫層，0.9.98 起）

管理員在「系統參數」頁（`/system-parameters`，管理員專屬）修改的值存在資料庫 `SystemParameter` 表，當成**一層設定來源疊在
appsettings、環境變數與命令列之上**（[系統參數 PRD](../prd/系統參數-prd.md)）。沒有覆寫的鍵沿用下層的值；「還原為設定檔值」就是刪掉覆寫。

- **優先順序**：系統參數 ＞ 命令列 ＞ 環境變數 ＞ `appsettings.{Environment}.json` ＞ `appsettings.json`。
  ⚠️ 覆寫**也蓋過環境變數**：部署人員改了設定檔或環境變數卻沒生效時，先到系統參數頁看那個鍵的「來源」是不是「系統參數」。
- **不會自動寫入**：第一次啟動不會把 appsettings 的值寫進資料庫（migration 沒有種子資料），升級新增的鍵也不會；資料表只有管理員在頁面存檔的覆寫。
  沒有覆寫的目錄內鍵改 appsettings 就生效（讀取端是 `IOptionsMonitor`，設定檔存檔即重載）。
- **要到哪裡改**：
  1. 鍵在下方「可覆寫的鍵」表 → 到系統參數頁改。
  2. 頁面上的來源是「系統參數」→ 只能在頁面改；要改回設定檔的值，按「還原為設定檔值」。來源是「設定檔」→ 頁面或設定檔都可以，改了設定檔就生效。
  3. 鍵不在表裡 → 只能改 appsettings 或環境變數，見下方「只在設定檔的區段」。
- **生效**：存檔後立即套用（讀取端都用 `IOptionsMonitor` 或 `ISystemIdentity`）；多個行程或多台主機每分鐘從資料庫同步一次。
- **驗證**：存檔前把「設定檔的值＋候選覆寫」交給與啟動時相同的驗證器，不合法就拒絕；啟動或同步時發現已不合法的覆寫（例如升級後範圍變窄）略過並標「未套用」，不讓啟動失敗。
  啟動時的 `ValidateOnStart` 只驗設定檔本身，所以 **appsettings 必須自己就合法**。
- **只放非機密、執行期可改、單一數值的鍵**。密碼、金鑰、連線字串、路徑、版本號、Cookie／JWT 這類啟動時就被讀走的值、陣列與字典（例如告警收件人、各作業的 cron）一律留在設定檔。
  不在下表的鍵就算出現在資料表裡也不會套用（頁面會列為「不認得的參數」讓管理員移除）。
- 每次修改與還原寫稽核 `SystemParameter.Update`／`SystemParameter.Reset`，Detail 為 `key=…; old=…(來源); new=…(來源)`。
- 備份資料庫時一併帶走這些覆寫（它們就在 `BackendDB.db`）。

### 4.16 `AiQuotaSettings`（0.9.109 起）

AI 用量上限，新台幣整數元，**0＝不限制**（預設四個都是 0）。四個鍵都是系統參數（分類「AI 用量」），通常在畫面上調整。見 [AI 用量配額 PRD](../prd/AI用量配額-prd.md)。

```json
"AiQuotaSettings": {
  "GlobalDailyTwd": 0,
  "GlobalMonthlyTwd": 0,
  "PerUserDailyTwd": 0,
  "PerUserMonthlyTwd": 0
}
```

| 鍵 | 說明 |
|---|---|
| `GlobalDailyTwd`／`GlobalMonthlyTwd` | 所有人今天／本月的 AI 費用合計上限。達到後所有人的 AI 分析暫停到明天 00:00／下月 1 日 00:00；80% 與 100% 時通知全體管理員，100% 另寄信。 |
| `PerUserDailyTwd`／`PerUserMonthlyTwd` | 每個人今天／本月的上限。達到後他的 AI 分析暫停；80% 與 100% 時通知本人。 |

- 以「Token 用量」記錄的台幣費用（`CostTwd`）加總；⚠️ **未定價的模型以 0 計**，模型沒有寫進 `AiPricingSettings` 時上限形同無效。
- 期間依伺服器本地時間；系統健康監控的 AI 連線檢查計入用量但不會被擋。
- 同時送出的呼叫可能讓已用金額小幅超過上限。

## 5. 環境差異設定

`appsettings.Development.json` 只有 `Logging` 區塊：

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Debug",
      "Microsoft": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
```

- `Logging`：☠️ **惰性**，見 §4.1 —— `ClearProviders()` 之後這些值不會生效。
- 寄信沿用 `appsettings.json` 的 `None`（0.9.62 起；0.9.61 曾在這裡預設 `Pickup`，已移除），所以本機登入頁沒有「忘記密碼？」。
  要在本機測，用 User Secrets 設 `EmailSettings:Provider = Pickup`（信寫成 `.eml` 到 `C:\temp\CustomerHelpAgent\Mails`，不需要任何帳密）。

未來可在 `appsettings.Production.json` 內切換 SystemSettings（例如連線字串、外部目錄）以符合不同部署環境。
