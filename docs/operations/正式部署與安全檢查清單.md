## JWT 與認證
- [ ] 將 `JwtSettings:SigningKey` 改由 secret manager、環境變數或部署平台 secret 提供。
- [x] Production 啟動時若仍使用開發用 signing key，會直接中止啟動。
- [ ] 確認 signing key 長度、亂數強度與輪替流程。
- [ ] 確認 access token 與 refresh token 有效期符合系統風險等級。
- [ ] 記錄 refresh token 採 stateless signed JWT，無法可靠撤銷單一 token；若需要撤銷能力，需改成落庫或加入 token version 機制。
- [ ] 確認正式環境的 `Security:ReturnExceptionDetails` 為 `false`（`appsettings.Production.json` 出貨值；未設定時只有 Development 會在 `ApiResult.Exception` 回傳例外細節，由 `ExceptionDetailPolicy` 統一判斷）。設成 `true` 也會讓**所有使用者**按錯誤通知的「複製」時拿到完整例外與堆疊（0.9.130 起；管理員不受此設定影響，一律可以）。

## 預設帳號

- [ ] 若系統需要保留預設管理者，必須將 `BootstrapSettings:SupportPassword` 改由部署 secret 提供；首次啟動強制改密碼可另開功能化任務。
- [ ] 檢查文件、seed、測試資料中沒有可被正式環境沿用的密碼。
- [ ] 售後示範（1.0.3 起）：「預設角色」每次啟動都會自動加入新頁面，因此預設就有「售後審核」「售後規則管理」「顧客商店」（1.0.4 起再加「Agent 執行紀錄」，1.0.8 起再加「效益對照」）。正式部署時請到角色管理把這些頁從「預設角色」移除，只指派給需要的角色（見[售後 Agent 示範系統](../features/售後Agent示範系統.md)）。

- [ ] 展示環境（非 Production、開啟示範模式）只給展示用途：示範帳號密碼為 `DemoSettings:DemoUserPassword`（預設 `demo1234`），系統管理員可從 `/demo-console` 免密碼切換成示範帳號；不要把真實客戶資料放進展示環境，也不要對外公開它的網址。

## Swagger 與 API
- [ ] 正式環境確認 Swagger UI 是否關閉，或限制在內網/VPN/授權後使用。
- [x] Production 必須明確設定 `Swagger:EnabledInProduction`，預設範本為 `false`。
- [ ] 確認所有 CRUD API 均需要 Bearer token（例外：`ProjectFileController` 的附件下載走 Cookie，呼叫端是畫面連結而非程式）。
- [ ] 確認受保護 API 具**動作級授權**（`[HasPermission]`）：以無對應權限的使用者實測 create/edit/delete 回 **403（非 200）**，view/search 回 200。
- [ ] 確認 API validation、401、403、404、500 都維持 `ApiResult<T>` 格式。
- [ ] 確認檔案下載成功時維持原生 File stream，錯誤才回 `ApiResult<T>`（`ProjectFileController.Download`）。
- [ ] 確認附件下載對「查無紀錄／團隊越界／實體檔案不存在」一律回 404，不以狀態碼洩漏檔案是否存在。
- [ ] 確認新用戶端使用 `/api/v1/...`，既有 `/api/...` 僅作相容路由。
- [x] Controller 未明確標註授權即拒絕（`MapControllers().RequireAuthorization()`）；新增需匿名存取的 Controller 必須自行標 `[AllowAnonymous]`。

### Web API 的團隊列級過濾（0.9.105 起）🟡

0.9.104 之前 Web API（`ProjectRepository`／`CategoryRepository`）完全沒有團隊過濾，非管理員持 JWT 可取得全部紀錄；0.9.105 起與畫面套用同一套規則（`RecordTeamScope`）。

- [ ] **升級後，以非管理員帳號呼叫 API 的整合程式會開始看到較少資料**：範圍外的紀錄不在搜尋結果裡，單筆、修改、刪除回 404；指定範圍外的團隊回 400。整合帳號需要看全部時，給它管理員或把相關部門指派給它，並事先通知整合方。
- [ ] 已登入卻解析不到身分的請求（自訂的驗證方式沒有帶使用者 Id）什麼都看不到 —— 確認整合用的 token 是 `/api/Auth/login` 發的。

詳見 [開發慣例與限制速查 §4.1](../architecture/開發慣例與限制速查.md) 與 [紀錄分類與團隊權控 PRD](../prd/紀錄分類與團隊權控-prd.md)。

## 寄信（0.9.59 起）
> 使用 Gmail 帳號寄信時，逐步設定見 [Gmail 寄信設定指南](Gmail寄信設定指南.md)。

- [ ] 確認 `EmailSettings:Provider`：不寄信維持 `None`（預設）；要寄信改 `Smtp`。
- [x] Production 若 `Provider=Pickup` 會直接中止啟動（`.eml` 明文寫入磁碟，含完整信件內容）。
- [x] Production 若 `Provider=Smtp` 但 `Host`／`FromAddress` 留空、或 `PublicBaseUrl` 不是完整 http(s) 網址，會直接中止啟動。
- [ ] `PublicBaseUrl` 填**使用者實際打開的網址**（含 https 與正式網域），信中連結一律以它為準。
- [ ] 依公司資安規定，在「系統參數」的「密碼與登入」確認密碼規則、有效天數與鎖定設定（0.9.101 起；預設至少 8 字、要有英文與數字、不重複最近 3 組、不過期、輸錯 5 次鎖 15 分鐘）。
- [ ] 管理員帳號填了**有效的 Email**（0.9.100 起排程作業失敗、0.9.101 起帳號被鎖定都會寄信給全體管理員；support 預設的 `support` 不是信箱，會被略過，只收得到站內通知）。
      只有 http 的環境可填 `http://...`（驗證接受），但帳密、Cookie 與重設 token 都會以明文傳送，建議盡早改走 https。
- [ ] **排查：本機正常、IIS 起不來**：本機以 `launchSettings.json` 的 `Development` 執行，不做這些檢查；
      IIS 未設定 `ASPNETCORE_ENVIRONMENT` 時預設即為 `Production`。到「事件檢視器 → Windows 記錄 → 應用程式」
      找「Production 啟動安全檢查失敗」，訊息會列出每一項未過的設定（PublicBaseUrl 另帶出目前讀到的值）。
      設定若放在部署不會覆蓋的位置（`web.config` 環境變數、主機上的 `appsettings*.json`），重新部署程式碼不會修好它。
- [ ] `EmailSettings__Password`（與 `UserName`）以環境變數或密鑰保管庫提供，`appsettings.json` 維持空字串。
- [ ] SMTP 主機的 TLS 憑證必須有效：程式刻意不略過憑證驗證，自簽憑證會連線失敗。
- [ ] 防火牆放行對外的 SMTP 埠（587 或 465）。
- [ ] 上線後到「系統健康監控」確認「寄信服務」為綠燈，並用「寄出測試信」寄一封給自己。
- [ ] 啟用寄信即開放「忘記密碼」（0.9.60 起）：確認使用者的 Email 都登記正確；用一個測試帳號實際走一次
      忘記密碼 → 收信 → 重設 → 登入，並確認信中連結是 `PublicBaseUrl` 的網域。
- [ ] 評估 `PasswordResetSettings`（連結效期 30 分、同帳號冷卻 60 秒）；冷卻是唯一的濫用防線，不建議調成 0。
- [ ] 若 IIS 開了 W3C 日誌，注意它會記下重設連結的完整網址（含 token）：縮短日誌保存期或限制存取。

## 速率限制與安全標頭（0.4.35 起）
- [ ] 依本案流量特性檢視 `RateLimit:ApiRequestsPerMinute`（預設 120）與 `RateLimit:LoginRequestsPerMinute`（預設 10）。
- [x] 限流**依呼叫端分割**（已驗證身分優先，其次來源 IP），不再是全站共用單一計數器。

## Data Protection 金鑰（登入存不存得住，取決於這一節）🔴

**登入 Cookie 是用 Data Protection 的金鑰加密的 —— 金鑰換一批，全站所有人立刻被登出。**
0.9.39 之前完全沒有設定，金鑰走框架預設位置；本節的檢查項就是為了不再重蹈覆轍。

- [ ] `SystemSettings:ExternalFileSystem:DataProtectionKeyPath` 已指向**應用程式重新部署後
      仍然存在**的目錄（不要放在會被發行流程清掉的位置），且執行身分對它有**讀寫**權限。
- [ ] 部署後確認該目錄底下**真的有產生 `key-*.xml`**。沒有就是設定沒生效。
- [ ] **IIS**：應用程式集區的**識別身分固定不變**。⚠️ Windows 上金鑰檔預設以 **DPAPI** 加密，
      換了識別身分即使檔案還在也**解不開**。
- [ ] **IIS**：建議把應用程式集區的 `loadUserProfile` 設為 `true`。
      ⚠️ 未載入使用者設定檔時，框架預設會退化成「金鑰只存在記憶體」——
      **每次回收就換一批**（IIS 預設 20 分鐘閒置關閉、29 小時定期回收）。
- [ ] **多機／多節點**：所有節點必須**共用同一個金鑰目錄**（或改用集中式金鑰儲存），
      否則使用者會隨負載平衡在節點之間隨機被登出。
- [ ] 確認 `MagicObjectHelper.DataProtectionApplicationName` 未被改動。
      ⚠️ 它是金鑰環的用途判別子，**改了等於讓所有既有登入失效**；
      不固定它的話，連「換一個部署目錄」都會失效。
- [ ] 金鑰目錄納入備份，且**不可**納入版本控制或公開的檔案分享。
- [ ] 0.9.104 起金鑰環也加密兩步驟驗證的密鑰：⚠️ 金鑰換一批，**所有開啟兩步驟驗證的人都登入不了**（驗證碼一律不正確），只能由管理員逐一「重設兩步驟驗證」。support 不受強制，是這時的救援入口。

> 相關設定與行為說明見 [日誌與設定檔說明 §4.6](日誌與設定檔說明.md)
> 與 [腳手架開發指引 §3.4](../guides/腳手架開發指引.md)。

## 排程作業（0.9.96 起）🟡

**排程作業跑在網站行程裡：應用程式集區停了，排程就跟著停。** IIS 預設閒置 20 分鐘就關閉集區，
半夜沒有人使用時，03:00 的清除作業根本不會執行（下次有人連上時才補跑一次）。

- [ ] **IIS**：應用程式集區的「啟動模式」設為 **AlwaysRunning**，「閒置逾時（分鐘）」設為 **0**。
- [ ] **IIS**：站台的「預先載入已啟用」（`preloadEnabled`）設為 **true**，回收後不必等第一個請求就會啟動。
- [ ] 部署後到「排程作業」頁確認八個作業（五個紀錄清除＋0.9.97 起的已刪除資料清理、0.9.99 起的系統備份、0.9.101 起的密碼到期提醒）都有「下次執行」時間；隔天確認「上次執行」是成功。
      「系統健康監控」的「排程作業」項目若顯示逾期，通常就是上面兩項沒設好。
- [ ] 多台機器共用同一個資料庫時，同一時段只會有一個行程執行（資料庫搶占）；若只想讓特定一台跑排程，
      其他台設 `ScheduledJobSettings:Enabled = false`。
- [ ] 資料庫檔旁的 `*.job-<作業名稱>.lock` 是作業的檔案鎖，**停站時可以刪除**，網站執行中不要動它。
- [ ] 關機時正在執行的作業會被中斷並記為「中斷」；長時間的作業（例如之後的備份）要留意 IIS 的關機時限（`shutdownTimeLimit`）。

> 設定見 [日誌與設定檔說明 §4.11](日誌與設定檔說明.md) 的 `ScheduledJobSettings`；規則見 [排程作業 PRD](../prd/排程作業-prd.md)。

## 系統備份（0.9.99 起）🔴

- [ ] `SystemSettings:ExternalFileSystem:BackupPath` 改到資料碟上的獨立目錄（不可與其他資料目錄重疊、不可在網站目錄底下，啟動時會檢查）。

- [ ] `appsettings*.json` 與環境變數不在備份裡，另外保存一份。

## 系統參數（0.9.98 起）🟡

管理員可在「系統參數」頁（`/system-parameters`）覆寫保留天數、監控門檻、系統名稱等 42 個非機密的值（0.9.135 時；以 `SystemParameterCatalog.All` 為準），存在資料庫、**蓋過 appsettings 與環境變數**。

- [ ] 上線前先在「系統參數」頁設定正式的系統名稱與簡介，並依規定確認各種紀錄的保留天數（稽核紀錄有保存年限時調大或設 0）。
- [ ] 部署人員改了設定檔或環境變數卻沒生效時，先到「系統參數」頁看那個鍵的來源是不是「系統參數」；要改回設定檔的值請按「還原為設定檔值」。
- [ ] 升級後打開「系統參數」頁，確認沒有「未套用」或「不認得的參數」提示（新版本若收窄了範圍，舊的覆寫會被略過並標示）。
- [ ] appsettings 本身仍要合法：啟動時只驗證設定檔，覆寫在資料庫初始化之後才套用。

## 同一主機名稱部署多個衍生系統

**瀏覽器的 Cookie 只看主機名稱、不看連接埠。** `http://server:8081` 與 `http://server:8082`
（或同一站台底下的兩個子應用程式）會共用同一批 Cookie；名稱相同就會互相覆蓋 —— 登入 B 會把 A 登出，
反之亦然（彼此的金鑰解不開對方的 Cookie，所以不會越權，但會一直被登出）。

以 `New-StarterProject.ps1` 產生的專案，下列項目已經依專案名稱區分，**不需要**另外處理：

| 項目 | 值（以專案名 `ProjA` 為例）|
|------|------|
| 登入 Cookie | `.ProjA.Auth`（0.9.64 起；之前是框架預設的 `.AspNetCore.CookieAuthenticationScheme`，會互撞）|
| 外部登入暫存 Cookie | `.ProjA.External` |
| 防偽 Cookie | `.AspNetCore.Antiforgery.<依應用程式名稱雜湊>` |
| Data Protection 應用程式名稱 | `ProjA` |
| 資料庫／上傳／金鑰等目錄 | `C:\temp\ProjA\...` |
| NLog 日誌 | `NLog:BasePath` 底下再分 `ProjA.Web\` 子目錄與檔名前綴 |

- [ ] 兩個系統的 `ExternalFileSystem` 各路徑**不要**指到同一個目錄（尤其是 `DatabasePath` 與 `DataProtectionKeyPath`）。
- [ ] 各自使用獨立的 IIS 應用程式集區。
- [ ] 0.9.64 之前產生的衍生專案：在 `Program.cs` 的 `AddCookie(MagicObjectHelper.CookieScheme, ...)` 補上
      `options.Cookie.Name = ".<專案名>.Auth";`（套用後既有登入會失效一次）。
