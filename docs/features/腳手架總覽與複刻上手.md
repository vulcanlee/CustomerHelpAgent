## 1. 這份腳手架是什麼

**What**：一套已經可以直接上線的 **.NET 10 + Blazor Server 企業後台系統底座**。

一句話說明：

> 它不是「範例專案」，而是「**把每個內部系統都會重寫一次的東西，先寫好**」。

你拿到的是一個能跑、能登入、有權限、有日誌、有稽核、有健康監控的完整系統。
你要做的，是在上面加入**你自己的業務功能**（例如設備管理、請假單、報價單）。

**定位**：

| 特性 | 意思 |
|---|---|
| 開箱即用 | 下載、建置、執行，就能用預設帳號登入一個完整的後台 |
| 預先設定 | 日誌、快取、寄信、安全檢查、AI 計費等設定都已經接好，只要改設定值 |
| 易於擴充 | 有腳本產生新功能模組的骨架，有文件說明每一條慣例 |

## 2. 為什麼需要這份腳手架

### 2.1 Why：企業內部系統一直在重寫同一批東西

想像公司要做三個系統：設備管理、採購流程、客戶服務。每個系統開工的前一兩個月，都在做這些事：

- 登入、登出、忘記密碼、帳號鎖定
- 使用者管理、角色、權限、「這個部門只能看自己的資料」
- 操作紀錄（誰在什麼時候改了什麼）
- 系統出錯時要記下來、要通知人
- 日誌要能查、要能匯出
- 正式上線前的安全檢查

這些東西**跟業務無關，但每個系統都少不了**。問題是：

| 問題 | 後果 |
|---|---|
| 每次都從零寫 | 前一兩個月都在做「看不出成果」的基礎建設 |
| 每次寫法都不一樣 | 系統 A 的權限做法跟系統 B 不同，維護的人要學好幾套 |
| 每次都踩同樣的坑 | 例如預設密碼沒擋、匯出的 CSV 用 Excel 打開是亂碼、對話窗點旁邊就把整份輸入弄丟 |
| 品質靠個人經驗 | 資深的人做得好，新人做的就漏東漏西 |

### 2.2 How：腳手架怎麼解決

1. **先寫好**：上面那些共通功能全部做完、測過、寫好文件。
2. **一鍵複刻**：`New-StarterProject.ps1` 把整套複製並改成你的專案名字，幾分鐘完成。
3. **慣例固定品質**：每一條踩過的坑都寫成「守門測試」，違反就測試失敗，不用靠記憶。
4. **文件給人也給 AI 看**：讓新人和 AI 助手都能照著既有做法擴充，而不是各自發明。

### 2.3 When：什麼時候該用它

- 公司要開一個**新的內部系統**，而且需要帳號、權限、日誌這些基本功。
- 你想讓多個系統**長得一樣、做法一樣**，降低維護成本。
- 你打算用 **AI 助手**幫忙開發，希望 AI 寫出來的程式碼符合規範。

## 3. 適不適合用這份腳手架

**Why 要先判斷**：腳手架的技術選擇（Blazor Server、SQLite）有明確的適用範圍。選錯起點，後面會很痛苦。

### 3.1 適合

- 企業內部管理後台、營運系統、專案追蹤平台。
- 使用者**數十到數百人**。
- 需要依**部門／團隊**切分「誰能看到哪些資料」。
- 一開始就需要帳號權限、日誌、稽核、健康監控。

### 3.2 不適合

| 情境 | 為什麼不適合 |
|---|---|
| 公開網站、高流量的一般消費者服務 | Blazor Server 每個使用者佔一條即時連線，畫面狀態放在伺服器上，人數一多伺服器負擔很重 |
| 需要離線或網路很不穩的環境 | 連線斷了畫面就不能操作 |
| 多租戶 SaaS（一套系統賣給很多家公司、資料要完全隔離） | 只有「團隊」層級的分權，沒有「租戶」隔離 |
| 大量同時寫入（例如每秒上千筆交易） | 只支援 SQLite，同一時間只能有一個寫入者 |
| 介面要支援多國語言切換 | 多語系目前只是空殼：沒有語系資源檔，介面文字都是繁體中文 |

### 3.3 簡單判斷流程

```
是公司內部用的系統嗎？
├─ 否 → 不建議（考慮其他架構）
└─ 是 → 使用者會超過上千人同時在線嗎？
        ├─ 是 → 不建議
        └─ 否 → 需要多國語言介面或多租戶隔離嗎？
                ├─ 是 → 可以用，但要自己補一大塊（先評估成本）
                └─ 否 → ✅ 適合
```

## 4. 已經預先設計好的企業共通功能

### 4.4 稽核紀錄：事後查得到「誰做了什麼」

**What**：登入、登出、使用者／角色／權限的變更、清除紀錄等事件，都會寫一筆稽核紀錄。管理員可以在 `/audit-logs` 查詢、匯出、清除。

**Why**：出事時要能回答「誰、什麼時候、做了什麼」。很多產業的內控或法規也要求保存操作軌跡。
「清除稽核紀錄」這個動作本身也會留下一筆紀錄，避免有人刪紀錄滅證。

每筆紀錄另記**來源 IP**（0.9.117 起；排程作業與更早的舊紀錄沒有 IP），可用「來源 IP」欄位前綴篩選（0.9.123 起）；個人資料頁的登入紀錄與首頁「上一次登入」也顯示 IP。
⚠️ 系統前面有反向代理時要設定 `ForwardedHeaders`，否則記到的都是代理的 IP（見 8.3）。

**出貨狀態**：✅ 開。預設保存 365 天，每天自動清除超過的部分（天數在「系統參數」頁或 `appsettings.json` 的 `LogRetentionSettings:AuditLogDays` 調整，設 `0` 代表不清）。

### 4.5 可觀測性：系統出問題時看得到、查得到

「可觀測性」的意思是：**系統在想什麼、哪裡壞了，你看得到**。這是上線後最常用到、卻最常被忽略的一塊。

| 功能 | 是什麼 | 企業為什麼需要 | 畫面 |
|---|---|---|---|
| 日誌檢視 | 依等級、關鍵字、時間查詢系統日誌，可匯出 | 不用登入主機翻檔案 | `/logs` |
| 日誌等級設定 | 執行中直接調整日誌要記多詳細（重啟後回到預設） | 出問題時臨時打開詳細日誌，不用重新部署 | `/log-level-setting` |
| 系統例外紀錄 | 程式出錯時自動收集，同一種錯誤合併計次，保存完整堆疊 | 錯誤不會被淹沒在日誌裡，一眼看出哪種錯誤最多 | `/system-exceptions` |
| 錯誤追蹤碼 | 使用者看到錯誤時，畫面會顯示一組追蹤碼 | 使用者回報「追蹤碼 XXX」，你就能在日誌找到同一次操作的所有紀錄 | — |
| 例外告警信 | 新種類的錯誤、或同一錯誤短時間暴增時寄信通知 | 系統壞了不用等使用者打電話來才知道 | ⚪ 預設關閉（填收件人＋啟用寄信） |
| 慢操作記錄 | HTTP 請求、資料庫指令、寄信、AI 呼叫超過門檻就記一筆警告 | 使用者說「系統很慢」時，知道是哪一步慢 | — |
| 瀏覽器錯誤回報 | 使用者瀏覽器裡的 JavaScript 錯誤也會送回伺服器記錄 | 伺服器原本完全看不到前端錯誤 | — |
| 系統健康監控 | 健康百分比、紅黃綠燈號，檢查資料庫、磁碟、寄信、AI、日誌管線、排程作業等 14 項 | 一頁看完系統是否正常 | `/system-health` |
| 資料庫用量 | 各資料表筆數與估算大小 | 提早發現資料暴增 | `/database-usage` |
| 健康檢查端點 | `/health/live`、`/health/ready` | 給負載平衡器或監控工具自動偵測 | API |
| 自動清除 | 每天自動刪除過期的例外紀錄（90 天）、稽核紀錄（365 天）、AI 對話紀錄（90 天）、Token 用量（365 天）、站內通知（90 天；已讀的 7 天，0.9.125 起），並永久刪除已刪除超過 90 天的資料；日誌檔保留 30 天 | 磁碟不會被塞爆 | `/scheduled-jobs` |
| 排程作業 | 固定時間自動執行的背景工作：看下次執行、上次結果、立即執行、停用；錯過會補跑、多個行程也只跑一次（0.9.96） | 自動清除有沒有跑一眼就知道；系統備份（0.9.99）也是用同一套做的，之後要加報表照做即可 | `/scheduled-jobs` |

| 功能 | 是什麼 | 企業為什麼需要 | 畫面 |
|---|---|---|---|
| 日誌 AI 分析 | 把查到的日誌送給 AI（Azure OpenAI 或 OpenAI），整理成看得懂的報告，可匯出 PDF | 幾千行日誌人工看不完 | `/logs` |

## 5. 預先整理好的文件

**What**：`docs/` 底下有上百份繁體中文文件，依主題分類。
**Why**：程式碼只能告訴你「怎麼做的」，文件告訴你「**為什麼這樣做、哪裡會踩雷**」。這對新人和 AI 都一樣重要。

### 5.1 文件分類

| 資料夾 | 管什麼 | 複刻時會帶走嗎 |
|---|---|---|
| `architecture/` | 架構、資料模型、API 規範、**開發慣例與限制速查**、視覺設計規範 | ✅ |
| `security/` | 登入、權限、密碼、記住我的原理、Google 登入設定 | ✅ |
| `features/` | 各功能機制（快取、檔案上傳、健康監控、AI 分析，以及本文） | ✅ |
| `guides/` | 操作指南：開發環境、新增 CRUD、EF Core、測試、畫面與欄位字典、**腳手架開發指引** | ✅ |
| `operations/` | 部署、維護規範、設定檔說明、CI、AI 計費更新 | ✅ |
| `prd/` | 每個功能的產品需求文件（PRD）：功能做什麼、規則是什麼 | ✅ |
| `changelog/` | 每次改版的紀錄 | ⚪ 只留索引骨架 `README.md`（新專案從自己的第一篇開始） |

> 為什麼清掉 `changelog/` 的歷史紀錄？那些是**腳手架自己的開發史**，對你的新專案沒有意義，留著反而會讓 AI 和新人誤以為是你專案的歷史。

### 5.2 什麼時候讀哪一份

## 6. 為什麼這些準備能讓 vibe coding 更順利

### 6.1 Why：AI 寫程式的四個常見問題，以及腳手架怎麼對付

| AI 常見問題 | 會發生什麼事 | 腳手架的對策 |
|---|---|---|
| **不知道上下文** | AI 不知道你的專案有哪些規則，只能猜 | 文件寫好規則；`CLAUDE.md`／`AGENTS.md` 是 AI 的入口，指引它先讀哪些文件 |
| **自己發明做法** | 同一件事每次用不同寫法，專案越來越亂 | 「這些事情不要自己發明」對照表（例如確認窗一律用 `ConfirmDialog`、顏色一律用 `var(--app-*)`），寫在指引 §14.2 和速查表 |
| **說完成了，其實沒做對** | 程式能編譯、測試也過，但畫面跑版、少了權限、匯出亂碼 | **守門測試**：把踩過的坑寫成測試，違反就紅燈，失敗訊息會說明原因 |
| **忘了收尾** | 改了程式，沒更新文件、沒改版本號 | `CLAUDE.md` 明定：每次異動版本號 +1、要同步相關文件、不可自動 commit；「每次異動寫一篇 changelog」則是 `docs/operations/維護規範.md` §2 的規定 |

**白話總結**：文件告訴 AI「該怎麼做」，守門測試在 AI 做錯時「自動抓出來」。兩者加起來，你不需要是資深工程師，也能讓 AI 產出符合規範的程式碼。

### 6.2 What：AI 會讀到哪些東西

AI 助手（例如 Claude Code）開啟專案時，會先讀根目錄的 `CLAUDE.md`（其他工具讀 `AGENTS.md`），裡面寫了最關鍵的規則，並指向下面這些文件。建議 AI 照這個順序讀：

| 順序 | 文件 | 管什麼 |
|---|---|---|
| 1 | `CLAUDE.md`／`AGENTS.md` | 行為準則與最關鍵的不變量 |
| 2 | `docs/architecture/開發慣例與限制速查.md` | 所有慣例與踩雷點（⚠️ 標記是硬紅線） |
| 3 | `docs/architecture/對話窗 UI 設計規範.md` | 對話窗、確認窗、通知 |
| 4 | `docs/architecture/介面視覺設計規範.md` | 色票、側邊欄、表格 |
| 5 | `docs/guides/畫面與欄位字典.md` | 既有欄位的意思 |
| 6 | `docs/prd/` 對應的 PRD | 該模組的既有行為 |

幾個代表性的守門測試：

| 測試 | 擋什麼 |
|---|---|
| `ThemeConventionTests` | 顏色寫死在頁面裡，而不是用 `theme.css` 的色票 |
| `PageHelpCatalogTests` | 新增了頁面卻沒有寫「操作說明」 |
| `MenuPermissionConsistencyTests` | 選單和權限設定對不上 |
| `DocumentationConventionTests` | `appsettings.json` 新增了區段卻沒寫進設定文件 |
| `StartupSafetyConventionTests` | 正式環境的安全檢查被改壞 |

### 6.3 How：一次對話的工作循環

```
1. 說清楚要什麼（一次只做一件事）
2. 請 AI 先讀相關文件，說明它打算怎麼做
3. 確認做法後，讓 AI 動手
4. 請 AI 跑品質關卡（見 6.5）
5. 你自己打開畫面看一次（視覺問題測試抓不到）
6. 看過變更內容（diff），確認沒有改到不相干的地方
7. 你自己決定何時 commit
```

### 6.4 可以直接照抄的提示詞

把 `Acme.Erp` 換成你的專案代號。

**① 新增一個業務模組**

```text
請用 scripts/New-CrudModule.ps1 新增一個「設備清單」模組（英文名 Equipment）。
欄位：設備編號（必填、唯一）、設備名稱（必填）、購入日期、保管人（使用者下拉）、備註。
動手前先讀 docs/guides/建立一個新 CRUD 操作網頁說明.md 與 docs/architecture/開發慣例與限制速查.md，
告訴我你打算怎麼做。腳本會直接寫進 src 並完成選單、權限、操作說明的登記（加 -SkipMigration，
補完欄位後再產生 migration）。做完跑 pwsh ./scripts/Invoke-QualityGate.ps1。不要 commit。
```

**② 在既有模組加欄位**

```text
在「專案項目」加一個欄位「預計完成日」（日期，可空白）。
要同步：資料模型、migration、DTO、新增／編輯對話窗、列表欄位、Web API、
畫面與欄位字典、該頁的操作說明第三段。先列出會改哪些檔案讓我確認。
```

**③ 新增一個頁面並設定權限**

```text
新增一個「月報表」頁面，只有被授權的角色看得到。
請依照速查表的「新增頁面權限」做法（Menu.json 的 id、MenuPermissionMap、
MagicObjectHelper 權限鍵常數），並在 HelpTopics.json 登記、撰寫 Datas/Help 的操作說明。
完成後確認 MenuPermissionConsistencyTests 與 PageHelpCatalogTests 都通過。
```

**④ 調整設定值**

```text
我們是金融業內部系統，想把登入效期縮短、稽核紀錄保存 7 年。
請依照 docs/guides/腳手架開發指引.md §4.6 的決策表，建議 CookieSettings 與
LogRetentionSettings 該怎麼設，說明理由，等我確認後再改 appsettings.json。
```

**⑤ 用錯誤追蹤碼查問題**

```text
使用者回報畫面出錯，錯誤追蹤碼是 K7Q2M9XA。
請在系統例外紀錄與日誌中找出這次操作的完整紀錄，分析原因並提出修正方案，
先不要改程式。
```

### 6.5 AI 寫完後一定要跑的品質關卡

一行指令（從任何目錄執行都可以）：

```powershell
pwsh ./scripts/Invoke-QualityGate.ps1   # 建置（0 warning）、格式、測試、文件編碼、弱點掃描，遇到失敗就停
```

最後一行顯示 `QUALITY GATE PASSED` 才算過；失敗時摘要表會指出停在哪一步。

⚠️ **這道關卡對「畫面好不好看」幾乎完全無感**。畫面跑版不會讓任何測試失敗，所以改了畫面一定要自己打開來看。

### 6.6 使用技巧

- **一次只做一件事**。一次要求太多，AI 容易漏掉其中幾項。
- **先叫 AI 讀文件、說明做法**，再讓它動手。方向錯了，早點發現成本最低。
- **看到守門測試失敗，先讀失敗訊息**。那裡寫著當初為什麼要有這條規則，通常照著改就對了。不要叫 AI 把測試改掉或跳過。
- **檢查 diff**。AI 有時會順手「改善」不相干的程式碼，`CLAUDE.md` 雖然有要求它不要，還是要看一下。
- **不要讓 AI 自動 commit**。commit 是你確認過、願意負責的時間點。

## 7. 用 `New-StarterProject.ps1` 複刻新專案

### 7.1 What／Why

**What**：一支 PowerShell 腳本，把整個腳手架複製到新資料夾，並把所有 `CustomerHelpAgent` 換成你的專案代號。

**Why**：手動複製再改名，要改的地方有上百處，其中有十幾個漏改**不會報錯**，例如：

- 樣式檔名稱沒改 → 全站畫面沒有樣式，卻沒有任何錯誤訊息。
- User Secrets 的 ID 沒改 → 兩個專案的密碼互相污染。
- 登入 Cookie 名稱沒改 → 同一台主機上的兩個系統互相把對方登出。

腳本把這些一次做完，並在最後掃描有沒有漏網之魚。

**When**：每要開一個新系統，就跑一次。**整個方案只要跑一次**，不是每個子專案跑一次。

### 7.2 事前準備

| 工具 | 為什麼需要 | 怎麼確認 | 怎麼安裝 |
|---|---|---|---|
| .NET SDK 10.0.400 以上 | 建置與執行。`global.json` 鎖定了版本 | `dotnet --info` | [.NET 下載頁](https://dotnet.microsoft.com/download) |
| PowerShell 7（`pwsh`） | 執行腳本。腳本只以 PowerShell 7 驗證過，Windows 內建的 5.1 不在支援範圍 | `pwsh --version` | Microsoft Store 或官網 |
| dotnet-ef | 腳本要用它重建資料庫 migration，**沒裝會直接中止** | `dotnet ef --version` | `dotnet tool install --global dotnet-ef` |
| Git | 版本控制 | `git --version` | 官網 |
| 開發用 HTTPS 憑證 | 第一次用 https 執行前要信任 | — | `dotnet dev-certs https --trust` |
| 網路 | 腳本會執行 `dotnet restore` 下載套件，也會 `git fetch` 比對遠端 | — | — |
| 腳手架是最新版 | 腳本複製的是你電腦上那份腳手架資料夾的**現況**；不是最新，新專案就帶著舊版或改到一半的檔案出生 | `git status`（乾淨）、`git branch --show-current`（是 `main`） | `git switch main`、`git pull`；未提交的修改先 commit 或 stash（0.9.116 起腳本會檢查，見 7.5） |

### 7.3 參數

| 參數 | 必填 | 預設 | 說明 |
|---|---|---|---|
| `-ProjectName` | ✔ | — | 新專案代號。可用點分段，**每一段**都要英文字母開頭，只能有英文、數字、底線。例：`Acme.Erp`、`HrPortal` |
| `-DestinationPath` | ✔ | — | 新專案要放的資料夾。已存在時會中止，不會覆蓋 |
| `-Force` | | 關 | 目標資料夾已存在時，**先整個刪除**再複製。⚠️ 無法復原 |
| `-SourceProjectName` | | `CustomerHelpAgent` | 要被取代的舊代號。從衍生專案再往下衍生時也不用填（衍生專案裡的腳本預設值已經是它自己的代號，舊連接埠也會從它的 `launchSettings.json` 讀出來） |
| `-UserSecretsId` | | 自動產生新的 GUID | 想指定 User Secrets ID 時才填 |
| `-KeepStarterHistory` | | 關 | 保留腳手架的開發史文件（`docs/changelog/` 的歷史紀錄） |
| `-AllowUnsyncedSource` | | 關 | 腳手架來源不是最新（有未提交修改或未追蹤檔、不在預設分支、落後 origin）時，仍照現狀複製（0.9.116 起）。不加的話腳本會中止 |

**代號怎麼取**：

- 代號會變成**程式的命名空間**，例如 `Acme.Erp.Web`。取一個短、穩定、日後不會改的名字。
- 用點分隔公司與系統是常見做法：`公司.系統`，例如 `Acme.Erp`。
- **不能有連字號（`-`）、空白或中文**，也不能出現 `Acme..Erp`、`Acme.`、`Acme.1x` 這種建置會失敗的寫法，腳本會一開始就拒絕。
- 目標資料夾**不要放在腳手架資料夾裡面**，否則會把自己複製進去。

### 7.4 使用範例

在**腳手架的根目錄**開啟 PowerShell 7 執行。

**範例一：最常用的寫法**

```powershell
pwsh ./scripts/New-StarterProject.ps1 -ProjectName Acme.Erp -DestinationPath D:\Work\Acme.Erp
```

**範例二：目標資料夾已存在，要覆蓋**（⚠️ 原資料夾內容會全部刪除）

```powershell
pwsh ./scripts/New-StarterProject.ps1 -ProjectName Acme.Erp -DestinationPath D:\Work\Acme.Erp -Force
```

**範例三：保留腳手架的開發史文件**（想研究腳手架為什麼這樣設計時）

```powershell
pwsh ./scripts/New-StarterProject.ps1 -ProjectName Acme.Erp -DestinationPath D:\Work\Acme.Erp -KeepStarterHistory
```

**範例四：指定 User Secrets ID**（通常不需要，例如要沿用某台機器上已經設好的機密時）

```powershell
pwsh ./scripts/New-StarterProject.ps1 -ProjectName Acme.Erp -DestinationPath D:\Work\Acme.Erp `
     -UserSecretsId 2f6c1d0e-1a2b-4c3d-8e9f-0123456789ab
```

**範例五：刻意從「不是最新」的腳手架複刻**（例如要用某個功能分支、或還沒 commit 的修改當起點）

```powershell
pwsh ./scripts/New-StarterProject.ps1 -ProjectName Acme.Erp -DestinationPath D:\Work\Acme.Erp -AllowUnsyncedSource
```

⚠️ 加了這個開關，腳本會照你電腦上資料夾的**現況**複製，未提交的修改、未追蹤的檔案都會進入新專案。
只有在你清楚知道自己要的是這個狀態時才用；一般情況請先 `git pull` 並讓工作目錄保持乾淨。

### 7.5 腳本做了什麼（白話版）

| 步驟 | 做什麼 | 為什麼 |
|---|---|---|
| 1 | 檢查有沒有安裝 dotnet-ef | 沒有就直接停，不留下做一半的資料夾 |
| 2 | **檢查腳手架來源是不是最新的**（0.9.116 起）：先 `git fetch origin`，再確認三件事 —— 工作目錄沒有未提交的修改或未追蹤檔、目前在 origin 的預設分支（通常是 `main`）、沒有落後 origin。任一項不符合就列出問題並中止（`-AllowUnsyncedSource` 可放行）。另外會列出「被 `.gitignore` 忽略、卻不在排除清單裡」的檔案（只警告） | 腳本複製的是你電腦上資料夾的**現況**，不是 git 上的某個版本。不檢查的話，改到一半的檔案、舊版內容都會靜悄悄地進入新專案。不是 git 資料夾（例如下載 zip）、沒有 origin、連不上網路時無法比對，只會警告 |
| 3 | 從來源的 `launchSettings.json` 讀出舊連接埠，再隨機挑一組本機沒被占用的新埠（http 5000–5300、https 7000–7300） | 同一台電腦開多個衍生專案時不會搶埠；從衍生專案再衍生也會換埠 |
| 4 | 檢查目標資料夾 | 已存在又沒加 `-Force` 就停 |
| 5 | 複製整個資料夾，跳過 `.git`、`bin`、`obj`、`.vs`、`.playwright-cli`、`output`、`*.user`、`*.suo`，以及 `artifacts`、`.gstack`、`PublishProfiles`、`.claude\settings.local.json` 等本機產物；複製完刪掉變空的資料夾 | 只帶走原始碼和文件，不帶編譯產物、個人設定和腳手架的版本歷史 |
| 6 | 把文字檔裡的 `CustomerHelpAgent` 全部換成新代號、全小寫的 `customerhelpagent` 換成新代號的小寫；舊的 User Secrets ID、舊連接埠也換掉。`.gitignore` 也會換（0.9.137 起） | 命名空間、設定、文件一次改完；`.gitignore` 裡有一條 `Backup/` 程式碼的例外規則帶著專案名，沒換的話那幾支程式提交不進 git |
| 7 | `appsettings.json`：JWT 金鑰換成「新代號-佔位符」、版本號重設為 `1.0.0 (今天)` | 新專案從 1.0.0 開始算版本 |
| 8 | 文件開頭的「現行系統版本」改成 `1.0.0` | 文件和系統版本一致 |
| 9 | 由深到淺改資料夾名稱，再改檔名 | 資料夾和檔名也要換成新代號 |
| 10 | 把新的 User Secrets ID 寫進 Web 專案的 csproj | 機密和其他專案分開 |
| 11 | 清空舊 migration，刪除寫死舊 migration 名稱的 `CategoryTeamUniqueIndexMigrationTests.cs` 與 `TeamTreeMigrationTests.cs`，重新產生一個叫 `Init` 的 migration | 腳手架的資料庫變更歷史對新專案沒意義，從乾淨的第一版開始；那兩支測試驗證的是腳手架自己的升級路徑，在新專案必定失敗（0.9.116 前漏刪後者，衍生專案會有 1 個測試失敗） |
| 12 | 清理文件：刪掉 `docs/changelog/` 的歷史紀錄（保留 `README.md` 索引骨架）；指向已刪檔案的索引行整行刪除，夾在敘述句裡的連結降為純文字 | 新專案不帶腳手架的開發史，但留著寫自己第一篇 changelog 的位置 |
| 13 | 掃描殘留字串並印出警告，最後印出新網址、Google 登入要註冊的網址 | 讓你知道下一步 |

**腳本「不會」做的事**（另外注意：`MagicObjectHelper.cs` 的 `DataProtectionApplicationName = "CustomerHelpAgent"` 在 `.cs` 檔裡，**會**跟著換成新代號。新專案沒有既有登入，換了沒影響；但若你是把已上線的系統重新複刻，換了會讓所有人重新登入）：

- 不會 `git init`（新資料夾沒有版本控制，要自己建）。
- 不會換 Logo 和網站圖示（圖片是二進位檔）。
- 不會改預設管理員密碼 `support`（換成另一個固定值也不會比較安全；正式環境由啟動檢查擋下）。

### 7.6 跑完的畫面怎麼看

**成功時**會看到：

```text
UserSecretsId set to <新的 GUID>
SystemVersion reset to 1.0.0 (執行當天)
...
警告: ...（一行標題＋五條）
...
Next: see docs/guides/VS Code 開發環境與新專案上手指南.md - section 7 ...
```

**那一行標題與五條「警告」全部都不用處理**。它們是掃描規則的必然命中，不是待辦：

| # | 位置 | 為什麼不用處理 |
|---|---|---|
| 1–2 | 上手指南的範例 | 文件正在教你「這個值要換掉」，本來就要把它印出來 |
| 3–4 | 腳本本身 | 腳本自己的取代規則，日後從這個專案再往下衍生時還用得到 |
| 5 | 整合測試 | 測試專用的金鑰，不進產品；改了測試會失敗 |

**來源不是最新時**（0.9.116 起），腳本一開始就會停下，還沒有複製任何東西：

```text
WARNING: The source is not the latest version, so the new project would not get the latest files and docs:
WARNING:   - Uncommitted changes or untracked files (1):
     M scripts/New-StarterProject.ps1
WARNING:   - Behind origin/main by 3 commit(s).
Exception: Source is not the latest version (see the warnings above). ...
```

照訊息處理：`git switch main`、`git pull`，未提交的修改先 commit 或 stash，再重跑一次。
如果你確定就是要用目前的狀態（例如刻意從功能分支複刻），加 `-AllowUnsyncedSource`（見 7.4 範例五）。

**反而不會警告、但你一定要處理的兩件事**：

1. **JWT 金鑰還是佔位符**（`Acme.Erp-ChangeThisJwtSigningKey-AtLeast32Chars`）。開發可以用，上線前必換。
2. **管理員密碼還是 `support`**。開發可以用，上線前必換。

這兩件事在正式環境啟動時會被擋下，不會靜悄悄地帶著弱密碼上線。

依時間分四個階段。每一項都說明為什麼。

### 8.1 第一天：讓它跑起來

- [ ] **建立 Git 儲存庫並做第一個 commit**
  - Why：之後每一步改動都能回頭比對、出錯能還原。
  - How：
    ```powershell
    cd D:\Work\Acme.Erp
    git init
    git add .
    git commit -m "從 NET10-Blazor-Starter <腳手架版本> 複刻初始版本"
    ```
  - commit 訊息寫明「從腳手架哪一版複刻」，日後要跟上腳手架更新時會用到（見第 10 節）。
- [ ] **確認沒有本機殘留**：`artifacts\`、`.gstack\`（腳本已略過不複製，通常不會出現）。
- [ ] **建置與測試**
  ```powershell
  dotnet build src/Acme.Erp/Acme.Erp.slnx -v:minimal
  dotnet test  src/Acme.Erp/Acme.Erp.slnx
  ```
  - Why：守門測試會抓出改名時漏掉的地方。全綠才代表複刻成功。
- [ ] **第一次執行**
  ```powershell
  dotnet run --project src/Acme.Erp/Acme.Erp.Web/Acme.Erp.Web.csproj --launch-profile https
  ```

  - 用腳本最後印出的 https 網址開啟，以 `support`／`support` 登入。
  - ⚠️ 一定要用 `https`，用 `http` 會被導到一個沒人在聽的連接埠。
  - 第一次啟動會自動建立 `C:\temp\Acme.Erp\` 底下的資料庫、上傳、例外、金鑰等資料夾（日誌另外寫在 `C:\temp\Logs\Acme.Erp.Web\`），並建立預設角色與帳號。

  - Why：金鑰放在 User Secrets 不會被 commit 進 Git。

### 8.2 第一週：變成「你的」系統

- [ ] **換品牌**
  - `appsettings.json` 的 `SystemSettings:SystemInformation:SystemName`、`SystemDescription`：登入頁、側邊欄、首頁、關於視窗都會顯示。
  - 換圖：`src/Acme.Erp/Acme.Erp.Web/wwwroot/images/brand-logo.png`、`wwwroot/favicon.png`。
  - 換顏色：只改 `wwwroot/theme.css` 的 `:root` 色票。
- [ ] **確認檔案路徑**：`SystemSettings:ExternalFileSystem` 的十一個路徑和 `NLog:BasePath`，開發機可以沿用 `C:\temp\Acme.Erp\...`。
- [ ] **決定範例功能和 AI 要不要留**（見第 9 節）。
- [ ] **做第一個自己的業務模組**
  ```powershell
  pwsh ./scripts/New-CrudModule.ps1 -Name Equipment -DisplayName 設備清單
  ```
  - 直接寫進 `src/` 並完成登記與 migration（0.9.110 起），接著照[檢查清單](../guides/建立一個新%20CRUD%20操作網頁說明.md)補上實際欄位與說明。
  - 或直接用第 6.4 節的提示詞 ① 請 AI 幫你做。
- [ ] **在 `CLAUDE.md` 補上你專案自己的規則**（`AGENTS.md` 要同步寫一樣的內容，見 [Q20](#q20-claudemd-和-agentsmd-有什麼差別要怎麼維護)）
  - Why：AI 每次都會讀它。把「我們公司的業務名詞」「這個專案特有的規則」寫進去，AI 就不會亂猜。
  - 例如：「本系統的『單位』指的是 Team；金額一律以新台幣整數儲存。」
- [ ] **寫第一篇 changelog**：`docs/changelog/` 新增一篇，記錄「從腳手架 <腳手架版本> 複刻」，並登記到 `docs/changelog/README.md`。
- [ ] **建立 CI**（建議）：在你使用的平台（GitHub Actions、Azure DevOps……）執行 6.5 的 `Invoke-QualityGate.ps1`，每次推送程式碼都自動檢查。
- [ ] **改寫 `readme.md`**：把腳手架的介紹換成你系統的介紹。

### 8.3 上線前：把開發用的值換掉

| 必改項目 | 怎麼改 | 不改會怎樣 |
|---|---|---|
| `JwtSettings:SigningKey` | 環境變數 `JwtSettings__SigningKey`，至少 32 字元隨機字串 | 正式環境拒絕啟動 |
| `BootstrapSettings:SupportPassword` | 環境變數 `BootstrapSettings__SupportPassword`，強密碼（**不要**放 User Secrets） | 正式環境拒絕啟動 |
| `Swagger:EnabledInProduction` | 明確寫 `true` 或 `false` | 正式環境拒絕啟動 |
| `ExternalFileSystem` 路徑、`NLog:BasePath` | 改到資料碟，並納入備份 | 資料放在暫存目錄，系統碟可能被塞滿 |
| `ForwardedHeaders` | 前面有反向代理（IIS ARR、Nginx、負載平衡器）就要設 | 日誌、限流與稽核紀錄看到的 IP 全是代理的 IP |
| `EmailSettings` | 要寄信就設 `Smtp` 與 `PublicBaseUrl` | 忘記密碼和告警信都不會寄 |
| `AutoMapper:LicenseKey` | 確認商用授權 | 啟動時日誌會印授權警告 |

設定值怎麼決定，見 `docs/guides/腳手架開發指引.md` §4.6；完整上線檢查見 `docs/operations/正式部署與安全檢查清單.md`。

### 8.4 長期：維持品質

- **每次異動，版本號最後一碼 +1**（例：`1.0.0 → 1.0.1`），寫在 `appsettings.json` 的 `SystemVersion`。

- **定期看腳手架有沒有重要修正**（見第 10 節）。

### 9.1 「專案項目」模組

- How 刪：它牽動的地方不少，建議交給 AI 並請它先列出清單：

```text
請幫我完整移除「專案項目」範例模組（路由 /projects）。
先列出會牽動的所有檔案與登記處，至少包含：資料模型與 migration、Business 服務、
```

### 9.2 AI 功能

- **不用 AI**：`AiSettings:ApiKey` 留空就是關閉，按鈕會停用並說明原因。不需要改程式。
- **連選單都不想看到**：「系統管理 → AI 管理」底下的 AI 提示詞、AI 對話紀錄、Token 用量頁還是會出現在選單（0.9.113 起）。可以請 AI 從 `Menu.json` 移除整個群組並同步權限對照與操作說明。
- **AI 對話紀錄**：會保存送給 AI 的完整內容。不需要時把 `AiCallLogSettings:Enabled` 設 `false`。

| 功能 | 開啟方式 |
|---|---|

## 10. 複刻後的版本控制與腳手架更新

### 10.1 Why：腳手架會繼續更新，但你的專案不會自己知道

腳手架會持續修安全漏洞、補守門測試、改善慣例。
但**已經複刻出去的專案和腳手架之間沒有任何自動連結**，目前也沒有自動升級的機制。
不主動追，你的專案就會停在複刻當天的版本。

### 10.2 How：建議的做法

**① 記下你從哪一版複刻**

在第一個 commit 訊息、`docs/changelog/` 第一篇、或 `readme.md` 寫明：「從 NET10-Blazor-Starter <腳手架版本> 複刻」。腳手架版本是**複刻前**腳手架 `appsettings.json` 的 `SystemVersion`（例如 `0.9.87`）—— 複刻後新專案已重設成 `1.0.0`，查不到了，請先記下來。
這是日後比對的起點。

**② 把腳手架加成第二個遠端**

```powershell
git remote add scaffold <腳手架的 Git 網址>
git fetch scaffold
```

- `origin` 是你自己的專案，`scaffold` 是腳手架。
- ⚠️ **不要直接 merge 腳手架**：兩邊的代號不同（`CustomerHelpAgent` vs `Acme.Erp`），直接合併會產生大量衝突。

**③ 定期挑選需要的修正**

1. 看腳手架的 `docs/changelog/`，找出你複刻之後的新紀錄。
2. 挑出跟你有關的（特別是安全性修正、守門測試）。
3. 照 changelog 說明手動套用到你的專案，或請 AI 幫忙：

```text
腳手架有一筆更新：<貼上那篇 changelog 的內容或連結>。
請評估這個修正是否適用於本專案，若適用，列出要改的檔案並說明差異。
注意本專案的代號是 Acme.Erp，不是 CustomerHelpAgent。
```

**When**：建議每個月或每季看一次；有安全性修正時立即看。

## 11. 常見卡關問題

| 症狀 | 原因 | 解法 |
|---|---|---|
| 腳本一開始就停：`dotnet-ef is required` | 沒安裝 dotnet-ef | `dotnet tool install --global dotnet-ef`，重開 PowerShell 再跑 |
| 腳本一開始就停：`Source is not the latest version` | 腳手架資料夾有未提交的修改或未追蹤檔、不在 `main`、或落後 origin（0.9.116 起會檢查） | 看上方警告列出的問題：`git switch main`、`git pull`、把修改 commit 或 stash 後重跑；確定要照現狀複刻才加 `-AllowUnsyncedSource`（見 7.6） |
| 腳本停在：`Destination already exists` | 目標資料夾已存在 | 換一個路徑，或加 `-Force`（⚠️ 會刪掉原資料夾全部內容） |
| 腳本說代號不符合格式 | 代號有連字號、空白、中文，或數字開頭 | 改成像 `Acme.Erp`、`HrPortal` 這樣的名字 |
| 腳本卡在 `dotnet restore` 或 `migrations add` | 網路下載套件失敗，或 SDK 版本不對 | 檢查網路與 `dotnet --info`；腳本會印出可以手動重跑的指令 |
| 腳本最後一行出現亂碼 | 很舊的腳手架副本用 Windows PowerShell 5.1 執行 | 改用 `pwsh`；純顯示問題，不影響結果 |
| 腳本印出五條警告 | 正常現象 | 不用處理，見 7.6 |
| 瀏覽器連不上或一直重導 | 用了 `http` profile | 改用 `--launch-profile https` |
| 瀏覽器說憑證不受信任 | 沒信任開發憑證 | `dotnet dev-certs https --trust` |
| 連接埠被占用 | 其他程式用了同一個埠 | 改 `Properties/launchSettings.json` 的 `applicationUrl` |
| 畫面完全沒有樣式 | 手動改名時漏改 `App.razor` 的 `*.Web.styles.css` | 改成 `<新代號>.Web.styles.css`（用腳本不會發生） |
| 一個小警告就建置失敗 | 刻意開啟「警告視為錯誤」 | 修掉警告，不要關掉這個設定 |
| 在畫面上改了 `support` 的密碼，重啟又變回去 | 系統每次啟動會用設定檔的值覆寫（刻意的救援設計） | 改 `BootstrapSettings:SupportPassword` 設定值 |
| 正式環境啟動失敗 | 啟動安全檢查擋下：JWT 金鑰、管理員密碼、Swagger 設定、寄信設定 | 錯誤訊息會說是哪一項，照 8.3 用環境變數設定 |
| User Secrets 設了沒效 | 環境不是 Development，或在錯的資料夾執行 | 確認 `ASPNETCORE_ENVIRONMENT=Development`；用 `dotnet user-secrets list --project <Web csproj>` 檢查 |
| 文件編碼檢查失敗 | 某份 `docs/` 的 Markdown 不是 UTF-8 含 BOM | 用編輯器以「UTF-8 with BOM」重存；PowerShell 寫檔用 `-Encoding utf8BOM` |
| 想把資料庫清空重來 | — | 先停止程式，刪除 `C:\temp\Acme.Erp\DB\BackendDB.db`，再重新執行 |

## 12. 常見問題 FAQ

第 11 節是「出錯了怎麼修」；這一節回答「能不能這樣做、要注意什麼」。每題先給結論，再說明理由與出處。

### 12.1 技術選擇與限制

#### Q1. 可以把資料庫換成 SQL Server 或 PostgreSQL 嗎？

**可以，但不是改設定就好，成本「中到大」。** 本系統只支援 SQLite，SQL Server 軌道在 0.4.24 已移除。
要換的話：換 NuGet provider、改 `AddConfiguredDatabase` 裡的 `UseSqlite`、**整套 migration 重新產生**（不同資料庫之間不通用），
還要重新檢查字串比較與定序（SQLite 的 `lower()` 只處理英文字母）。系統備份用的是 SQLite 專屬的 `VACUUM INTO`，也要一起改寫。
這是本腳手架「最可能需要換掉的一項」，如果一開始就知道會有大量同時寫入，建議在複刻後馬上評估。

出處：[腳手架開發指引 §3.3](../guides/腳手架開發指引.md#33-ef-core--sqlite)、[§11.5](../guides/腳手架開發指引.md#115-資料層)、[資料模型與資料庫](../architecture/資料模型與資料庫.md)

#### Q2. 介面可以做多國語言切換嗎？

**目前不行，只做到元件層級。** Ant Design 元件（日期選擇器等）會依瀏覽器語言顯示，但專案裡沒有任何語系資源檔（`.resx`），
介面文字都直接寫成繁體中文，連「預設角色」這類存在資料庫裡的值也是中文。要補做的成本是「大」。

出處：[架構總覽 §6 語系與本地化](../architecture/架構總覽.md)、[腳手架開發指引 §3.14](../guides/腳手架開發指引.md#314-多語系)、[§11.6](../guides/腳手架開發指引.md#116-真正的多語系)

#### Q3. 可以做成一套系統賣給很多家公司（多租戶 SaaS）嗎？

**不建議。** 目前的「團隊分權」是同一家公司內的部門模型，不是公司與公司之間的資料隔離。
多租戶「不是加功能，是改架構」：每一個查詢都要帶租戶條件，成本「大」，而且要在專案一開始就決定，不能事後補。

出處：[腳手架開發指引 §11.5](../guides/腳手架開發指引.md#115-資料層)、本文 [3.2](#32-不適合)

#### Q4. 可以把 Ant Design Blazor 換成別的 UI 套件嗎？

**幾乎不要換。** 全站樣式已經跟它產生的 HTML 結構綁在一起（浮層樣式在 `OverlayStyles.razor`、頁內樣式在 `theme.css`），
確認窗、通知、表格排序等共用元件也都包著它。換掉等於重做整個介面層。

出處：[腳手架開發指引 §3.2](../guides/腳手架開發指引.md#32-antdesign-blazor)、[§14.2](../guides/腳手架開發指引.md#142-這些事情不要自己發明)

#### Q5. 可以部署在 Linux 或 Docker 嗎？

**目前沒有現成支援。** 專案裡沒有 Dockerfile，預設的檔案路徑都是 Windows 的 `C:\temp\...`，
文件化的部署目標是 Windows ＋ IIS（或 Kestrel）。要容器化，至少要把十一個外部路徑與 `NLog:BasePath` 改成掛載的磁碟區，
SQLite 資料庫也要放在持久保存的位置；PDF 用的中文字型已經內嵌，這部分不用擔心。

出處：[腳手架開發指引 §12.2](../guides/腳手架開發指引.md#122-環境)、[§11.3](../guides/腳手架開發指引.md#113-維運與部署)、[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)

#### Q6. 使用者變多、想開多台主機分流，怎麼辦？

**先確認規模：本腳手架的定位是數十到數百位使用者。** 幾個要知道的事：

- Blazor Server 每個瀏覽器分頁都佔一條即時連線與一份伺服器記憶體，人數上去，伺服器負擔就上去。
- 把快取切成 Redis **不等於**能多台主機：SQLite 資料庫無法讓多台主機共用。真的要多台，要先換資料庫（Q1）。
- 多台主機時，登入用的 Data Protection 金鑰資料夾一定要共用，否則使用者會一直被登出。
- 排程作業有防重複機制，同一個時段只會由一個行程執行。

出處：[腳手架開發指引 §3.1](../guides/腳手架開發指引.md#31-blazor-server)、[§3.3](../guides/腳手架開發指引.md#33-ef-core--sqlite)、[§3.8](../guides/腳手架開發指引.md#38-分散式快取memoryredis)、[正式部署與安全檢查清單](../operations/正式部署與安全檢查清單.md)

### 12.2 複刻與跟上更新

#### Q7. 用腳本複刻出來的，是腳手架的最新版嗎？

**是「你電腦上那份腳手架資料夾的現況」，不一定是最新版。** 腳本複製的是磁碟上的檔案，不是 git 上的某個版本。
0.9.116 起，腳本開跑前會先 `git fetch`，確認工作目錄乾淨、在 `main`、沒有落後 origin，不符合就中止；
所以只要腳本順利跑完、沒有加 `-AllowUnsyncedSource`，複刻出來的就是 origin 上的最新版。
如果腳手架是下載的 zip（不是 git 資料夾），腳本無法比對，只會警告，請自己確認版本。

出處：本文 [7.5](#75-腳本做了什麼白話版)、[7.6](#76-跑完的畫面怎麼看)

#### Q8. 怎麼知道自己是從腳手架哪一版複刻的？

**複刻「之前」看腳手架的 `appsettings.json` 裡的 `SystemSettings:SystemInformation:SystemVersion`**，或登入後從右上角選單開「關於」視窗。
複刻後新專案的版本會重設為 `1.0.0`，就查不到了，所以請先記下來，寫進第一個 commit 訊息。

出處：本文 [10.2](#102-how建議的做法)

#### Q9. 可以從衍生專案再複刻出另一個專案嗎？

**可以。** 衍生專案裡的腳本，預設代號已經是它自己的名字，連接埠也會從它的 `launchSettings.json` 讀出來再換新，
所以直接在衍生專案的根目錄執行就好，不用填 `-SourceProjectName`。

出處：本文 [7.3](#73-參數)

#### Q10. 複刻後想改專案代號，怎麼辦？

**沒有專用的改名工具，要照手動步驟改，所以代號請一開始就想清楚。** 手動步驟見 VS Code 上手指南 §8.2～§8.3。
⚠️ 已上線的系統改代號，登入 Cookie 的加密名稱會跟著變，所有人都要重新登入。

出處：[VS Code 開發環境與新專案上手指南 §8.2](../guides/VS%20Code%20開發環境與新專案上手指南.md#82-手動更名步驟)、本文 [7.5](#75-腳本做了什麼白話版)

#### Q11. 腳手架更新了，我的專案會自動跟上嗎？

**不會。** 複刻出去的專案與腳手架之間沒有任何自動連結，也沒有升級腳本（曾經規劃，2026/10/04 決定不實作）。
請照第 10 節：記下複刻版本、把腳手架加成 `scaffold` 遠端、定期看 changelog 挑修正手動套用。

出處：本文 [第 10 節](#10-複刻後的版本控制與腳手架更新)

### 12.3 功能取捨與授權費用

#### Q12. 我們不打算用 AI，系統會不會壞？

**不會。** `AiSettings:ApiKey` 留空就是關閉，沒有另外的開關；AI 相關按鈕會停用並說明原因。
連選單都不想看到的話，見 [9.2](#92-ai-功能)。

#### Q13. 哪些功能可以關掉？怎麼關？

| 功能 | 怎麼關 | 出貨預設 |
|---|---|---|
| AI 分析 | `AiSettings:ApiKey` 留空 | 關 |
| AI 對話紀錄 | `AiCallLogSettings:Enabled=false` | 開 |
| Google 登入 | `GoogleOAuthSettings:Enabled=false` | 關 |
| 寄信 | `EmailSettings:Provider=None` | 關 |
| 例外告警信 | `ExceptionAlertSettings:Recipients` 留空 | 關 |
| Redis 快取 | `CacheSettings:Provider=Memory` | 用記憶體 |
| 排程作業 | 全部：`ScheduledJobSettings:Enabled=false`；單一作業：在 `/scheduled-jobs` 停用 | 開 |
| Swagger（正式環境） | `Swagger:EnabledInProduction=false`（正式環境一定要明確寫出 true 或 false） | 關 |
| 強制兩步驟驗證 | `TwoFactorSettings:RequireForAdmins=false`，角色不勾「需要兩步驟驗證」 | 不強制 |

出處：`src/CustomerHelpAgent/CustomerHelpAgent.Web/appsettings.json`、[排程作業 PRD](../prd/排程作業-prd.md)、本文 [9.3](#93-其他出貨時就是關閉的功能)

#### Q14. 正式商用，要注意哪些第三方授權？

**最需要注意的是 AutoMapper。** 16.x 是商業授權版本：沒填 `AutoMapper:LicenseKey` 時程式照樣能跑，但啟動日誌會印出授權警告，
說明開發與測試可以用、正式環境需要授權版。上線前請確認授權，或評估改用免費的替代方案（見開發指引 §3.6）。

repo 內有記載授權的其他項目：

| 項目 | 授權 |
|---|---|
| Noto Sans TC（PDF 內嵌中文字型） | SIL Open Font License 1.1，允許內嵌與重新發行 |
| PDFsharp／MigraDoc | MIT |
| ClosedXML | MIT；相依的 SixLabors.Fonts 目前是 1.0.0（Apache-2.0），2.x 起改為 Split License，升級前要確認 |

MailKit、QRCoder、Ant Design Blazor、NLog 等其他套件的授權，**repo 內沒有記載**，請自行到各套件官方確認。
腳手架本身是內部樣板，依團隊約定條款使用（`readme.md` §11）。

出處：[腳手架開發指引 §3.6](../guides/腳手架開發指引.md#36-automapper)、[通用匯出 PRD](../prd/通用匯出-prd.md)、`readme.md` §11

#### Q15. AI 費用怎麼控制？

**用「AI 用量上限」設金額天花板，用「Token 用量」頁看花費。**

- 系統參數 → AI 用量：全系統與每個人的每日、每月新台幣上限，四個值預設都是 `0`（不限制）。到 80% 與 100% 會通知；達到上限就不再送出 AI 呼叫。
- `/token-usage`：每次呼叫用了多少 token、花多少錢，有趨勢圖與匯出。
- 費率表在 `appsettings.json` 的 `AiPricingSettings`；模型調價或改用新模型時，照 [AI 模型計費更新指南](../operations/AI模型計費更新指南.md) 更新。⚠️ 找不到費率的模型會記成「未定價」，它的花費以 0 計入上限，等於不受上限管控。

出處：[AI 用量配額 PRD](../prd/AI用量配額-prd.md)

### 12.4 開發與 AI 協作

#### Q16. 不用 AI 助手，也能用這份腳手架開發嗎？

**可以。** 文件、腳本與守門測試對人一樣有效：新模組用 `New-CrudModule.ps1` 產生，動手前讀《開發慣例與限制速查》，
提交前跑品質關卡（VS Code 可直接執行 `quality-gate` 任務）。AI 只是讓「照慣例寫程式」這件事更快。

#### Q17. 守門測試失敗擋住我，怎麼辦？

**先讀失敗訊息，照著改。** 守門測試的訊息通常寫著「為什麼有這條規則、該怎麼改」，
每一條都對應一次實際踩過、而且「不會報錯只會默默壞掉」的坑。**不要刪掉或略過測試**，也不要叫 AI 這樣做。
有哪些守門測試、各自擋什麼，見測試指南。

出處：[測試指南 §2](../guides/測試指南.md#2-測試類別與涵蓋範圍)、[腳手架開發指引 §14.4](../guides/腳手架開發指引.md#144-為什麼慣例這麼多)

#### Q18. 為什麼每次改東西都要加版號、寫 changelog？

**為了日後查得到「哪一版改了什麼」**：使用者回報問題時，從「關於」視窗的版號就能對到當時的程式；
衍生專案要跟上腳手架時，也是靠 changelog 挑修正。
⚠️ 這兩件事**目前沒有任何測試或品質關卡會檢查**，完全靠紀律，所以請把它們寫進你給 AI 的完工檢查要求裡。

出處：[維護規範 §1](../operations/維護規範.md#1-規範一每次更新必須-bump-版本)、[§2](../operations/維護規範.md#2-規範二影響到既有文件就必須同步更新)

#### Q19. 哪些地方不要自己發明新做法？

**新模組、對話窗、確認窗、通知、狀態徽章、顏色、表格樣式、圖示、資料存取、匯出、頁面說明、呼叫 AI，都有指定的寫法。**
例如確認窗一律用 `ConfirmDialog`、顏色一律用 `var(--app-*)`、資料存取一律用 `IDbContextFactory`。完整對照表在開發指引 §14.2。

出處：[腳手架開發指引 §14.2](../guides/腳手架開發指引.md#142-這些事情不要自己發明)

### 12.5 用 Claude Code／Codex 開發要注意什麼

AI 助手寫程式很快，但它**不知道你沒告訴它的事**，也常常「說完成了，其實沒做對」。下面幾題是避免做出不好或錯誤系統的重點。

#### Q20. `CLAUDE.md` 和 `AGENTS.md` 有什麼差別？要怎麼維護？

**內容相同，只是給不同工具讀。** Claude Code 讀 `CLAUDE.md`，Codex 等工具讀 `AGENTS.md`；兩份除了標題以外一模一樣。

- 改了其中一份，**一定要同步另一份**。目前沒有任何自動檢查會發現兩份不一致（過去就曾經漏同步過）。
- `src/CustomerHelpAgent/.github/copilot-instructions.md` 是給 GitHub Copilot 的，**只有通用的行為準則，沒有專案的不變量**；用 Copilot 的話，要自己補上或請它先讀 `CLAUDE.md`。

出處：[腳手架開發指引 §14.1](../guides/腳手架開發指引.md#141-給-ai-的閱讀順序)

#### Q21. 怎麼下指令，AI 比較不會做錯？

- **一次只做一件事。** 一次要求太多，AI 容易漏掉其中幾項。
- **先叫它讀文件、說明打算怎麼做，你確認後才動手。** Claude Code 可以先用計畫模式（plan mode），只讀不改。
- **說清楚驗收條件**，例如「做完跑品質關卡、要通過 `PageHelpCatalogTests`」，不要只說「做好」。
- **指名要它參考的既有做法**，例如「照 `/projects` 頁的結構」、「用 `New-CrudModule.ps1` 產生」。
- 第 6.4 節的提示詞可以直接照抄。

#### Q22. AI 說「完成了」，我要檢查什麼？

1. **品質關卡**：`pwsh ./scripts/Invoke-QualityGate.ps1` 最後一行要是 `QUALITY GATE PASSED`。
2. **自己打開畫面看**：品質關卡對「畫面好不好看」幾乎完全無感。至少看 640／768／1024／1800px 四種寬度。
3. **看 diff**：有沒有改到不相干的程式、有沒有刪掉或改弱測試。
4. **收尾有沒有做**：版號 +1、changelog、受影響的文件、頁面的操作說明。

出處：[腳手架開發指引 §14.3](../guides/腳手架開發指引.md#143-完工驗收清單)

#### Q23. 哪些事不要交給 AI 自己決定？

| 事情 | 為什麼 |
|---|---|
| commit、push | commit 是你確認過、願意負責的時間點；`CLAUDE.md` 明定不可自動 commit |
| 刪除或略過測試、關掉「警告視為錯誤」 | 等於拆掉防線，問題會在上線後才出現 |
| 把密碼、金鑰、正式環境資料貼進對話 | 機密一律放 User Secrets 或環境變數，不要出現在對話或程式碼裡 |
| 決定正式環境的設定值 | 保存天數、登入效期、上限金額這些是業務與法規決策，讓 AI 提建議、由你決定（見提示詞 ④） |
| 執行刪除資料、`git reset --hard`、`-Force` 這類無法復原的指令 | 先看清楚對象，再自己決定要不要執行 |

#### Q24. AI 改壞了，或越改越亂，怎麼辦？

- **小步 commit**：每完成一件確認過的事就 commit，壞了才能乾淨地退回上一步。
- **請它先找根本原因再修**，不要讓它「再試一次看看」地一直疊補丁。
- 對話太長、它開始忘記前面的規則時，**開一個新對話**，重新說明目標並請它重讀相關文件。
- 真的改亂了，用 git 退回上一個好的版本，比叫 AI 修回來更快也更可靠。

#### Q25. 怎麼讓 AI 記得我們專案自己的規則？

**寫進 `CLAUDE.md` 和 `AGENTS.md`（兩份都要寫）。** AI 每次開始工作都會先讀它們。
適合寫進去的是「業務名詞」與「本專案特有的規則」，例如「本系統的『單位』指的是 Team；金額一律以新台幣整數儲存」。
細節比較多的規則寫成 `docs/` 底下的文件，再在 `CLAUDE.md` 指路，不要把入口檔寫成上千行。

出處：本文 [8.2](#82-第一週變成你的系統)

依類別排列。粗體是名詞本身，後面是白話解釋；括號裡的節號是本文提到它的地方。

### 腳手架與專案

| 名詞 | 白話解釋 |
|---|---|
| **腳手架（Scaffold／Starter）** | 蓋房子前先搭好的鷹架。在軟體裡指「一套已經能跑、把共通功能先做好的專案骨架」，你在上面蓋自己的業務功能 |
| **複刻／衍生專案** | 用腳手架複製出來、改成自己名字的新專案。本文的例子叫 `Acme.Erp`（第 7 節） |

| **命名空間（namespace）** | C# 程式碼的「姓氏」，用來分組、避免同名衝突。複刻後會從 `CustomerHelpAgent.*` 換成 `Acme.Erp.*` |
| **方案（`.slnx`）與專案（`.csproj`）** | 專案是一個可以建置的程式單位；方案把七個專案綁在一起，一次建置（7.7） |
| **分層（Web → Business → AccessDatas）** | 畫面與 API 放 Web、商業邏輯放 Business、資料庫存取放 AccessDatas，只能由上往下呼叫，不可反過來（7.7） |
| **CRUD** | Create／Read／Update／Delete，新增、查詢、修改、刪除，一般資料維護頁的四個基本動作（4.3） |
| **範例模組** | 腳手架附的「專案項目」頁，示範一個標準模組長什麼樣（9.1） |

### 平台與技術

| 名詞 | 白話解釋 |
|---|---|
| **.NET 10** | 微軟的程式開發平台，本專案用 C# 語言撰寫 |
| **Blazor Server** | 用 C# 寫網頁畫面的技術。畫面邏輯跑在伺服器上，瀏覽器和伺服器之間保持一條即時連線 |
| **SignalR／Circuit（連線）** | Blazor Server 用來保持即時連線的技術；每個瀏覽器分頁就是一條連線，伺服器替它保留一份畫面狀態，所以人數越多伺服器負擔越重（Q6） |
| **Razor 元件（`.razor`）** | Blazor 的畫面檔，HTML 和 C# 寫在一起 |
| **Ant Design Blazor** | 本專案使用的 UI 元件庫，提供表格、表單、對話窗等現成元件（Q4） |
| **相依性注入（DI）** | 程式需要某個服務時，不自己 `new`，而是由系統在啟動時統一登記、需要時自動提供。換實作只要改登記的地方 |
| **IIS／Kestrel** | 兩種網頁伺服器。Kestrel 是 .NET 內建的；IIS 是 Windows Server 的網頁伺服器，本專案文件化的部署目標（Q5） |
| **NuGet 套件** | .NET 的第三方程式庫；本專案所有套件版本集中寫在 `Directory.Packages.props`（4.11） |

### 資料與資料庫

| 名詞 | 白話解釋 |
|---|---|
| **SQLite** | 一種「單一檔案」的資料庫，不用另外安裝資料庫伺服器。本系統只支援 SQLite（Q1） |
| **EF Core** | 用 C# 類別操作資料庫的工具，不必手寫 SQL |
| **Migration（遷移）** | 「資料表結構的變更紀錄」。改了資料模型就要產生一份，系統啟動時會自動套用；複刻時會重建成一份 `Init`（7.5） |
| **Seed（種子資料）** | 系統第一次啟動時自動寫入的預設資料，例如預設角色與 `support` 帳號（4.1） |
| **軟刪除** | 按「刪除」只是標記為已刪除、資料還在，可以還原；超過保留天數才真的刪掉（4.3） |
| **樂觀並行（版本號）** | 兩個人同時編輯同一筆資料時，後存檔的人會被告知「資料已被別人改過」，而不是默默蓋掉對方的修改 |
| **`VACUUM INTO`** | SQLite 的指令，在系統運作中產生一份一致的資料庫副本；系統備份就是用它（4.8、Q1） |

### 帳號、權限與安全

| 名詞 | 白話解釋 |
|---|---|
| **角色權限（RBAC）** | Role-Based Access Control。先定義「角色」能做哪些事，再把角色指派給使用者，而不是一個一個人設定（4.2） |
| **動作級權限** | 不只控制「能不能進這一頁」，還控制「能不能新增、修改、刪除、匯出」；沒權限時 API 回 403（4.2） |
| **團隊資料分權** | 非管理員只看得到公開或同團隊的紀錄；上層部門看得到下屬部門的資料（4.2） |
| **Cookie 驗證** | 網頁登入後，瀏覽器保存一張加密的「通行證」（Cookie），之後每次操作都帶著它證明身分（4.1） |
| **JWT／Bearer token** | 給程式呼叫 Web API 用的通行證，放在請求標頭裡；跟網頁的 Cookie 登入分開（4.7） |
| **兩步驟驗證（TOTP）** | 密碼之外，再輸入手機驗證器 App 每 30 秒變一次的 6 位數驗證碼（4.1） |
| **PBKDF2 雜湊** | 一種把密碼轉成無法還原的亂碼再存的方法，資料庫外洩也看不到原始密碼（4.1） |
| **Data Protection 金鑰** | ASP.NET Core 用來加密登入 Cookie 的金鑰，存在固定資料夾；金鑰不見，全站使用者會被登出（4.8、Q6） |
| **User Secrets** | 開發機上專門放密碼、金鑰的地方，存在你的使用者資料夾裡，**不會**被 commit 進 Git（8.1） |
| **環境變數** | 作業系統層級的設定值。正式環境的機密（例如 `JwtSettings__SigningKey`）用它設定，不寫進設定檔（8.3） |
| **Development／Production 環境** | 開發環境與正式環境。部分檢查只在 Production 執行；⚠️ IIS 沒有指定環境時預設就是 Production |
| **啟動安全檢查** | 正式環境啟動時，發現預設密碼、佔位金鑰、設定不完整就拒絕啟動（4.10、8.3） |
| **速率限制** | 限制每個呼叫端每分鐘最多呼叫幾次，防止被灌爆或暴力猜密碼（4.7） |
| **CORS** | 瀏覽器的跨網站存取規則；決定其他網站的網頁能不能呼叫本系統的 API，預設不開放 |
| **反向代理** | 擋在本系統前面轉送請求的伺服器（例如 IIS ARR、Nginx）；有的話要設定 `ForwardedHeaders`，否則看到的 IP 都是代理的（8.3） |

### Web API

| 名詞 | 白話解釋 |
|---|---|
| **Web API** | 給其他系統或程式呼叫的介面，回傳 JSON 資料而不是網頁（4.7） |
| **`ApiResult<T>`／`PagedResult<T>`** | 本專案所有 API 統一的回應外層格式；分頁查詢再包一層 `PagedResult<T>`（4.7） |
| **DTO** | Data Transfer Object，專門給 API 傳資料用的類別，不直接把資料庫的結構對外公開 |
| **Swagger** | 自動產生的 API 說明頁（`/swagger`），可以直接在網頁上試呼叫（4.7） |
| **版本化路由（`/api/v1/...`）** | API 網址帶版本號，日後改版時舊的呼叫端不會壞（4.7） |

| 名詞 | 白話解釋 |
|---|---|
| **日誌（NLog）** | 系統運作過程的文字紀錄；本專案用 NLog 寫到檔案，可在 `/logs` 查詢（4.5） |

### 開發流程與品質

| 名詞 | 白話解釋 |
|---|---|
| **Git／commit／remote** | Git 是版本控制工具；commit 是一次存檔紀錄；remote 是遠端的儲存庫，例如 `origin`（你自己的專案）、`scaffold`（腳手架）（第 10 節） |
| **origin／預設分支（main）** | `origin` 是 Git 對「主要遠端」的慣用名稱；預設分支通常叫 `main`，代表目前正式的最新版本（7.5、Q7） |
| **工作目錄乾淨** | 電腦上的檔案跟最後一次 commit 完全一樣，沒有未提交的修改或多出來的檔案（`git status` 沒有輸出）（7.5） |
| **diff** | 兩個版本之間的差異，也就是「這次改了哪些行」（6.3） |
| **版本號（Major.Minor.Patch）** | 例如 `1.0.3`；本專案規定每次異動最後一碼 Patch +1（8.4） |

| **PRD** | Product Requirements Document，產品需求文件，說明某個功能做什麼、規則是什麼（5.1） |

| **品質關卡** | `Invoke-QualityGate.ps1` 一行指令跑完建置、格式、測試、文件編碼、弱點掃描（6.5） |
| **警告視為錯誤** | 編譯時任何警告都會讓建置失敗，避免小問題越積越多（4.11） |
| **UTF-8 BOM** | 檔案開頭的三個位元組標記，讓 Windows 工具正確辨認 UTF-8 中文；本專案的 `.md` 文件與匯出的 CSV 都要有（第 11 節） |
| **CI** | Continuous Integration，每次推送程式碼時自動建置與測試的機制；本腳手架目前沒有（7.8） |
| **Vibe coding** | 用自然語言描述需求，讓 AI 助手（例如 Claude Code）幫你寫程式，你負責說清楚要什麼、檢查結果（第 6 節） |

| **計畫模式（plan mode）** | Claude Code 的模式：只讀檔案、提出計畫，經你同意才開始修改（Q21） |
