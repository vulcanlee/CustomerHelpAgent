# 系統健康監控

- 文件版本：1.9
- 文件狀態：已實作
- 現行系統版本：1.0.0
- 首次實作版本：0.1.68
- 最後核對日期：2026/10/23

## 文件目的

說明本專案的健康檢查端點與人工巡檢頁面，讓維運人員可以快速判斷網站、API、資料庫、日誌、身分驗證、檔案系統、主機資源、安全設定、LLM API、快取服務、AI 計費表、寄信服務、日誌管線與排程作業是否正常。

---

## 1. 部署探針

系統保留 ASP.NET Core Health Checks 端點：

| 路徑 | 用途 | 說明 |
|------|------|------|
| `/health/live` | Liveness | 檢查應用程式處理程序是否仍存活（tag `live`，`self` 檢查恆為 Healthy）。 |
| `/health/ready` | Readiness | 檢查資料庫連線是否可用，供部署平台判斷是否可接流量（tag `ready`，`DatabaseHealthCheck`）。 |

兩個端點於 `Program.cs` 以 `MapHealthChecks` 對應，檢查項目註冊在 `ServiceCollectionExtensions.AddConfiguredHealthChecks`，皆可匿名存取。

這兩個端點只提供簡短狀態，適合部署平台、反向代理或外部監控系統輪詢，不提供詳細診斷資料。

## 2. 人工巡檢頁

管理員可直接開啟：

```text
/system-health
```

此頁自 0.9.22 起列於左側選單，0.9.113 起位置為「系統管理 → 監控與診斷 → 系統健康監控」（`Menu.json` id 65，圖示 `monitor_heart`）。
必須先以 Cookie 登入，且目前使用者必須是管理員（`IsAdmin=true`）才可查看 —— 選單只是入口，
把關的仍是頁面 `OnInitializedAsync` 內的 `CheckIsAdmin()`；非管理員不會看到這個選單項，直接輸入網址會看到「您沒有權限檢視系統健康監控。」，
並留下一筆 `Permission.Denied` 稽核（0.9.78 起）。

頁面內容包含：

- 整體健康百分比、最後檢查時間。
- 整體紅 / 黃 / 綠燈號與狀態文字（正常／警示／異常）。
- 每個檢查項目的紅 / 黃 / 綠燈號、分類、權重、狀態、證據與失敗訊息。
- 「寄信測試」區塊（0.9.59 起）：輸入收件者、按「寄出測試信」同步寄一封測試信，當場顯示成敗；
  寄信未啟用（`Provider=None`）時停用。每次寄送都寫一筆稽核 `Email.Test`（不含收件者）。
- 「站內通知測試」區塊（0.9.122 起）：按「發送測試通知」發一則標題為「測試通知」的站內通知給**全體管理員**（啟用中、勾選「管理員」的帳號），
  確認右上角鈴鐺與即時更新正常；**不寄信**（寄信另用上一個區塊）。通知連結回 `/system-health`，不設 `SourceKey`，可以重複測。
  開著的其他頁面會立即收到，多台主機時其他主機上的頁面最慢約 1 分鐘。成功時顯示「已發送給 N 位管理員」；沒有可收的管理員或發送失敗時顯示原因。
  每次都寫一筆稽核 `Notification.Test`（Detail 為 `recipients=N`，失敗另加 `; failed`）。實作在 `Health/NotificationTestService.cs`。
- 頁尾「最近 24 小時警告以上日誌」列出等級 WARN 以上（WARN／ERROR／FATAL）的日誌（0.9.111 起，取代原本「今日日誌檔最後 100 筆」）：表格上方顯示實際查詢的時間區間與筆數；沿用日誌檢視的 `ILogQueryService.QueryAsync`（`MinimumLevel = Warn`、`Take = LogQueryRequest.MaxTake` 10,000），會跨到昨天的日誌檔；以表格呈現（時間／等級／記錄器／訊息／TraceId），新到舊、每頁 20 筆在畫面上分頁，展開列顯示深色等寬原文。達 10,000 筆時提示改到日誌檢視查詢。此查詢與健康報告分開，讀取失敗只在本區顯示原因，不影響檢查結果與分數。
- 頂欄頁名旁的「操作說明」按鈕（0.9.66 起），內容為 `Datas/Help/system-health.md`。

報告在頁面初始化時產生一次（`ISystemHealthService.GetReportAsync`），要重新檢查請重新整理頁面 —— 每次都會重跑全部 14 項，包含會產生費用的 LLM API 檢查（見 §4.1）。

## 3. 燈號與分數

整體健康分數採加權計算：

| 狀態 | 單項得分 | 燈號 |
|------|----------|------|
| Healthy | 取得完整權重 | 綠燈 |
| Degraded | 取得一半權重 | 黃燈 |
| Unhealthy | 不得分 | 紅燈 |

分數＝`round(得分 ÷ 總權重 × 100)`（`SystemHealthScoreCalculator`）。整體燈號門檻：

| 分數 | 燈號 | 說明 |
|------|------|------|
| `>= 90` | 綠燈 | 系統健康。 |
| `70-89` | 黃燈 | 系統可運作，但有項目需要關注。 |
| `< 70` | 紅燈 | 系統健康程度不足，應立即檢查失敗項目與日誌。 |

## 4. 檢查項目

權重合計 **150**（0.9.24 起由 100 增為 125；0.9.59 加入「寄信服務」增為 135；0.9.79 加入「日誌管線」增為 145；0.9.96 加入「排程作業」增為 150）。分數是「得分／總權重」，
總權重由項目自行加總，不是固定 100 —— 新增項目會等比稀釋既有項目的佔比。

| 項目 | 權重 | 主要證據 |
|------|------|----------|
| 網站 / 應用程式 | 10 | 環境、版本、啟動時間、運作時間。`SystemVersion` 未設定為黃燈。 |
| API | 10 | Controller action 數量、Swagger 啟用狀態。找不到任何 action 為紅燈。 |
| 資料庫 | 25 | Provider（固定 SQLite）、連線狀態、待套用 migration 數量。連不上或拋例外為紅燈，仍有待套用 migration 為黃燈。 |
| 日誌 | 15 | NLog 目錄、今日 log 檔、最後 100 筆讀取狀態。目錄不可寫入為紅燈；今日檔不存在或沒有內容為黃燈。 |
| 身分驗證 | 15 | Cookie scheme、JWT bearer、Issuer/Audience 是否設定、SigningKey 長度。設定不完整（含 SigningKey 不足 32 字元）或 Production 仍用範本佔位金鑰為紅燈。 |
| 檔案系統 | 10 | Database、Download、Upload、ProjectFile 目錄存在與可寫入。任一目錄不存在或不可寫入為紅燈。 |
| 主機資源 | 5 | Process working set、目前磁碟可用空間。磁碟剩不到 1 GB 為黃燈。 |
| 安全設定 | 10 | Swagger in Production、CORS origins、`Security.ReturnExceptionDetails`。Production 開啟 Swagger 或回傳例外細節為黃燈。 |
| LLM API | 10 | 端點主機、模型名稱、往返耗時。**每次載入都會真的呼叫一次**（見下方警告）。AI 未設定為黃燈，呼叫失敗為紅燈。 |
| 快取服務 | 10 | Provider、InstanceName、Redis 連線字串是否設定、寫入後讀回的往返耗時（上限 5 秒）。Provider 打錯字或讀寫拋例外為紅燈，讀回值不符為黃燈。 |
| AI 計費表 | 5 | 目前模型、計費表筆數、命中的價格鍵、匯率。AI 未啟用時直接綠燈；匯率 `UsdToTwd` ≤ 0 或模型查無價格為黃燈。 |
| 寄信服務 | 10 | Provider；Smtp 時另有主機、埠號、加密方式、帳號／寄件者是否設定、連線＋登入耗時。Provider 無法解析為紅燈；None／Pickup 黃燈；Smtp 實測（上限 5 秒、**不寄信**），失敗為紅燈。 |
| 日誌管線 | 10 | 日誌與例外管線本身（0.9.79 起，LOG-22）：例外佇列長度與丟棄數、例外寫入失敗、前端錯誤回報因限流丟棄的筆數、告警信入列／寄送失敗、NLog 內部錯誤、日誌所在磁碟（`NLog:BasePath`）可用空間（數值為本次啟動以來）。佇列滿或磁碟剩不到 200 MB 為紅燈；任何丟棄、寫入或告警失敗、NLog 內部錯誤、佇列使用率達八成、磁碟剩不到 1 GB 為黃燈；前端回報被限流不影響燈號。判斷邏輯為純函式 `SystemHealthService.EvaluateLoggingPipeline`，由 `LoggingPipelineHealthTests` 覆蓋。 |
| 排程作業 | 5 | 排程作業的狀態（0.9.96 起）：啟用中的作業最近一次執行失敗為紅燈；排程總開關關閉、作業逾期（時段過了一小時仍沒有任何行程執行，常見原因是 IIS 閒置停止）或設定被改壞為黃燈。判斷邏輯為純函式 `SystemHealthService.EvaluateScheduledJobs`，由 `ScheduledJobFrameworkTests` 覆蓋。 |

### 4.1 ⚠️ LLM API 檢測會產生費用

這是唯一一項**每次開啟頁面都會對外發出付費 API 呼叫**的檢查（送一句 `hello`）。

- 每次約 27 個 token、費用約 **NT$0.005**，並會依專案慣例記入「Token 用量」，
  作業名稱為「**系統健康檢測**」，可在該頁用作業篩選器單獨檢視；0.9.72 起同時寫一筆「AI 對話紀錄」（與 Token 用量同一個 CallId）。
- 頁面載入會因此多等 **1～3 秒**。
- 逾時固定 **30 秒**（`AiHealthProbe.ProbeTimeout`），**刻意不沿用** `AiSettings.TimeoutSeconds`
  —— 後者預設 600 秒，沿用會讓端點失聯時整個管理頁卡住十分鐘。
- AI 未設定時**不會發出任何請求**，該項顯示黃燈並註明「AI 未設定（選配功能）」。
  這是刻意的：沒接 AI 的部署不該因此變成紅燈。
- 0.9.24 新增的三項檢查（LLM API、快取服務、AI 計費表）都各自防護並自帶逾時；寄信服務項由 `EmailHealthProbe` 內部吞例外並限 5 秒。
  最早的 8 項裡只有「資料庫」有 try/catch，其餘單一項目拋例外仍會炸掉整份報告。新增外部相依的檢查時務必自行防護。

## 5. 日誌顯示注意事項

`/system-health` 頁尾會顯示最近 24 小時 WARN 以上的原始日誌紀錄，不會額外遮罩內容。此設計是為了讓管理員快速追查失敗項目，但也代表頁面可能顯示路徑、帳號或例外訊息。

部署時請確認：

- 只有可信任管理員可以登入此頁。
- NLog 不應寫入密碼、token、完整連線字串等 secret。
- 正式環境的日誌保存期限與存取權限符合組織政策。
