## 一、為什麼需要這套系統

### 1.1 傳統系統的日常

想像一位顧客剛買了鞋，尺碼不合想換大一碼。在多數企業的系統裡，事情是這樣發生的：

1. 顧客要自己找到「售後申請」入口，自己判斷要選哪一筆訂單、哪一種申請類型。
2. 表單送出後進入排隊，等客服人員有空處理。
3. 客服人員打開訂單系統查訂單、打開售後規定對照條件、計算簽收天數、確認庫存。
4. 資料不齊（例如顧客沒說鞋子穿過沒有）就要再聯繫顧客，來回一兩次。
5. 最後才核准或駁回。

系統本身「有功能」，但**把功能串起來、把事情辦成的工作，全落在顧客和客服人員身上**。

### 1.2 「接上 AI」不等於「會辦事」

很多「已導入 AI」的展示，其實只是讓模型讀一段文字、回一句話。模型本身**沒有連著您的訂單系統，也不知道您店裡現行的規定**；
就算它嘴上說「已經幫您提交申請」，只要後端沒有真的執行建立申請的程式，系統裡就不會多出任何一張單子。

看到任何 AI 展示時，可以問三個問題，馬上看清底細：

1. **真實的業務資料從哪裡來？**
2. **模型實際收到了什麼？**
3. **模型產生的結果，最後由誰處理？**

### 1.3 Agent 多出來的是什麼

真正「會辦事」的 AI Agent，差別在於**下一步由誰決定**：

- 程式先劃定目標與邊界：可以用哪些工具、哪些紅線不能碰、最多走幾步。
- 模型看著眼前的真實結果，決定下一步：繼續查、開口問顧客，還是給出建議。
- 程式負責真的去執行、把關身分與權限，再把**真實結果**交回給模型。
- 碰到資訊不足、服務異常、規則衝突時，**停下來說清楚卡在哪裡**，不瞎猜、不空轉。

這套示範系統，就是把上面這些觀念做成一個看得見、摸得到的實物。

> 本節觀念參考自一系列「手把手開發 Agent」的公開教學內容（第四期：以一次換貨看 Agent 如何一步步完成任務），本文以自己的話重新整理。

## 二、示範情境：一次換鞋

示範店家是一間鞋服電商。登入的顧客名下有兩筆剛簽收的訂單：

| 商品 | 原尺碼 | 簽收 |
|------|--------|------|
| 黑色運動鞋 | 40 碼 | 3 天前 |
| 白色運動鞋 | 41 碼 | 2 天前 |

店家現行售後說明：**簽收 7 天內、鞋子未穿過，可換同款其他尺碼；開膠屬品質問題，需先上傳照片給客服核驗。**

顧客只說了一句：「**這雙想換大一碼，另一雙開膠了，也幫我看看。**」

Agent 的處理過程：

1. 查這位顧客的訂單 → 發現兩雙都剛買，分不清哪雙換碼、哪雙開膠 → **停下來問顧客**。
2. 顧客回答「黑的換大一碼，白的開膠」。
3. Agent 連續查黑鞋的換碼規定、白鞋的品質處理規定，並確認 41 碼有庫存。
4. 回覆：「黑鞋可以換碼，請確認是從 40 碼換成 41 碼；白鞋請先補一張開膠照片。」
5. 跳出**確認卡**，顧客按下確認後，系統重新核對身分與資格，才真正建立申請，並回報申請編號。
6. 白鞋這邊，系統**停下來等顧客上傳照片**，不會在背後一直空轉。

同一件事，系統也保留傳統做法（顧客自己填表、客服手動審核），讓您並排比較。

## 三、傳統做法 vs Agent 做法

| 面向 | 傳統做法 | Agent 做法 |
|------|----------|------------|
| 顧客怎麼開始 | 找入口、自己選訂單與申請類型、填表 | 用一句話說出問題 |
| 一句話兩件事 | 要分兩張表單各填一次 | Agent 自動拆成兩件事分別處理 |
| 規定怎麼對照 | 客服人員打開規定文件人工對照 | Agent 依當下有效版本查詢，並標示版本 |
| 資料不齊 | 表單送出後客服再聯繫，來回往返 | 當場問清楚再往下走 |
| 寫入系統 | 客服人員手動建單 | 顧客確認後，由程式重核並建立 |
| 客服人員的工作 | 查資料、對規定、算天數、聯繫顧客 | 看 AI 整理好的案件摘要與初審建議，做最後決定 |
| 服務異常時 | 顧客只看到錯誤或沒有回應 | 明確說明「暫時無法核實」，並轉人工 |
| 成效看得見嗎 | 難以量化 | 系統自動記錄步驟數、耗時、人工介入次數與 AI 成本 |

## 四、系統特色

以下每一項標示目前狀態：**〔已提供〕**表示現在就能實際展示，**〔規劃中〕**表示尚在開發。

1. **〔已提供〕受控的工具，而不是萬能的 AI**：每一項能力（查訂單、讀規定、查庫存、查物流、建立申請）都是程式寫好的受控入口，事先定清楚輸入、輸出、失敗時怎麼說、誰能用、會不會改動資料。
2. **〔已提供〕身分由系統把關**：模型不能決定「查誰的訂單」；身分一律由系統依登入狀態帶入，查不到別人的資料。
3. **〔已提供〕寫入前一定確認**：任何會改動資料的動作，都要先讓顧客看過確認卡、按下確認，系統再重新核對一次才寫入，寫完還會回查。
4. **〔已提供〕拿不準就停下來問**：查不到、服務逾時、規定衝突時，Agent 一律停下來詢問或轉交人工，絕不自行假設往下走；需要照片時也會停下來等顧客上傳。
5. **〔已提供〕只給模型需要的資料**：收件地址、手機號碼等與當下問題無關的資料，一律不送給模型；畫面上看得到哪些欄位被刻意保留。
6. **〔已提供〕幕後透明**：展示時可打開「幕後面板」，用白話一步步看 Agent 決定了什麼、系統核對了什麼、拿回什麼真實結果、為什麼停下。需要時再展開技術細節；客服與店家也能在後台回頭查看任何一次的處理過程。
7. **〔規劃中〕故障也說得清楚**：可以現場模擬訂單服務逾時、權限過期、規定服務停擺等狀況，看 Agent 如何正確停下並說明，而不是亂回答（目前 Agent 遇到逾時或權限不符已會正確停下，現場模擬開關則在後續提供）。
8. **〔已提供〕規定改了，馬上生效**：店家修改售後規定後，Agent 下一次就依新版本判斷，並標示版本，舊說法不會被沿用。
9. **〔規劃中〕可刪除的長期記憶**：Agent 可以記住「顧客平常穿 41 碼」這類偏好（記住之前先徵求同意），顧客隨時可以查看、刪除；記憶只當參考，不會被當成事實。
10. **〔規劃中〕多 Agent 分工**：可切換成「分流 Agent ＋ 換退貨專員／品質專員／物流專員」的團隊模式，與單一 Agent 對照。
11. **〔規劃中〕客服人員也有 AI 助手**：申請進來後，系統同時做照片初審、規定核對、歷史紀錄檢查並整理摘要；**核准與否永遠由人決定**。
12. **〔規劃中〕效益可量化**：對照頁並排呈現兩種做法的步驟數、耗時、人工介入次數、AI 成本，並可加入您的實際假設（排隊時間、人力成本、每月案件量）推估節省。

## 五、架構概念（白話版）

```
 ┌──────────── 顧客 ────────────┐        ┌────────── 客服人員 ──────────┐
 │  一句話說出問題 / 確認 / 上傳 │        │  審核佇列 / 案件摘要 / 決定   │
 └──────────────┬───────────────┘        └──────────────┬───────────────┘
                │                                       │
        ┌───────▼────────┐                     ┌────────▼─────────┐
        │   售後 Agent    │  ← 大腦：決定下一步  │  初審流程（固定）  │
        │（單一 / 分工團隊）│                     │ 照片・規定・歷史並行 │
        └───────┬────────┘                     └────────┬─────────┘
                │ 提出「請幫我執行」                      │
        ┌───────▼─────────────────────────────────────▼───────┐
        │        執行底座（程式）：核對身分、權限、確認紀錄、       │
        │        步數上限、何時該停，並記錄每一步供幕後面板顯示       │
        └───────┬─────────────────────────────────────────────┘
                │ 只有通過把關的動作才會執行
        ┌───────▼─────────────────────────────────────────────┐
        │  業務系統：訂單、售後規定（含版本）、庫存、物流、售後申請   │
        └─────────────────────────────────────────────────────┘
```

重點只有一句話：**模型負責判斷下一步，程式負責執行與把關，權限永遠屬於業務系統。**

本系統以 Microsoft 官方的 AI Agent 開發框架（Microsoft Agent Framework）實作，模型服務可使用 Azure OpenAI 或 OpenAI。

## 六、套用到您的產業

### 6.1 盤點方法：哪些工作適合交給 Agent？

拿出您現在的一個流程，逐步問這幾個問題：

| 問題 | 若答案是「是」 |
|------|----------------|
| 下一步做什麼，要看當下情況才知道？（情況多到無法事先排成固定流程）| 適合 Agent |
| 步驟固定、規則明確、每次都一樣？ | 適合固定流程（可以加 AI 輔助，但不必讓模型決定步驟）|
| 需要查多個系統、對照多份規定才能回答？ | Agent 的工具能大幅省力 |
| 會改動資料、牽涉金錢或權益？ | 一定要有「確認＋程式重核」關卡 |
| 出錯的代價很高？ | 先從只讀助手開始，決定權保留在人 |

這套示範系統本身就是例子：**顧客端**情況多變，用 Agent；**客服後台的初審**步驟固定，用固定流程並行處理，再交給人決定。

### 6.2 醫療／健康

| 情境 | 傳統做法 | Agent 做法 | 必守的邊界 |
|------|----------|------------|------------|
| 門診改約 | 病人打電話、櫃台查班表、手動改 | 病人說「下週三的回診想改到週五下午」，Agent 查本人掛號、查醫師班表、提出可選時段，確認後改約 | 身分由系統驗證；改約前確認；不提供醫療判斷 |
| 檢查前衛教 | 發紙本、護理人員反覆說明 | 依病人實際排定的檢查項目，回答「前一天能不能吃東西」，並附衛教文件版本 | 只依院內現行衛教內容回答，查不到就轉護理人員 |
| 保險申報文件 | 病人自己判斷要申請哪些文件 | Agent 依保單類型列出需要的文件並代為申請 | 涉及病歷的文件一律人工核准 |

### 6.3 製造業

| 情境 | 傳統做法 | Agent 做法 | 必守的邊界 |
|------|----------|------------|------------|
| 客訴與保固 | 客戶填表、客服查出貨與保固條款 | 客戶描述「上個月那批馬達有異音」，Agent 查出貨批號、保固條款、同批次客訴紀錄，請客戶補照片或影片 | 判定是否保固由品保人員決定 |
| 維修派工 | 調度員看表格排人 | Agent 依故障類型、技師專長與排程提出派工建議 | 派工確認後才寫入；緊急案件直接通知主管 |
| 業務查詢 | 業務打電話問生管、倉庫 | 業務問「A 客戶的訂單何時能出」，Agent 查生產進度與庫存回覆 | 只讀，不能改生產排程 |

### 6.4 金融／保險

| 情境 | 傳統做法 | Agent 做法 | 必守的邊界 |
|------|----------|------------|------------|
| 理賠申請 | 保戶自己找表單、補件往返多次 | 保戶說「上週住院三天想申請理賠」，Agent 查本人保單、比對理賠條款，列出缺少的文件 | 理賠金額與核准一律由理賠人員決定 |
| 保單查詢 | 打客服專線排隊 | 即時回答「我的醫療險有沒有含門診手術」，並標示條款版本 | 只能查本人保單；條款查不到就轉專人 |
| 文件檢核 | 人工逐份檢查 | 自動檢核文件是否齊全、欄位是否一致，標出疑點 | AI 只標記疑點，不自動退件 |

## 七、導入建議

### 7.1 建議分四個階段

| 階段 | 目標 | 要準備什麼 | 主要風險與對策 |
|------|------|------------|----------------|
| 1. 盤點流程 | 找出最值得改善的一個流程 | 現行流程圖、每一步的耗時與人力、相關系統與規定文件 | 範圍太大 → 先挑一個高頻、規則清楚的流程 |
| 2. 只讀助手 | 讓 AI 幫忙「查」與「整理」，不改任何資料 | 現有系統的查詢介面（API）、整理好的規定文件與版本 | 回答不準 → 規定必須從系統讀取，不靠模型記憶 |
| 3. 受控寫入 | 讓 Agent 在確認後代為建立申請或單據 | 寫入介面、確認紀錄、重新核對的規則、稽核紀錄 | 誤寫入 → 確認卡＋程式重核＋寫入後回查 |
| 4. 擴大範圍 | 擴展到更多流程，或導入多 Agent 分工、長期記憶 | 前面階段的成效數據、使用者回饋 | 成本失控 → 用量上限、成本監控、步數上限 |

每個階段都能單獨上線、單獨看到成效，不需要一次到位。

### 7.2 效益怎麼評估

| 指標 | 怎麼量 |
|------|--------|
| 顧客端花費時間 | 從提出問題到申請建立的時間 |
| 顧客操作步數 | 點擊、填寫、往返的次數 |
| 客服人工介入 | 每件案件客服需要動手的次數與分鐘數 |
| 一次解決率 | 不需要再聯繫顧客就完成的比例 |
| AI 成本 | 每件案件的模型使用費用（系統自動記錄） |
| 錯誤與越界 | 未經確認的寫入（目標為零）、轉人工的比例與原因 |

建議先記錄導入前的基準值（例如每月案件量、客服每件處理分鐘數、平均排隊時間），再與導入後並排比較。示範系統的「效益對照頁」就是用這套方法呈現的。

## 八、展示安排

一場約 30 分鐘的展示，大致包含：問題與觀念（5 分鐘）→ 傳統做法走一遍（5 分鐘）→ Agent 做法與幕後面板（10 分鐘）→
故障情境與客服後台（6 分鐘）→ 效益對照與導入討論（4 分鐘）。

> 目前進度：**「傳統做法」與「Agent 做法」這兩段已可實際展示**（傳統：顧客表單申請、客服人工審核、補件往返、店家改規則版本；Agent：線上客服對話、規則卡、確認卡、停等照片、幕後面板與後台處理紀錄）；展示 Agent 需要可用的 AI 模型連線。故障情境模擬、客服 AI 助手與效益對照頁仍在開發中。
