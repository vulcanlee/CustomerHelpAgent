## 一、專案總覽（白話）

### 1.1 這是什麼系統

一套**自己從頭開發**的「鞋服電商售後」示範系統，建在本 repo 的 .NET 10 Blazor 腳手架上，AI 部分使用 Microsoft Agent Framework（MAF）1.25.0。

同一套資料上，並排做了兩種處理售後的方式：

| | 傳統做法 | AI Agent 做法 |
|---|---|---|
| 顧客怎麼申請 | 在「我的訂單」點「申請售後」，填五步驟表單 | 在「線上客服」用一句話說需求 |
| 誰把資訊串起來 | 顧客自己找訂單、自己看規則；客服逐一按「查看訂單」「查看售後規則」「查看照片」 | Agent 自己決定先查訂單、再查規則與庫存，不清楚就停下來問 |
| 寫入資料 | 顧客按送出 | Agent 只能「提議」，顧客按確認卡、程式重核後才寫入 |
| 系統出狀況時 | 常常只顯示「查無資料」 | 分清楚「查過了沒有」和「沒查完」，說明下一步 |

另外還有：客服後台的 AI 初審與 AI 助手（M4）、讓一個人也能穩定展示的「展示控制台」（M3：故障模擬、一鍵重置、錄製回放、身分切換）、多 Agent 交接與長期記憶（M5）。

### 1.2 為什麼要做

負責人讀了一篇講「Agent 怎麼一步步把事辦成」的教學文章（全文在[企劃規劃說明書附錄](售後Agent示範系統企劃規劃說明書.md)），想把文章的觀念做成**真的能操作的系統**，目的有三個：

1. **自己弄懂**：親手用 MAF 把每個觀念做實，了解嵌入 AI Agent 的系統和傳統系統差在哪裡、好在哪裡。
2. **說服客戶**：讓客戶看見自己現有的流程、工作與工作環境，可以變成什麼樣子。
3. **全部自建**：訂單、規則、庫存、物流、申請等「客戶端業務系統」全部自己開發、模擬真實情況。

傳統做法的痛點，展示時用一句話講：「系統每個功能都有，但把它們串起來的工作，全落在顧客和客服身上。」

**成功的樣子**：觀眾看完 30 分鐘展示，能自己說出「Agent 和接上 AI 的聊天機器人差在哪」；現場不翻車；效益說得出數字；沒有人挑得出「越界」（沒確認就寫入、查到別人訂單、編造規則）。

**失敗標準**（使用者訂的，四項都算失敗）：劇情跑不出來、面板太工程師、看不出效益、Agent 越界。

## 二、白話核心觀念：AI Agent 開發入門

> 本節用這個系統當例子，把教學文章（[企劃規劃說明書附錄](售後Agent示範系統企劃規劃說明書.md)）的觀念講一遍。沒做過 AI 的人請從這裡開始。

### 2.1 從問答到 Agent 的四個階段

先記住一句話：**接上 AI ≠ 會辦事**。差別在「下一步由誰決定」。

| 階段 | 白話 | 下一步誰決定 | 在本系統的樣子 |
|---|---|---|---|
| ① 單次呼叫 | 使用者說一句，程式把挑好的資料和一句任務交代（提示詞）送給模型，模型回一句 | 程式（寫死） | 程式先查到黑 40、白 41 兩雙鞋，只把品名、顏色、尺碼送給模型，模型回「您要換的是黑色 40 碼還是白色 41 碼？這雙鞋穿過沒有？」 |
| ② 多輪對話 | 模型**不記事**，每次呼叫都是新的開始；要由程式把前文接上 | 程式（寫死） | 顧客接著說「黑色那雙，還沒穿過」，程式要把前面的對話一起送，模型才知道「那雙」是哪雙。本系統把對話（`AgentSession`）序列化存進 SQLite |
| ③ 工具呼叫 | 模型可以提出「請幫我執行這個動作」的請求單，程式真的去執行，照實交回結果 | 模型提議、程式執行 | 模型提出「查本人訂單，顏色＝黑」，程式帶上**登入身分**去查，把結果交回 |
| ④ Agent 迴圈 | 模型選一步 → 程式執行 → 結果交回 → 模型看結果再選下一步，直到辦完或該停的地方停住 | 模型看現場決定，程式把關 | 劇本 B：查訂單 → 分不清就停下來問 → 查黑鞋換碼規則 → 查白鞋品質規則 → 規則說開膠要照片 → 停下來等照片 |

```text
          ┌──────────── 目標與邊界（程式交代：能用哪些工具、哪些紅線、最多幾步）
          ▼
   ┌─▶ 模型：看現場，選下一步 ──▶ 回覆顧客／追問／停下來等  ──▶ 本輪結束
   │        │ 提出工具請求單
   │        ▼
   │   程式（Harness）：核對身分與權限 → 執行工具 → 判斷要不要停
   │        │ 把「真實結果」交回
   └────────┘
```

**兩個常見誤會**：

- 模型嘴上說「已經幫您提交申請了」，只要程式沒真的執行建立申請的程式碼，系統裡就**不會**多一張單。
- 聊天裡確認過的目標尺碼，**不等於**已經寫進業務系統；長期記憶也**不等於**業務事實（見 2.4）。

**看穿「已接入 AI」展示的三個問題**（文章原話）：真實的業務資料從哪來？模型實際收到了什麼？它生成的結果最後由誰處理？本系統的幕後面板就是為了讓觀眾隨時看到這三個答案。

### 2.2 核心機制：讓 Agent「可信」的七件事

模型很聰明，但會猜、會講錯、會被誤導。下面七個機制，就是把一個「會聊天的模型」變成「可以交給客戶用的 Agent」的骨架。

#### ① 受控工具：AI 只能用我們準備好的入口

- **白話**：工具就像櫃台的「申請窗口」。AI 不能直接進倉庫（資料庫），只能到窗口遞單子；窗口後面的人（程式）決定准不准、照實回覆。
- **為什麼**：模型填的身分可能是算錯的、也可能是使用者隨口報的，不能憑這個決定他有權查誰的訂單。
- **本系統怎麼做**：
  - 每個工具定清楚五件事：輸入、輸出、失敗怎麼說明（跟模型的規矩），誰有權呼叫、會不會改資料（程式的底線）。
  - 工具參數**沒有**使用者 Id 欄位，身分一律由程式從登入狀態帶入；模型多傳的參數會被忽略。
  - 顧客端 7 個工具：`query_my_orders`、`get_effective_policy`、`check_variant_stock`、`track_shipment`、`request_photo_upload`、`create_after_sales_request`（寫入）、`remember_preference`（M5，寫入記憶）。
  - 統一回傳信封 `ToolOutcome`，`status` 分成 `ok`／`not_found`／`timeout`／`forbidden`／`unavailable`／`no_policy`／`conflict`／`blocked`／`invalid`。
- **重點例子**：同樣是「沒拿到訂單」，有三種完全不同的情況，絕不能混成一句「查無資料」：

| 情況 | status | 該怎麼做 |
|---|---|---|
| 查完了，確實沒有 | `not_found` | 請顧客核對線索；本輪不准建立申請 |
| 查詢逾時，沒查完 | `timeout` | 程式立即停止，說明「目前無法確認，**不代表您沒有這筆訂單**」 |
| 權限不符（登入過期） | `forbidden` | 程式立即停止，不再往下讀 |

#### ② 寫入前確認：確認卡

- **白話**：AI 想改資料時，只能把「我想這樣做」擺在顧客面前，顧客點頭了，程式還要再核一次才寫入。就像網購結帳前的「訂單確認頁」。
- **為什麼**：模型判斷「可以辦了」不能當放行證明；真正寫入的權利不在模型手上。
- **本系統怎麼做**：
  - 寫入工具用 `ApprovalRequiredAIFunction` 包起來；模型提出呼叫時，框架**不執行**，改回傳核准請求。
  - 確認卡的內容由程式**重新查詢**組成（商品、規格原 → 新、規則版本、簽收第幾天），不採用模型寫的文字。
  - 顧客按「確認送出」後，程式重核身分與資格 → 寫入 → 回查申請真的存在 → 才回報申請編號。
  - 顧客改打字而不按卡＝不確認，卡片作廢；兩個分頁同時按同一張卡，只會建立一筆（條件式認領 `TryClaimConfirmationAsync`）。

#### ③ 該停就停：停止原因

- **白話**：好的 Agent 知道什麼時候該閉嘴等人。資料不夠就問、要照片就等、系統壞了就說清楚卡在哪，而不是一直繞圈花錢。
- **本系統怎麼做**：每一輪結束都有一個由**程式判定**的停止原因（`AgentStopReason`）：

| 類型 | 停止原因 |
|---|---|
| 正常收尾 | `Answered`（已回覆） |
| 等人 | `AwaitingUserReply`（等顧客回答）、`AwaitingConfirmation`（等按確認卡）、`AwaitingPhotoUpload`（等上傳照片） |
| 防繞圈 | `StepLimitReached`（步數上限，預設 8）、`ConsecutiveToolFailures`（工具連續失敗，預設 2 次） |
| 出狀況 | `Forbidden`、`Timeout`、`ServiceUnavailable`、`PolicyConflict`、`QuotaExceeded`、`ModelError`、`Canceled` |
| 回放專用（M3） | `ReplayDiverged`、`ReplayFinished`、`ReplayActionMismatch` |

- **例子**：劇本 B 停在 `AwaitingPhotoUpload`，程式不會在背景反覆催模型去要一張還不存在的照片；F1 訂單系統逾時，停在 `Timeout`。

#### ④ Harness：外層那段把關的程式

- **白話**：模型像一位很聰明的新進員工，Harness 就是公司的規章、主管簽核與打卡鐘。員工可以自己判斷下一步，但規章不是靠員工自覺，而是制度強制。
- **為什麼**：文章說，撐起整個迴圈、把住出口與關卡的「不是模型自己」，是包在外層的程式。提示詞只是「拜託」，程式才是「規定」。
- **本系統怎麼做**：
  - **Guard 中介層**（`AfterSalesAgentGuard`，掛在 MAF 的函式呼叫中介層）：每次用工具前後都檢查。`forbidden`／`timeout`／`unavailable` → 立即終止；`not_found`／`no_policy`／`conflict` → 本輪封鎖建立申請（`blocked`）。
  - **步數上限**：一輪最多 `MaxSteps`（預設 8）次工具往返，整輪模型呼叫總數不超過 `MaxSteps + 1`（含確認後的續跑）。
  - **固定說明**：逾時、權限不符這類情況，顧客看到的是程式寫好的固定文字，不是模型臨場發揮。
  - **規則卡**：顧客看到的規則條文一律由工具結果渲染，不採模型轉述。

#### ⑤ 幕後透明：幕後面板

- **白話**：把 AI 的「腦內過程」攤開給人看，像透明廚房。
- **為什麼**：回應「三個問題看穿展示」；也是開發與除錯時最好用的工具。
- **本系統怎麼做**：每一步發出事件（白話層＋可展開的原始資料），標上來源色標（對話／資料庫／規則／記憶／程式）；每個工具結果都列出「未送出：…」（地址、手機等刻意不送的欄位）。後台 `/agent-runs` 可回看任何一輪。

#### ⑥ 故障說得清：故障模擬

- **白話**：真實世界的系統一定會壞。展示時要能「故意弄壞」，讓觀眾看到 Agent 壞掉時也說得清楚。
- **本系統怎麼做**：展示控制台有 7 種故障開關（訂單系統逾時、查無訂單、物流異常、規則服務停擺、規則衝突、無適用規則、權限過期），注入在模擬業務服務層，所以**傳統頁面與 Agent 同受影響**，可以並排對照。
- **例子**：F1 訂單逾時 → Agent 說「訂單系統暫時沒有回應，目前無法確認，不代表您沒有這筆訂單。已為您轉交客服。」；傳統頁面則是等很久才失敗。

#### ⑦ 錄製回放：展示不翻車的保險

- **白話**：模型每次的走法可能不一樣，網路也可能斷。所以排練時把真實模型的回應錄下來，展示時可以「放錄音」，但查訂單、建立申請仍然真的執行。
- **本系統怎麼做**：
  - 錄製在模型呼叫層（`IChatClient`）：`RecordingChatClient` 錄下每次請求的摘要與回應。
  - 回放用 `ReplayChatClient`：**不連模型、不扣額度**；每次請求先比對摘要，資料或故障開關和錄製時不同就中止（`ReplayDiverged`）。
  - 示範資料用**固定編號**，重置幾次都一樣，錄製裡的工具參數才對得上（這是 M3 才學到的，見 7.7）。
  - 回放有沒有真的省錢，用數字證明：回放前後 Token 用量筆數不變（例：M3 實機 63 → 63 筆）。

### 2.3 Workflow 與 Agent 的差別

| | Workflow（固定流程） | Agent（模型決定） |
|---|---|---|
| 白話 | 事先畫好的流程圖，每次照圖走 | 給目標與邊界，模型看現場選下一步 |
| 下一步誰決定 | 開發者事先排好 | 模型依剛拿回來的真實結果決定 |
| 適合 | 步驟每次都一樣、要稽核、要停下來等人決定 | 情況多到沒辦法事先一條條排，要看對話現場 |
| 本系統例子 | **M4 客服初審**：進件 → 照片／規則／歷史三路同時跑 → 摘要 → **停下來等客服決定** → 執行 → 通知 | **M2 顧客端 Agent**：顧客一句話扯出兩雙鞋，先查什麼、要不要追問，由模型判斷 |

- Workflow 裡也可以有 AI 節點：初審的照片、歷史、摘要是模型節點，規則核對是純程式。
- 展示話術（企劃規劃說明書 §5.4）：「這裡我們刻意用固定流程，因為步驟每次都一樣，固定比較穩。AI 負責整理，**決定權在人**；而且 AI 沒能力核准，真正開單的是程式。」
- **判斷準則**：能畫成固定流程圖、而且畫得完的，就用 Workflow；畫不完、要看現場的，才用 Agent。

### 2.4 多 Agent 交接與長期記憶（M5 觀念）

> 本小節只講觀念；M5 的實作過程與驗證結果見第九節。

**多 Agent 交接（Handoff）**

- **白話**：像醫院的掛號櫃台。顧客先跟「分流 Agent」說話，它判斷需求後轉給換退貨專員、品質專員或物流專員；專員辦完或遇到不屬於自己的事，再交回分流。
- **為什麼**：每位專員只拿得到自己需要的工具（例如物流專員查不了庫存），權限更小、提示詞更專注；也讓觀眾對照「一個 Agent 全包」和「一個小團隊分工」。
- **要知道的事**：交接路線由模型決定，可能和預期的路線不同；安全規則（Guard 的停止規則）在兩種模式完全相同。

**長期記憶**

文章特別提醒要分清三件事：

| | 當前對話 | 長期記憶 | 業務狀態 |
|---|---|---|---|
| 白話 | 這次聊天講過的話 | 跨對話記住的顧客偏好 | 系統裡真的存在的訂單、申請 |
| 本系統 | `AgentSession` | `CustomerMemory`（鞋碼、衣服尺碼、顏色、溝通偏好） | 訂單、售後申請等業務資料表 |
| 能不能當事實 | 只代表這次說過 | **不能**，只是參考，要再確認 | 可以 |

- 寫入記憶要經過「記憶確認卡」，顧客按「記住」才寫入；電話、Email、地址、姓名、帳號一律拒絕。
- 每次呼叫模型前，程式把記憶以**系統指示**注入，固定寫明「來自記憶，需與顧客確認，不可當作訂單或規則等業務事實」。
- 顧客可以在「我的 AI 記憶」（`/shop/memory`）查看、刪除；刪除後下一次呼叫就不再注入。
- **例子**：記憶裡是 41 碼，但顧客這次說要 42，確認卡就是 42。

### 2.5 AI 安全與個資

**模型永遠看不到的東西**：使用者 Id、收件人姓名、地址、手機、付款資訊；價格與庫存數量也不送（庫存只回有貨／無貨）。

**為什麼這麼嚴**：文章說「發給模型的內容是實實在在離開了你的業務程式碼」。多送無關欄位只多風險、不多幫助。挑料原則只有一條：**這一步需要什麼就只給什麼**。

| 風險 | 白話 | 本系統的做法與教訓 |
|---|---|---|
| 個資送進模型 | 不小心把地址、電話塞進給模型的文字 | 每個工具有專屬投影 DTO 與「刻意不送欄位」清單；M4 的四次審閱分別抓到四條沒遮蔽的路徑（照片描述、歷史、摘要輸入、助手工具），所以**每一條**送模型的路徑都要有測試 |
| AI 日誌外洩 | 日誌也是資料，存了就可能外流 | M4 審閱發現照片以 base64 全部寫進 AI 對話紀錄，改成只記「類型＋大小」 |
| 提示詞注入（prompt injection） | 有人把「指令」藏在資料裡，騙模型照做（例如把「忽略前面的規則」存成記憶） | 記憶值一律放在引號內當「資料」、引號字元被替換跳不出來；注入文字由程式產生、不在可編輯的提示詞裡；最關鍵的是**模型沒有寫入權**，就算被騙也只能「提議」，程式會重核 |
| 把記憶當事實 | 記憶可能過時，顧客的腳也會變 | 記憶是「偏好不是事實」：只能拿來向顧客確認，不可當申請規格 |
| 金鑰外洩 | 模型金鑰被寫進程式、日誌或報告 | 金鑰只放 user secrets；實機驗證、報告、本文件都不寫金鑰與端點 |
| 日誌含個資 | 除錯日誌印出姓名、電話 | 日誌一律英文、不含姓名、地址、電話、Email |

### 2.6 名詞解釋

**AI 與模型**

| 名詞 | 白話解釋 |
|---|---|
| LLM（大型語言模型） | 讀一段文字、產生下一段文字的模型，例如本專案用的 Azure OpenAI 部署 `gpt-6.1-sol`。它不會自己連到你的系統 |
| Token | 模型計算文字量與費用的單位，大約是一個字或半個字。每次呼叫都會記在「Token 用量」頁 |
| 提示詞（Prompt） | 給模型的任務交代，例如「先問清楚換哪雙、穿過沒有，別說已經建立申請」 |
| 系統指示（Instructions） | 放在最前面、權限最高的提示詞，模型會當成規則；本系統的記憶也以系統指示注入 |
| 上下文（Context） | 這次呼叫送給模型的全部內容：系統指示、對話、工具結果 |
| Responses API／`store=false` | OpenAI 的一種呼叫介面；`store=false` 表示不在模型服務端保存對話，歷史由我們自己保存 |
| 結構化輸出 | 要求模型照固定欄位（JSON）回答，程式可直接讀，例如初審的「建議、理由、檢查清單」 |
| 多模態 | 模型除了文字也能看圖片，例如初審的「照片初審」 |

**Agent 機制**

| 名詞 | 白話解釋 |
|---|---|
| 工具呼叫（Function Calling） | 模型提出「請執行某工具」的請求單，程式執行並交回真實結果 |
| 核准／確認卡 | 寫入工具的請求先停下來給顧客確認；按確認後程式重核才執行 |
| Agent loop（執行迴圈） | 模型選一步 → 程式執行 → 結果交回 → 模型再選，直到辦完或該停 |
| Harness（執行底座） | 包在模型外面、跑迴圈並管住邊界的程式；本系統是 Runner＋Guard＋步數上限＋固定說明 |
| Guard | 本系統的函式中介層 `AfterSalesAgentGuard`，每次用工具前後檢查身分、權限、要不要停 |
| 停止原因 | 每輪結束時程式判定的原因，例如「等待確認」「步數上限」 |
| Session（會話） | 一段對話的完整狀態；本系統序列化後存 SQLite，重新整理或重啟都能接續 |
| 幕後面板 | 顧客頁右側用白話列出每一步的面板 |
| 錄製／回放 | 把真實模型回應錄下來，之後不連模型照樣重播；工具仍真的執行 |
| 金劇本 | 某個劇本被選為展示用的那一筆錄製 |

**Workflow 與多 Agent**

| 名詞 | 白話解釋 |
|---|---|
| Workflow | 事先畫好的流程圖，由框架照圖執行 |
| Executor | Workflow 裡的一個節點，例如「照片初審」「摘要」 |
| fan-out／fan-in | 一個節點分成多路同時跑（fan-out），再等全部到齊才往下（fan-in） |
| 人工節點（`RequestPort`） | 流程停下來等人回覆的點，例如等客服核准 |
| Checkpoint | 遊戲存檔點；重啟後從存檔接著跑。MAF 的存檔單位是「一整步」（superstep），不是一個節點 |
| Handoff（交接） | 一個 Agent 把對話交給另一個 Agent，例如分流 → 品質專員 |
| AIContextProvider | MAF 的擴充點，每次呼叫模型前自動補上額外的指示或資料；本系統用來注入長期記憶 |
| MAF／MEAI | MAF＝Microsoft Agent Framework（Agent、Workflow、多 Agent）；MEAI＝Microsoft.Extensions.AI（`IChatClient`、工具、核准型別等底層介面），MAF 建在 MEAI 之上 |

**開發方法**

| 名詞 | 白話解釋 |
|---|---|
| 統籌者 | 和使用者對話的那個 Claude；不自己寫程式，負責拆任務、派工、裁定、記帳本 |
| 子代理 | 統籌者派出去的「全新的 Claude」，只拿到一份說明檔，做完回報；看不到主對話 |
| 探索代理 | 唯讀的子代理，負責查現有程式與框架原始碼 |
| 審閱（Review） | 由沒參與實作的子代理檢查程式差異，分 Critical／Important／Minor 三級 |
| 複審（Re-review） | 修正後，只檢查「這次修正」有沒有解決問題、有沒有改壞別的 |
| 最終全分支審閱 | 所有任務做完後，用最強的模型看整個分支，專找跨任務問題 |
| 帳本（`progress.md`） | 工作日誌：每次派工、審閱結果、裁定、延後的小問題都寫一行 |
| 裁定（Ruling） | 計畫有缺口時，統籌者當場決定並寫下「決定、理由、若錯的代價」 |
| 審閱包 | 把程式差異輸出成一個 `.diff` 檔交給審閱代理 |
| TDD（測試驅動開發） | 先寫會失敗的測試（RED），再寫程式讓它通過（GREEN） |
| 變異測試 | 故意拿掉修正，確認測試會失敗，證明測試真的有在測 |
| 試跑（spike） | 第一次用的框架，先寫一組小測試摸清楚行為並長期保留，再寫正式程式 |
| 品質關卡 | 一支腳本跑完建置、格式、測試、文件編碼、弱點掃描（`Invoke-QualityGate.ps1`）；本專案沒有 CI，以它取代 |
| 實機驗證 | 用使用者真實的模型跑劇本，抓假模型測不到的問題 |
| user secrets | .NET 的本機機密設定，金鑰放這裡，不進 git |
| 競態（race） | 兩件事同時發生、結果取決於誰先誰後，例如兩位客服同時按核准 |
| 冪等 | 同一件事做兩次，結果和做一次一樣；例如重啟後已完成的初審節點不再花一次錢 |

## 三、Microsoft Agent Framework 在這個專案的角色

> 完整說明（每個功能的白話用途、用在哪裡、為什麼需要、沒用到的功能與原因、踩到的框架行為）見 [MAF 功能運用說明](../features/售後Agent示範系統-MAF功能運用說明.md)。本節只做摘要，不重複內容。

**一句話**：MAF 是 AI Agent 的「作業系統」。**框架管「怎麼跑」，我們管「准不准、對不對」。**

| MAF 負責（怎麼跑） | 本系統自己負責（准不准、對不對） |
|---|---|
| 執行迴圈：模型 → 工具 → 模型（`ChatClientAgent`） | 身分與權限、Guard 的停止規則 |
| 寫入前暫停、等確認後續跑（核准請求） | 確認卡內容由程式組成、確認後重核、寫入後回查 |
| 對話保存與還原（`AgentSession`） | 會話樂觀版本、多分頁防覆蓋 |
| 固定流程：並行、人工節點、checkpoint 續跑（Workflows） | 節點結論存資料庫避免重複計費、個資遮蔽 |
| 多 Agent 交接（Handoff）、記憶注入擴充點（`AIContextProvider`） | 工具子集、記憶內容政策、注入文字 |
| 底層介面 `IChatClient`（來自 MEAI） | 計費、錄製、回放、幕後面板四個 client |

**給新手的三個提醒**：

1. **分清楚來源**：有些功能來自 MAF、有些來自 MEAI、有些是我們自己寫的。對客戶說明時不要把自己寫的說成框架功能（MAF 功能運用說明每一項都標了來源）。
2. **版本要釘死**：套件鎖在 1.25.0（`Directory.Packages.props`）；MAF 的小版本也可能改行為，升級要重跑框架行為測試。
3. **框架會有缺陷，也會有實驗性 API**：Workflows 1.25.0 的 fan-in checkpoint 還原缺陷（見 8.7）、多 Agent 確認卡依賴的實驗性 API（`MAAI001`），都靠自己的程式繞過並用測試釘住。

### 8.7 學到的事

- **新框架先讀原始碼再寫計畫**：探索代理從 1.25.0 原始碼整理出的 API 清單，避免了計畫裡寫錯方法名稱（草稿中的 `StreamAsync`、`AddFanInEdge` 都不存在）。
- **框架也會有缺陷**：Workflows 1.25.0 的 fan-in 訊息從 checkpoint 還原時內容為空，而且不報錯。只有「真的丟掉主機、再從資料庫續跑」的測試抓得到；這個測試要保留，升級套件時一定要重跑。
- **checkpoint 的單位是「一整步」不是「一個節點」**：三個節點併行時，任何一個沒做完就重啟，三個都會重跑（重複計費）。解法是每個節點完成就把結果存進資料庫，續跑時先讀，有就不再呼叫模型。
- **個資遮蔽要逐條路徑檢查**：照片描述、歷史紀錄、摘要輸入、助手的初審結果工具，審閱四次分別抓到不同的漏網路徑。「有一個共用的遮蔽函式」不等於「每條路徑都有用它」。
- **AI 日誌也是資料外洩點**：送給視覺模型的照片，原本會以 base64 全部寫進 AI 對話紀錄（每次可能數十 MB），審閱才發現。
- **時間差問題要靠整個分支的審閱**：背景初審讀取顧客對話時，顧客端那一輪可能還沒寫完。單一任務看不到，回放時才會隨機失敗。

## 十、開發過程與技術架構：Claude 怎麼執行一個里程碑

> 使用者 2026/10/24 指示：說明目前使用的開發過程與技術，它的整個架構，以及運作邏輯是如何做到的。

### 10.1 一句話說明

使用者只和**一個 Claude（統籌者）**對話；統籌者不自己寫程式，而是把每個工作拆成小任務，派給**一個個全新的子代理**去實作、再派**另一批互不認識的子代理**去審閱，所有交接都透過檔案，所有進度都記在帳本，最後由使用者決定是否 commit。

> **白話比喻**：統籌者像工地主任。主任不親自砌磚，而是把工程拆成一張張工單，交給不同的師傅（實作代理）；每完成一張，就請另一位沒參與的監工（審閱代理）來驗收；所有工單、驗收單都歸檔，工地日誌（帳本）每一步都記；最後由業主（使用者）決定要不要驗收入帳（commit）。

### 10.2 整體架構

```
使用者（需求、選擇、核准、commit 決定）
   │  繁體中文對話；選擇題（AskUserQuestion）；計畫核准（ExitPlanMode）
   ▼
Claude 統籌者（主對話，Opus 5.5，1M 上下文）
   │  讀規範：CLAUDE.md、開發慣例速查表、專案記憶（MEMORY.md）
   │  只做：拆任務、寫說明檔、派工、讀結論、裁定、記帳本、暫存檢查點
   │
   ├─▶ 探索代理（唯讀，可多個同時）──▶ 回報：現有程式接點、框架 API 事實
   ├─▶ 實作代理（每任務一個全新代理）──▶ 寫測試→寫程式→跑測試→報告檔
   ├─▶ 審閱代理（每任務一個，不認識實作者）──▶ 只看程式差異，分級列出問題
```

### 10.3 角色與分工

| 角色 | 由誰擔任 | 看得到什麼 | 產出 | 為什麼這樣設計 |
|---|---|---|---|---|
| 使用者 | 你 | 全部 | 需求、選擇、核准、commit 決定 | 決定權在人 |
| 統籌者 | 主對話的 Claude | 計畫、帳本、各代理的「結論」 | 任務說明檔、裁定、檢查點 | 上下文保持乾淨，才能長時間統籌好幾個小時的工作 |
| 探索代理 | 唯讀子代理 | 程式碼、套件原始碼、文件 | 事實清單（含不存在的 API 名稱） | 先查清楚再寫計畫，避免計畫寫錯方法名稱 |
| 實作代理 | 每任務一個全新的子代理 | 只有該任務的說明檔與規則 | 程式、測試、報告檔 | 不帶前面任務的雜訊；說明檔是唯一需求來源 |

### 10.4 一個里程碑的完整流程

1. **需求釐清**：用選擇題問使用者（附建議選項），直到沒有模糊的地方。
2. **探索**：同時派 1～3 個唯讀探索代理。一個查現有程式的接點；一個讀框架原始碼（例如 MAF 1.25 的 tag），整理出真實的 API 與「不存在的名稱」。
3. **計畫**：在計畫模式中寫出逐任務計畫，每個任務都寫明這些內容：
   - 要改的檔案
   - 介面（名稱與型別）
   - 要寫的測試名稱
   - 審閱重點（最可能出事的 5 種情況）
   - 時間預估

   使用者核准後，另存到 `docs/prd/`。
4. **準備工作區**：
   - 建功能分支。
   - 用工具從計畫抽出每個任務的說明檔。
   - 寫好全域限制、實作規則、審閱規則、API 事實檔。
   - 建立帳本。
5. **預檢**：逐一比對任務之間「誰產出、誰使用」，找出衝突並先做裁定。
6. **逐任務迴圈**（一次只跑一個實作代理，避免改到同一批檔案）：
   1. 派實作代理。它的步驟是：寫失敗的測試，看它失敗，寫程式，看它通過，跑全套測試與格式檢查，寫報告。
   2. 產生審閱包：工作目錄與 git 暫存區之間的差異，排除自動產生的 migration 檔。
   3. 派審閱代理。
   4. 有 Critical／Important 問題就交回原實作者修正，再派複審代理，最多 5 輪。Minor 問題記在帳本。
   5. 審閱通過後 `git add` 進暫存區，當作這個任務的檢查點。
7. **最終全分支審閱**：最強模型看整個分支，並分類帳本裡所有延後的小問題（哪些要修、哪些寫進文件）。接著做一次修正、一次複審。
8. **文件**：版本號 Patch +1；功能說明、設計、企劃書、資料模型、索引全部同步。
9. **品質關卡**：`Invoke-QualityGate.ps1` 依序跑建置、格式、全套測試、文件編碼、弱點掃描。
10. **實機驗證**：
    - 用暫時的整合測試驅動真實服務與使用者的模型，金鑰只從 user secrets 讀，絕不寫出。
    - 每項都記錄申請編號、Token 用量筆數等證據。
    - 驗完刪除驗證程式，把開發資料庫恢復成初始示範資料。
11. **開發歷程**：把指示、選擇、結果、耗時、審閱發現寫進本文件。
12. **交付**：列出「Claude 代為決定的事項」，等使用者決定 commit／合併／推送。依 CLAUDE.md 規定，不自動 commit。

### 10.5 關鍵機制是怎麼做到的

| 機制 | 怎麼做 | 解決什麼問題 |
|---|---|---|
| 子代理隔離 | 每個子代理是全新的上下文，只拿到說明檔路徑與規則檔，不繼承主對話 | 不被前面的討論影響；審閱者不會「同情」實作者 |
| 用檔案交接 | 說明檔 `task-N-brief.md` → 報告檔 `task-N-report.md` → 審閱包 `*.diff`；主對話只讀結論 | 程式差異動輒上千行，若都貼進主對話，幾個任務後統籌者就會失去上下文 |
| 不 commit 的檢查點 | 審閱通過才 `git add`；審閱包＝工作目錄 vs 暫存區；修正輪用暫時的 index 拍「樹快照」（`git write-tree`），只比對這次修正 | CLAUDE.md 規定不能自動 commit，但仍需要可回溯的檢查點與精確的差異 |
| 帳本 `progress.md` | 每次派工、審閱結果、裁定、延後的小問題都寫一行；第一行標明屬於哪份計畫 | 對話太長會被壓縮，統籌者可能忘記做到哪；以帳本恢復，避免重做已完成的任務 |
| 裁定（Ruling） | 計畫有衝突或缺口時，由統籌者決定並寫下「決定、理由、若錯的代價」，不停下來等使用者 | 不讓整個流程卡在小問題上；事後可檢查每個決定 |
| 問題分級與修正輪 | Critical／Important 必修，最多 5 輪，第 4 輪起換更強的模型；Minor 交給最終審閱分類 | 重要問題一定修好，小問題不會無限延長工期 |
| 審閱者守則 | 唯讀；不相信報告只信程式碼；針對指定風險（越權、個資、併發）做聚焦檢查；每個問題附檔案與行號 | 審閱結果可驗證、可執行 |
| 變異測試 | 實作者暫時拿掉修正，確認測試會失敗，再還原 | 證明測試真的有在測，不是「怎樣都會過」 |
| 試跑（spike） | 第一次用的框架，先寫一組行為測試摸清楚並長期保留，再寫正式程式（M5 起） | 避免做到一半才發現框架行為和想像不同；升級套件時能立即發現改變 |
| 品質關卡 | 一支腳本跑完建置、格式、測試、文件編碼、弱點掃描 | 專案沒有 CI，以本機關卡取代 |
| 實機驗證 | 暫時的 Live 測試＋開發設定＋user secrets；每項有可對照的證據 | 只有真實模型才會出現的問題（例如 M2 的介面不相容） |
| 規範與記憶 | CLAUDE.md（版本、編碼、不自動 commit）、開發慣例速查表、專案記憶 | 每個新代理都遵守同一套規則；跨對話也記得使用者的偏好 |

### 10.6 白話版：每個機制為什麼存在（給新手）

| 機制 | 白話比喻 | 如果不這樣做，會發生什麼（本專案的例子） |
|---|---|---|
| 子代理隔離 | 請沒看過草稿的人來校稿，才看得出錯字 | 自己寫、自己審，容易「看到自己想看的」；M4 四條個資漏網路徑都是獨立審閱者找到的 |
| 用檔案交接 | 工單與驗收單，不靠口頭交代 | M5 最終審閱的差異檔約 1.56 萬行；若貼進對話，統籌者很快就「記不住」前面的事 |
| git 暫存區當檢查點 | 遊戲的存檔點：每過一關就存一次 | 不能自動 commit，但修壞了仍要能精確知道「這一輪改了什麼」 |
| 帳本 | 工地日誌 | 長對話會被壓縮；沒有帳本，統籌者可能重做已完成的任務或漏掉延後的小問題 |
| 裁定 | 現場主管當場拍板，並在日誌寫下理由 | 每個小缺口都停下來問使用者，一個里程碑會被拖成好幾天 |
| 問題分級 | 醫院的檢傷分類：重症先處理，小傷登記後統一處理 | 每個小問題都要求立即修，修正輪會無限延長 |
| 變異測試 | 故意拔掉保險絲，看警報會不會響 | M3 有個測試兩邊比的是同一個字串，「怎樣都會過」，等於沒測 |
| 試跑 | 正式開店前先試菜 | M4 做到一半才發現框架的 fan-in 缺陷；M5 起先試跑再寫計畫 |
| 品質關卡 | 出貨前的品管檢驗 | 沒有 CI，沒人幫你擋格式錯、編碼錯、弱點套件 |
| 實機驗證 | 正式演出前的彩排 | M2 的模型在原本的介面上直接拒絕工具呼叫；假模型永遠不會告訴你這件事 |
| 不自動 commit | 業主簽收才入帳 | 使用者保有最後決定權，也能先看「Claude 代為決定的事項」 |

### 10.8 實例：「用最強的模型做全分支最終審閱」的提示詞怎麼下

> 使用者 2026/10/24 提問：「現在用最強的模型做全分支最終審閱，這樣的提示詞該如何下達？」以下是 M5 實際送出的內容與每一段的用意。

**第一步：先把要審的程式差異做成一個檔案**（統籌者自己跑，不貼進對話）：

```bash
# 工作目錄 vs main（M5 起點 ea599dc），排除自動產生的 migration Designer／Snapshot
git add -N .
git diff --stat ea599dc -- . ':(exclude)*.Designer.cs' ':(exclude)*ModelSnapshot.cs' ':(exclude).superpowers'
git diff -U10   ea599dc -- . ':(exclude)*.Designer.cs' ':(exclude)*ModelSnapshot.cs' ':(exclude).superpowers' > final-review.diff
```

**第二步：派一個子代理，並指定最強的模型。**

- **「最強的模型」怎麼指定**：派工時，在工具參數裡寫明模型，而不是在提示詞文字裡要求。
  - 這次的參數：`subagent_type: general-purpose`、`model: opus`、`description: "Final whole-branch review M5"`。
  - 不指定的話，子代理會沿用預設模型。
  - 本專案的分工：最終審閱、第一次使用的框架、併發與安全相關的任務都用 Opus；一般任務用 Sonnet；小範圍的複審用 Haiku。
- **提示詞文字**：以下是實際送出的內容。提示詞用英文寫，因為子代理讀程式與英文 API 較精確；給使用者的說明一律用繁體中文。

```text
You are a Senior Code Reviewer. Review the whole M5 branch of a Blazor/.NET 10 after-sales demo
built on Microsoft Agent Framework 1.25 before it is merged.

## What Was Implemented (Tasks 1–7 + Task 8 step 1 docs)
1. Spike: MafHandoffBehaviorTests pinning MAF Handoff/AIContextProvider behaviour.
2. Long-term memory data layer … 3. Memory in the single agent … 4. 「我的 AI 記憶」 page …
5. Multi-agent Handoff mode … 6. AgentHandoff channel + IsAi() … 7. Customer page UI … 8. Docs …

## Requirements / Plan
- Plan: docs/prd/售後Agent展示系統-M5實作計畫.md (Global Constraints, Review Focus, Tasks).
- Spec: docs/prd/售後Agent展示系統-設計.md §4.7, §3.1, §6.
- Conventions: docs/architecture/開發慣例與限制速查.md
- Ledger with every ruling (R1–R7), every finding and every deferred minor: …/progress.md
  — triage the deferred minors (fix before merge / document / accept).
- Per-task reports task-1..8-report.md and maf-handoff-api.md in the same folder.

## Diff to Review
No commits: base = main ea599dc, head = working tree (staged). Whole-branch diff in one file:
…/final-review.diff (~15.6k lines — review in passes). Read-only: never mutate the working tree,
index, HEAD or branch. Do not dispatch subagents.

## Focus (cross-task issues per-task reviews could not see)
- End-to-end flows: Handoff turn → card → confirm/cancel/abandon → request creation (channel
  AgentHandoff) → M4 pre-review/panel/staff assistant; memory remember → injection next turn →
  delete on page → not injected; replay of Handoff recordings; demo reset.
- Privacy: every new model-facing path — no personal data; injection-safety of memory values.
- Concurrency/threading: OffThread workflow vs circuit-scoped services, emit lock, page callbacks.
- DI/lifetimes, migrations order, prompt keys (11) consistency, audit totals.
- Test-suite stability: known remaining flakes … recommend a concrete fix and grade it.
- Docs accuracy: spot-check the new MAF feature doc against the code (MAF vs MEAI attribution,
  "used / not used" claims, no invented APIs).

## Declined to judge
Before your verdict, list every behaviour you set aside as outside the plan/spec, with the reason.

## Output Format
### Strengths / ### Issues (Critical / Important / Minor — each: file:line, what's wrong,
impact if not fixed, how to fix) / ### Deferred-minor triage / ### Declined to judge /
### Recommendations / ### Assessment — Ready to merge? [Yes | No | With fixes]
```

**每一段的用意：**

| 段落 | 寫什麼 | 為什麼要寫 |
|---|---|---|
| 角色一句話 | 資深審閱者、審整個分支、合併前 | 定調：這是合併前的最後一道關，不是單一任務的檢查 |
| 做了什麼 | 逐項列出本里程碑的任務 | 子代理是全新的上下文，完全不知道前面發生什麼；給地圖，它才知道要看哪裡 |
| 需求來源 | 計畫、設計、慣例速查、**帳本**、各任務報告的路徑 | 讓它以「規格」為準來判斷，而不是憑感覺；帳本裡的裁定與延後的小問題要它一併分類 |
| 差異檔 | 一個檔案包含整個分支的差異，並說明起點是哪個 commit | 審閱代理一次讀完，不用自己跑 git、也不會漏看；主對話不必承載上萬行差異 |
| 唯讀＋不可再派子代理 | 明文禁止改檔、改 git、再分派 | 審閱不能動到程式；也避免它自己再開審閱者，造成重複成本 |
| 聚焦項目 | 這次最可能出事的跨任務風險：端到端流程、個資、執行緒、DI、測試穩定、文件正確性 | 最強的模型也需要方向；這一段是讓它花時間在「單一任務審閱看不到的地方」 |
| Declined to judge | 要它列出「刻意不判斷」的項目與理由 | 避免它默默略過，統籌者可以逐條決定要不要處理 |
| 輸出格式 | 固定標題、三級嚴重度，每個問題都要附檔案行號、影響、修法，最後給明確的「可否合併」 | 結果可以直接轉成修正任務；也正好對應使用者要求的「怎麼找到、不解決會怎樣」 |

**第三步：處理結果。**
1. 所有 Critical／Important 問題，加上統籌者判斷要修的 Minor，整理成一份清單。
2. 派**一次**修正：同一個實作代理，或一個新的強模型代理。
3. 修正後再派一次範圍內複審，只檢查那份清單有沒有解決、有沒有改壞別的地方。
4. 所有發現連同「怎麼找到、影響、修法」寫進本文件第十四節。

**自己要下類似提示詞時的重點：**
1. 用參數指定模型，不要只在文字裡說「用最強的」。
2. 把差異做成檔案、把規格與帳本給路徑，不要把大量內容貼進提示詞。
3. 明確寫出「要找的是跨任務問題」，並列出這次最擔心的幾個風險。
4. 要求固定的輸出格式與明確的結論（可否合併），並要求每個問題都附影響與修法。
5. 要求列出「刻意不判斷」的項目，避免遺漏被默默帶過。

### 10.9 為什麼比「直接寫完」慢，以及為什麼值得

- **為什麼比較慢**：
  - 每個任務都由新代理重新讀程式碼。
  - 每個任務都跑完整測試（2000 多個，約 1～2 分鐘一輪）。
  - 審閱常抓到真問題，多一輪修正。
  - 任務會改到同一批檔案，只能依序執行。
  - 專案規範測試很多，每個新功能都要做齊。
- **為什麼值得**：第十四節的紀錄顯示，大部分重要問題都是「功能能跑、測試也過」的情況下，由審閱者找到的，例如個資外洩路徑、併發重複執行、回放失準。這些問題如果到展示時才發現，代價遠大於多花的時間。

## 十一、實戰手冊：下次如何用同樣的方法開發新系統

> 本節把第四～十節的經驗整理成「照著做」的步驟。每一步都寫：做什麼、誰做、產出什麼、大約多久（依第十三節的實際資料）、常見錯誤、檢查清單。

### 11.0 全流程一覽

```text
【專案開始一次】
  ① 需求釐清 ──▶ ② 寫設計與企劃 ──▶ ③ 切里程碑
【每個里程碑重複】
  ④ 計畫（含探索） ──▶ ⑤ 執行（逐任務：實作 → ⑥ 審閱與修正 → 暫存）
       ──▶ ⑦ 最終審閱 ──▶ ⑧ 品質關卡 ──▶ ⑨ 實機驗證 ──▶ ⑪ 寫歷程 ──▶ ⑩ 交付與 commit
```

| 步驟 | 誰做 | 主要產出 | 大約時間 |
|---|---|---|---|
| ① 需求釐清 | 使用者回答、Claude 提問 | 決策表 | 與 ② 合計約 1 小時（約 20 輪問答） |
| ② 設計與企劃 | Claude 寫、審閱代理找疑點、使用者核准 | 設計文件、企劃書 | 同上 |
| ③ 切里程碑 | Claude 提案、使用者核准 | 里程碑表（在設計文件內） | 含在 ② |
| ④ 計畫 | 探索代理＋統籌者；使用者核准 | 實作計畫、工作區 | 15～30 分（M4 含探索約 50 分） |
| ⑤ 執行 | 實作代理 | 程式、測試、報告檔 | 每任務 20～30 分；高風險任務 45～60 分 |
| ⑥ 審閱與修正 | 審閱代理、複審代理 | 問題清單、修正 | 約佔里程碑 15%～20%；每個問題修正平均 3～5 分 |
| ⑦ 最終審閱 | 最強模型的審閱代理 | 跨任務問題、小問題分類 | 20～40 分（M3 約 30、M4 約 45） |
| ⑧ 品質關卡 | 統籌者跑腳本 | `QUALITY GATE PASSED` | 數分鐘（全套測試一輪約 1～2 分） |
| ⑨ 實機驗證 | 實機驗證代理＋使用者的模型 | 驗證表與證據 | 20～40 分（M3 約 20、M4 約 25） |
| ⑩ 交付與 commit | 使用者決定、Claude 執行 | commit／合併／推送 | 數分鐘 |
| ⑪ 寫歷程 | 統籌者 | 本文件新增一節 | 約 10 分 |

### 11.1 步驟 ①：需求釐清

- **做什麼**：說清楚「為什麼做、給誰看、怎樣算成功、怎樣算失敗」，然後回答 Claude 的選擇題，直到沒有模糊的地方。
- **誰做**：使用者回答；Claude 一次問一題、每理解一部分就複述確認；探索代理同時讀現有程式。
- **產出**：決策表（像 4.2 那張 22 列的表）。
- **怎麼回答 Claude 的選擇題**：
  - 每題 Claude 會附一個「建議」選項與理由。理由說得通就選建議（本專案使用者常這樣做，見 4.6）。
  - 會改變**範圍、成本、對外承諾、安全底線**的題目，一定自己想清楚再選。例如：要不要做多 Agent、要不要長期記憶、失敗標準、展示長度、Agent 拿不準時要停還是猜。
  - 不確定時可以回答「先用建議，之後可以改」，並請 Claude 寫進設計文件的「代為決定的事項」，之後核准時再看一次。
  - 一開始就說「若有不清楚的地方，需要反覆與我提問討論，直到完全理解我的需求與目的」（本專案的原話），Claude 就會問到底。
- **一定要自己決定的事**：目的與觀眾、做／不做的範圍、失敗標準、對外的東西（企劃書、展示劇本）、安全底線。
- **可以交給 Claude 決定的事**：類別名稱、資料表設計、套件版本、測試寫法——但要看它的「代為決定」清單。
- **常見錯誤**：
  - 一開始說「全部都要」卻不排順序。
  - 沒有定「失敗標準」，做完才發現「面板太工程師」。
  - 把技術選擇全丟給 AI，卻不看它的「代為決定的事項」。
- **檢查清單**：
  - [ ] 目的、觀眾、成功與失敗標準都寫下來了
  - [ ] 做什麼、不做什麼（非目標）都寫下來了
  - [ ] 安全底線寫下來了（例如「拿不準一律停下來問」）
  - [ ] Claude 複述的內容我都確認過

### 11.2 步驟 ②：寫設計與企劃

- **做什麼**：把決策寫成設計文件（目標／非目標／反目標、使用者的決定、Claude 代為決定的事項、系統組成、里程碑與驗證方式），大系統另寫企劃書（對外版、內部版）。
- **誰做**：Claude 寫；再派一個「實作者視角」的審閱代理找疑點（階段 0 找出 9 個，只有 3 題需要回問使用者）；使用者核准。
- **產出**：`docs/prd/<系統>-設計.md`、企劃書。
- **常見錯誤**（本專案的教訓）：
  - 只寫功能、不寫「怎麼驗證」。
  - 沒把「可重現的示範資料」列為需求（M3 做回放才發現重置後編號會變）。
  - 沒列出「所有送給模型的路徑」（M4 審閱抓到四條沒遮蔽的路徑）。
- **檢查清單**：
  - [ ] 每個里程碑都有驗證方式
  - [ ] 有「Claude 代為決定的事項」清單，使用者看過
  - [ ] 示範資料可重現（固定編號）
  - [ ] 送給模型的資料路徑與「刻意不送的欄位」列出來了
  - [ ] 文件 UTF-8 含 BOM、列入索引

### 11.3 步驟 ③：切里程碑

- **做什麼**：把系統切成一段段「可以單獨展示」的里程碑。
- **原則**：
  - **大小**：建議 1～2 小時一段（第十九節 #6）。本專案實際每段 2.5～7 小時，越大越難預估。
  - **風險高的先做**：第一次用的框架排在前面，並在里程碑的第一個任務做「試跑」，把框架行為釘成測試（M5 任務 1：`MafHandoffBehaviorTests`）。
  - **第一個里程碑就接真實模型**：做一次真實模型冒煙測試（第十九節 #2；M2 中段才發現模型不接受原本的介面）。
  - **地基先做**：計費、日誌、模擬資料（M0、M1）先於 Agent（M2）。
- **常見錯誤**：把「展示用功能」（重置、回放）放到最後，結果前面的資料設計不支援。
- **檢查清單**：
  - [ ] 每個里程碑都能單獨展示
  - [ ] 第一次用的框架有試跑任務
  - [ ] 第一個里程碑含真實模型冒煙測試

### 11.4 步驟 ④：計畫

- **做什麼**：先探索、再寫逐任務計畫，使用者核准後存進 `docs/prd/`，並建立工作區。
- **誰做**：探索代理（1～3 個同時）＋統籌者；使用者核准。
- **探索要查兩件事**：現有程式的接點；框架的**真實** API 與**不存在**的名稱（M4 草稿裡的 `StreamAsync`、`AddFanInEdge` 都不存在）。
- **一份好的任務說明（brief）要有**：

| 項目 | 例子（M5 任務 4「我的 AI 記憶」頁） |
|---|---|
| 要建立／修改的檔案 | `ShopMemoryPage.razor`（`/shop/memory`）、`ShopMemoryView.razor(.cs/.css)`；修改 `ShopLayout.razor`、`PageHelpCatalogTests.RoutesWithoutHelp` |
| 行為 | 列出記憶（種類、內容、記住時間）；每筆可刪除、另有「全部刪除」，都先確認；沒有記憶時顯示空狀態 |
| 要寫的測試名稱 | `Memory_ListsOnlyOwnMemories`、`Memory_Delete_RemovesAndRefreshes`、`Memory_DeleteAll_AsksConfirm`、`Memory_Empty_ShowsHint` |
| 步驟 | 失敗測試 → 實作 → 通過（含規範測試）→ 檢查點 |

- **整份計畫還要有**：全域限制（所有任務都要遵守的規則）、審閱重點（最可能出事的 5 種情況，各對應一個測試名稱）、已驗證的框架事實、時間預估、「Claude 代為決定的事項（請檢查）」。
- **工作區**：`.superpowers/sdd/<計畫名>/`（git 不追蹤），放任務說明檔、全域限制、實作規則、審閱規則、帳本。
- **常見錯誤**：計畫憑記憶寫 API 名稱；說明檔沒寫測試名稱，審閱時無從對照。
- **檢查清單**：見 16.1。

### 11.5 步驟 ⑤：執行（子代理迴圈）

- **做什麼**：一次派一個實作代理，照說明檔做一個任務。
- **實作代理的固定步驟**：先寫會失敗的測試並記錄（RED）→ 寫程式 → 測試通過（GREEN）→ 跑全套測試與格式檢查 → 自我檢查 → 寫報告檔 → 只回覆短短的結論（狀態、一行測試摘要、疑慮、報告路徑）。
- **四種回報狀態**：`DONE`（完成）、`DONE_WITH_CONCERNS`（完成但有疑慮）、`BLOCKED`（做不下去）、`NEEDS_CONTEXT`（缺資訊）。做不下去時要停下來說，**不要硬做**。
- **為什麼一次只派一個**：任務常會改到同一批檔案，同時做會互相覆蓋。
- **常見錯誤**：
  - 先寫程式、後補測試，卻沒用變異測試證明測試有效。
  - 為了讓規範測試通過而削弱規範測試（規則要求「滿足它，不要削弱它」）。
  - 順手改了範圍外的東西。
- **檢查清單**：見 16.2。

### 11.6 步驟 ⑥：審閱與修正

- **做什麼**：每個任務完成後，派一個全新的審閱代理看程式差異。
- **審閱代理的守則**：先判斷「有沒有照需求做（不多不少）」，再判斷品質；差異檔讀一次；只有在能說出具體風險時才去看差異以外的程式；不相信實作者的報告；每個問題附檔案與行號；分三級。
- **修正流程**：Critical／Important → 交回原實作者修正 → 派複審代理只檢查這次修正（最多 5 輪）；Minor → 記進帳本，最後由最終審閱分類。
- **計畫有缺口時**：統籌者做「裁定」，寫下決定、理由、若錯的代價（例如 M4 的「不新增『已完成』狀態」寫進「Claude 代為決定的事項」）。
- **常見錯誤**：讓實作者自己找人審（審閱是統籌者的工作，重複審閱只增加成本）；複審時擴大範圍，修正輪永遠結束不了。
- **檢查清單**：
  - [ ] 每個 Critical／Important 都是 ADDRESSED（「嘗試過」不算）
  - [ ] 修正報告列出涵蓋的測試與輸出
  - [ ] Minor 都進了帳本，含「怎麼找到、影響」

### 11.7 步驟 ⑦：最終全分支審閱

- **做什麼**：所有任務完成後，用最強的模型看整個分支，專找「單一任務看起來都對、組合起來才錯」的問題，並分類帳本裡延後的小問題。
- **怎麼下提示詞**：見 10.8 的完整實例。
- **處理結果**：整理成一份清單 → 派**一次**修正 → 一次範圍內複審 → 寫進第十四節。
- **例子**：M3 最終審閱抓到「故障開關在確認卡這一步沒作用」，修正前以測試證實**真的會建立申請**；M4 抓到「回放金劇本 B 會隨機中止」的時間差問題。
- **檢查清單**：見 16.3。

### 11.8 步驟 ⑧：品質關卡

- **做什麼**：在本機執行 `pwsh ./scripts/Invoke-QualityGate.ps1`，依序跑建置、格式、全套測試、文件編碼（`docs/` 與根目錄的 `.md` 要 UTF-8 含 BOM）、弱點掃描。各步驟擋什麼見 [CI-CD 與品質檢查](../operations/CI-CD與品質檢查.md)。
- **同時要做**：`appsettings.json` 的版本 Patch +1（例：1.0.5 → 1.0.6）；相關文件與操作說明同步。
- **常見錯誤**：測試偶爾失敗就重跑到過——不穩定的測試會藏住真正的回歸，要當成問題處理。
- **檢查清單**：
  - [ ] 看到 `QUALITY GATE PASSED`
  - [ ] 版本 Patch +1
  - [ ] 文件同步、含 BOM

### 11.9 步驟 ⑨：實機驗證（一定要做）

- **為什麼一定要做**：自動測試用的是「假模型」（照腳本回答的模型），它不會檢查真實服務的規則。本專案三次實例：
  - **M2**：使用者的模型在原本的介面（Chat Completions＋工具）直接回 HTTP 400，整個 Agent 在真實環境無法運作；追加任務 7b 改用 Responses API 才跑通。
  - **M3**：`ReasoningEffort=low` 看不出有沒有送出，改送 `none` 被模型以 400 拒絕，才證明設定真的有傳到服務端；回放省錢也是用 Token 筆數 63 → 63 證明。
  - **M5**：真實的 Responses API 會檢查「工具呼叫與工具結果要成對」，假模型不檢查；第一次實機驗證因此抓到一個「自動測試全過、實機卻會讓多 Agent 劇本中斷」的缺陷（詳細待 M5 小節與 14.8 補上）。
- **怎麼做**（M3 起的固定做法）：
  - 寫一個**暫時的**整合測試（`WebApplicationFactory`＋開發設定＋user secrets），直接驅動真實服務。
  - 每一項開始前先重置示範資料、即時模式、故障全關。
  - 每一項都記證據：申請編號、停止原因、Token 用量與 AI 對話紀錄筆數前後、錄製編號。
  - 發現產品缺陷就**停下來回報**，不要在驗證時順手修。
  - 驗完刪除暫時檔、用 `git status --short` 確認沒留下變更，把開發資料庫恢復成初始示範資料。
  - 金鑰與端點絕不寫進檔案、日誌或報告。
- **檢查清單**：
  - [ ] 每一項都有可對照的證據
  - [ ] 暫時的驗證程式已刪除
  - [ ] 開發資料庫已恢復（故障全關、即時模式、初始資料）
  - [ ] 報告不含金鑰、端點、個資

### 11.10 步驟 ⑩：交付與 commit

- **做什麼**：統籌者列出「Claude 代為決定的事項」與驗證結果，**等使用者決定**；使用者說「commit / merge / push / delete local branch」後才執行。
- **為什麼不自動 commit**：CLAUDE.md 規定「需要 commit 的時候，不能自動去做 commit」。使用者保有最後決定權。
- **commit 訊息**：要說明版本變更（例：「M4：申請初審 Workflow、核准執行與顧客通知、客服 AI 助手；版本 1.0.5 → 1.0.6」）。
- **檢查清單**：見 16.3。

### 11.11 步驟 ⑪：寫歷程

- **做什麼**：在本文件新增一節，固定記錄：使用者指示（原話）、選擇、Claude 做了什麼、結果（測試數、版本、commit）、最花時間的工作、新工件、學到的事；審閱發現寫進第十四節（四件事：是什麼、怎麼找到、影響、怎麼修）；更新第十三節估時對照與第十九節回顧。
- **時間**：約 10 分（M4）。
- **常見錯誤**：工作區（含帳本與報告檔）在里程碑結束時刪除，小問題就無法回補（M0～M4 就是這樣，見 14 節開頭的說明）。**刪除工作區前，先把帳本重點寫進本文件。**

### 12.3 派實作代理（統籌者 → 子代理）

**關鍵條款（中文摘要）**：
1. 先讀任務說明檔，它是**唯一**的需求來源；有疑問先問（`NEEDS_CONTEXT`），不要猜。
2. 只做說明檔寫的事，不多做；照著既有程式的寫法。
3. TDD：先寫失敗測試、記錄 RED，再實作、記錄 GREEN；若先寫了程式，就暫時拿掉程式證明測試會失敗（變異測試）。
4. 不准執行 `git add`／`commit`／`stash`／`checkout`／`reset`（統籌者用暫存區當檢查點）；不准自己改版本號。
5. 不准再派子代理（審閱是統籌者安排的，自己找人審只會重複花錢）。
6. 太難就停下來回報 `BLOCKED`，「做不好比不做更糟」。
7. 開發時跑聚焦測試；回報前跑一次全套測試與 `dotnet format --verify-no-changes`。
8. 專案規則：先讀速查表；遵守全域限制與已驗證的 API 事實（不要猜 API 名稱）；規範測試要滿足、不能削弱；新的送模型路徑要遮蔽個資；不寫出金鑰；文件 UTF-8 含 BOM。
9. 完整報告寫進報告檔；回覆只給短短的結論。
10. 審閱有問題時會被叫回來修，修完把「改了什麼、跑了哪些測試、輸出」附加在報告檔後面。

**範本**（Agent 工具參數：`subagent_type: general-purpose`、`model: <sonnet，高風險改 opus>`、`description: "Implement Task N: <名稱>"`）：

```text
You are implementing Task N: <task name>.

Read your task brief first: <workspace>/task-N-brief.md — it is the only source of requirements.
Binding rules: <workspace>/implementer-rules.md and <workspace>/global-constraints.md
(it includes verified framework API facts; do not guess API names).

Context: <where this task fits; which earlier task's output it uses; rulings that affect it>.

If anything is unclear, ask now (reply NEEDS_CONTEXT) instead of guessing.
TDD: record RED, then GREEN. If you wrote code first, prove the tests bite with a temporary revert.
Never run git add/commit/stash/checkout/reset. Do not bump the version. Do not dispatch subagents.
Run focused tests while iterating; run the full test project and
`dotnet format src/CustomerHelpAgent --verify-no-changes` once before reporting.

Write the full report to <workspace>/task-N-report.md.
Reply only with: Status (DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT),
a one-line test summary, your concerns, and the report path.
```

### 12.4 派任務審閱代理

**關鍵條款**：
1. 這是單一任務的關卡，不是合併前審閱。
2. 先判斷符合需求（缺了什麼、多了什麼、誤解了什麼），再判斷品質（責任分離、錯誤處理、重複程式、邊界情況、測試是否真的有測）。
3. 差異檔讀一次，不重跑 git；只有在能說出具體風險時，才去看差異以外的程式，而且要寫出「風險是什麼、查了什麼」。
4. 唯讀；不准再派子代理。
5. **不相信報告**：報告是實作者的說法，要對照程式驗證；「刻意保持簡單」這類理由不能降低問題等級。
6. 不重跑全套測試；只有在有具體疑慮時跑一個聚焦測試。報告裡的警告或雜訊也算問題。
7. 每個問題附檔案:行號；三級：Critical（必修）、Important（不修就不能信任這個任務）、Minor；計畫本身要求的缺陷算 Important 並標「plan-mandated」。
8. 先寫優點，再列問題；結論 `Approved` 或 `Needs fixes`。

**範本**（參數：`model: sonnet`，安全／併發／第一次用的框架改 `opus`；`description: "Review Task N"`）：

```text
Review Task N (spec + quality). Follow <workspace>/reviewer-instructions.md.
Task brief: <workspace>/task-N-brief.md
Implementer report: <workspace>/task-N-report.md
Diff file (working tree vs index, migrations' Designer/Snapshot excluded): <workspace>/task-N-review.diff
Named risks — make one focused check for each and say what you checked:
1. <例：customer A can read customer B's memory>
2. <例：a new model-facing path leaks phone/address>
3. <例：two tabs confirm the same card concurrently>
```

### 12.5 派範圍內複審代理

**關鍵條款**：
1. 只做兩件事：對每個列出的問題下結論，並檢查修正差異有沒有改壞東西。
2. 每個問題：`ADDRESSED` 或 `NOT ADDRESSED`，附檔案:行號證據；「嘗試過」不算解決。
3. 確認修正報告有列出涵蓋的測試與輸出。
4. 修正差異以外的問題寫在「範圍外觀察」，不阻擋這個任務。
5. 唯讀、不再派子代理、不重跑全套測試。

**範本**（參數：`model: haiku` 或 `sonnet`；`description: "Re-review Task N fix round R"`）：

```text
Findings under verification (verbatim from the review):

- <finding 2>

Fix diff (working tree vs fix-base tree <hash>): <workspace>/task-N-fix1.diff
```

### 13.3 實作範例：怎麼估下一個里程碑

| 項目 | 低 | 高 |
|---|---|---|
| 規劃 | 15 分 | 30 分 |

- 只算實作，忘了審閱、修正、最終審閱與實機驗證（它們合計常佔 30% 以上）。

- 忘了外部因素：模型服務過載（M4 遇到 529 兩次，多花約 10 分）。
- 沒記錄實際時間，下一次只能憑感覺。

## 十四、審閱與修正機制紀錄（持續累積）

> 使用者 2026/10/24 指示：Agent 在審閱階段找到問題並修正的過程也要記錄下來，說明這個機制的價值。之後每個里程碑都在本節補上一個小節。
>
> **自 M5 起的記錄方式**（使用者 2026/10/24 追加）：**所有**審閱發現都要記錄，包括小問題。每一項要寫：
> - 問題是什麼
> - **怎麼找到的**（哪一層審閱、用什麼方法：讀差異、針對指定風險的聚焦檢查、變異測試、試跑測試、實機）
> - **若不解決會造成什麼影響**
> - 怎麼修、修了幾輪
>
> M0～M4 的工作區（含帳本與報告檔）在各里程碑結束時已刪除，所以這幾節只保留當時整理的重要問題，小問題無法完整回補。

### 14.1 機制怎麼運作

| 層級 | 什麼時候 | 誰做 | 看什麼 |
|---|---|---|---|
| 任務審閱 | 每個任務實作完 | 新開的審閱代理（不認識實作者、不帶先入為主） | 這個任務有沒有照需求做、有沒有多做、品質與測試是否可信 |
| 範圍內複審 | 每一輪修正後 | 另一個審閱代理 | 只看這次修正：問題是否真的解決、有沒有改壞別的 |
| 最終全分支審閱 | 所有任務做完、交付前 | 最強的模型 | **跨任務**的問題：安全、資料一致性、併發、計費、個資、規格是否整體成立 |
| 實機驗證 | 里程碑尾端 | 實作代理用使用者的真實模型 | 自動測試用假模型測不到的行為 |

- 問題分三級：**Critical**（必修）、**Important**（交付前要修）、**Minor**（記錄下來，最後統一判斷要不要修）。
- Critical／Important 一律交回原實作者修正，再由新的審閱代理做範圍內複審，最多 5 輪；本專案到 M3 為止每個問題都在第 1 輪就修好；M4 任務 3 第一次出現第 2 輪（複審發現重試範圍太寬）。
- 審閱代理被要求「不相信實作者的報告，只相信程式碼」，並對指定風險（例如越權、個資外洩）做針對性檢查。
- 遇到計畫本身有缺陷（例如漏寫的需求），由 Claude（統籌者）做出「裁定」並記錄理由與代價，不停下來等待。

### 14.2 新手怎麼讀這些發現

- **不要只看「問題」那一欄**。每一列最有價值的是「如果沒抓到會怎樣」：它告訴你這類錯誤的代價，下次寫程式時就會主動防。
- **注意「功能能跑、測試也過」**。下面大部分問題，當下的程式都能跑、測試也全綠；這正是要有審閱的原因。
- **把每一列換成一句自問**。例如看到「寫入後才逾時卻回報失敗」，就問自己：「我的程式在『已經寫入、但後面出錯』時，會不會告訴使用者『沒成功』？」
- **先看 14.3 的分類**，再挑一類深入讀，比從頭讀到尾有效。

### 14.3 問題類型索引：寫程式時要主動找的九種錯

| 類型 | 白話 | 本專案的例子（節次） | 寫程式時自問 |
|---|---|---|---|
| 個資外洩路徑 | 個資跟著某條路送進模型或日誌 | 照片節點送出顧客描述原文、照片 base64 寫進 AI 對話紀錄（14.7 任務 5）；助手「查看初審結果」工具原文送出（14.7 任務 8） | 這段文字最後會不會送給模型？會不會寫進日誌？有沒有經過共用遮蔽與測試？ |
| 併發與重複執行 | 兩件事同時發生，做了兩次或互相蓋掉 | 兩個分頁同時按確認（14.5）；兩個初審同時建立撞號（14.7 任務 3）；重啟後已完成節點重跑、重複計費（14.7 任務 4） | 兩個人／兩個分頁同時按，會怎樣？做兩次會怎樣？ |
| 當機復原 | 做到一半當機，復原後狀態錯 | 決定已寫入、進度還沒存檔就當機，案件被標成執行失敗（14.7 任務 6）；寫入申請時關閉頁面（14.5） | 在每兩行之間斷電，重開後看到的狀態對嗎？ |

### 14.10 這個機制的價值

1. **很多問題是「功能都能跑、測試也都過」的情況下才被抓到的**：例如照片沒備份、寫入後逾時被當成失敗、重置後編號會變。這類問題靠自動測試抓不到，要靠一個「沒參與實作、專門找碴」的角色。
2. **越早發現越便宜**：任務審閱抓到的問題，修正平均只要 3～5 分鐘；同樣的問題如果到展示當天才發現，可能整場展示失敗。
3. **後面的功能會檢驗前面的功能**：M2 的錯誤是在 M3 才被發現的。這說明「每個里程碑都做最終審閱」之外，下一個里程碑的實作也是一種審閱。
4. **最終審閱專抓跨任務問題**：單一任務看起來都對，但組合起來才出錯（例如故障開關 × 確認卡、回放 × 執行紀錄）。這類問題只有看整個分支才看得到。
5. **代價是時間**：審閱與複審約佔每個里程碑 15%～20% 的時間，再加上修正。對核心流程、安全、會被重用的程式，這筆時間非常值得；對低風險的畫面調整，可以考慮只做最終審閱。

## 十五、經驗法則與常見陷阱

> 從各階段的「學到的事」（4.6、5.8、6.7、7.7、8.7）與第十九節回顧整理而成。每條一句白話＋一個本專案的例子。

### 15.1 AI Agent 設計

| 法則 | 本專案的例子 |
|---|---|
| **模型只提議，程式才執行。** 寫入的權利永遠不交給模型。 | `create_after_sales_request` 包成需要核准的工具，顧客按確認卡、程式重核後才寫入 |
| **身分永遠由程式帶入。** 工具參數裡不要有使用者 Id。 | `query_my_orders` 只收顏色、關鍵字；測試驗證「偽造他人 Id」無效 |
| **拿不準就停，而且由程式強制。** 提示詞說「要停」不夠，程式要真的擋。 | `not_found`／`conflict` 之後，Guard 直接封鎖建立申請，不出確認卡 |
| **失敗要分種類講清楚。** 「沒查完」和「查過了沒有」是兩回事。 | F1 逾時回覆「目前無法確認，不代表您沒有這筆訂單」 |
| **顧客看到的關鍵事實由程式產生。** 不採用模型轉述。 | 規則卡、確認卡、申請編號、逾時固定說明都由程式產生 |
| **寫入成功之後的任何錯誤，都要照樣回報結果。** | M2 審閱：寫入後才逾時卻回報失敗，顧客可能重送；改成照樣回報申請編號 |
| **步驟固定的用 Workflow，要看現場的用 Agent。** | M4 初審是固定流程圖；M2 顧客對話由 Agent 判斷 |
| **AI 可以建議，決定權在人。** | 初審只給建議，客服按核准才開處理單 |

### 15.2 提示詞

| 法則 | 本專案的例子 |
|---|---|
| **提示詞是軟限制，程式是硬限制。** 重要規則兩邊都要有。 | 「拿不準就停」寫在提示詞，也由 Guard 依 `ToolOutcome.status` 強制 |
| **依實機行為調整提示詞。** 假模型會照腳本回答，真模型不會。 | M2 任務 7b 依真實模型的回應調整提示詞，劇本 A、B 才跑通 |
| **劇本台詞會影響模型是否追問。** | 劇本 B 第二句沒說黑鞋穿過沒，模型最後會再問一次 |
| **不能被拿掉的規則，不要放在可編輯的提示詞裡。** | 記憶注入文字由程式產生；提示詞範本後面固定附加 `AiPromptGuardrails` |
| **給子代理用英文、給使用者用繁體中文。** | 10.8 的最終審閱提示詞用英文；進度回報一律繁體中文 |

### 15.3 測試

| 法則 | 本專案的例子 |
|---|---|
| **測「下一步」，不要只測到動作本身。** | M2 沒測「確認後再講一句」，嚴重錯誤留到 M3 才發現 |
| **證明測試會失敗。** 拿掉功能，測試要紅。 | M3 有個測試兩邊比同一個字串，等於沒測 |
| **假模型測不到真實服務的規則。** | M2 的介面不相容、M5 的「呼叫與結果要成對」都只有實機抓得到 |
| **用數字證明。** | 回放前後 Token 用量 63 → 63、116 → 116 筆，證明沒有呼叫模型 |
| **證明設定有送出，用一個會被拒絕的值。** | `ReasoningEffort=none` 被模型以 400 拒絕，證明設定有傳到服務端 |
| **當機復原要「真的丟掉主機再續跑」。** | 只有這種測試抓到 Workflows fan-in checkpoint 缺陷 |
| **每一條送模型的路徑都要有個資測試。** | M4 四條漏網路徑都是審閱找到的，之後要改成設計時就列清單、每條一個測試 |

### 15.4 框架使用

| 法則 | 本專案的例子 |
|---|---|
| **新框架先讀原始碼，再寫計畫。** | 探索代理發現 `StreamAsync`、`AddFanInEdge` 不存在，避免計畫寫錯 |

| **分清楚框架提供的和自己寫的。** | MAF 功能運用說明每一項都標了 MAF／MEAI／本系統自訂 |

## 十七、新手常見問題（FAQ）

**Q1：為什麼不直接讓 AI 一次寫完整個系統？**
A：能寫，但寫出來的東西沒人敢保證對。一次寫完的程式量太大，AI 自己也記不住前面的決定；錯誤會混在一起，很難知道是哪裡壞的。拆成 20～30 分鐘的小任務，每一個都有測試、有人審，錯了也只要修一小塊。第十四節的紀錄顯示，大部分重要問題都是在「功能能跑、測試也過」的情況下被審閱者找到的。

**Q2：為什麼要那麼多審閱？很浪費時間吧？**
A：審閱與複審約佔 15%～20% 的時間。但任務審閱抓到的問題，修正平均只要 3～5 分鐘；同樣的問題如果在客戶面前才發生，可能整場展示失敗。例如 M3 最終審閱抓到「故障開關在確認卡失效」，修正前測試證實**真的會建立申請**。低風險的畫面調整，可以只做最終審閱（相對時間約 0.6～0.7）。

**Q3：子代理是什麼？跟主對話的 Claude 有什麼不同？**
A：子代理是統籌者派出去的「全新的 Claude」。它看不到主對話，只拿到一份任務說明檔與規則檔，做完寫報告、回覆一句結論就結束。好處是：不被前面的討論影響、審閱者不會「同情」實作者、主對話不會被上千行程式差異塞滿。可以把它想成「每張工單都請一位新師傅」。

**Q4：為什麼不自動 commit？**
A：這是專案規定（CLAUDE.md：「需要 commit 的時候，不能自動去做 commit」）。commit 代表「這個版本被認可」，決定權在使用者。開發過程中改用 git 暫存區當檢查點：審閱通過才 `git add`，所以仍能精確知道每個任務改了什麼。

**Q5：假模型測試和實機驗證差在哪？**
A：假模型（腳本化模型）照我們寫好的腳本回答，所以測試快、穩定、可重複，適合測「程式的把關邏輯」（例如未確認不寫入、偽造身分無效）。但它不會檢查真實服務的規則，也不會像真模型一樣「自己決定」。實機驗證用使用者真實的模型跑劇本，專抓假模型抓不到的事：M2 的介面不相容、M3 的設定有沒有送出、M5 的「工具呼叫與結果要成對」。兩者缺一不可。

**Q6：遇到框架行為和想像不一樣，怎麼辦？**
A：照這個順序：
1. 先查證：讀套件的 XML 文件或原始碼（本專案讀 MAF 1.25 的 tag），不要憑記憶。
2. 寫一個最小的測試重現它。
3. 確定是框架行為或缺陷後，用自己的程式繞道（例如 fan-in 缺陷用自訂序列化轉換器）。
4. 把重現測試**長期保留**，升級套件時先跑它。
5. 寫進文件（MAF 功能運用說明 §4、速查表的踩雷點）。

**Q7：怎麼估時間？**
A：用第十三節的公式：規劃 15～30 分＋任務數 × 20～30 分＋最終審閱 20～40 分＋實機驗證 20～40 分；第一次用的框架、併發、當機復原的任務改用 45～60 分。13.3 有完整的算法範例。最重要的是**記錄實際時間**，下一次就更準。

**Q8：我只有 1 年經驗，可以照這個方法做嗎？要先學什麼？**
A：可以。這個方法的好處是「每一步都有檢查」：選擇題幫你想清楚需求、計畫幫你拆小、審閱幫你抓錯、清單幫你不漏。你要負責的是**判斷**：看得懂審閱抓到的問題為什麼嚴重、知道哪些決定要自己做。建議先照第十八節的學習路徑補基礎，特別是 C#／async、EF Core、測試與 git；然後從一個小功能開始，完整走一次第十一節的步驟。

**Q9：使用者每一步都要盯著嗎？**
A：不用。使用者主要在四個時間點出現：回答需求選擇題、核准計畫、看「Claude 代為決定的事項」、決定 commit。中間可以隨時問「現在做到哪裡了」。

**Q10：AI 會不會偷偷記住顧客的資料？**
A：本系統的長期記憶只記鞋碼、衣服尺碼、顏色、溝通偏好四種，記之前一定先出記憶確認卡；電話、地址、姓名一律拒絕；顧客可以在「我的 AI 記憶」隨時刪除，刪了下一句就不再使用（見 2.4）。

## 十九、回顧與改進建議（持續累積）

| # | 觀察 | 下次可以怎麼做 |
|---|---|---|
| 1 | 需求釐清花了約 20 輪問答，但後面設計很少返工 | 值得保留；可先給一份「預設選項清單」讓使用者一次勾選，減少輪數 |
| 2 | 實機模型相容問題到 M2 中段才發現 | 第一個里程碑就先做「真實模型冒煙測試」 |
| 3 | 「確認後下一句出錯」M2 沒測到 | 測試要涵蓋每個動作「之後的下一步」 |
| 4 | 「重置後編號會變」到 M3 做回放才發現 | 設計時就把「可重現的示範資料」列為需求 |
| 5 | 使用者不容易感受進度與時間 | 每個里程碑開始前先給預估時間；本文件持續記錄實際時間 |
| 6 | 每個里程碑 3 小時左右 | 可把里程碑切小（1～2 小時一段），或對低風險里程碑改用「直接做完再審一次」 |
| 7 | M2、M3、M4 的實機驗證都臨時寫驅動程式，驗完就刪 | 保留一支可重複使用的實機驗證程式（例如 `Category=Live`、需金鑰才執行），每個里程碑直接加項目 |
| 8 | M4 的個資遮蔽漏網路徑被審閱抓到四次 | 設計時就列出「所有送給模型的路徑」清單，每條路徑一個測試，不要靠審閱一條條找 |
| 9 | 第一次使用的框架（Workflows）實作時間是一般任務的 2 倍 | 預估時這類任務用 45～60 分；或先用一個 15 分鐘的「試跑」任務摸清框架行為，再寫計畫 |
| 10 | 實機驗證時子代理遇到服務過載（529）而中斷 | 驗證指示寫成檔案，中斷時可直接換模型重跑，不必重寫指示 |
| 11 | 進度回報曾用英文 | 回報一律用繁體中文（使用者 2026/10/24 指示） |
| 12 | M0～M4 的工作區在里程碑結束時刪除，小問題無法回補到第十四節 | 刪除工作區前，先把帳本裡的發現（含怎麼找到、影響）整理進本文件 |
| 13 | 假模型不檢查真實服務的規則（M2 介面不相容；M5 實機發現工具呼叫與結果未成對，根因是 MAF＋MEAI 轉送時帶了「來自歷史」標記，見 14.8） | 讓腳本化假模型也檢查已知的 API 規則（例如工具呼叫與結果要成對），把實機才會出現的錯誤提早到自動測試 |
| 14 | 新進開發人員很難從純紀錄式的文件學會這套方法 | 本文件 1.0 版加入觀念、實戰手冊、範本、檢查清單、FAQ 與學習路徑；之後每個里程碑也補充新的經驗法則與範例 |
| 15 | 框架的實際行為常和名稱給人的印象不同（checkpoint 單位、fan-in 缺陷、交接沒有事件型別） | 第一次使用的框架一律先試跑並把行為釘成測試（M5 起已採用），結果寫進 MAF 功能運用說明 §4 |
| 16 | M5 第一次實機就遇到框架缺陷（測試全過仍失敗） | 實機驗證排在最終審閱之前就先跑一次「冒煙」版本，越早發現越便宜；假模型持續加入真實服務的規則 |
| 17 | 提示詞規則只加在部分 Agent，其他模式沒照做 | 改提示詞時列出「所有會用到這條規則的 Agent」清單，每一份都加，並用測試檢查 |
| 18 | 測試不穩定先用「拉長等待、依序執行」處理，只降低機率 | 偶發失敗先找根因（讀錯誤訊息、檢查元件內部），不要先調參數 |

**給下一個專案的五個建議**：

1. **第一天就做三件事**：真實模型冒煙測試、可重現的示範資料、所有送模型路徑的清單。
2. **里程碑切小**：每段 1～2 小時，風險高的框架放第一段並先試跑。
3. **審閱分層不省略**：任務審閱、最終審閱、實機驗證各抓不同的錯。
4. **時間與發現都即時記錄**：帳本照記錄規則 6 的四件事寫，里程碑結束時直接搬進本文件。
5. **把經驗寫成可以照做的東西**：範本、清單、法則比長篇故事更容易傳承。
