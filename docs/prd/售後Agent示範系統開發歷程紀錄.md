> **記錄規則**（使用者 2026/10/24 指示，之後每個階段都照做）：
> 1. 所有開發歷程只寫在**這一份檔案**，不分散到其他文件。

> 4. 每個里程碑完成時更新本檔；期間若使用者提出新的要求或做出新的決定，也立即補記。
> 5. 審閱階段（任務審閱、最終審閱、實機驗證）找到的問題與修正過程，記錄在第八節「審閱與修正機制紀錄」（使用者 2026/10/24 追加）。

## 二、階段 0：需求釐清與設計（2026/10/23）

### 2.1 使用者的指示

- 貼上一篇教學文章（第四期「Agent 怎麼一步步把事辦成」的逐字稿），並說明：
  > 「我想要使用 microsoft agent framework，使用這裡的腳手架系統，開發出下面論述的內容……讓我了解到當一個系統嵌入 ai agent 功能之後，可以表現與傳統的系統有哪些差異和更好的效果……讓我的客戶看到他們可以將現有的運作流程工作流以及現在的工作改變成什麼樣更好的環境。在這裡所提到的系統環境，都需要自己把它開發出來，模擬客戶端的真實情況。」
  > 「若有不清楚的地方，需要反覆與我提問討論，直到完全理解我的需求與目的。」
- 設計討論後追加：「我還需要一份文件，有點像是這個系統的企劃規劃說明書……說明為什麼會有這樣的系統存在、當初的需求是怎麼說明的、整個系統的架構，以及展示和說明方法，並且也要說明這個系統的各種特色。」
- 文件完成後：「commit / merge / push / delete local branch」。

### 2.2 使用者做的選擇（Claude 提問 → 使用者回答）

| 問題 | 使用者選擇 |
|---|---|
| 展示給誰看 | 都有可能；盡量發揮 Microsoft Agent Framework 的功能 |
| 怎麼呈現差異 | 傳統做法與 Agent 做法都開發，並排對照 |
| 幕後面板 | 展示時可開關，預設開 |
| 故障情境 | 要做故障模擬開關 |
| 展示階層 | 只要「傳統 vs 完整 Agent」（不做四階升級） |
| 客服後台 | 也要有 AI 助手 |
| 模型服務 | Azure OpenAI 與 OpenAI 都要支援 |
| 售後類型 | 換尺碼／換顏色、退貨退款、品質問題、物流查詢／催件 |
| Agent 拿不準時 | 一律停下來問 |
| 顧客端架構 | 單一 Agent 與多 Agent Handoff 兩種都做、可切換 |
| 長期記憶 | 要，顧客可檢視／刪除 |
| 失敗標準 | 劇情跑不出來、面板太工程師、看不出效益、Agent 越界（四項都算失敗） |
| 回放 | 要做錄製／回放 |
| 效益數字 | 實測＋可設定的假設值 |
| 使用方式 | 幾乎都是使用者一人展示 |
| 顧客畫面 | 另做商店風格版面 |
| 里程碑順序 | 照預設 M0→M6 |
| 企劃書 | 拆對外版與內部版，都放 repo `docs/` |
| 需求來源呈現 | 內部版附原文，對外版只摘要 |
| 產業延伸 | 加「套用到您的產業」：醫療／健康、製造業、金融／保險 |
| 展示長度 | 約 30 分鐘 |
| 導入建議 | 要，含階段與效益評估框架（不含報價） |

### 2.3 Claude 做了什麼

1. 以「先問清楚再動手」的方式，一次問一個問題，每理解一部分就複述給使用者確認（共約 20 輪問答）。
2. 派兩個探索代理讀腳手架現況（AI 呼叫、計費、日誌、權限、選單、測試慣例），並查詢 MAF 1.x 的最新狀態。
3. 寫出設計草稿後，派一個「實作者視角」的審閱代理找出 9 個會影響設計的疑點；能自行決定的補進文件，只有使用者能決定的 3 題再問。
4. 依使用者追加需求寫兩份企劃書。

### 2.4 結果與產出

- `docs/prd/售後Agent展示系統-設計.md`（設計文件，之後所有里程碑的依據）
- `docs/prd/售後Agent示範系統企劃書.md`（對外版）
- `docs/prd/售後Agent示範系統企劃規劃說明書.md`（內部版，含 30 分鐘展示劇本與文章原文）
- 專案記憶：專案目標、「規劃大型系統要附企劃書」

### 2.5 最花時間的工作

- 來回提問與複述確認（約 20 輪）。這是刻意的：需求越清楚，後面越少返工。

### 2.6 學到的事

- 使用者在問題中常選「建議」選項；之後的提問可以更聚焦在真正會改變做法的決定上。

## 三、階段 1：M0＋M1 計費接軌與傳統流程（2026/10/23）

### 3.1 使用者的指示

- 「開始寫 M0 和 M1 的實作計畫」
- 選擇執行方式：「用子代理逐任務執行」
- 完成後：「commit / merge / push / delete local branch」

### 3.2 使用者做的選擇

- 執行方式：子代理逐任務執行（每個任務由新的實作代理完成，再由獨立審閱代理把關）。

### 3.3 Claude 做了什麼

1. 派 3 個探索代理查清楚：AI 呼叫的計費與日誌流程、領域模組的寫法、所有會擋住新功能的規範測試（約 25 個）。
2. 查 NuGet 確認 MAF 版本（1.25.0）與相依套件。
3. 寫 11 個任務的實作計畫（`docs/prd/售後Agent展示系統-M0M1實作計畫.md`）。
4. 逐任務執行：實作 → 審閱 → 修正 → 複審。因 CLAUDE.md 規定「不可自動 commit」，改用 git 暫存區當每個任務的檢查點。
5. 最後做整個分支的最終審閱，修正跨任務問題後才交給使用者決定是否合併。

### 3.4 結果

- M0：所有 Agent 的模型呼叫都經過額度檢查、Token 用量與 AI 對話紀錄（`AgentChatClientFactory`、`AuditingChatClient`）。
- M1：模擬鞋服電商（商品、訂單、物流、可改版規則、售後申請）、示範帳號（customer1／customer2／agent1／merchant1）、商店風格顧客版面、傳統顧客表單與客服人工審核、操作埋點。
- 測試 1871 個全過；版本 1.0.3；commit `8f00c74`。

### 3.5 審閱抓到並修正的問題（舉例）

| 問題 | 修法 |
|---|---|
| AI 對話紀錄漏存 Agent 的系統指示 | 紀錄加入 instructions |
| 售後照片資料夾不在系統備份內 | 加入備份與還原腳本 |
| 照片點了會下載而不是開新分頁 | 改為 inline |
| 文件寫錯物流事件排序、稽核碼總數 | 更正 |
| 軟刪除顧客的申請從審核清單消失 | 改用明確查詢 |
| 有訂單的顧客讓「清除已刪除帳號」整批失敗 | 加入「使用中」判斷 |

### 3.6 最花時間的工作（估算）

| 任務 | 約耗時 | 原因 |
|---|---|---|
| 後台審核／規則頁＋照片下載 | 約 24 分 | 選單、權限、說明文件、整合測試都要齊 |
| 顧客售後表單 | 約 19 分 | 多步驟表單＋照片上傳＋元件測試 |
| 商店版面與訂單頁 | 約 13 分 | 新版面的登入閘門與權限 |
| 售後申請服務 | 約 13＋5 分 | 擁有權、去重、檔案清理、一次修正 |

### 3.7 產出的新工件

- 程式：`Web/Agents/`（工廠、計費包裝）、`AccessDatas/Models/Shop/*`、`Business/Services/DataAccess/Shop*`／`AfterSales*`、`ShopLayout`、`/shop/*` 顧客頁、`/after-sales-review`、`/after-sales-policies`、照片下載端點、示範種子資料。
- 文件：M0M1 實作計畫、`docs/features/售後Agent示範系統.md`（功能說明，之後每個里程碑都更新）、資料模型、端點目錄、畫面欄位字典等。

### 3.8 學到的事

- 獨立審閱的價值很高：每個任務平均抓到 0～1 個重要問題，若等到最後才審，修正成本會更高。
- 規範測試很多（選單、說明文件、編碼、日誌、稽核），新頁面花的時間有一半在「把規範做齊」。

### 4.6 產出的新工件

### 4.7 學到的事

- **實機測試不可省**：模型相容問題只有用真實模型才會發現。

### 5.7 學到的事

- **後面的功能會暴露前面的問題**：做回放時才發現「重置後編號會變」，做補強時才發現「確認後下一句出錯」。

- **實機驗證寫成暫時的整合測試程式最快**：用 `WebApplicationFactory`＋開發設定＋user secrets 直接驅動 Runner 與展示服務，9 個項目約 5 分鐘跑完，每一步都有可對照的紀錄（會話、錄製編號、停止原因、申請編號、Token 用量筆數）；比在瀏覽器手動操作快且可重複。
- **回放「省錢」要用數字證明**：比對 Token 用量與 AI 對話紀錄的筆數前後不變，才能確定回放真的沒有呼叫模型。
- **證明設定有送出，用一個會被拒絕的值**：`ReasoningEffort=low` 時用量裡的推理 token 一直是 0，看不出差別；改送 `none` 被模型以 400 拒絕，才確定設定確實有傳到服務端。
- **劇本台詞會影響模型是否追問**：劇本 B 第二句沒說黑鞋有沒有穿過，模型最後會再問一次；想讓 B 更順，可把第二句改成「黑的換大一碼沒穿過，白的開膠」（改台詞要重錄金劇本，待使用者決定）。

## 六、工作方式說明：Claude 怎麼執行一個里程碑

1. **探索**：派 1～3 個唯讀探索代理讀相關程式與文件（約 3～6 分鐘）。
2. **計畫**：寫成逐任務的實作計畫，每個任務含檔案、介面、要寫的測試名稱，存到 `docs/prd/`。
3. **逐任務執行**（子代理模式）：
   - 新的實作代理：先寫測試→看它失敗→寫程式→看它通過→跑建置、格式、全套測試。
   - 新的審閱代理：讀差異，檢查是否符合需求與品質，標出 Critical／Important／Minor。
   - 有 Critical／Important → 交回實作者修正 → 範圍內複審。Minor 記在帳本，最後統一處理。
   - 依 CLAUDE.md 不自動 commit，以 git 暫存區當檢查點。
4. **最終審閱**：用最強的模型審整個分支，專找跨任務的問題；一次修正＋一次複審。
5. **交付**：整理「Claude 替使用者做的所有決定」，由使用者決定 commit／合併／推送。

**為什麼比「直接寫完」慢**：每個任務都由新代理重新讀程式碼；每個任務都跑完整測試（2000 多個，約 1～2 分鐘一輪）；審閱常抓到真問題而多一輪修正；任務會改到同一批檔案，只能依序執行；專案規範測試很多，每個新功能都要做齊。

## 八、審閱與修正機制紀錄（持續累積）

> 使用者 2026/10/24 指示：Agent 在審閱階段找到問題並修正的過程也要記錄下來，說明這個機制的價值。之後每個里程碑都在本節補上一個小節。

### 8.1 機制怎麼運作

| 層級 | 什麼時候 | 誰做 | 看什麼 |
|---|---|---|---|
| 任務審閱 | 每個任務實作完 | 新開的審閱代理（不認識實作者、不帶先入為主） | 這個任務有沒有照需求做、有沒有多做、品質與測試是否可信 |
| 範圍內複審 | 每一輪修正後 | 另一個審閱代理 | 只看這次修正：問題是否真的解決、有沒有改壞別的 |
| 最終全分支審閱 | 所有任務做完、交付前 | 最強的模型 | **跨任務**的問題：安全、資料一致性、併發、計費、個資、規格是否整體成立 |
| 實機驗證 | 里程碑尾端 | 實作代理用使用者的真實模型 | 自動測試用假模型測不到的行為 |

- 問題分三級：**Critical**（必修）、**Important**（交付前要修）、**Minor**（記錄下來，最後統一判斷要不要修）。
- Critical／Important 一律交回原實作者修正，再由新的審閱代理做範圍內複審，最多 5 輪；本專案到目前為止**每個問題都在第 1 輪就修好**。
- 審閱代理被要求「不相信實作者的報告，只相信程式碼」，並對指定風險（例如越權、個資外洩）做針對性檢查。
- 遇到計畫本身有缺陷（例如漏寫的需求），由 Claude（統籌者）做出「裁定」並記錄理由與代價，不停下來等待。

### 8.6 這個機制的價值

1. **很多問題是「功能都能跑、測試也都過」的情況下才被抓到的**：例如照片沒備份、寫入後逾時被當成失敗、重置後編號會變。這類問題靠自動測試抓不到，要靠一個「沒參與實作、專門找碴」的角色。
2. **越早發現越便宜**：任務審閱抓到的問題，修正平均只要 3～5 分鐘；同樣的問題如果到展示當天才發現，可能整場展示失敗。
3. **後面的功能會檢驗前面的功能**：M2 的錯誤是在 M3 才被發現的。這說明「每個里程碑都做最終審閱」之外，下一個里程碑的實作也是一種審閱。
4. **最終審閱專抓跨任務問題**：單一任務看起來都對，但組合起來才出錯（例如故障開關 × 確認卡、回放 × 執行紀錄）。這類問題只有看整個分支才看得到。
5. **代價是時間**：審閱與複審約佔每個里程碑 15%～20% 的時間，再加上修正。對核心流程、安全、會被重用的程式，這筆時間非常值得；對低風險的畫面調整，可以考慮只做最終審閱。
