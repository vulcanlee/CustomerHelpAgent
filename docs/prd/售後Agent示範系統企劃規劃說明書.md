## 一、緣起與目的

### 1.1 緣起

專案負責人讀了一篇講解「Agent 是怎麼一步步把事辦成」的教學內容（全文見附錄），內容以一次換鞋為例，依序說明：
單次呼叫只是「回一句話」、多輪對話要靠程式承接前文、工具是程式寫好的受控入口、執行迴圈要能停能等、寫入要過確認關卡、
撐起整個迴圈的是外層的執行底座（harness）。

負責人想把這些觀念做成**一套真的能操作的系統**，而不只是投影片。

### 1.2 目的

1. **自己弄懂**：親手用 Microsoft Agent Framework（MAF）把每個觀念做實，了解嵌入 AI Agent 的系統和傳統系統差在哪裡、好在哪裡。
2. **說服客戶**：拿這套系統給客戶看，讓他們看見自己現有的流程、工作與工作環境，可以變成什麼樣子。
3. **全部自建**：系統中的訂單、規則、庫存、物流、申請等「客戶端業務系統」全部自己開發、模擬真實情況，不依賴外部服務。

### 1.3 成功的樣子

- 觀眾（老闆、客服主管、IT 都可能在場）看完 30 分鐘的展示，能自己說出「Agent 和接上 AI 的聊天機器人差在哪」。
- 現場不翻車：劇情可重現、出狀況能切回放。
- 效益說得出數字。
- 任何人都挑不出「越界」：沒確認就寫入、查到別人訂單、編造規則，這些都不可能發生。

## 二、需求的來龍去脈

### 2.1 原始需求（負責人原話摘錄）

> 我想要使用 microsoft agent framework，使用這裡的腳手架系統，開發出下面論述的內容，完成後的系統，可以呈現出底下所說的效果，
> 讓我了解到當一個系統嵌入 ai agent 功能之後，可以表現與傳統的系統有哪些差異和更好的效果。當然我也可以利用這樣新建立出來的系統，
> 讓我的客戶看到他們可以將現有的運作流程、工作流以及現在的工作改變成什麼樣更好的環境。在這裡所提到的系統環境，
> 都需要自己把它開發出來，模擬客戶端的真實情況。

（後附教學文章全文，見附錄。）

### 2.2 討論中的決策與理由

| # | 問題 | 決定 | 理由 |
|---|------|------|------|
| 1 | 觀眾是誰 | 老闆、客服主管、IT 都可能 | 所以每個畫面都要讓三種人看得懂：白話層在前，技術細節可展開 |
| 2 | 怎麼呈現差異 | 傳統流程與 Agent 流程都開發，共用同一套資料 | 同一件案件並排對照最有說服力 |
| 3 | 要不要做文章的「四階升級」模式 | 不做，只要「傳統 vs 完整 Agent」 | 對決策者最直白，範圍較可控 |
| 4 | 幕後面板 | 展示時可開關，預設開 | 回應文章「問三句看清底細」：資料從哪來、模型收到什麼、結果誰處理 |
| 5 | 故障模擬 | 做成開關 | 文章強調三種「沒拿到訂單」不能混為一談，現場要能演 |
| 6 | 客服後台 | 也要有 AI 助手 | 客戶要看的是整個工作方式的改變，不只顧客端 |
| 7 | 模型服務 | Azure OpenAI 與 OpenAI 都支援 | 客戶環境不同，用設定切換 |
| 8 | 售後類型 | 換尺碼／換顏色、退貨退款、品質問題、物流查詢／催件 | 涵蓋常見售後，且各有不同的停等點（照片、物流） |
| 9 | 拿不準時 | **一律停下來問** | 回答文章最後的提問；保守、可預測，最能取信客戶 |
| 10 | 顧客端架構 | 單一 Agent 與多 Agent Handoff 兩種都做、可切換 | 盡量發揮 MAF 的編排能力，並讓觀眾對照 |
| 11 | 長期記憶 | 要，顧客可檢視／刪除；寫入前要徵求同意 | 文章提到要分清「當前對話／長期記憶／業務狀態」 |
| 12 | 防翻車 | 示範劇本＋一鍵重置＋錄製／回放 | 模型每次走法可能不同，展示必須可重現 |
| 13 | 失敗標準 | 劇情跑不出來、面板太工程師、看不出效益、Agent 越界——四項都算失敗 | 據此設計白話層、效益對照頁、越界自動化測試 |
| 14 | 效益數字 | 實測＋可設定的假設值（明確標示） | 單人點傳統表單看不出排隊與往返的真實成本 |
| 15 | 使用方式 | 幾乎由負責人一人展示 | 故障開關與重置全站共用一份即可 |
| 16 | 顧客畫面 | 另做商店風格版面 | 老闆看到的要像真的電商會員中心，不是後台 |
| 17 | 里程碑 | M0→M6（見第六章） | 每個里程碑都能單獨展示 |
| 18 | 企劃書 | 拆對外版與內部版，都放 `docs/prd/` | 對外版給客戶（不引原文），內部版附原文供日後對照 |
| 19 | 產業延伸 | 對外版加「套用到您的產業」：醫療／健康、製造業、金融／保險 | 負責人的客戶多在這些產業 |
| 20 | 導入建議 | 對外版含分階段導入與效益評估框架，不含報價 | 讓客戶知道如何開始 |

另有數項由開發方判斷、隨設計一併核准的決定（傳統 vs Agent 以「管道」切分、「拿不準就停」由程式強制、錄製在模型呼叫層、種子資料日期相對化等），
詳見設計文件 §3、§3.1。

## 三、系統架構

### 3.1 分層與放置位置

沿用腳手架的分層（Web → Business → AccessDatas；Models／Dtos 只相依 Share）：

| 層 | 新增內容 |
|----|----------|
| `CustomerHelpAgent.AccessDatas` | 業務實體（M1 已完成，位於 `Models/Shop`）：商品／規格庫存、訂單／明細、物流、售後規則（含版本）、售後申請、附件；Agent 實體：Session、執行軌跡、記憶、故障設定、指標 |
| `CustomerHelpAgent.Business` | 模擬業務服務（訂單、規則、庫存、物流、申請）、故障注入點、種子 `IDatabaseSeeder` |
| `CustomerHelpAgent.Web/Agents/` | MAF Agent、工具、Middleware、`AuditingChatClient`、`ReplayChatClient`、Workflow 定義 |
| `CustomerHelpAgent.Web/Components/` | `ShopLayout` 與顧客頁（`/shop/*`）、客服後台頁、展示控制台、效益對照頁 |

### 3.2 MAF 元件對應

| 文章觀念 | 系統中的實作 |
|----------|--------------|
| 模型＝大腦 | `ChatClientAgent`（`IChatClient` 由 OpenAI SDK 建立，Azure 走 v1 端點） |
| 工具＝受控的手腳 | `AIFunctionFactory` 建立的函式工具，回傳統一的 `ToolOutcome` 信封 |
| 寫入要過確認 | `ApprovalRequiredAIFunction` 包裝寫入工具＋程式重核＋寫入後回查 |
| 執行底座（harness） | Agent／函式呼叫 Middleware：身分帶入、步數上限、強制停止、軌跡記錄、故障注入 |
| 多輪承接 | `AgentSession` 序列化存 SQLite |
| 長期記憶 | 自訂 `AIContextProvider` 注入 `CustomerMemory` |
| 固定流程比較穩的地方 | `Microsoft.Agents.AI.Workflows`：客服初審並行 fan-out／fan-in＋人工決策節點＋Checkpoint |
| 多 Agent 分工 | Handoff 編排：分流 → 換退貨／品質／物流專員 |
| 成本與稽核 | `AuditingChatClient : DelegatingChatClient` 接上既有額度、Token 用量、AI 對話紀錄 |

### 3.3 工具五要素

每個工具都要定清楚：**接收什麼輸入、回傳什麼結果、失敗了怎麼說明**（跟模型打交道的規矩），以及**誰有權呼叫、會不會改動資料**（程式守住的底線）。

| 工具 | 讀／寫 | 身分 | 失敗狀態 |
|------|--------|------|----------|
| 查本人訂單 | 只讀 | 程式從登入帶入，模型不能填 | 查無／逾時／權限不符 |
| 讀有效規則 | 只讀 | 先核對訂單歸屬 | 無適用規則／規則服務不可用／規則衝突 |
| 查同款庫存 | 只讀 | 同上 | 查無／逾時 |
| 查物流 | 只讀 | 同上 | 查無／逾時／物流異常 |
| 建立售後申請 | **寫入** | 確認後程式重核 | 資格不符／重核失敗，並回明確原因 |
| 請顧客上傳照片 | 停等 | — | 讓迴圈停住等待 |
| 記住偏好 | 寫入（記憶） | 需顧客同意 | — |

### 3.4 迴圈出口

已給建議、等待顧客回覆、等待上傳、步數上限、工具連續失敗、權限不符立即停、規則衝突、使用者取消。
逾時／權限不符／服務不可用時，由程式直接終止並顯示固定說明；查無／無規則／衝突時，本次封鎖寫入工具，只能追問或轉人工。

### 3.5 計費與日誌

一次 Agent 執行可能呼叫模型多次；每次都經過 `AuditingChatClient`，各自做額度檢查、記錄 Token 用量與 AI 對話紀錄，並共用同一個對話識別碼，
可在既有「Token 用量」「AI 對話紀錄」頁查到，也供效益對照頁計算每件案件的 AI 成本。

## 四、各特色的技術做法

| 特色 | 做法 |
|------|------|
| 身分由系統把關 | 工具簽章不含使用者 Id；Middleware 從 Cookie 登入 Claims 取身分注入工具執行環境 |
| 只給需要的資料 | 每個工具有專屬投影 DTO，並宣告「刻意不送欄位」清單，供幕後面板顯示 |
| 寫入前確認 | 確認卡內容由程式依參數重新查詢組成（不採模型文字）；確認後重核身分、資格（簽收天數由程式算）、確認紀錄，寫入後回查 |
| 拿不準就停 | 提示詞要求＋Middleware 依 `ToolOutcome.status` 強制終止或封鎖寫入 |
| 規則不編造 | 顧客看到的條文一律以本次工具結果渲染成「規則卡」（含版本），測試檢查來源 |
| 幕後面板 | Middleware 發出 `AgentTraceEvent`（白話層＋原始層），即時推到 Blazor，並持久化供回看與回放 |
| 故障模擬 | `FaultSimulationSetting` 在模擬業務服務層注入，傳統流程與 Agent 同受影響 |
| 錄製／回放 | 在 `IChatClient` 層錄製所有模型回應；回放時工具仍對重置後資料真實執行，參數不符即中止並提示 |
| 客服初審 | Workflow：照片初審 Agent（視覺、結構化輸出）、規則核對（純程式）、歷史紀錄 Agent 並行 → 摘要 → 人工決策 → 執行 → 通知 |
| 效益對照 | `ProcessMetric` 埋點＋Token 用量，加上 `DemoAssumption` 假設值（另以底色標示） |

## 五、30 分鐘展示劇本

### 5.0 展示前檢查（展示前 10 分鐘）

示範帳號由種子建立（`DemoSettings.Enabled=true` 的環境；正式環境不建立），密碼一律 `demo1234`：

| 帳號 | 角色 | 用在哪 |
|---|---|---|
| `customer1` 王大同 | 顧客 | 主要示範顧客：黑鞋 40 碼（簽收 3 天前）、白鞋 41 碼（簽收 2 天前） |
| `customer2` 陳怡君 | 顧客 | 備用顧客：外套（簽收 10 天前）；另一件外套已出貨 4 天尚未簽收（催件） |
| `agent1` 客服小李 | 客服人員 | 客服後台：有「售後審核」，**沒有**「售後規則管理」 |
| `merchant1` 店長阿明 | 店家管理者 | 新增售後規則版本 |

M1 已完成的部分（M2 起才有重置、控制台、模型）：

1. 開兩個瀏覽器分頁（建議一個一般視窗、一個無痕視窗，避免共用登入）：A＝顧客，登入 `customer1` 後自動進 `/shop`；B＝客服後台，登入 `agent1` 後進 `/App`，從側邊選單「售後服務」進 `/after-sales-review`。
2. 準備一張開膠照片檔案（jpg／png／webp，10 MB 內，最多 3 張）。
3. 若要重來，需自行清除資料庫的示範資料（一鍵重置於 M3 提供）。
4. 〔M2 起〕確認模型連線正常（系統健康監控頁的 AI 項）；若網路不穩，預先切到**回放模式**並選好「金劇本」。〔M3 起〕開啟展示控制台確認故障開關全部關閉。

### 5.1 開場：問題與觀念（0:00–5:00）

- **話術**：「很多公司說自己導入了 AI，但大多只是讓模型回一句話。今天我想讓各位看看，一個真的能把事情辦成的 AI Agent，和傳統系統差在哪裡。」
- 丟出三個問題：資料從哪來？模型收到什麼？結果誰處理？「等一下每一步，我們都可以在畫面上看到這三個問題的答案。」
- 介紹情境：鞋服電商，顧客有兩雙剛買的鞋。
- **觀眾要帶走**：接上 AI ≠ 會辦事。

### 5.2 傳統做法（5:00–10:00）

- 分頁 A（`customer1`）：`/shop` 我的訂單 → 點商品的「申請售後」（`/shop/after-sales/new?orderItemId=`）→ 五步驟表單（選擇訂單商品 → 申請類型 → 填寫規格與是否穿過 → 問題描述（含照片）→ 送出申請）；白鞋開膠（品質問題）要再上傳一張照片。送出後在 `/shop/after-sales` 看狀態。
- 分頁 B（`agent1`）：`/after-sales-review` 打開審核佇列 → 開窗後**逐一**按「查看訂單」「查看售後規則」「查看照片」（三者各自展開，是刻意的多步操作）→ 對照規定 → 算簽收天數 → 發現「不知道穿過沒有」→ 按「要求補件」請顧客補資料；符合規定者按「核准」。
- 顧客回 `/shop/after-sales`，在「待補件」那筆開補充窗，補說明後重新送出，客服再審核。
- **話術**：「系統每個功能都有，但把它們串起來的工作，全落在顧客和客服身上。」
- **觀眾要看到**：步數多、往返多、客服在當人肉轉接器。

#### 5.2.1 傳統流程手動驗證清單（發版前／展示前，約 10 分鐘）

1. [ ] `customer1` 登入 → 自動進 `/shop`（不會看到後台側邊選單；手動輸入 `/App` 也被導回 `/shop`）。
2. [ ] `customer1` 對黑鞋 40 碼送「換尺寸」（目標 41 碼）；對白鞋 41 碼送「品質問題」並上傳照片。`/shop/after-sales` 兩筆都是「已提交」。
3. [ ] `agent1` 登入 → 側邊選單有「售後服務 → 售後審核」，**沒有**「售後規則管理」；直接開 `/after-sales-policies` 被拒絕。
4. [ ] `agent1` 在審核佇列開白鞋那筆，依序按「查看訂單」「查看售後規則」「查看照片」都能展開，縮圖可在新分頁開啟原圖；對該筆按「要求補件」並填備註。
5. [ ] `agent1` 對黑鞋那筆按「核准」；`customer1` 重新整理後黑鞋顯示「已核准」。
6. [ ] `customer1` 在白鞋那筆（需補件）開補充窗，補說明後送出；`agent1` 再審核並核准。
7. [ ] `merchant1` 登入 → `/after-sales-policies` 對 `SIZE-EXCHANGE` 新增 v2（例如換碼期限改為 10 天）；清單顯示 v1、v2，v2 為現行。之後新送的換尺寸申請，審核窗的「查看售後規則」顯示 v2；舊申請仍顯示送件當時的 v1。
8. [ ] `customer2` 登入 → 看不到 `customer1` 的訂單與申請；在已出貨未簽收（物流顯示延遲）的外套訂單明細按「申請催件」成功，外套簽收已 10 天、超過 7 天的換貨期限，可用來示範客服依規則駁回。
9. [ ] 稽核紀錄頁可查到 `Shop.Request.Submit`、`Shop.Request.MoreInfo`、`Shop.Request.Resubmit`、`Shop.Request.Decide`、`Shop.Policy.AddVersion`、`Shop.Attachment.Download`。

### 5.3 Agent 做法（10:00–20:00）

1. 重置資料（或換一位示範顧客），分頁 A 打開線上客服。
2. 輸入：「**這雙想換大一碼，另一雙開膠了，也幫我看看。**」
3. 指著幕後面板逐步講解（白話層）：
   - 「Agent 決定先查訂單——注意，**是系統帶入你的身分**，模型不能指定要查誰。」
   - 「查到兩筆。收件地址、手機**沒有送給模型**。」
   - 「兩雙分不清，Agent **停下來問你**，而不是自己猜。」
4. 回答：「黑的換大一碼，白的開膠。」
5. 面板顯示連續兩次查規定，**規則卡標示版本**；查庫存確認有 41 碼。
6. 確認卡跳出 →**先不要按**，強調：「模型覺得可以辦，但真正寫入的權利不在它手上。」→ 按確認 → 面板顯示程式重核 → 回查 → 申請編號。
7. 白鞋：Agent 請求上傳照片，系統**停下來等**。上傳照片。
8. （IT 觀眾在場時）展開一則事件的原始層：看模型實際收到的上下文與工具參數。
9. （時間許可）切到「多 Agent」模式重跑一次，看分流交接。
- **觀眾要帶走**：模型決定下一步、程式執行與把關；該問就問、該等就等。

### 5.4 故障與客服後台（20:00–26:00）

1. 控制台打開「**訂單服務逾時**」→ 顧客再問一次 → Agent 說「暫時查不到，不代表您沒有這筆訂單」，並轉人工。
   - **話術**：「沒查完和查過了沒有，是兩回事。傳統系統常常把它們混成一句『查無資料』。」
2. 關閉逾時，打開「**權限過期**」→ Agent 立即停止，不再往下讀。關閉。
3. 分頁 B：客服後台看 Agent 管道送來的申請 → 流程圖顯示照片初審、規定核對、歷史紀錄**同時跑完**並整理成摘要 → 客服按核准。
   - **話術**：「這裡我們刻意用固定流程，因為步驟每次都一樣，固定比較穩。AI 負責整理，**決定權在人**。」
4. （時間許可）店家改規定（例如換碼期限改成 10 天）→ 顧客再問 → Agent 讀到新版本。

### 5.5 效益對照與導入討論（26:00–30:00）

- 打開效益對照頁：兩種做法並排的步驟數、耗時、人工介入次數、AI 成本。
- 切換假設值（排隊時間、客服人力成本、月案件量）→ 推估每月節省。**明說哪些是實測、哪些是假設。**
- 轉入對外版企劃書第六、七章：「回到各位的產業，我們可以先從哪一個流程開始？」

### 5.6 常見提問與回答

| 提問 | 回答要點 |
|------|----------|
| AI 會不會亂回答？ | 規定一律從系統讀當下版本；查不到就停下來問或轉人工；條文以規則卡呈現，不是模型轉述 |
| AI 會不會亂改資料？ | 會改資料的動作一律要顧客確認，程式再重核一次，寫完回查；模型沒有寫入權 |
| 個資會不會外流？ | 只送當下需要的欄位，地址、手機不送；面板可看到哪些欄位被保留 |
| 成本高嗎？ | 每次呼叫都有記錄與費用估算，可設每日／每月上限；效益頁有每件成本 |
| 要換掉我們現有的系統嗎？ | 不用。Agent 透過工具呼叫您現有系統的查詢與寫入介面，權限仍屬於您的系統 |
| 可以只做一部分嗎？ | 可以，建議從只讀助手開始（對外版企劃書第七章） |
| 模型服務綁定哪一家？ | 目前支援 Azure OpenAI 與 OpenAI，以設定切換 |

### 5.7 出狀況時

- **模型回應異常或很慢**：控制台切到**回放模式**，選金劇本，畫面會標示「回放中」；向觀眾明說這是排練時的真實紀錄。
- **劇情走偏**：一鍵重置，換回旗艦劇本重來。
- **網路中斷**：直接用回放模式完成第 5.3 節。

## 附錄：教學文章原文（負責人提供）

> 以下為負責人貼上的教學內容逐字稿，原樣保留供日後對照；對外文件不引用本文。

Agent 的開發是什麼？到底該怎麼開發？在開發 Agent 之前，我們需要先弄清它怎麼從回你一句話變成能替你把事辦成。手把手帶你開發 Agent，這是第四期。今天就順著一次換貨，看看 Agent 是怎麼一步步完成任務的。一，先看最簡單的意思：使用者說句話，程式讓模型回句話。我們用換鞋的場景來看，登入使用者輸入剛買的鞋尺碼不合適，想換大一碼，頁面收下這句話，交給背後處理請求的程式，也就是後端。要辦成換貨，你的後端本來就得有查訂單、查規則、存申請這些本事，這裡得說清一件事，就算你做的不是 Agent，想讓系統辦成換貨，也得有這些功能才行。他們不會因為接了 AI 大模型就憑空冒出來，因為查訂單、存申請是要真去讀寫你係統裡的資料的，而模型並不會自己連上你的系統。這一次，我們只想讓模型幫忙理解一下使用者的意思，回一句話，可光憑一句想換大一碼，到底換哪雙鞋，原來買的幾碼還不知道，所以後端先核對登入身份，去查這個人名下的訂單，假設查出來兩筆，一筆是簽收三天的黑色運動鞋 40 碼，另一筆是簽收兩天的白色運動鞋 41 碼，兩雙都剛買不久，程式沒法直接替他選。接著，後端再從店裡的售後說明裡取出換碼規則，假設是簽收七天內，鞋沒穿過，可以申請換同款的其他尺碼，這條規則必須從店裡現行的售後說明裡取，不能讓模型憑常識瞎猜。拿訂單和規則一對，就知道還缺什麼。訂單能看出簽收幾天了，卻看不出鞋穿沒穿過，使用者也還沒說要換哪一雙，所以這一步得先把這兩件事向使用者問清楚。料被齊了，也不是一股腦全塞給模型，既然這一步只是讓它問清換哪雙、穿沒穿過，那訂單裡只給商品名稱、顏色和原尺碼，就夠它把兩雙鞋分開了。簽收時間留給後端程式，等使用者選定哪雙鞋之後，再由程式去算有沒有超期。收貨地址、手機號跟這次追問毫無關係，一律不發，更不會把整個訂單庫交出去。畢竟發給模型的內容是實實在在離開了你的業務程式碼交到模型那頭去的，多發無關欄位只多風險不多幫助，挑料的原則就一條，這一步需要什麼就只給什麼。現在後端這一趟要餵給模型的內容就湊齊了：使用者原話、兩筆訂單裡用來區分的幾個欄位、店裡的換碼規則、外加一句任務交代。根據這些資訊，先問清他要換哪雙，穿沒穿過，別說已經建立了申請，這句任務交代就是常說的提示詞。它和前面挑出來的業務資料、規則放在一起，統稱這次呼叫的上下文，通過模型 API 一塊發給模型。模型收到這些，就能回一句像樣的：您要換的是黑色 40 碼還是白色 41 碼，這雙鞋穿過沒有？後端拿到這句回覆，再傳回頁面展示給使用者。順著這條鏈看下來就很清楚，接上模型只是在你的程式裡多加了一個理解輸入、生成回覆的環節。模型看到的只是這一次請求裡發給它的文字，既沒有連著你的……
訂單系統也沒有連著店裡的售後說明，所以哪怕模型嘴上回一句已經幫您提交申請了，只要後端沒真去跑建立申請的程式碼，系統裡就不會憑空多出一張單子。同樣，哪天商家改了這款鞋的換碼規則，模型自己也不會知道，後端下次呼叫時得重新核對並取出當前適用的說明發過去，不能順手沿用上次請求裡的舊文字。二、多聊幾句怎麼接上，跑通了又離 agent 差在哪兒？使用者接著會：是黑色那雙，還沒穿過。這句我們一聽就懂，是因為我們記得他前面說想換大一碼，也記得剛查出過一雙黑色 40 碼的鞋。可模型自己是不記事的，每一次呼叫對它來說都是新開的頭。如果下一次只把是黑色那雙，還沒穿過這八個字發過去，前面的換碼訴求和訂單資訊都沒帶上，它根本不知道那雙指的是哪雙，原來買的幾碼。想讓對話接得上，就得有人把前面的內容續上去。常見有兩種做法：要麼由你的程式自己挑出這次回答用得上的前文或濃縮摘要，跟著新請求一塊兒重發一遍；要麼用模型服務提供的會話承接功能，讓新請求直接掛在剛才那段對話後面。把前文續上了，模型才有依據接著追問：您是想把黑色這雙從 40 碼換成 41 碼，對嗎？所以使用者在頁面上看到聊天氣泡一路往下走，背後只是程式或模型服務在幫忙把前文續上。這既不代表模型自己長出了跨對話的長期記憶，也不代表聊天裡剛確認過的目標尺碼就已經寫進了業務系統。當前對話、長期記憶和系統裡的真實業務狀態到底怎麼分清，後面會專門拆開講。到這裡，系統既能聽懂人話，又能結合訂單和規則順著上下文聊上好幾輪。但這樣一來一回的呼叫，一次也好，續上幾輪也好，跑通了最多隻證明你的程式能把挑好的材料發給模型，再把生成的回覆拿回來。以後你再看到所謂已接入 AI 的演示，順著剛才這條鏈問三句就能看清底細：真實的業務資料從哪兒來？模型實際收到了什麼？它生成的結果最後由誰處理？那很多人看到這種能結合訂單聊上幾輪的演示，覺得這不就是 agent 了嗎？到底還差在哪？就差在下一步誰定。在剛才的例子裡，查什麼資料、先走哪一步，全是你事先在程式碼裡排死的；要讓它真正變成會辦事的 agent，還得看模型能不能在安全邊界裡照著實際拿回來的結果，自己決定下一步幹什麼。三、下一步要看現場時，得給模型配上受控的工具。回頭看第一節，訂單和規則是誰決定去查的？是後端照著寫好的程式碼固定去查的。使用者一開口，程式就按既定順序去查本人訂單、取換碼規則，模型壓根沒參與要不要查、先查哪個的決定。可要是下一步查什麼得看對話現場，而且情況多到沒法預先一條條排成固定插口，比如使用者一句話裡扯出兩雙鞋的不同問題，查回來的結果又牽出新的規則疑問，那就得讓模型根據現場情況自己提出這一步先查什麼。但模型光動嘴沒用，得有真能去系統裡幹活的程式碼接著，這個東西就是工具。工具說白了就是開發者用程式碼寫好的、能真辦……
從一件事的業務功能，再配上一份給模型看的呼叫說明，拿查本人訂單來說，你先在後端寫好去訂單系統查詢的程式碼，再告訴模型有這麼個工具，叫什麼名字，能填哪些篩選條件，等到對話裡需要查黑鞋時，模型就可以說呼叫查本人訂單，顏色填黑色。注意，模型自己不能憑空編一筆訂單出來，它交出來的只是一張請幫我執行這個動作的請求單。程式接住這張請求單，帶上服務端何時過的登入身份，真去訂單系統裡查，不管查沒查到、成沒成功，都把真實結果照實交回給模型。這一模型提出、程式執行、結果交回的配合，就叫工具呼叫，常見的一種解法叫 Function Calling，也就是函式呼叫。這裡最核心的分工是，模型只能提出用哪個工具，真去執行真把關的永遠是程式。為什麼查訂單時連使用者身份都不讓模型填？因為模型填出來的編號可能是它算錯的，也可能是使用者在聊天框裡隨口報的，不能憑這個就認定它有權查誰的訂單，身份必須由程式自己核實後再帶進去。所以把一個普通功能變成模型能用、程式又管得住的工具，光有個名字遠遠不夠，至少要把五件事定清楚：前三條是跟模型打交道的規矩，也就是接收什麼輸入、返回什麼結果、失敗了怎麼說明；後兩條是程式自己守住的底線，也就是誰有權呼叫、會不會改動真實的資料。放到售後助手要用的三個工具上，這五件事的作用一下就看清了。就拿剛才的查本人訂單來說，它是隻讀工具，前面已經定了身份，由程式核實帶入，登入憑證絕不交給模型。模型只填顏色或訂單線索，拿回這位使用者名稱下的訂單編號、商品和能拿來核對的狀態。這裡最容易踩坑的是失敗了怎麼說明，同樣是沒拿到訂單，背後其實有三種完全不同的情況：一是查詢正常做完了，確實沒有匹配的訂單，那可以請使用者核對一下線索；二是查詢超時了，在約定時間裡沒拿到結果，這時候絕不能張嘴告訴使用者您沒有這筆訂單，因為沒查完和查過了沒有完全是兩回事；三是許可權對不上，比如它的登入已經過期，或者賬號被限制檢視訂單，那就該立刻停下，不再往下讀。程式必須把這三種情況用不同的手法交回去，模型才知道下一步該追問按允許的辦法重試還是直接停下。要是統統糊弄成一句沒查到，模型就只能瞎猜。再看第二個工具，讀有效規則，它同樣只讀，模型只明要查哪筆訂單或商品的售後事項，程式先核對訂單歸屬，再返回適用的規則內容，因為店裡的規則會改，返回時不能光給條文，還得帶上來源、版本或者生效範圍，這樣才說得清這次判斷依據的到底是哪一版。它的失敗說明同樣要分清，沒有適用的規則和規則服務暫時不可用不是一回事，前者是店裡確實沒規定這種情況，可能得轉交人工判斷；後者是系統這次沒查成，只能明說暫時核實不了，不管哪種都不能讓模型拿自己記得的舊說法去冒充當前規則。到了第三個工具，建立售後申請。
性質就徹底變了，前兩個查完不改任何東西，而它會往系統裡真記一筆。正因為它會改動真實資料，輸入必須明確到哪一筆已經核對過的訂單，使用者確認的目標尺碼和使用者確認要辦的換碼事項，執行後返回新申請的編號或明確的失敗原因。更關鍵的是呼叫把關，哪怕模型判斷符合條件可以辦了，程式也不能拿這句當放行證明，必須攔下來走完使用者確認和程式重核，才能真寫進系統。所以只讀和寫入雖然表面上都叫呼叫工具，輕重完全不一樣，絕不能偷懶揉成一個籠統的處理售後大工具。把這五件事合起來看也就明白了一點，工具不會因為交給了 agent 就自動拿到資料庫的許可權，許可權始終屬於業務系統。工具只是一個定義好受控制的入口，能查誰的、能改什麼，由業務系統按真實身份和規則說了算，不是模型說了算。四，把檢視結果再決定連起來轉，就是執行迴圈。現在把前面的呼叫和工具串起來看，如果把模型想象成系統裡負責理解問題、判斷下一步的大腦，那查訂單、讀規則這些工具就是系統給它準備的辦事手腳。普通呼叫是大腦回一句話就結束，而到了 agent 這裡，使用者把任務交過來，大腦先選要用哪個功能，程式核驗後去執行，把真實結果交回來，大腦看著剛拿回來的結果再決定下一步是接著查、開口問使用者還是給出答覆。拿個真實換貨裡常見的現場來看，登入使用者一句話帶了兩件事，這雙鞋想換大一碼，另外一雙開膠了，也幫我看看。開跑之前，程式先把目標和邊界給模型交代清楚，這次要弄明白涉及哪兩筆訂單，照著有效規則給建議，手上有哪些只讀工具可用，哪些紅線不能碰，比如不能查別人訂單，不能沒經確認就建立申請，以及這一趟最多允許走幾步，這些邊界不是靠模型自覺，是程式一直攥在手裡的。接著就開始轉了，模型先提出查當前使用者的訂單，程式查出黑白兩筆訂單交回去，模型一看，還分不清哪雙換碼、哪雙開膠，就決定先停下來問使用者，等使用者答了黑的換大一碼，白的開膠了，程式把這句回答補進去再問模型，這一輪模型就開始連續調工具了，它先去查黑鞋的換碼說明，拿到結果確認能換，緊接著又去查白鞋的質量處理說明，查回來的規則寫著開膠需先傳一張照片給客服核驗，這時候模型才把兩邊的結果合起來告訴使用者，黑鞋按換碼繼續辦，白鞋請先補一張開膠的照片。到這兒，程式就把這一步停下，等使用者傳照片，而不是在後臺反反覆覆催模型去要一張還不存在的照片。這種模型選一步、程式去執行、把真實結果交回、模型再看著結果定下一步的反覆推進，就是 agent 執行迴圈，也叫 agent loop。一個靠譜的迴圈必須能停、能等，料查齊了就給建議，這是正常收尾，資訊不夠，使用者還沒回就停下等著，要是走的步驟到頭了，工具老是失敗。
或者查出來的規則互相打架，也得及時停下來說清楚卡在哪兒，程式必須認得出這些出口，不然再問模型一次可以沒完沒了地空轉下去，時間和錢都花掉了，離真實結果卻一點沒進。前面分清的那幾種工具失敗，放到這個迴圈裡作用就非常直接了，訂單查不到，規則服務超時，都是實打實的執行結果，它們該讓任務轉去追問、報錯或者交給人，絕不能被模型一句順口的回覆抹過去。要是沒有真實結果一步步喂進去校準，只剩模型順著自己的話一句接一句往下編，那就不是一個靠得住的迴圈了。要是任務的目標不只是給建議，而是真替使用者把申請嵌進系統，那就算模型在迴圈裡提出寫入，也越不過確認這一關。系統得先把你建立的內容擺給使用者看，使用者點確認了，程式還要自己重新核一遍身份、資格和這次確認記錄，然後才由業務程式真正寫進資料庫，最後再查一下申請記錄是不是真的生成了。這一串動作可以接在 agent 的建議後面，但真正寫入的權利並不會因為模型會規劃步驟就交到它手上。那背後是誰在維持這一整套迴圈、把住這些出口和關卡？不是模型自己在後臺連軸轉，而是包在外層的那段程式，它在負責接住模型提的動作，去調工具、送回結果、判斷該停還是該繼續。這段擔著把整個過程跑起來並管住邊界的程式，常被叫做 agent，執行底座英文是 harness，這裡先認得它是幹這個的就行。它既可以自己寫程式碼實現，也可以用現成的底座，還可以交給別人家的平臺託管替你把它跑起來，等後面把系統的責任和資料邊界定下來，再去挑最合適的那條路。看到這兒，它和事先排好的固定流程差在哪兒也就清楚了。如果程式裡早就寫死先查訂單，查到兩筆分不清就追問，再查話碼規則，那條路線是開發者預先排好的。而在執行迴圈裡，程式只預先劃定能用哪些動作、哪些紅線不能越，具體的下一步是由模型看著剛拿回來的真實結果去挑的。所以 agent 的關鍵也不在接了幾個工具，就算它不碰外部系統，只是在一堆複雜材料裡自己看著結果決定是接著分析、問人還是停下，跑的也是這套機制。工具只是它要辦外面的事實最常用的那雙手。至於你的任務什麼時候值得這樣做，什麼時候固定流程反而更穩，下一集專門講。五，把這臺機器收成一句話。把前面這一整套連起來看，agent 的會辦事的機制其實就一句話：給它目標和邊界，模型看著現場選一步，程式去辦，把真實結果交回來，模型再照著結果接著選，直到把事辦完，或者在該停、該等人的地方停住。回你一句話，那只是單次呼叫的起點，能照著一個個真實結果用受控的工具在迴圈裡一步步把事推到辦成，這中間多出來的挑料與承接、工具、執行迴圈，就是 agent 比會聊天多出來的真正骨架。後面每一集，我們就是把這幾樣一件一件做實。你希望你的 agent 碰到查不到、拿不準的時候，是停下來問你，還是自己先墊一個往下走？
